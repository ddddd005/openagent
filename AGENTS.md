# Workflow Lifecycle

- Develop changes on `develop`; the normal `start.bat` must keep selecting a clean `main` checkout.
- Treat the sidebar as a thin application-shell base for layout, collapse, navigation and component hosting. Workflow, provider/model and global-content components own their respective business state and operations; no one component owns the sidebar or coordinates saves for the others. Reuse shared storage and transport without introducing an all-purpose sidebar backend.
- Prioritize the agreed core path and simple code over exhaustive handling of individual tasks. Implement required business branches directly, without speculative fallback/recovery states, broad retry frameworks or abstractions for hypothetical cases. A save should follow one main submit/write/result path, not accumulate extra application stages. Verify the core path and its necessary regression coverage; do not make a comprehensive exception matrix a prerequisite for moving forward. Record non-core issues from practical testing, report their reproduction and impact, and agree on a focused integration plan before expanding behavior. Fix clear in-scope blockers minimally, while retaining necessary data ownership, truthful write results, credential protection and no automatic replay of unknown requests.
- Proactively consider and report deletion or archival followed by removal for obsolete, invalid or redundant content; do not retain multiple architectures merely to avoid deleting things. Before removing anything outside explicit authorization, report what code/modules/interfaces/nodes/docs/tests/data are affected, why removal is appropriate, its dependencies and effects, and whether reference archival is needed, then obtain user confirmation. Reports may group related items rather than repeat per-file explanations. Previously enumerated legacy configuration/product-data cleanup and temporary validation-data removal need no repeated proposal or confirmation once their authorized development stage starts; this exemption does not extend to additional code or unrelated data. Reference archives must not become executable legacy fallback routes. Record actual cleanup outcomes without treating this planning update as permission to delete now.
- Cleanup scopes R01-R14 and P01 in the 2026-10-11 midterm audit are approved for their planned implementation stages and replacement prerequisites. Remove P01's dedicated post-failure Key-binding recovery rather than building more speculative remedies; keep truthful failures, private Key protection and original-request evidence. Preserve P02's within-workflow response-candidate selection and necessary state restoration associated with reroll, without retaining cross-workflow/version rebinding or claiming new reply generation is already implemented. P03-P06 remain deferred to human discussion at their corresponding stages. Scope approval alone does not start the restructuring.
- Before the explicitly started restructuring batch, clear all pre-existing provider/model configurations, global presets and related content, workflows, sessions, linked runtime/history data, ordinary product archives and obsolete editor drafts in the selected development/test data scope. This is not limited to incompatible records. Do not build compatibility readers, migrations, fallbacks or parallel architectures for old content; use only the new architecture and its newly created content.
- Track intermediate validation workflows and their linked sessions/history/temporary test configurations by exact identity and remove them when that validation stage ends. Preserve user-created acceptance content under the new architecture; do not repeatedly treat it as legacy data. Report cleanup failures, and retain non-secret verification logs and cleanup receipts.
- Ordinary user edits to Key, model, temperature, thinking or capacity do not trigger workflow cleanup. Workflows only reference global provider/model configurations; subsequent calls and content reads use the current saved values, including within unfinished runs. Do not freeze a second configuration copy for the whole run or rewrite already-sent request facts.
- Creating or editing a provider starts as a draft. Use one "Save provider" action for its complete configuration and any newly entered Key; never split Key and resource saving into separate user steps. An empty Key preserves the saved Key. Typing a Key must not lock other draft fields or lose it when those fields change. Lock mutations only during submission or unresolved requests, and report success only after the effective configuration and private Key outcomes are verified.
- The only product credential route is a Key entered and saved in the provider page, stored in the protected private vault as `local:<UUID>`. Do not restore environment-variable credentials, a manual credential-reference selector or a plaintext fallback.
- Complete the remaining responsibility corrections on `develop`, then perform one unified acceptance and merge into `main`. Real-model acceptance uses DeepSeek; the user starts the visible page and enters/saves their Key. Do not start services or call the real model on their behalf.
- The restructuring reset deletes authorized legacy browser workbench records and ordinary historical product archives instead of maintaining a legacy recovery route. Identify unknown-request evidence separately and preserve it; this reset does not authorize deleting an unrelated main/production database or the private Key vault. Verify the selected absolute data paths before deletion. Planning-document updates alone never trigger a reset.
- Workflow edits automatically submit to the backend. Saving does not require a runnable workflow: retain only necessary storage-format, identity, permission and genuine write-conflict checks. Run compilation, missing-input/cycle checks and resource availability handling in the actual execution path; do not probe model upstreams merely to save a workflow.
- Manual session/runtime-data edits are forbidden during execution. Permitted edits affect subsequent runs only; do not automatically delete later history, recompute outputs or rewrite confirmed request/execution facts.
- Keep management operations direct and object-scoped. Do not nest unrelated form saves, workflow validation or host-readiness checks before switching, creating, archiving or deleting. Report actual write/execution failures at their responsible operation, retaining necessary ownership, truthful results and unknown-request protections.
- Prioritize explicitly established backend ownership, provider/communication and content boundaries. Node additions/adaptation, workflow-order optimization and node responsibility/contract optimization require a report explaining necessity, scope, reuse, effects and verification, followed by user confirmation before implementation. This gate also covers the corresponding backend scheduler or node-contract changes; do not bypass it by editing backend files first.
- Batches D (node execution/chat data flow) and E (creation/tavern entry) both require subsequent human participation in reviewing the concrete design and user flow before implementation, followed by manual acceptance. Permission to investigate code or update planning documents is not implementation or removal approval for these batches.
- External-tool side-effect rollback, replay-on-round-restart and recovery policies are placeholders for now, not implementation or full acceptance requirements. Do not replay pending model/tool requests or silently upgrade node versions.
- Verify save/reload of incomplete and current workflows, execution-time diagnostics, archive failure, original-request reconciliation, full legacy-data cleanup, temporary validation-data removal and new user acceptance-content preservation. Do not automatically push or start hidden services.
