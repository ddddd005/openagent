## 2. 已确定的方向

1. 同一工作流的真实修改未结束时，不能开始第二次修改。
2. 后端先判断修改互斥，再校验请求基线与当前后端版本是否一致。
3. 前端发送修改期间自锁并等待后端；成功后接纳正式结果，再解除前端修改锁。
4. 稳定修改与明确反馈优先，成本精简随后进行。
5. 项目内部四步完成约定目标并验证后，再整理外部 Agent 接入。

实现时应先核对已有 `RLock`、事务、CAS 和 pending/locked 的覆盖。方向已经确定，不需要重新讨论是否采用修改闭环；具体命令覆盖、锁实现和异常路径还没有全部定案。

## 3. 五个大步骤

| 顺序 | 目标 | 阶段内可并发的主要内容 | 必须先串行完成的事项 |
| --- | --- | --- | --- |
| 1 | 修改能等待、能接纳、能解释结果 | 后端互斥/CAS；前端提交/接纳；独立故障场景设计 | 核对命令覆盖与现有锁，确认忙时和未知结果行为 |
| 2 | 画布动作与实际结果一致 | 连线取消；选择/删除；浏览器复现脚本准备 | 确认点击连线和混合选择行为，约定组件整合负责人 |
| 3 | 保存、引用与运行规则可解释 | 保存结构/引用；运行诊断；前端错误呈现 | 确认保存边界、引用策略及诊断契约 |
| 4 | 减少已证实的内部成本 | 证据协议；修订读取；轮询/历史；只读冗余核查 | 先测量并确认保全、坏记录和刷新要求 |
| 5 | 外部 Agent 复用稳定后的项目能力 | 只读发现/诊断；调用侧结果处理；独立契约检查 | 先确认外部接入方式、权限、目标和运行范围 |

大步骤按顺序推进；并发主要发生在同一步内部。不得以提前写后续阶段代码来掩盖前一步未完成的依赖。
