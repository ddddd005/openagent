## 2. 验证原则

1. 验证具体行为与边界，不按函数逐一复制实现断言。
2. 优先复用有效的当前检查；发现旧架构预期时记录并处理其适用性，不为通过旧测试恢复退役 API。
3. 先跑本批相关检查，出现真实风险再扩大。通过后不无理由重复全量测试。
4. 浏览器取消/松手必须检查真实 Vue Flow 行为；SSR 和应用变量检查不能代替。
5. 并发场景采用可控 gate、事件或 deferred Promise；不依赖长时间 sleep 猜测时序。
6. 数据写入限于隔离夹具与临时库。已有服务启停、浏览器安装、依赖安装、真实模型、业务数据及提交推送须有对应授权。

## 9. S1-00 盘点结论（只读，2026-11-04）

### 9.1 定义修改入口与锁/事务事实

| 入口 | 事务入口 | 锁 | 基线 | 成功返回 |
| --- | --- | --- | --- | --- |
| `definition.update`（整文档；节点配置/移动/连线/删除/撤销重做/改名/新建首存均汇入） | `_configuration_change` → `_change` → `GraphRecordStore.atomic` | 实例级 `RLock`（全局，不分工作流）+ 每命令独立 `BEGIN IMMEDIATE` 事务 | `expected_edit_sequence` + 文档 `revision`；事务内 CAS | `saved` / `unchanged` / `confirmation_required` / `derived` |
| `graph.frontend-node.patch-input`（前端扩展窄补丁） | 同上（`_configuration_change`） | 同上 | 同上（与整文档保存共用 edit_sequence） | 同上 |
| `definition.copy` | `_configuration_change` | 同上 | 源 `expected_source_definition_revision` + `expected_source_edit_sequence`；目标三查无记录 | 新目标定义 |
| `definition.archive/delete` | 事务外预检 `expected_revision` + 实例内 marker，随后 `_change` 写事务 | 同上，但**预检在事务外**（跨实例有窗口，且事务内不复检 revision） | `expected_revision`（仅事务外） | management 结果 |
| `session.create/archive/delete` | 各自 `_change` 事务 | 同上 | 会话 `expected_revision`；create 校验定义固定修订 | 会话/管理结果 |
| `run.start/control/event.submit` 等运行命令 | `_change` / execution 事务 | 同上 | 会话 `expected_revision`；G21 另行判定 | 运行结果 |

其他事实：
- `GraphRecordStore.atomic`：`BEGIN IMMEDIATE` → 幂等 receipt 回放（同 key 同 digest 返回旧结果，异 digest `idempotency_conflict`）→ change → 校验 → 写 receipt → COMMIT；异常 ROLLBACK。receipt 与业务在**同一事务**，业务已提交 ⇒ receipt 必存在。
- G21：`workflow_configuration.py:374-388` `_require_no_unfinished_run`，任一持久化会话 `active_chain_run_id != None` 即 `configuration_run_locked` 409；位于 CAS 判定之前的同一事务内。
- 跨实例/进程正确性：SQLite `timeout=30` + `BEGIN IMMEDIATE` 排队；30s 超时表现为未映射的 500 `internal_error`。
- 无显式忙状态：同实例后来请求阻塞在 `RLock`；实例锁还保护配置读取（全局锁，慢保存会阻塞读取）。
- 服务实例：常规单进程下执行/管理共享同一实例；Host 懒建最多 2 个实例（执行与管理），两实例各有独立 `RLock`。
- 只读核实：`graph_receipts.py:582-619` 以只读连接按完整原请求严格核对回执；无匹配回执**不能**证明业务未发生。

### 9.2 前端等待链事实

- `workflowEditing.edit` 同步构造文档 → `acceptDraft` → `void submitConfigurationDocument(...)`（fire-and-forget）→ 立即返回 `workflowId`；所有 `editable()` 调用方（添加/移动/连线/删除/撤销重做/改名/复制节点/预加载/事件绑定等）把 truthy 当成功，提前改选区/关对话框/清提示。
- 一个**已等待真实结果**的通道存在：窄补丁 `sdk.configureNode → patchNodeConfiguration`；管理/复制通道亦 await 回执。
- application 层 `submit` 已有完整顺序（证据写→读确认→业务→接纳→读确认→结案）与 `progress`（evidence-unknown/request-in-flight/result-unknown/rejected/acceptance-failed/closure-failed/completed）区分；缺口在 store/UI 层折叠失败与反馈不可持续。
- 请求构造后目标/基线/正文/key 固定；`configurationSubmitting` 在首个 await 前设置；轮询不写 accepted。唯一换 key 路径是用户确认派生。

- 现有守卫：viewToken/selectionSequence/viewGeneration/refreshGenerations/mutationGeneration/sessionSelectionGeneration 等均在。

- **Q04-2 取消与提示：取消必须终止本次连线手势**。Esc：有待连线时优先取消连线并清理相关提示、保留选区；随后松手或同一次手势的 click 都不能补建边。空白：点击空白取消待连线；拖拽到空白松手正常结束，不建边、不报错、清除兼容提示。非法目标：结束本次连线、不建边，显示具体原因（类型不兼容/输入已占用等），提示允许关闭或下一次连线开始时清除。取消后可立即重新连线。保存失败继续使用第一步提交错误反馈，与连线准入失败区分。验收必须包含真实浏览器"拖拽中 Esc → 移到合法目标 → 松手"不建边，不能只检查应用变量。
- **Q04-3 选择：节点与边互斥**。节点允许多选、边单选，二者不能同时存在；点击/添加/定位/框选节点都清除旧边选择，选边清除节点选择；Delete 与垃圾桶使用同一目标计算；删除节点仍按现有规则同批删除关联边，无关旧选边不得进入删除范围；本步不重写整套选择数据结构。
- **Q04-4 选区修剪：正式文档变化后统一按存在性修剪**。删除成功移除已删除对象选择，明确失败保留仍有效选择；撤销/重做成功仅保留恢复后文档中仍存在的选中节点或边、不自动恢复历史选区；正式结果接纳或刷新采用相同规则并保持互斥；切换工作流清空选区、待连线与相关提示，旧请求迟到不能清理新工作流选择；Delete 遇到失效选区时清掉无效身份，不发送无变化保存，也不保留失效选区。
- 影响任务：S2-01（连线生命周期/提示）、S2-02（互斥选择/删除目标/修剪）、S2-03（组件整合）、S2-04（真实浏览器验收与 C01 回归）。

### 10.8 Q05/Q06 结构与诊断决定（2026-11-04，用户回复）

- **Q05-1 普通边端点**：节点存在性属于保存结构约束，保存与编译入口都检查。普通数据边的 source/target 节点必须存在，与控制边等保持一致；保存时拒绝悬挂边并定位 edge_id、缺失节点及对应字段。编译入口也必须独立检查，避免未保存文档或历史文档绕过；任何边都不能因目标不存在而被静默忽略。端口不存在、类型不匹配等继续作为编译诊断阻止运行；不把完整编译通过升级为保存门槛，未接完输入的图仍可保存。
- **Q05-2 删除/替换引用**：依据声明检查引用，默认阻止造成存活引用失效的删除。使用 `config_node_references`、`object_accesses` 与实际对象绑定规则计算影响，不猜字段名、不自动清空必填配置、不自动重绑对象。若删除后仍有存活节点引用该节点或失效对象键，阻止本次删除，列出引用者、字段路径和目标；用户先修正引用或在同一份修改中一并处理相关节点。已有控制边、事件目标、对象绑定和预加载继续同批清理。后端也要校验确认后的规则，不能只靠前端阻止；未配置完成与明确悬挂引用须区分。
- **Q05-3 替换节点旧边**：替换保留兼容边，不兼容则阻止替换。替换前按新组件及配置检查相关旧边；确定兼容的边保留原身份和顺序；不兼容或无法确认兼容时列出具体边和原因，要求先断开再替换。不猜端口映射、不静默删除旧边，也不把"替换成功后留下错误"作为默认流程。配置引用和对象登记同时检查；旧登记不适用于新组件时必须先明确处理，不自动迁移已有会话对象或历史数据。
- **Q06-1 诊断增补**：增补阶段与字段路径，范围先覆盖本轮工作流链路。保留现有诊断字段，重点增加：`phase`（保存校验/编译/准备/节点执行/结算/存储失败）、`path`（JSON Pointer，并明确指向文档、运行输入等哪个检查对象）、可获得的节点/边/端口/对象键及经脱敏的期望/实际类型或值摘要。结构错误也必须有定位（不能只有一句 `graph_invalid_control_edge`）；无法获得的信息如实缺省，不虚构、不输出整份敏感载荷；明确外层 reason_code 与诊断项 code 的对应关系；本步不全库改名或重构所有错误模型。
- **Q06-2 保存预演**：新增正式只读保存预演，复用现有规则。分别说明：当前是否满足保存条件、编译结果、变更分类、是否需要派生确认，以及哪些运行条件已检查/尚未检查。包与资源只检查可只读判断的条件，不调用模型、不执行工具、不预占资源；保留 `definition.inputs` 的输入声明职责，不直接改变其现有用途。预演不写业务、证据或幂等记录，不取得保存资格；实际提交仍重新执行 CAS、G21 和必要校验；预演成功不保证稍后提交或运行成功。
- **Q06-3 契约承载**：提供版本化机器可读契约，通过现有发现入口暴露。集中提供 GraphDocument schema、实际容量上限、保存语义、诊断字段和相关错误码目录，由 `describe()` 提供发现入口；节点配置与端口细节继续使用 catalog。上限与规则复用后端实际来源，避免另抄一套常量；JSON Schema 描述结构，动态节点及编译语义由目录和校验器承担，不能宣称 schema 覆盖全部运行约束。目录先覆盖本轮保存、编译、准备与运行相关诊断，配少量有效示例，不扩大为全项目契约重建。
- 影响任务：S3-01（保存结构/引用/契约）、S3-02（运行诊断/G21/close/preview）、S3-03（前端校验/阻止/诊断展示）、S3-04（整合验证）。

### 10.9 Q07-Q10 成本与精简决定（2026-11-04，用户回复）

- **Q07 证据协议：窄查询 + 分层初始化**。确认读按 owner+operation+key 点查并返回完整原请求，校验本条证据身份/正文/完整性；初始化先查 pending 摘要，无 pending 即结束，有 pending 再精确读取正文；摘要读取遇字段异常或唯一性异常必须明确报错，不能当作"没有 pending"。保留现有历史全量读取能力，不删除/不迁移证据；本批保留五步确认链；未知业务结果继续通过只读 receipt 核实、不自动重放。明确接受"正常编辑不再顺带校验该 owner 全部旧证据"这一完整性检查范围缩小，不宣称全历史校验覆盖不变，也不为此另建后台扫描机制。
- **Q08 历史读取：只优化第二遍 MAX**（1A）。前提：逐个调用者确认同一事务内已完成原有第一遍全量校验，不能只凭主要保存入口判断；SQL MAX 统计范围与原实现一致（原逻辑跳过非法 JSON/非 graph 负载，不能对整表取 max 让被跳过记录改变修订号）；无法满足前提的调用路径保留原实现。坏记录跳过/报错/回滚行为本批不变，也不能把保留描述成坏记录问题已解决。
- **Q09 轮询：冻结定义复用 + 摘要读取**（1B）。GraphHistory 按 (workflow_definition_id, definition_revision) 复用成功读取结果，不随链 revision 重复下载；保留 run.read 触发/更新与现有 viewToken/generation/单调接纳守卫；冻结定义读取失败明确显示缺失、不用当前编辑图替代、不永久缓存失败；refreshPublishedRevision 改读 summaries 中固定修订字段，需要"最新值"时仍发起摘要读取，不能拿可能过期的本地摘要。本批保留会话摘要轮询频率；event.bindings 先核实变化来源，未确认前不精简。
- **Q10 冗余：仅清理逐项确认的死路径**（1B，执行范围由逐项证据确定）。可清理：已确认无生产用途的旧前端状态、不可达分支、无调用函数、no-op 接口、LocalDraftStore.save 退役写入口。保留：原请求证据、历史读取及仍有效的当前行为验证、LocalDraftStore 仍被使用的读取能力、外部使用面未确认的公共查询/移动端接口/store 导出面。依赖 no-op 的测试夹具随之调整，不为保旧测试重造替代接口；重复校验、双副本职责未定，本批不动。Q07/Q08/Q09 可各自边界确认后并行；Q10 与这些改动重叠的清理放到调用关系稳定后。验收关注请求数量、传输量、保存耗时与既有错误反馈。收益表述为"减少证据全量读取、一次重复历史扫描、冻结定义重复下载"，不宣称保存路径变常数成本。
- 影响任务：S4-00（新基线测量）、S4-01（证据协议前后端）、S4-02（历史读取）、S4-03（前端冻结定义/摘要）、S4-04（逐项死路径核查）、S4-05（整合复测）。

### 10.10 Q11/Q12 外部 Agent 接入决定（2026-11-04，用户回复）

- **Q11-1 承载方式：复用现有本地接口接入**。以现有 HTTP 的 describe／command／query 为正式入口，复用 document.contract、节点目录、预演和回执查询；Codex、dsh 等 harness 通过各自已有的工具执行能力调用；确实需要适配时只增加薄调用层，不复制业务逻辑，也不要求先建设专用 Agent 平台、调度器或认证体系。当前保持“本地可信调用”边界；"用户信任某个 harness"是使用前提，不为此建设来源认证/白名单系统；以后需要远程接入时再单独讨论远程认证。
- **Q11-2 目标与写入范围：开放完整的工作流编辑和调试能力**。开放已有能力范围内的：查询工作流/节点契约/配置/引用/诊断/运行记录；创建、复制、修改、改名、归档和删除工作流；修改节点、连线、绑定、配置与预加载等完整定义内容；保存预演、正式提交、读取正式结果及核实未知结果；根据诊断继续修改形成完整调试循环。不限定 Agent 只能改某几种节点，也不把每次写入变成用户确认问询；派生确认等现有语义由接口返回可处理信息并允许已授权 Agent 明确选择。保留的约束是既有工程规则：同工作流修改互斥、CAS、结构校验、幂等与证据闭环；前端与外部 Agent 共用这些规则避免互相覆盖。**读取、分析和预演不占用编辑锁**；锁只覆盖实际修改过程，不能让 Agent 整轮思考调试占住工作流。外部提交后前端需识别正式版本变化并明确反馈本地编辑冲突。工作流内部 Agent 自修改继续留在本步范围之外。
- **Q12 运行与控制：开放完整能力**。允许外部 Agent 创建会话、启动运行、读取进度，以及显式调用 pause／resume／close／retry_*。用户启用的调试接入范围可以直接包含真实模型调用，在接入说明中明确即可，不必对每次启动/恢复/重试反复弹窗；原有模型配置和工具权限继续生效。同时保留动作准确含义：run.start 返回已启动不等于运行成功，最终状态通过查询获取；close 由 Agent 明确调用，不能因 G21 在调用层自动执行；retry_* 是明确控制动作，请求结果未知时先核实不能自动重放；运行失败完整返回阶段、节点和原因。本阶段可宽开放操作权限，同时严格保证操作语义。**第 5 步验收目标**：用户启用一个可信 harness 后，能通过现有接口独立完成“发现契约 → 编辑 → 预演 → 保存 → 运行 → 定位错误 → 再修改”的完整循环。
- 影响任务：S5-00（能力矩阵与最小操作集、本地编辑冲突识别）、S5-01（只读发现/预演/诊断使用说明与薄调用层，如需）、S5-02（编辑/保存/结果核实循环）、S5-03（运行与控制语义）、S5-04（隔离夹具验证 + 接入说明）。
- 限制说明：本会话未获授权启停现有服务、未安装依赖；因此 S5 验收以隔离夹具/模拟 transport 演示完整循环，真实模型调用按 Q12 属于“用户启用调试范围内的许可”，在接入说明中明确，不在此会话内未经服务启停授权实际消耗模型。

## 19. 显示问题订正：编辑状态区整体迁移为浮层（2026-11-05）

### 19.1 用户报告与决定

- 2026-11-05 用户报告：每次修改节点（即使只是改位置）都会在页面顶部出现提示，导致页面上下抖动；要求“要么单独划一块区域展示信息，要么作为浮层展示”。
- 同日用户决定：**整体迁移，使用浮层机制**（本记录 §19 即该决定的落实）。

### 19.2 根因（已定位，非猜测）

- `WorkflowWorkspace.vue` 的“工作流修改状态”区块（原 `<section class="workflow-edit-state">`）是**普通文档流**中的兄弟节点，位于顶栏与 `.workbench-canvas-region`（`flex:1`）之间；它出现或消失都会改变画布区域高度，即用户看到的上下抖动。
- 每次节点编辑（含拖动位置）都走一次正式保存：`GraphWorkbench.onNodeDragStop` → `graph.moveNodes` → `editable()` → 配置 application `submit`。保存期间进度依次为 `evidence-writing` → `request-in-flight` → `business-confirmed` → `completed`，而原 `showRequestState` 的可见集合包含 `request-in-flight`/`business-confirmed`，于是**普通保存每编辑一次就让该区块出现再消失一次**（估算高度约 48–50px），一次编辑内抖动两次。
- 同类问题与已定规则冲突：`docs/中期检查2/157` §R4/§10 与 `158` §6 已由用户确认“普通配置保存中、成功及连续节点移动不逐次提示，不再在画布上方插入 pending 横幅”“需要状态反馈时使用尺寸稳定的固定区域，不改变画布位置或高度”。本次第 1 步新增的持久状态区把正常在途重新做成画布上方横幅，属于回归。
- 补充核对：项目通知 `ErrorToast` 为 `position:fixed` 浮层，不参与布局，不是本次抖动来源；`WorkflowWorkspace` 之外的 `App.vue` 横幅只在持久化错误时出现。
