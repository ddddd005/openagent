## 1. 范围与进入条件

进入条件是前四步约定目标完成并验证，代码执行方应先阅读其实际交付，重新核对操作描述和保存语义。外部 Agent 复用这些能力，不维护第二套绕过修改互斥、CAS 或 G21 的保存逻辑。

本步面向外部代码 Agent 或其他外部调用方。工作流内 Agent 管理另一份图、同图运行中修改自身、工具注册重构均不作为本步前提。

Q11 决定承载、身份、目标及写入范围，Q12 决定运行和控制权限。当前应用声明的可信本地 scope 不能直接当作远程或模型调用认证。

## 4. 调用方使用流程

### 4.1 发现、读取与构造

1. 根据已有应用描述和 `catalog.node-types` v2 了解本次可用节点、端口、配置 schema 和包条件；v2 已含 platform 信息时不重复全量读取。
2. 找到明确目标，读取当前 `definition.read` 文档及 `edit_sequence`/fixed `revision`。指定修订的历史原文不能直接作为当前编辑基线。
3. 在同一捕获基线上构造完整修改，不借机更改目标身份或自动吸收其他调用方的新编辑。
4. 使用第三步实际提供的检查能力。若仍使用 `definition.inputs`，同时检查诊断和输入声明；不要把编译未通过的 200 当作可运行。
5. 如果 Q11 只允许副本试验，按确认流程先复制，记录新定义与节点映射；不能把副本规则默认施加到所有调用方。

### 4.2 提交与结果

一次业务尝试保留 operation、目标、参数原文、基线和 key。保存键只属于该次固定请求，不为绕过未知状态或冲突自动更换。

| 结果 | 调用方行为 |
| --- | --- |
| `saved` / `unchanged` | 使用服务端正式返回，更新当前目标和基线；不凭本地文档推断最终状态 |
| `confirmation_required` | 按 Q12 的确认策略报告；未获授权时停止该修改，不自动确认 |
| `derived` | 使用新定义身份及映射继续操作，不再向原身份误写 |
| 修改忙/G21 | 返回真实原因和当前可用信息，不绕过、不自动 close |
| CAS 失败 | 保留原提案与旧基线，重新判断差异；不把旧正文自动附到新序号提交 |
| 结果未知 | 保存原请求/key，采用确认的只读核实；无回执仍属未决，不能自动重放 |
| 业务确认但调用侧结果处理失败 | 保留已确认结果，修正消费或显示；不重新执行业务 |

后端命令本身不强制走前端证据协议，不代表外部 Agent 可以丢弃原请求和未知结果核实。是否复用现有保全设施由 Q11 的方案明确，不另造未经确认的 outbox。

### 4.3 运行与结果观测

仅在 Q12 明确允许时：

1. 使用实际保存结果中的目标和 fixed 修订创建会话。
2. 启动时使用当前会话修订作为 `expected_revision`，不与定义修订或编辑序号混用。
3. 启动响应不代表运行完成，随后观测 `session.read/run.read`。不必照搬工作台轮询频率，但必须有确定的完成/失败判断。
4. public 输出与管理运行详情分别读取，不把 `output.list/read` 当作所有中间端口的无条件读取。
5. 准备失败没有运行记录时，保留原失败响应；历史为空不代表未发生错误。
6. 失败/暂停可能保留 active 占用。只报告可用动作；需要关闭、派生或重试时按 Q12 执行。

`close` 是有后果的运行控制，不能作为失败后的固定下一步。即使关闭一条链，也要重新判断其他会话占用和有效会话下的派生规则。

## 6. 出口检查

- 操作范围符合 Q11/Q12；超出目标、权限或控制范围的请求明确失败。
- 读取当前基线、检查诊断、批量修改、接纳正式结果依照同一套规则。
- 旧基线冲突时不自动覆盖；结果未知时业务调用次数不自动增加。
- 派生/复制后身份和节点映射用于后续操作；不会继续误写原定义。
- 启动获授权的隔离运行后能观测真实完成/失败，而非把启动当完成。
- 准备失败原响应、运行失败诊断和输出来源能保留并解释。
- 不自动关闭/派生/重试，不突破 G21，不安装工作流内自修改能力。

验证优先使用模拟 transport、临时库和纯文本/确定性节点。真实模型调用、业务数据和现有服务操作须另有明确授权。本步完成后交付调用说明及实际可执行示例，而不是只列一组工具名称。
