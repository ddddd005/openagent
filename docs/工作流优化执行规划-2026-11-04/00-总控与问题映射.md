## 4. 同步与并发的基本约束

1. 阶段内先固定本次涉及的契约，再并行写前后端；契约变化后先同步受影响执行者。
2. 同一文件只有一名写入负责人。不同函数也不默认可以多人同时改。
3. 前端 store、工作台组件、后端服务、存储/契约文件是高冲突位置，各阶段明确归属。
4. 检查设计与复现准备可并行；依赖实现的断言在接口稳定后编写和执行。
5. 整合与阶段出口验收串行，由执行负责人处理，不由多个执行者各自宣布全阶段完成。
6. 文档中的并发是项目执行建议，本次未启动代码子代理或后台执行任务。

各阶段的波次、文件冲突和交接材料详见 07；所有跨阶段的共享文件先完成前一步交接，再转移写入责任。

## 5. 不扩大本次计划的内容

- 不把后台运行改为一次阻塞直到模型完成的 HTTP 请求。
- 不移除 G21，不自动关闭运行，不自动确认派生或重试外部效果。
- 不强制完整编译通过才能保存未完成图。
- 不默认引入新调度器、编辑队列、租约、分布式锁、自动恢复器或新的持久化草稿。
- 不把前端扩展字段归属、可调分类、完整配置 schema 与窄补丁准入合并成一个白名单。
- 不把旧勘察中的建议接口直接视作待安装要求。

如果当前部署确实需要上述新机制，执行方应先提交事实、理由、范围与最小方案，取得决定后再更新规划。

## 6. 阶段完成的判断

阶段完成至少需要：受影响决定已记录、约定改动实际落地、相关行为检查通过、限制与未覆盖项明确、下一步依赖已交接。只写方案、只编译成功、只有历史测试结果或只拿到某个代理的“完成”消息，均不满足出口。
