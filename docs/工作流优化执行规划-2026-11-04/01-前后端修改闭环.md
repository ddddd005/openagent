# 第一步：前后端修改闭环

日期：2026-11-04。对应 S01、S03。状态：待执行。

## 1. 目标与前置决定

让一次工作流修改从前端发起到后端接纳具有一致的等待、锁与反馈语义。用户已确定前端自锁、后端先互斥后 CAS、成功接纳后解锁的方向；具体命令覆盖与异常行为按 Q01-Q03 确认。

本步不删除原请求证据协议，不改变后台执行和 G21，不把所有管理、资源、凭据通道合并成一个新系统。

### S1-00：先把覆盖与结果写清

入口盘点至少包含整文档保存、节点配置/策略、展示移动、连线/删除、撤销/重做、窄补丁及前端扩展提交。新建、复制、归档/删除等另列竞争关系，由 Q01 决定是否纳入本步，不能因“归一”就扩大锁的业务范围。

每个入口记录：调用方、工作流身份、版本依据、事务入口、已有防重入、调用方等待方式、正式结果应用位置。对没有现成后端事务的入口先报告事实，不自行发明异步修改任务。

对同 key 的幂等回放单独说明：读取已接纳结果不等于开始第二次真实修改。调整互斥时不得无意破坏既有回放与 `idempotency_conflict` 行为。

### S1-01：后端修改互斥与版本校验

按确认范围逐项核对：

1. 互斥资格取得是原子的，不能用“先查一个标志，再设置标志”造成竞争窗口。
2. 版本检查和业务写入在实际事务保护下，不能在事务外预读后直接写。
3. 以当前编辑基线核对 `expected_edit_sequence`，保留已有固定修订约束。仅修改展示/可调值后，旧编辑基线也必须失败。
4. 忙时行为按 Q02 执行并明确反馈。若采用等待，等到资格后仍须重新检查 CAS；等待不能赋予旧请求新的基线。
5. 成功提交和明确回滚都结束本次真实修改。建议该互斥不等待前端确认或证据结案；具体生命周期写入 Q02 决定。
6. 保留 G21 的现行冻结范围。修改互斥和运行冻结分别报出实际原因，不静默合并。

若现有机制已经满足某项，保留并用有意义的竞争检查证明，不为完成任务强行增加一把锁。只有部署事实需要时才验证跨进程方案，不默认建设分布式锁。

### S1-02：前端提交与接纳

前端执行者统一处理应用层、store 及其调用方，重点是：

- 在首个异步间隙前确认现有防重入是否已经生效，避免初始化证据或异步草稿交接时漏掉第二次修改。
- 一次请求固定捕获目标身份、当前基线、文档正文和 key，发出后不随页面切换或轮询改写。
- 传播可等待的结果直至连线、删除、节点配置、移动和历史操作的实际入口；不只把某个方法改为 `async`。
- 正式文档、基线、历史和选择相关变化按接纳结果更新。不得提前给出删除/保存成功。
- 无实际变化时结束本次入口处理，说明没有写入；不伪造保存回执，也不留下忙状态。
- 派生结果使用返回的新身份和节点映射。用户已经切换工作流时，不把迟到结果投到当前无关画布。
- 修改等待期间对相关编辑入口一致禁用或明确拒绝。只读查看是否允许按既有规则处理，不扩大为整页冻结。

组件原文/草稿与正式文档的职责继续区分。Q03 如要求新增持久化编辑草稿，应另报方案；保留本次编辑不等于自动重建退役的草稿保存 API。

### S1-03：结果反馈矩阵

下表是必须覆盖的事实分类；具体交互和解除阻塞规则由 Q03 决定。

| 实际结果或失败位置 | 已知事实 | 预期处理方向 |
| --- | --- | --- |
| 本地无变化/明确校验拒绝 | 本次业务未发送 | 说明原因或无变化，结束入口忙状态，保留必要原文 |
| `saved` / `unchanged` | 服务端已经给出正式结果 | 接纳结果，更新相应投影与历史，再结束前端提交锁 |
| `confirmation_required` | 此次未写配置，等待派生决定 | 显示待确认，不宣称保存完成，不自动确认 |
| `derived` | 新定义已产生 | 接纳新身份和映射；旧画布上下文不可误用 |
| CAS/G21/忙时明确拒绝 | 该业务修改明确未接纳 | 显示实际原因，按证据规则结束提交；不得重读新序号后覆盖旧正文 |
| 写证据失败且业务未发送 | 未发送业务，但证据持久化事实可能待核实 | 明确标注“业务未发送”，不与业务响应丢失混同 |
| 业务请求响应丢失 | 业务结果未知 | 保留原请求/key，进入只读核实，不自动重发 |
| 正式结果已确认，当前投影失败 | 后端结果已知，界面尚未正确接纳 | 保留正式结果，说明显示问题；不得重新执行业务 |
| 业务已确认，证据结案失败 | 业务与证据状态不同 | 分别反馈；按 Q03 限定动作，不把它说成保存未发生 |

核实读不到匹配回执，不证明修改没有发生；不得以“没有回执”为理由清空原请求并换 key 重发。何时恢复编辑、如何处理未发送但有 pending 的证据，须有具体决定，不能依靠刷新页面碰运气。

## 5. 验收重点

- 慢保存期间同一工作流再改一次，不能产生第二次未受控业务修改；用户能看到为什么不能继续。
- 两个调用方持有同一旧基线，最终不能覆盖已经接纳的新内容。等待后仍需 CAS。
- 明确失败时没有提前成功提示、错误历史推进或提前清空选区。
- 模拟响应丢失后只读核实原请求，业务调用次数不自动增加。
- 已确认业务但投影/结案失败时，显示准确阶段；没有隐式重新保存。
- 保存期间切换工作流/会话，迟到结果不覆盖新视图；既有单调接纳守卫仍有效。
- 调用 key 冲突、派生确认和 G21 的既有规则未被锁改动破坏。

检查入口及可用命令见 06。第一步通过后向第二步交付可等待的编辑返回约定、锁原因、成功接纳时点、失败时选择处理责任，以及本轮未改变的规则。
