## 3. 根因：版本钉死是最大单一杠杆

**实测当前注册版本**（由主代理运行服务实例读取注册表，非文档转述）：

```text
models.source@7     models.chat@5     agents.execute@10   agents.compaction-policy@2
context.output@5    context.assembly@5   context.merge@6
tools.variable-register@2   prompts.item@2,3   其余tools.*@1 / prompts.*@2
```

**而共享图夹具仍写着旧版本**——`tests/test_graph_service.py:22-23`：

```python
version = {"models.source": "5", "models.chat": "3", "agents.execute": "5"}.get(
    component, "5" if component.startswith("context.") else "2" if component.startswith("prompts.") else "1")
```

三处失配：`models.source 5→7`、`models.chat 3→5`、`agents.execute 5→10`；且 `context.` 前缀一律取 `5`，而 `context.merge` 现行是 `6`。

**更严重的是第 28 行的静默兜底**：`... if entry else config`。版本查不到时不报错，塞一个裸 config 继续，把故障推迟到图编译期，表现为毫不相干的 `Object registrar node definition is unavailable`（全基线 19 项同签名：`test_agent_integration` 5、`test_context_adopt_retirement` 3、`test_result_acceptance_retry` 3、`test_context_value_snapshot_boundaries` 2、`test_schema3_context_edit_preconditions` 2 等）。该夹具被约 70 个测试文件 import。

同一根因的另一种形态是 `NoneType` 无 `definition`（**74 项**，66 failure + 8 error，主代理按 JUnit 逐条复算）：夹具内直接 `registry.get(组件, 版本).definition`，取到 `None` 即炸。

### 4.1 上下文档位族（101 项，3 个根因）

1. **v4→v5 档位漂移（83 项）**：夹具构造 `CONTEXT_VIEW@4` 送进只接受 `@5` 的现行装配入口。抛出点 `context_v4.py:92-94`，触发点 `context_prompt_v6.py:157-158`。
2. **共享图夹具版本漂移（17 项）**：见第 3 节。
3. **对象值形状陈旧（1 项）**：`test_context_update.py:259-262` 塞旧的指针值 `{view_ref, accepted_delta_ids}`，现行要求内联逻辑值 `{messages, layout, accepted_delta_ids, generation}`（`context_contract.py:40-69`）。

契约自洽的反证：现行活动版本为 `CONTEXT_VIEW@5`（`context_v4.py:87-125`），`@4` 仍注册但只作历史只读解码（`graph_receipts.py:427-466`）；现行图**不存在** `CONTEXT_VIEW@4` 端口（`context_v4_nodes.py:246,249,265`），且边连接强制 `(type, schema_version)` 相等（`graph_contracts.py:891-893`）。5 个现行路径模块实测 **142 项全通过**，含 `agents.execute@10 → context.merge@6` 的端到端提交/检查点/分叉。

### 4.2 模型服务与限额族（95 项）

- `PublicModelService` 在 `src/` 中零引用，定义于 `c8af63e~1:model_service.py:152`，由提交 `c8af63e` **彻底移除**（新旧构造参数集合无重叠）；现行接缝是 `graph_service.py:193-194` 的 `public_model_factory` 与 `MODEL_SERVICE_REF["transport_factory"]`，**无 1:1 替代类**。影响 62 项。
- 预算参数：`SnapshotKernel.run()`（`runtime.py:335-348`）已无预算参数；`model_request_budget_exhausted` / `model_attempt_budget_exhausted` 在 `src/` 中完全消失，仅保留每请求 4 次传输尝试的 `model_retry_exhausted`。影响 29 项。
- 反证：现行模型请求契约的 5 个测试文件实测 **158 项全通过**，说明现行路径本身健康。

## 5. 产品侧问题（不在 469 项失败内，勘察期间核出）

### 5.1 开发库重置helper缺新聊天表（已修复）

`backend/scripts/reset_development_data.py` 的 `_PRODUCT_TABLES` 未收录 `workflow_chat_round_inputs` 与 `workflow_chat_invocations`，而这两张表由 `workflow_chat_runtime.py:15-19` 在产品运行中创建。后果：开发库一旦跑过逻辑聊天，重置即被 `Unclassified tables; reset not performed` 拒绝。**已按用户指示修复并验证**（22 passed），另补一条覆盖用例。

### 5.2 契约导出 schema 已过期

`backend/schemas/contracts-v2.schema.json` 自 2026-10-09 起未再生成。主代理用既有脚本 `backend/scripts/export_contract_schemas.py` 导出到临时目录比对，实测：

- `workflow_operation`：导出 **14** 个变体 vs 已提交 **15** 个
- `input_snapshot`：结构已重整

导出脚本两次运行结果一致（非确定性已排除）；该文件**无运行时消费方**（只有导出脚本自身与 `test_schema_export` 读它）。修复方式=用既有脚本再生成。

### 5.3 测试资产缺失导致永久失败

`backend/tests/frontend_controls.test.cjs` 由提交 `8eb7e93` 删除，但其唯一消费者 `tests/test_frontend_controls.py:14` 留在原处，该测试**永久失败**。同目录仍有 15 个 `.cjs` 存活，属单点遗漏而非整体清理。处置需裁定：恢复资产或退役该测试。

### 5.4 事件操作词表未随公开契约退役 `extend_budget`（唯一产品侧轻微不一致）

`backend/src/phase1_agent/event_contracts.py:34-42` 仍把 `extend_budget` 列在现行事件 schema 的枚举里：

- `:35` 的 `_ACTIONS`（`workflow_operation_result` 等事件的动作枚举）
- `:38-42` 的 `WORKFLOW_OPERATION_KINDS`（`:61` 用作 `workflow_operation_result.operation_kind` 的 enum）

而公开操作契约已在 `c8af63e`（2026-10-15，与二次限额退出同批）从 `contracts_v2.py:756` 的 `_OPERATION_VARIANTS` 删除该项，服务侧也不再产生该动作（`graph_service.py:526-536`）。主代理实测两侧差集恰为 `{extend_budget}`。

其它两处命中属**历史只读解释**，不是现行矛盾：`contracts_v2.py:408` 是 `ControlCommand` 的旧字面量、`:1073` 是旧控制命令的只读解释变体；`graph_drafts.py:147-149` 是旧草稿动作允许集。

影响有限：不会损坏数据，但允许新的 `workflow_operation_result` 事件声明一个公开契约已不存在的操作种类。处置需裁定——按31号回执只允许"历史只读解释"，则应从事件词表移除（并同步用例）；否则要写明例外。

### 5.5 缺包 paused 会话的 `available_actions` 自相矛盾（未判定，需裁定）

`graph_service.py:526-532` 对 `paused` 状态一律给出 `["resume","close"]`，`:558` 在"缺包但有活动链"时仍原样透出；而缺包服务的所有控制事务都被全局拒绝（`test_graph_package_selection.py:191-195` 已断言 `control(resume)` 抛 `package_missing_dependency`，该断言通过）。前端 `workflowGraph.ts:131` 以该列表是否含 `resume` 决定主按钮，因此缺包 paused 会话会显示一个必然失败的"继续"。旧门禁 `120d37e:graph_service.py:499` 在不可用时只给 `close`。两种读法都有文档支撑，勘察单元未单方定性。

### 5.6 未连线未知节点会让整份定义只读（行为性断言，需确认）

`test_current_architecture_retirement.py:156-158`（本批唯一的行为性断言失败）实测：文档含一个未连线的 `unknown.custom-node@1` 时，`can_submit=False`、`readonly=True`、`available_actions=[]`，运行抛 `graph_missing_node_type`；而该用例后半段（`:165-171` 期望 `graph_missing_node_type` 且 `chains==[]`）仍成立。

实现依据是 `graph_service.py:218-225` 的 `_document_available` 使用 `all(... for node in document["nodes"])`，同一规则在 `checkpoint_collection.py:70`、`checkpoint_loading.py:150`、`graph_input_declarations.py:14`、`graph_public.py:36` 复制。设计授权见 [23号实施回执](../归档/2026-10-17/中期检查2/23-定义层安装与普通执行筛选实施回执-2026-10-14.md)（"按新来源判断定义可用性"）。

勘察判定为**契约变更而非缺陷**（规则系统性且有授权），但授权文字未逐字写明"一个未连线未知节点会让整份文档只读、连可达部分也不能运行"这一后果，故按流程交回确认。

### 5.7 修好第一层后必然暴露的第二层陈旧

补查实验发现两处：`test_public_runtime_review.py:52` 的内嵌脚本仍写 `ModelHostService.prepare_run`，而该类在 `src/` 中已无 `prepare_run`（实测两个现行类 `hasattr(...,'prepare_run') is False`）；`test_runtime_content_boundaries.py` 的变量登记簇在版本修正后还会撞上注册者 binding 与 `non_working` 依赖。

### 5.8 测试因错误原因而通过

`tests/test_prompt_lifecycle.py:408-411`：v4 夹具让它抛 `context_update_invalid`，恰好被 `pytest.raises` 收下；换成 v5 视图才会抛它真正要验的 `graph_prompt_artifact_refs_invalid`，即该用例当前**因为错误原因而绿**。同类结构在迁移时应自查。

另外两处产品/契约层面的问题见第 7 节待裁定项（`execution_roots` 字段"接受但无作用"、`PROMPT@6` 一个标识覆盖两种互斥形状）。

## 6. 对勘察过程中间结论的订正

**订正一：`context_update.py:305/311` 不是活动缺陷。** 模型族单元报告该处用已退役的 v2 校验器 `validate_public_model_binding`（只接受 schema 2/4）校验现行 v5 绑定，必然抛错。主代理逐环节复验：事实链成立，但**可达性结论需要订正**——该函数只被 `context_v4_nodes.py:65` 的 `_merge_legacy` 调用，而 `_merge_legacy` **未注册、不可达**（实测运行时只注册 `context.merge@6`；全仓 `_merge_legacy` 仅出现在定义行，无注册点、无测试引用）。活动的 `context.merge@6` 走 `_merge` → `prove_context_merge_execution_v2` → `validate_model_binding`，**接受 v5**。因此它是死代码内的版本错配，不是影响当前保存/执行路径的产品缺陷。

**订正二：三处计数偏差，已在[现有测试失败清单](现有测试失败清单-2026-10-16.md)修正。** `test_execution_facts.py` 48 项实为 43 `save_bundle` + 5 `get_record`（原写含`NoneType`有误）；`test_prepared_request_gate.py` 14 项实为 12 项直接 `CONTEXT_VIEW@5` 拒绝 + 2 项子进程同因（原写"子进程脚本回溯失败"有误）；`NoneType.definition` 计数 64→**74**（按 JUnit failure+error 口径）。
