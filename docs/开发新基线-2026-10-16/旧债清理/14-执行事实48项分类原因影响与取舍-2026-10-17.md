## 2. 为什么不是把 seed 改一个名字就能结束

旧测试把建图、旧记录校验、事实落盘及整段因果校验集中到 `SqliteStore`，使用旧 `run_record/input_snapshot` 等记录和 `execution_facts` 表。当前代码已经有不同的职责落点：

| 已存在的当前落点 | 已能确认的职责 | 不能据此推定 |
| --- | --- | --- |
| `SqliteStore`，storage 20 | 当前基础表初始化、底层图记录存储及回执读取 | 自动恢复旧 `save_bundle/get_record/append_execution_fact`，或恢复旧 `execution_facts` 表 |
| `RuntimeFactStore` | 按 invocation/stream 存储不可变事实、幂等冲突及相邻序号检查，依赖外部事务 | 能理解每个能力包的全部事实类型、模型请求及工具因果 |
| `GraphRuntimeHost._accept_runtime_fact` | 在事务中检查仍在运行的 session/chain/node 归属，再写入事实 | 单独调用通用仓储已经覆盖了 Host 写入权限检查 |
| 模型事实 reader 与 `prove_model_request` | 可信来源、冻结请求、原始 wire、模型事实阶段和调用坐标的证明 | 旧请求/attempt/retry 模型与现行服务一一等价 |
| `prove_execution_facts_v2` | 已完成 Agent 轮次的执行顺序、精确输入/输出及终态证明 | 每一段不完整或未知结果的事实前缀都应被当作成功轮次接受 |

具体差异包括：旧测试写死 storage 13，当前为 20；旧 seed 的 run/chain 为 prepared，而当前 Host 事实接纳要求 running；旧事实的身份和事件结构也不能靠字段重命名变成当前事实。

因此，“通用仓储通过”“完整轮次 proof 拒绝篡改”“不完整事实能原样重开”是不同层级的检查。迁移需要把有效意图放回实际承担该职责的已有边界，不能恢复旧 API，也不能给通用仓储塞入全部能力语义。

源码依据：`backend/tests/test_execution_facts.py:37`、`backend/src/phase1_agent/storage.py:16`、`backend/src/phase1_agent/runtime_fact_store.py:25`、`backend/src/phase1_agent/graph_runtime_host.py:86`、`backend/src/phase1_agent/model_execution_contracts.py:206`、`backend/src/phase1_agent/execution_facts_v2.py:144`。这些是本轮核对的当前行号。

### A. 不可变存储、幂等竞争与事务回滚：5 项

**原因。** 旧写入口退出，且旧故障点是 `fact.before_write/after_write/before_commit`；当前仓储和 Host 的实际故障点分别包括 `after_runtime_fact_write`、`before_runtime_fact_commit`，不能保留一个永远不会命中的旧注入名称假装测了回滚。

**影响。** 尚未由这五项证明读取副本不会改坏原值、双连接竞争不会重复/覆盖事实、写后或提交前故障不会留下部分记录。这些是验证缺口，不是已经观察到的数据损坏。

**取舍建议。** 保留有效意图，分别落到当前仓储和 Host 事务测试。`test_runtime_fact_store.py:23`、`:39`、`:58` 已有持久化、冲突/跳号和写后回滚测试，可作为对照；但不能直接宣布覆盖了旧测试的副本变更、双 store 竞争及所有故障阶段。只有逐断言证明重复后才合并，故障参数仍须独立保留。

本类详细分析见 [15 号](15-执行事实持久化幂等与事务回滚5项详细分析-2026-10-17.md)：当前已有基础防护和历史测试，不是从零缺失；旧双 store 测试为先后调用，不是真正同时写压力测试；当前写后回滚单测由测试手动 rollback，不能替代真实 Host 自动回滚验收。本轮未改或重新运行这五项测试。

### B. 旧版本初始化与历史原值保留：5 项

**原因。** 这五项分别构造 storage 0–4 的旧库，之后调用退役的 `get_record`。测试还混合了“旧业务记录可经旧接口读取”“升级到版本 13”“创建旧事实表”“不编造事实”“不改写原记录”等不同要求。

**影响。** 对这五种旧输入，尚未由本批证明哪些初始化与原值保留保证仍成立。当前正常业务库已经是新的 store，不能把这五个临时旧库输入的失败解释为默认产品库已经损坏。

**取舍建议。** 保留“不凭空制造执行事实、不破坏原字节”的意图；对照 `test_storage_initialization.py:27` 的当前初始化保留检查，逐版本核对，不能拿当前版本输入代替 0–4。版本 13、旧表必须存在、旧业务读取 API 可用等旧实现要求不能硬恢复；若某子断言确属纯退役要求，先列明依据和剩余有效覆盖，不自行删除这五个迁移身份或新增业务数据迁移功能。

### C. 执行归属与写入隔离：5 项

**原因。** 旧测试修改 run、chain、session、binding、snapshot 五种归属，要求 `SqliteStore.append_execution_fact` 集中拒绝。当前运行归属检查、可信 reader 及 snapshot proof 不在同一个入口。

**影响。** 这五项尚未证明错误归属不能污染另一会话/节点的事实。仅用随机 owner 直接调用通用仓储的测试不能替代这组权限边界。

**取舍建议。** 按实际责任分别迁移 Host 写入归属和可信读取/快照绑定检查，保留每种错误坐标的拒绝及零写入断言。`test_model_request_fact_reader.py:243`、`:297` 有读取来源/归属对照，但读权限通过不等于写入权限已经验证；也不能简单将旧 run 改名为 node_run 就视为等价。

### D. 冻结请求完整性与实际计数：5 项

**原因。** B104–B107 针对旧 snapshot 中的消息、模型参数、工具 schema/name；B129 针对失败事实中的实际 request/attempt 计数。当前原始请求、settings、模型事实及终态证明已经分开。

**影响。** 缺口涉及“保存的请求是否就是实际请求”和“失败计数是否真实”，而非恢复旧次数上限。若只断言成功/失败状态，会漏掉请求缺项、篡改或凭空计算 usage 的问题。

**取舍建议。** 保留四种冻结内容负例及失败计数的正反两侧。对照 `test_context_update_v2.py:199` 的当前请求/模型参数/终态篡改测试和 `test_runtime_execution_facts.py:134` 的失败事实检查，但需证明准确覆盖。冻结的是每个请求实际准备的内容，不倒退成已经否定的全局资源整轮冻结，也不恢复二次限额。

### E. 请求、工具及结果的因果顺序：15 项

**原因。** B108–B116 涉及 request/attempt 引用和序号、调用接受→dispatch→settlement→消息接受；B130–B135 涉及 unknown 后 never_started、批次顺序及下一请求不得越过未接受结果。旧测试把这些都交给旧事实追加 API。

**影响。** 若不保留有效检查，测试将无法证明不存在伪造工具执行、乱序采纳、重复使用结果，或绕过未知批次继续操作等情况。这里是潜在验证风险，不是已确认发生了工具重放。

**取舍建议。** 迁移到当前实际执行事件、模型事实证明和 Agent 完整轮次证明，保留不同伪造字段及前缀长度的独立参数。`test_context_update_v2.py:199`、`test_runtime_execution_facts.py:101`、`test_model_execution_requests.py:344` 有相邻检查，但不存在“一个成功流程覆盖十五项”的结论。尤其旧 attempt/retry 序列不能机械搬到当前模型服务：`prove_model_request` 要求每请求一个原始 attempt；独立 kernel 的 retry 测试也不能冒充现行服务新增了自动重试。发现纯旧机制子断言时先单列，不自行新增或恢复机制。

### F. 不完整/未知事实的持久化与重开：5 项

**原因。** B117 保存 dispatch 未闭合及 unknown；B118–B121 保存四个不同阶段的事实前缀。它们要求“原样保存和读取”，不是“补齐到成功轮次”。

**影响。** 这组尚未证明重开后不会丢失真实在途证据、伪造成功或把未知执行当成未执行。不能用新建干净会话或重放原请求来绕过验证。

**取舍建议。** 保留五种前缀的持久化/重开检查，按当前事件边界重新建立输入；既不能只证明进程内 callback 收到事件，也不能强行套用要求 terminal result 的完整 proof。`test_model_request_fact_reader.py:385` 的不补造 outcome 与 `test_runtime_execution_facts.py:62` 的 pause 事实仅是相邻对照，不是五种重开场景已完成的证据。此类清理不授权新增 crash recovery、重放或重试机制。

### G. 持久数据损坏与伪造拒绝：7 项

**原因。** 七种原输入为未知 kind、未知版本、重复 JSON key、列/载荷 identity 不符、序号缺口、伪造 owner、缺 dispatch。旧测试要求旧仓储在读取和继续追加时统一拒绝；当前通用存储、严格 JSON、可信 reader 和能力 proof 的职责不同。

**影响。** 这组的主要缺口是“持久证据被改坏后，真正消费它的边界是否拒绝”，不能用正常写入时的字段校验代替。尤其删除整组会丢掉落盘后篡改和恢复读取场景。

**取舍建议。** 保留七种独立损坏输入，使用当前真实表和事实结构，分别定位拒绝位置。`test_model_request_fact_reader.py:350`、`:363`、`:385` 以及当前完整 proof 有相关检查，但未证明与七项逐一等价。不要为了维持旧断言而让通用仓储认识所有包的 kind，也不要只改错误码或将旧 schema 伪装成新 schema。若“损坏后继续追加”的当前承诺与旧断言不同，单列准确边界再裁定。

### H. 归属检查复杂度：1 项

**原因。** B136 monkeypatch 的 `_execution_fact_owner` 已不属于当前 `SqliteStore`；它原本要求一次读取或幂等追加只检查一次 owner。

**影响。** 尚未迁移的是避免历史越长、归属重复扫描越多的性能保护，不是已经发现线上性能退化。

**取舍建议。** 保留可解释的性能意图，但不要把旧私有函数名或“恰好调用一次”当作无条件架构要求。先限定当前某一读取/接纳入口的范围，再用可观察的查询/归属检查次数核对复杂度；不能为了减少次数跳过逐事实身份校验。此项可后置于正确性和隔离检查，不据此建设缓存或新优化机制。

## 4. 方案取舍与建议顺序

| 方案 | 收益 | 代价或风险 | 本次建议 |
| --- | --- | --- | --- |
| 只替换 seed/旧方法名 | 可能让部分用例跨过第一个异常 | 仍混有旧记录、表、版本、归属和事件模型；可能把后续语义问题藏住 | 不作为整批解决方案 |
| 48 项整删或强并成一项 | 表面减少失败和维护量 | 丢失持久化、事务、权限、unknown 和防篡改等独立检查 | 不采用 |
| 按有效意图迁往已有责任层 | 保留真实风险保护，不恢复旧生产接口 | 需逐断言证明等价；同一历史身份可能对应多个当前层级 | 优先采用，当前仍只是分类建议 |
| 纯退役子断言另列候选 | 避免把旧实现细节重新固化 | 必须说明准确删除范围和剩余有效检查，不可据此扩大已批准的 20 项移除 | 记录后再确认，不在本次直接移除 |

建议先用 A 的当前最小存储夹具及 C 的真实运行归属，建立能承接后续检查的准确基础；随后推进 D/E/G 的请求、因果和损坏拒绝，F 单独验证不完整事实，不与成功 proof 混合。B 按历史输入保留边界独立处理，H 最后确认性能保护的准确口径。这是测试迁移顺序建议，不是新架构设计或产品实现授权。
