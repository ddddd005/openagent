## 3. 保存格式、四项参数与容量

推荐命名模型配置 `workflow.model-profile` 的 `data_schema_version = 2`。资源 identity 与 `update_sequence` 沿用现行格式，`value` 严格接受：

```json
{
  "name": "已保存命名模型配置",
  "provider": {
    "envelope_version": 1,
    "scope": "workspace",
    "type_id": "workflow.chat-provider",
    "resource_id": "<UUID>"
  },
  "model": {
    "id": "<模型名称>",
    "capacity": {
      "context_window_tokens": 400000,
      "input_limit_tokens": 400000,
      "max_output_tokens": 64000
    }
  },
  "runtime": {
    "thinking": "disabled",
    "context_length_tokens": 300000,
    "compaction_threshold_bps": 8500,
    "output_limit_tokens": 32000
  },
  "enabled": true
}
```

`model.capacity` 是该型号的明确容量资料，集中在模型模块记录，并保留人工填写的现行能力；不是工作流可调参数。型号列表若没有给出容量，就要求配置模块明确填写，不能从型号字符串、旧配置或猜测默认值补全。其 `input_limit_tokens` 是按完全冷输入校验的已声明输入上限；仅当所选 transport 的明确容量资料表明只有总窗口约束时才填写等于窗口，不能假装发现接口已验证此值。上述数字只展示字段，不宣称任一真实模型拥有该容量。

协议由当前供应商记录决定，profile 不再保存第二份 `protocol`。profile 改绑供应商和供应商修改协议都通过下一次准备生效；两者操作之间暂时不支持的状态在请求边界直接报错。输出能力仍以已安装 adapter 及 capability 表为准。

| 四项参数 | 推荐字段 / 单位 / 校验 | 初值与解释 |
| --- | --- | --- |
| 思考强度 | `thinking`，复用原 `disabled` / `{mode:"budget",budget:N,include_summary:true}` / `{mode:"level",level:L,include_summary:true}` | 一个组合控件按型号能力呈现强度或原生思考 budget，沿用实际支持模式；不新增跨协议猜测映射。`include_summary` 作为固定内部策略，不另开放第五项开关。 |
| 上下文长度 | `context_length_tokens`，`null` 或正整数 tokens | 用户确定默认 `300000`，即十进制 `300k tokens`。保留建议的 `null` 可选语义，表示本请求沿用真实窗口；显式值必须不大于真实窗口。默认值或修改型号后的显式值越界即报错，不静默截小。 |
| 压缩阈值 | `compaction_threshold_bps`，整数万分比，`1..10000` | 用户确定默认比例 `0.85`，按本方案存为 `8500`，界面显示 `85%`。允许小数百分比通过整数万分比精确保存。其含义只有开始压缩。 |
| 输出上限 | `output_limit_tokens`，正整数 tokens | 用户确定默认 `32000`，必须同时不超过型号声明输出上限和已安装 transport 的真实协议能力上限，且小于真实窗口；不静默调低默认值。 |

当前 Chat 路线只接受 `thinking = "disabled"`，Gemini 型号只按本地已登记的原生 budget / level 能力验证：[gemini_capabilities.py:33](../../backend/src/phase1_agent/gemini_capabilities.py#L33)。这是源码现状，不是本次新增所有型号的支持承诺。思考 budget 放在这一项内部，并不另设“思考预算”和“思考强度”两份同时生效的参数。

温度不再存在于新 profile 的用户 runtime 格式，新 transport 不发送用户温度。流式仍为现有固定 `false`；本轮不实现 streaming。当前 [model_contract.py:20](../../backend/src/phase1_agent/model_contract.py#L20) / [model_contract.py:79](../../backend/src/phase1_agent/model_contract.py#L79)、[workflowModelResources.ts:110](../../frontend/src/domain/workflowModelResources.ts#L110) 和 [CurrentModelProfilesPanel.vue:163](../../frontend/src/components/CurrentModelProfilesPanel.vue#L163) 写死的输出上限 `8192` 与默认 `32000` 冲突，应在新模型契约实施时一起退出，同步后端参数校验、前端资源校验和表单约束。新校验采用真实型号输出容量及 transport 的真实协议能力限制，不能保留旧人为上限，也不能通过填写虚假容量绕过真实限制。本次只订正实施方案，现行产品限制尚未改动。

摘要输出预留采用固定、版本化实现规则 `S = min(O, 1024)`，其中 `O` 是该次压缩设置的输出上限；普通输出预留 `R = O`。摘要上限是输出限制，不能称为“压缩后上下文目标”。取消用户单独填写 `output_reserve_tokens`、`summary_max_tokens`、`max_cold_input_tokens`；冷输入检查采用真实模型资料的 `input_limit_tokens`，没有缓存折扣。

现行 `agents.compaction-policy@1` 把 `trigger_tokens` 放在工作流，还保留 `target_tokens: null` 占位：[context_compaction_policy.py:13](../../backend/src/phase1_agent/context_compaction_policy.py#L13)。推荐替换为策略 schema / 节点版本 2，只保留 `enabled`、`keep_depth`、`summary_prompt`，继续负责允许压缩的历史范围和摘要正文；触发阈值只归模型模块。删除 `target_tokens` 占位，不新增用户压缩目标。缺少或关闭策略时不自动压缩，真实容量超限直接失败；未超容量可继续普通调用，记录“未启用压缩”决策。

## 4. 引用、授权与版本

### 4.1 稳定公开模型绑定

推荐 `MODEL_BINDING@5` 严格字段：

```json
{
  "schema_version": 5,
  "kind": "workflow.model-binding",
  "binding_id": "<UUID>",
  "reference": {
    "envelope_version": 1,
    "scope": "workspace",
    "type_id": "workflow.model-profile",
    "resource_id": "<UUID>"
  },
  "authorization": {
    "purposes": ["normal", "compaction"]
  }
}
```

`authorization` 是已注册模型源授予的调用用途上界；不声称 tools、thinking、协议或容量在整轮固定。消费者仍必须拥有准确 `models:call` 操作 grant；普通 Chat 只调用 normal，Agent 可调用 normal / compaction。当前型号是否支持工具由该次设置和实际 tools 在准备时验证，权限和实际能力不混写。

公开 binding 不含 provider 地址、Key 引用、lease、参数或容量观察值。宿主保留 `{owner, producer_node_run_id, accepted_output_id, reference, authorization}` 的私有授权记录，继续核对所属运行和精确已接纳源输出。引用本身不是可伪造的访问令牌；任何跨运行、修改 binding 或替换原模型输出的调用直接拒绝。

### 4.2 当前依赖读取授权

现行 `environment.read_resource` 的初始白名单不宜直接扩大。推荐在 `HostServiceEnvironment` 增加受控 `read_resource_bundle(context, root_reference, binding_output_id)`，仅供获授权模型服务使用：

## 5. 单次设置、私有租约与服务操作

推荐三项 JSON host 操作，沿用 `models:resolve` / `models:call` 注册机制。普通 Chat 仍由服务从精确 prompt 解析输入；Agent 传入自己当前已确认的消息和已注册工具投影。

| 操作 | 精确输入 | 输出与用途 |
| --- | --- | --- |
| `models:call / prepare-request` | `{binding_id, request_key, purpose, messages, tools}`，`purpose` 为 normal / compaction | `{request_id, preparation_id, settings, projection, measurement, requires_compaction, hard_capacity_ok, capacity_diagnostic, reserved_model_fact_ids}`；只准备，不执行通信 |
| `models:call / dispatch-request` | `{binding_id, request_key, preparation_id}` | `MODEL_RESULT@3`；消费原准备及私有 lease，不能附带更改参数或消息 |
| `models:call / discard-prepared-request` | `{binding_id, request_key, preparation_id}` | `{request_id, discarded:true}`；仅允许未派发的准备，关闭 adapter / lease 引用并留下未派发状态 |

源操作保留 `models:resolve / bind-native-model` 名称，返回 binding 5。普通 Chat 保留 `models:call / chat` 的一次入口，内部按 normal 准备和派发运行；普通 Chat 没有压缩策略，容量不足直接报错，不自动借用 Agent 压缩。

`request_key` 由调用方单调分配，例如 `agent:<node_run_id>:normal:<ordinal>`、`agent:<node_run_id>:compaction:<ordinal>`，普通 Chat 固定 `chat`。准备若因压缩而放弃，该 ordinal 退出；压缩结束后的普通请求用新键，不能把前后不同消息塞入同一旧键。准备序号不等于外部请求计数，模型请求 / attempt 计数只计实际进入对应事实阶段的调用。

推荐 `settings` 严格字段：

```text
schema_version: 1
kind: workflow.model-request-settings
settings_id: UUID
request_id: UUID
binding_id: UUID
purpose: normal | compaction
configuration: {reference: ResourceIdentity, update_sequence: integer}
provider: {reference: ResourceIdentity, update_sequence: integer}
protocol: chat | gemini
parameters: {model, thinking, stream:false, max_tokens}
capabilities: {protocol, tools, stream, thinking}
capacity: {context_window_tokens, input_limit_tokens, max_output_tokens}
budget: {context_length_tokens, compaction_threshold_bps, trigger_total_tokens,
         output_reserve_tokens, normal_output_limit_tokens, summary_output_limit_tokens,
         calculation_version:1}
```

`parameters.max_tokens` 是本次实际输出上限：normal 为 `O`，compaction 为 `S`。`budget.output_reserve_tokens` 与它相等。`normal_output_limit_tokens` 保留该次设置中的 `O`，用于同次压缩前后普通工作上下文测量。`settings` 不含 `base_url`、`credential_ref`、generation、lease 证据或 Key。地址与受保护租约仅在服务的私有 `_PreparedRequest` 中；诊断只使用非秘密身份和修订。

`projection` 返回 `{projection_version, wire_digest}`。`measurement` 严格返回 `{input_tokens, output_reserve_tokens, total_tokens, context_window_tokens, input_limit_tokens, token_count_kind, estimator_id, estimator_version}`，记录实际投影测量，`total_tokens = input_tokens + output_reserve_tokens`。

`hard_capacity_ok` 是返回顶层的 boolean，不隐含在 measurement 内：它精确等于 `measurement.input_tokens <= measurement.input_limit_tokens && measurement.total_tokens <= measurement.context_window_tokens`。通过时 `capacity_diagnostic = null`；未通过时严格返回 `{code, input_limit_exceeded, context_window_exceeded}`，`code = "model_request_capacity_exceeded"`，后两个 boolean 分别表示上述输入或总量条件失败。normal 可以返回 `hard_capacity_ok:false` 供内核决定先压缩；`dispatch-request` 必须核对服务留存的同一 measurement，拒绝 false 的准备，不能相信调用方复述判断。compaction 准备若为 false 直接报此容量错误，不返回可派发准备。

`requires_compaction` 单独表示 normal 的开始阈值是否达到；compaction 请求固定为 false，没有递归压缩。它不能代替 hard_capacity_ok。`reserved_model_fact_ids` 严格返回 `{request:UUID, attempt:UUID, outcome:UUID}`，仅预分配身份，准备时对应 facts 尚未持久接纳，不能把它们作为 accepted fact refs。仅 `dispatch-request` 返回的 result `fact_refs` 和最终回执核对后的事实才具有接纳证明。完整 wire 内容继续属于请求事实的受控数据；返回值不公开 adapter 或 HTTP header。

### 5.1 新准备的主路径

1. 检查调用 grant、精确 model / prompt artifact 与所属运行。按 `(session_id, chain_run_id, node_run_id, request_key)` 先查询已有记录。
2. 已有键只核对原始调用输入摘要 `intent_digest = digest(binding_id,purpose,messages,tools,input_refs)`；不先读当前配置，不重投影。已完成 / 结果待接纳返回原准备或原结果；未知、已拒绝、已放弃保持其原状态。
3. 仅真正新键读取第 4.2 节的一致当前 bundle，校验型号能力和四项参数，生成不可变 `settings_id`。保留私有 provider address 与当前 `broker.freeze(credential_ref)` 租约；lease 不进入 JSON。
4. 按该 settings 的协议调用匹配 `prepare_request`，计算唯一投影和预算。normal 返回触发结果与硬容量是否通过；尚待内核决定先压缩的准备不能发送，只有实际派发必须通过硬容量。compaction 准备直接要求维护请求容量通过。协议或参数校验失败在通信前直接报错；不得以旧 profile、旧 adapter、旧 Key 或另一协议补救。
5. 将准备登记为私有 `_PreparedRequest`，含 intent digest、settings、完整 prepared wire、精确 artifact refs、私有 lease 和状态。准备返回的设置与后续派发始终相同，不能允许调用方用 `settings_id` 重建另一份设置。

配置保存发生在步骤 3 之后，原准备仍使用自己的设置，下一次新的准备使用最新值。为了避免资源读取和租约捕获之间换代，捕获后对本次读取到的两个资源修订做一次一致核对，且立即 `broker.authorize(lease)`；实际变化即报告 `model_request_configuration_changed_before_prepare`，不循环重读。读取事务只用于取得 bundle，不跨网络通信或 Key 解密持锁。

### 5.2 派发与接纳

派发核对 preparation ownership、原 intent、artifact refs、未派发状态及 settings digest；接纳原请求事实和 attempt intent 后，只创建该次 transport，`max_retries = 0`，参数、地址和 wire 都取原准备。进入 transport 前再次授权同一私有 lease；若 Key 在准备后更新，则这次准备报告未派发，不能偷换新 Key。之后新请求冻结新 Key。正在通信时的配置保存不取消已发送请求，也不改变其结果事实。

`dispatched` 原子状态只允许首次由未派发进入。一个 preparation 只派发一次；请求锁按逻辑键持有，不能用两次并发 `prepare` / `dispatch` 建立两个 attempt。transport 返回后关闭该次 adapter，不保留整轮普通 / 压缩 adapter 缓存；结果接纳只需要已留存 response 和事实，无需 Key 或 adapter。

保留结果接纳失败时的原 outcome，以原 `request_id` / `attempt_id` / `settings_id` 重试数据库接纳；这不是模型重试。provider_error、response_invalid、dispatch_unknown、not_dispatched 按原分类保存，不自动分配新键或继续调用。服务释放先阻止新准备和派发，释放私有 lease / adapter；已持久化未知请求证据不能随 `_requests` 清空而删除。

## 6. 完整预算计算与压缩顺序

设：

```text
C = 当前型号真实 context_window_tokens
K = 当前型号真实 input_limit_tokens（完全冷输入）
M = 当前型号真实 max_output_tokens
B = runtime.context_length_tokens 为 null 时 C，否则该显式值
q = runtime.compaction_threshold_bps
O = runtime.output_limit_tokens
S = min(O, 1024)
T = ceil(B * q / 10000) = (B*q + 9999) // 10000
I = 对本次实际 prepared wire 的一致 input token estimate
R = normal 时 O，compaction 时 S
U = I + R
```

保存 / 准备必须满足 `0 < B <= C`、`1 <= q <= 10000`、`0 < O <= min(M, installed_transport_output_limit)`、`O < C`，并要求 `K > 0`。整数乘法在后端精确计算；前端不使用可能失真的浮点大数乘积作最终依据。

普通请求的压缩触发按 `I + O >= T` 判断，**包含输出预留**；比例分母是 `B`，不是 `C-O`。真实发送门禁另检查 `I <= K` 且 `I + R <= C`。调低 `B` 不修改 `C/K/M`，触发通过不等于容量通过。

推荐先继续使用保守 `utf8_bytes_estimate`，但测量对象必须统一为实际 `prepared["wire_request"]` 的 canonical UTF-8 字节；不声称这是上游精确 tokenizer。capacity 表示模型 tokens，估算值是在同一 token 预算中的保守字节估计，证据必须标注 `token_count_kind`。后端一次生成测量，Agent / 回放只验证并消费它；不再独立按 canonical message JSON 算另一份“同单位”预算。若测试注入 `provided` counter，则须携带其精确 estimator id，普通、压缩和前后投影使用同一 counter；缓存是否命中不影响 `I` 或 `K` 校验。

例：使用与保存示例一致的合成型号容量 `C=400000,K=400000,M=64000`，采用用户确定的默认值 `B=300000,q=8500,O=32000`，则 `T=255000,S=1024`。normal 投影 `I=223000` 时 `U=255000`，恰好达到开始压缩阈值；这仍低于真实窗口，不是容量超限。压缩自己的当前设置若仍为这些值，包含摘要指令的 wire 为 `I_compact=224000`，则 `U_compact=225024`，冷输入和真实窗口均可容纳。摘要应用后按该压缩设置、同一普通输出预留 `O` 测得 `I_after=150000,U_after=182000`。这些前后数值用于证明缩短和容量，没有要求等于某个压缩目标。`S=min(O,1024)` 仍是待审阅的内部摘要输出规则，用户本次订正的 `32000` 是普通模型输出上限，不自动确立摘要上限。

普通 / 压缩各读当前设置的推荐控制顺序：

1. 普通边界先 `prepare-request(normal)`，在其真实 wire 上判断触发。未触发且硬容量通过，直接派发原准备。
2. 已触发且启用策略时，先记录本次触发决策，放弃未派发 normal 准备；不是先生成整轮容量配置。内核按已有 layout / keep_depth / closed tools 规则选择覆盖范围。
3. 构造维护指令后 `prepare-request(compaction)`，重新读取当前设置。使用这一份设置投影压缩请求、校验 `I_compact <= K_compact` 和 `I_compact+S_compact <= C_compact`，再派发一次。
4. 压缩前后的普通工作上下文分别用这一份 **压缩设置** 重新投影测量，预留均采用 `O_compact`。触发决策的旧 measurement 单独保留，不能冒充这份前测量。压缩前后必须同 settings id、同 projector 和 estimator；期间全局保存不会改变这组证明。
5. 新摘要必须满足现存非空纯文本且无工具调用条件；替换后 `I_after < I_before` 且冷输入 / 真实窗口均通过。不要求低于 `T`，否则把触发阈值变成了隐含压缩目标。
6. 重新 `prepare-request(normal)`，重新读取当前配置，以当前消息、当前 wire 和当前硬容量校验后发送。该次已确认压缩后的完全相同消息视图允许继续一次业务调用，不因仍超过低触发值就连续摘要；任何硬容量不足仍失败。这沿用当前 exact after-message-view 去重方向，[runtime.py:698](../../backend/src/phase1_agent/runtime.py#L698)，不是循环压缩、模型重试或换模型。

第 3 步若配置在触发后变化，不撤销已经确认的压缩意图，也不谎称新配置触发了它：压缩事实同时保存 `trigger_settings_id` / trigger measurement 和自己的 `settings_id` / 请求预算。第 6 步若新的真实窗口更小而不能容纳，直接报告当前容量错误，不追加一轮自动压缩来掩盖换代冲突。恢复未完成执行保留当前已确认压缩进度与尚未派发准备的状态，不重新发送旧压缩请求。

现行 90% 固定水位、policy `trigger_tokens` 及“摘要后必须低于 90%”约束应在新契约中退出；只保留上述一个开始阈值和真实容量检查。没有或禁用压缩策略时，只验证真实容量，不把达到早触发值直接判成超限。回合成功后是否还需维护属于 D 的成功收尾接线方案；若保留现存 final 后维护调用，也必须采用同一逐请求接口，不能复用最后一次 normal 的设置。

## 7. 事实与证明如何关联

服务请求 fact schema 2 的 `details` 在原 basis 上增加 `settings`、`preparation_id`、`intent_digest`、`wire_digest`、完整 measurement；`provider_reference` / `configuration_reference` 不再有两份不受核对的重复来源。attempt 保持 `attempt_index:1` / `attempts_consumed:1`，outcome 保留真实分类。prepare 预分配三个 fact ID，供 Agent 建立关联；此时不声称已接纳。dispatch 使用原 ID，在通信前持久接纳 request 和 attempt，随后接纳 outcome。被 discard 的准备没有外部请求事实，只由 decision / discard 状态证明未发送，最终回执也不把其预分配 ID 列为已接纳模型事实。

Agent `model_request` 保存 `{request_id, request_index, messages, tools, settings_id, reserved_model_fact_ids}`；其中 request_id 使用宿主准备分配的真实模型 request id，不再独立分配无法直接关联的内核请求 UUID。这里预分配的 IDs 只建立意图关联；不能声称此时模型请求已持久接纳。正常 / 压缩的参数证明最终都来自 dispatch / 原结果接纳回执对应的已接纳模型请求 fact。Agent 尚未派发的触发决策只保存为 `context_compaction_decided` executor fact，包含原 normal 准备的公开设置与测量以及 discard 身份；不计作已发送模型请求。

压缩 request 保存 `{messages, tools, settings_id, reserved_model_fact_ids}`，capacity 前后增加 `settings_id`、estimator id 和真实硬上限。`context_compaction_started` 同时保存 trigger decision reference、实际压缩设置和覆盖范围；`finished` / `applied` 仍只接纳原请求回应及依序替换。内核更新 packet / receipts 收集 dispatch / 原结果接纳返回的实际 request / attempt / outcome `fact_refs`；更新证明通过宿主的受控 fact reader 核对其 owner、stream、settings id 与 request id，并要求真实 fact IDs 精确等于该请求预分配 IDs。只有这一步完成后才能将它们列为 accepted facts，准备和 discard 的预分配身份不进入 accepted 清单。

这要求补齐服务模型事实和 executor 事实的可信关联读取；不能只相信 Agent 自报 `settings`。现存 `facts:read / read-executor-facts` 只能证明 executor 流，对应上下文证明消费者增加 4.4 节的精确 `model-facts:read / read-model-request-facts` 操作：仅读取同源 Agent 的已接纳 model input 和 receipts 列出的模型 request fact，不能凭任意 fact UUID 读取其他运行。该操作沿用现有 fact 所有权与 stream 存储，不建设新通用事实库。

Agent 输入快照仍固定 prompt、工具定义、输出 schema、模型授权 artifact、压缩 policy 及 layout；从快照移除运行参数和容量。`validate_execution_update`、`ExecutionFactHistory._check_request_basis`、`replay_context_operations` 都按每条请求所引用的模型 fact 验证，不再核对等于 binding 初始参数。历史恢复不查询当前全局配置来重新解释旧事实。

原逻辑键重入分为：已完成返回原 result；成功响应待接纳只提交原 outcome；unknown / provider_error / response_invalid 保留原错误并拒绝自动派发；未派发且准备已被放弃报告原状态。原输入摘要变化均为 `model_request_conflict`。Key、配置、协议或容量保存后这些分支外部通信计数必须不增加。进程不再保有准备时，不从数据库证据重建可派发 lease 或 adapter；要求核实原请求，不能自动恢复通信。
