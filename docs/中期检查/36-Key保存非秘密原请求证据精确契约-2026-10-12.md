## 2. 准确公开请求身份

对于 `provider.credential.save`，公开 `request` 严格包含且只包含：

```json
{
  "identity": {
    "envelope_version": 1,
    "scope": "workspace",
    "type_id": "workflow.chat-provider",
    "resource_id": "<provider UUID>"
  },
  "expected_sequence": 0,
  "credential_ref": "local:<UUID>",
  "expected_generation": 0,
  "idempotency_key": "<original UUID>",
  "provider_seed": {
    "name": "<name>",
    "protocol": "chat",
    "base_url": "https://offline.invalid/v1",
    "enabled": true
  }
}
```

以上是 schema 示意，不是创建的产品记录。`scope`、协议及序号取准确原值，不按示意重写。保存要求完整 `provider_seed`；`provider_seed: null` 是旧只读证据接口允许的另一种输入，不能用于新 save evidence。原 `validate_provider_key_request`、provider schema 3、`local:<UUID>` 和整数/CAS 检查保持。

[request_evidence.py:52](../../backend/src/phase1_agent/request_evidence.py#L52) 对该 operation 显式走六字段校验分支，之后仍执行 JSON 容量、秘密字段禁止、原 idempotency key 一致性及摘要检查。即使 `secret: ""`，多出的第七字段也被拒绝；不把缺失秘密包装成可重发的普通命令。

复用原证据 envelope，字段集合不变：

| 字段 | 精确语义 |
| --- | --- |
| `schema_version / kind` | `1 / workflow.request-evidence` |
| `operation` | `provider.credential.save`；删除使用已有 `credential.delete` |
| `idempotency_key` | 原 UUID；也是原 provider 请求和私有 mutation receipt 的 key，不创建第二个请求 ID |
| `owner_kind / owner_id` | 新前端 channel 为 `provider-credential / <scope>:<resource_id>`；同 provider 的 save/delete 共用一把未决证据锁 |
| `request` | save 是上述准确六字段；delete 是准确 `credential_ref / expected_generation / idempotency_key` |
| `request_digest` | 服务端 `application_command_digest(operation, request)`，即 `SHA256(canonical_bytes({"operation": operation, "parameters": request}))` 的小写 64 位 hex |
| `resolution` | `pending / verified / archived`；`verified` 表示已核实结案，不单独证明保存成功；`archived` 不表示撤销已发生效果 |

`pending_commands` 的 `(operation,idempotency_key)` 主键、同 owner 仅一条 pending 的约束，以及不可换正文/digest/owner 的要求全部复用。不改存储表版本或一般证据 envelope，不新增 secret 标识摘要。此次新增的是明确 operation 分支，并非改变普通 `definition.update` 证据的请求语义。

## 3. Digest 与私有接受证据对照

1. 前端以完整六字段写 `request-evidence.write`，并核实返回/回读的 operation、原 UUID、owner、准确请求正文和 pending 状态。只在准确证据已确认落盘后发送一次包含原内存 Key 的业务命令。
2. 业务 command receipt 的 `request_sha256` 必须等于该证据的 `request_digest`；同时核对 operation、management scope、idempotency key、空 target、service receipt authority、accepted/result 一致性及 provider/Key 精确序号。不能只检查 hex 格式。
3. provider 原记录严格核对 `{"operation":"provider.credential.save","parameters":<六字段>}` 的 canonical 正文和 `content_digest`；其摘要是 `"json-v1:sha256:" + request_digest`，不把整串当公开裸 SHA-256 比较。其固定 `binding_record` 再对应原 global resource receipt。
4. vault 原 receipt 以同一 UUID 查询，并严格核对原 `credential.save`、准确 local reference 和 expected generation；其写入事务同时保存受保护 Key、原 mutation receipt 和结果代次。provider 的 [原请求查询:287](../../backend/src/phase1_agent/graph_provider_host.py#L287) 只核实这些原记录与当前有效状态，不执行 mutate、资源 write 或补绑。
5. 返回 `saved` 还必须确认 vault 当前 generation/state 和当前 provider 保存值与原接纳结果一致；后来的更改分别报告 `partial` 或 `unresolved`，不能以“原来保存过”代替现在已生效。

**公开摘要证明的是完整公开身份，不是秘密字节。** 内存 Key 消失后，页面不能凭公开摘要重新计算、重新猜测或宣称核对了原秘密正文。能够核实的是：准确原 UUID 对应的 provider 请求、可信私有保存事务、原 private receipt 和精确接受结果。私有 HMAC 在原 mutation 路径防止同 UUID 换秘密；只读 receipt 不重算历史秘密 HMAC，也不把当前 Key 当成原秘密补回。

原 private receipt 缺失、私有库不可用、原 provider 请求不存在或正文不匹配时，直接保留 pending 并报告原因。不得以当前 Key、空秘密、新 UUID、provider 当前配置或恢复后的 session 重新绑定原请求。无需且不得公开 `SHA256(secret)`、公开盐加秘密、秘密长度、秘密前后缀、私有 HMAC 或私有 receipt key；低熵输入不能获得公开离线猜测通道。

服务端 canonical JSON 使用自身数值表示。前端消费证据服务对准确原请求计算并返回的 digest，不另造浏览器 JSON canonical 实现，避免 Python/JavaScript 数字拼写差异。此比较仍以六字段正文精确一致作为前提。

## 4. 页面保存及 Unknown

[CurrentProviderPanel.vue:44](../../frontend/src/components/CurrentProviderPanel.vue#L44) 的一个“保存供应商”动作保持：有新 Key 时，整个最新供应商配置及 Key 进入上述一次业务提交；Key 输入空时，走原资源保存并保留已有 local reference，不调用 Key save/delete。

输入 Key 不锁住其他表单字段，不丢失同一表单中的 Key；只有提交或未决请求锁住 mutation。秘密只在内存和一次 Key 保存命令中存在，成功、失败、切换上下文或卸载后按原规则清空。不做浏览器备份、draft、自动重发、环境变量或手工 credential reference 路线。

必要分支由 [providerCredentialEditing.ts:145](../../frontend/src/application/providerCredentialEditing.ts#L145) 和 [evidence channel:35](../../frontend/src/adapters/providerCredentialEvidence.ts#L35) 处理：

- 初始 evidence write 的返回丢失：锁住当前原 UUID；只能读取同 owner 的准确原证据。未确认原证据前不派发 Key。若已写证据但业务从未发送，原 provider 查询明确 `provider_credential_request_missing`，不会补发。
- 业务结果 unknown：只 `request-evidence.read`、原 provider/credential receipt 查询和精确结案，不调用 `saveBound`、private mutate、resource write 或 bind。
- verified/archive resolution 已提交但返回丢失：只有已捕获准确 original 的当前 channel 才查到同 UUID/正文/digest 的 terminal record 并收尾。新的 channel 不把旧 verified/archived 记录重新当 pending。不重复业务提交，也不把 verified 改解释成 archived。
- 第二页面写证据被 `request_evidence_pending` 拒绝：新内存 Key 没有发送；只读实际已落盘的同 owner 原证据，并明确显示另一页面的准确原 UUID。不得把被拒绝的新本地 intent 冒充已提交 unknown，不覆盖实际原正文。
- 已确认的拒绝可按原精确证据结案；`idempotency_conflict`、缺失/变化证据、partial/unresolved 仍保留诊断和锁。页面“归档并解除锁定”仍需明确确认，仅原地归档同一证据，不撤销效果，也不补绑。

## 5. 旧证据门禁与退出边界

[providerCredentialEvidence.ts:11](../../frontend/src/adapters/providerCredentialEvidence.ts#L11) 对旧地址 `management / intent / credential:<scope>:<resource_id>` 只读存在性：

- 不存在或准确 deleted/null tombstone：可使用新证据通道；不写新 draft。
- 存在未删除记录，即便未知 `format_version` 或正文形状：明确“旧原 Key 请求证据尚未接管，禁止新保存”；原记录不解释为恢复输入、不转换、不迁移、不归档、不清空。
- 外层身份/格式异常或读取失败：直接报告并保持保存禁令，不能默认当不存在。
- 已存在 formal pending 可以读取原回执；有旧证据时仍不能新 Key mutation。

这是保留未知原请求的退役前只读门禁，不是可执行旧保存 fallback。现 `LocalDraftRecord` 约定 `deleted` 与 `value === null` 必须一致；不接受 `deleted:false,value:null` 冒充不存在。旧平台、旧 archive、旧未知请求字节及其其他消费者没有在本批删除，也没有数据 reset；不能称整套 drafts 已退出。
