## 1. 已确认的架构职责

这里的层级用于划分职责，不要求每层单独建立服务，也不是所有模块必须逐层调用的线性结构。

| 层级 | 对应职责 |
| --- | --- |
| 1. 应用壳与通信层 | 承载入口、导航和组件，传递命令、查询、状态及回执；各业务组件管理自己的操作。 |
| 2. 工作流与会话管理层 | 管理工作流及所属会话的创建、保存、派生、归档、删除和历史。会话是同一工作流下独立的数据与运行归属。 |
| 3. 定义与能力注册层 | 声明节点类型、版本、配置、端口、连接、执行器、数据权限和交互能力。能力包提供声明，工作流选择并实例化。 |
| 4. 编译与 runtime 层 | 计算普通执行范围、实际依赖和顺序，检查输入、类型与循环，统一筛选节点，调度执行并协调运行状态和输出接纳。 |
| 5. 节点业务层 | 完成读取、装配、处理、执行、写回及交互操作。Agent 执行器与内核属于对应节点的内部实现。 |
| 6. 工作流数据层 | 按工作流、会话和节点归属保存正式节点数据、变量、上下文、消息、产物及执行事实，提供明确的读取、写入、权限和冲突检查。 |
| 7. 成功回合检查点层 | 回合成功结束后保存规定需要保存的结果，提供固定恢复起点；形成后保持不变，不跟踪后续交互或数据变化。 |
| 8. 交互层 | 暴露节点的可调用能力，接收输入与操作，返回数据、状态及回执。 |
| 9. 外部资源与宿主服务层 | 独立管理模型、供应商、私有 Key、全局提示词和世界书等资源，提供模型通信、工具等受控能力，供节点引用和调用。 |

用户明确订正两项：

- 不设独立的“Agent 执行器与内核层”。Agent 节点接受工作流 runtime 调度，其内部完成模型请求、工具循环、压缩及最终回答。其他读取、装配和上下文更新能力仍由各自节点表达，不因 Agent 节点化而吞并这些职责。
- 不设工作流“前端展示与交互层”，只保留交互层。页面排版、渲染和呈现由前端负责；后端节点维护展示所需的数据，提供数据不等于工作流承担页面展示。

Agent 包和前端包通过节点及能力注册接入，不各自占用一个工作流架构层。通用组件、节点类型声明和宿主可以复用，不能把可复用代码解释为跨工作流、跨会话共用业务状态。

## 2. 前端包作为工作流内部项目

每个后端节点绑定自己的前端实例，实例的逻辑归属同时包含所属工作流、节点及会话；不能由页面另行维护第二套业务会话和数据。复制节点生成新节点身份，加载的新实例绑定复制后的节点，不复用原节点的实例、owner、输入或业务状态。相同类型节点、不同工作流和会话可以共享前端代码、组件实现及通信基础设施，业务状态仍各自独立。

32/35 原先集中 `frontend.instance` 的映射只保留为历史提案，不再作为所有节点唯一实例 owner。运行、输入、展示及功能调用可以有明确的目标引用，但引用关系不能吞并目标节点自己的实例归属；迟到结果仍只归原工作流、节点及会话。

前端包节点化的已定能力范围是：

| 能力 | 后续职责 |
| --- | --- |
| 前端注册 | 通过节点注册机制声明本节点前端能力、端口及实例归属；具体入口与节点清单在 D 中收敛，不预设集中节点是所有实例唯一 owner。 |
| 展示上下文 | 后端节点维护常驻的展示上下文，以工作流数据层中的内容为基底，每回合更新；页面读取并呈现。 |
| 工作流运行开关 | 通过节点交互能力请求工作流启动运行，实际运行由 runtime 管理。 |
| 用户输入 | 接收输入并保存为后端节点数据；保存输入与发送、启动运行是不同动作。 |
| 重 roll 与分叉 | 通过节点调用既定历史和运行操作，沿用成功检查点、已有输入及同工作流内独立会话规则。 |
| 功能映射 | 将工作流对应功能声明为可供前端调用的节点能力，明确目标、输入和返回结果。 |

本页不指定每项能力必须新建一个节点，也不指定服务进程数量、端口字段、追加次数或事务格式；这些由实际节点盘点和复用方案给出。页面服务端口与图数据端口在具体方案中分别表达。初期固定/可调按钮只在单条提示词条目节点内部通过注册机制提供，不推广到提示词组或任意节点。

前端关闭、刷新、重新打开及会话切换通过所属后端节点取得正式状态。页面连接的生命周期和工作流运行的生命周期分别由其责任方处理；运行状态及真实回执由后端返回，页面不自行推断业务完成。

## 3. 页面临时数据与正式节点数据

用户明确：前端页面不持有正式业务数据，所有相关正式数据储存在后端工作流的节点中。节点是逻辑归属，实际持久化仍由工作流数据层负责，不要求节点各自建立数据库。

例如，用户在页面输入一段话但未发送：

1. 页面接收输入，通信前的内容只在临时内存中。
2. 按用户指定的 200ms 自动通信，将当前内容传给所属后端节点。
3. 后端实际接纳、写入后，这段话成为正式节点数据，即使尚未发送也已保存。
4. 尚未进入后端的部分，在程序崩溃或页面刷新时可能丢失；这是正常机制，不增加浏览器持久副本、独立草稿或失败输入恢复路线。

200ms 说明自动通信的节奏，不保证每次网络和写入都能在 200ms 内完成；是否已保存以实际后端接纳与回执为准。提交顺序及发送取值在具体接口中保证准确，不以定时器触发冒充保存成功。

这里只维护一套正式数据。已经接纳的未发送输入是输入节点自身的数据，不是另一套需要“应用后再保存”的编辑草稿。此规则不把所有全局资源表单的提交方式统一改为 200ms；全局资源与私有 Key 继续沿用各自已定保存规则。

## 4. 数据层内容显式进入运行时

所有需要与工作流数据层交互的上下文，包括 Agent 内核上下文和展示上下文，都必须通过显式引用、读取或导入，把保存的内容变成运行时数据，之后才能消费或编辑。

```text
工作流数据层中的正式内容
  -> 节点显式引用、读取或导入
  -> 运行时值或上下文
  -> 节点消费、编辑或计算
  -> 明确的写回操作
  -> 工作流数据层中的正式结果
```

变量沿用同一逻辑：先取得数据层中当时的变量值，这个值才进入工作流被消费。之后变量存储发生变化，不自动追改已经取得的运行时值；再次读取才取得当时的新值。

Agent 上下文与展示上下文各由所属后端节点维护，不要求内容相同。运行时内容与存储内容是有明确来源和写回关系的不同阶段，不是两套各自独立生效的正式数据。页面临时输入也不能未经后端接纳就被当成已保存节点状态。

这里的“导入”是把所属数据层内容引入当前运行，不等于此前暂缓的上下文 JSON 导入导出产品功能，不恢复跨工作流隐式继承或旧执行续跑。

## 5. 工作节点与非工作节点

用户确认统一规范，将节点分为工作节点和非工作节点，按黑名单语义由 runtime 集中过滤普通执行范围。类别属于节点注册声明，具体字段和版本随 D 契约给出，不在节点实现中重复判断。

- 工作节点按实际连接、输入及依赖进入普通图执行；变量赋值等无输出写入节点仍沿用 28 的规则。
- 非工作节点接受显式交互调用，runtime 在普通图执行中忽略它们；前端注册、运行开关、重 roll、分叉等能力按这一职责分类。
- 普通执行排除不等于删除节点或禁止用户调用。交互调用复用既有宿主、节点执行和数据能力，不另建一套调度引擎。
- 非工作节点过滤与无上下游孤立节点排除是两条 runtime 规则；不能把非工作节点的显式调用重新依赖普通图连线，也不能由节点自行计算激活。

具体节点分类、交互接口与连接约束在实际清单中落实；保持真实数据依赖、权限、写入结果和原请求事实。

## 6. 成功检查点只提供固定出发点

用户明确撤回把交互状态与检查点混在一起规划的解释。成功检查点类似存档，其唯一职责是保存成功回合结束时规定需要保存的结果，使之后无论如何操作，都能回到这个固定出发点。39进一步确定检查点是历史回溯唯一权威：同工作流历史新会话拷贝整份历史检查点并建立自己的当前状态，不依赖源会话 current/Head、旧产物来源链、跨会话 history membership 或逐层 executor/M2 事实证明。

保存范围只有两类：节点明确注册、合规且允许保存的业务内容；数据层中的上下文、变量及其他节点合规注册存储内容。不另建 once 台账、通用计数平台或历史核验证据包。once 由提示词装配根据当前上下文实时检测，压缩后的检测语义和最小上下文信息在具体契约中收敛。

| 内容 | 责任 |
| --- | --- |
| 当前输入、200ms 自动通信、未发送内容及节点当前状态 | 所属节点、交互接口和工作流数据层负责。 |
| 工作流未启动或启动后的数据变化、运行进度 | 节点、数据层和 runtime 负责；不持续写入既有成功检查点。 |
| 成功回合规定需要保存的结果 | 在助手消息闭合且工作流本次运行成功结束时形成检查点，形成后不因后续操作改变。 |
| 恢复固定起点 | 检查点恢复规定状态，不自动重放模型或工具请求，不改写原执行事实。 |

检查点不负责任何交互，不负责跟踪或保存之后的未发送输入、运行前编辑和执行中变化。当前节点数据仍可正常持久化；暂停、失败和继续所需进度另行维护，不冒充成功检查点。

初始基线及 full/diff 存储方向保持。后续成功回合形成新的检查点，已有检查点保持不变。助手消息及其后面一条用户消息关联同一检查点的规则保持；关联后续输入不等于把该输入写入先前成功状态快照。同流会话使用相同节点结构和身份，不做节点映射、替换或跨版本迁移；恢复保留工作流当前可调配置，正常数据层 CAS 不随业务值回退。未注册保存的输入、控制数据如何处理只按最小实际需要重新列明，不直接安装35全面 reset 方案。

源码内部用于暂停继续的 `KernelCheckpoint` 是 Agent 执行现场，不等同于这里的成功回合存档。已有同进程暂停继续能力及纯状态辅助函数不能被表述为完整生产存档恢复已完成。

## 7. 后续交付和验收

本页归既有配置/状态基础与 D/E 范围，不增加新批次或并列计划。当前工作统一按40推进；保留早期源码调查和实际实施记录。

- 工作/非工作节点的注册声明与 runtime 统一筛选，显式交互调用和普通执行的边界。

- 单条提示词节点内部按钮及正式配置提交：有未归档会话的固定修改由后端判需派生，前端询问，同意后才写入新流；拒绝不写、不造新流，原流与会话不改，新流不继承历史。

核心验收目标：

- Agent 内核作为节点内部实现，图调度仍统一由 runtime 负责。
- 前端页面无独立正式数据；输入写入后可重读，未进入后端的部分丢失不启动额外恢复。
- 每个节点使用自己的前端实例和后端节点数据，复制节点绑定新实例；不因共享代码、切换会话或迟到回执而串用 owner、输入或上下文。
- 上下文和变量显式进入运行时后消费；节点写回及展示上下文每回合更新可重读。
- 非工作节点不进入普通图执行，仍可显式调用；孤立排除及类别筛选不重复写到节点中。
- 成功检查点形成后不随交互、运行前编辑或执行中变化改动，规定内容完整恢复，同流新会话完整复制历史检查点；once 依据恢复后的当前上下文检测，不另建台账。
- 页面展示由前端负责，工作流只提供交互能力、数据、状态及回执。
