## 3. 严格引用

所有下述 object 都拒绝未列字段，整数不接受 bool，UUID 使用现 UUID4 canonical 格式；正序号为 `1..2^53-1`。一个装配 envelope 与一条读取事实各受现 4,000,000-byte 上限约束，不新增无限读取通道。

`PROMPT_CONFIGURATION_REF@1` 顶层准确字段：

```text
schema_version: 1
kind: "workflow.prompt-configuration-ref"
workflow_definition_id: UUID
fixed_definition_revision: positive integer
node_binding_id: UUID
component_id: "prompts.item" | "prompts.group" | "prompts.global-resolve"
component_version: "3"
source: one of the exact variants below
```

节点配置 variant：

```json
{"kind":"node-configuration","business_profile":"prompt-members@2"}
```

全局资源 variant：

```text
kind: "global-resource"
reference: exact ResourceIdentity
data_schema_version: 2
input_ref: {edge_id: UUID, output_id: UUID, order: safe nonnegative integer}
```

`source.kind=node-configuration` 只允许 item/group 3；`global-resource` 只允许 global-resolve 3。`node_binding_id/component/version` 必须等于真实引用产物 producer 的冻结声明，而不是 caller 任选的读取目标。节点 variant 不携带正文、成员清单、已消费 lifecycle 或旧 edit sequence，业务范围固定为该节点的全部正式提示词成员。

global-resolve 3 的 `input_ref` 必须等于它唯一实际 `input: GLOBAL_RESOURCE_REF@1` 绑定，`reference` 必须等于该原产物中的身份，type_id 限 `workflow.prompt-resource`。其输出的注册 `references/artifact_bindings` 保留该准确原 input artifact；读取资源的身份不是字符串 UUID 扫描结果。

该类型 `references` 只声明全局 variant 中的原 input artifact 和准确资源 retention 身份；节点 variant 不授任意 node read。`public_artifact_references` 不新增导出。mapper 保持原 workflow/revision/node/artifact/resource 出处，不因 from-history 改归目标会话。

现 [global_resources.py:34](../../backend/src/phase1_agent/global_resources.py#L34) 的稳定 GLOBAL_RESOURCE_REF、[prompt_lifecycle_nodes.py:28](../../backend/src/phase1_agent/prompt_lifecycle_nodes.py#L28) 的严格成员 schema 与 [workflow_configuration.py:15](../../backend/src/phase1_agent/workflow_configuration.py#L15) 的可调白名单继续复用；引用类型不是第二份配置平台。

## 4. 准确读取服务及事实

### 4.1 声明和授权

准确 service ref 为 `{service_id:"workflow.configuration",exact_version:"1.0.0"}`，operation 为 **`configuration:read / read-prompt-sources`**。

request 只有 `{"port":"prompt_refs"}`；response 是下节完整 `prompt_source_read@1`。不接受 workflow/node/resource UUID、正文、caller 的引用列表或 fact IDs。无 prompt_refs 时装配节点不调用服务，产物 `read_fact_id=null`。

装配节点声明 `configuration:read`、`resources:read` 和该准确 service requirement。服务的全局读仍要求 `resources:read` 声明及真实 accepted prompt_refs 的精确资源输入授权；不能因为服务能读配置而授予整个资源库。新增类型的资源输入解析必须注册 `PROMPT_CONFIGURATION_REF@1` 的准确 global variant，不能把现在仅识别 GLOBAL_RESOURCE_REF 的处理写成已经适配。

可信宿主在一次短事务中：

1. 核对真实 session active chain、running assembler、原 chain workflow/fixed revision、准确冻结包/service grant；保持 [graph_runtime_host.py:59](../../backend/src/phase1_agent/graph_runtime_host.py#L59) 的 live owner 检查。
2. 读取持久化 assembler `input_refs.prompt_refs`；逐个核对真实成功 producer、准确 output_refs、端口/type/version、同 chain 和图边。读取请求没有权力补入其他引用。
3. 校验引用与其 producer 冻结 node/input 完全一致。节点源只读取该 workflow 当前 configuration 正式表，固定投影须仍等于原固定定义，policy 和可信调整声明保持；当前业务字段按现 [workflow_configuration.py:203](../../backend/src/phase1_agent/workflow_configuration.py#L203) 的组合规则求得，不复用更早 ref producer 的正文。
4. 在同一 SQLite snapshot 读取全部本地当前业务与准确全局 prompt records，统一保存 workflow `edit_sequence` 及各资源真实 `update_sequence`。缺失、禁用、schema 不符直接失败；不返回部分材料、不读浏览器内存。
5. 以真实 assembler owner 接纳完整事实，核对数据库坐标与 JSON，并取得原 receipt；事务提交成功后才返回它。这个可信宿主入口复用原事实表/接纳语义，不通过节点调用通用 accept_fact 任意构造正文，也不给 package mutable store。

这项读取只冻结本次装配所得正文，不冻结整轮配置。装配结束后的新配置继续生效于下一次装配/新请求；已经装配的产物和原请求事实不追改。

### 4.2 `prompt_source_read@1`

数据库 stream 精确为 **`service:workflow.configuration@1.0.0:prompt-sources`**。每 assembler invocation 只接纳一条，sequence 固定 1；事实 ID 由可信宿主首次分配 UUID。再次观察只读取该原事实，不产生第二次读/新正文；不同读取意图不能借同 ID 覆盖。未知接纳只查准确原事实，不重新求今日配置。

```text
schema_version: 1
kind: "workflow.prompt-source-read"
fact_id: UUID
sequence: 1
owner: {workflow_session_id, chain_run_id, node_binding_id, node_run_id}
workflow_definition_id: UUID
fixed_definition_revision: positive integer
workflow_edit_sequence: positive integer
sources: bounded array of {
  binding: {edge_id, output_id, order}
  reference: exact PROMPT_CONFIGURATION_REF@1 accepted payload
  snapshot: one exact variant below
}
```

`sources` 必须与真实 prompt_refs 全部绑定一一对应，按现 `_artifact_refs` 的 `(order,edge UUID)` 排序，不能漏项、重复边、调换引用或多项指向自选 facts。上限沿用 4096 个绑定、至多 128 个不同全局资源身份及装配材料/资源字节约束；它不是绕开原 1024 items/4096 origins 的合并通道。

snapshot variants：

```text
node:
  kind: "node-configuration"
  configuration_policy: exact frozen {schema_version:1,prompt_mode:"fixed"|"adjustable"}
  config: exact current item@3 or group@3 config
global:
  kind: "global-resource"
  record: {
    envelope_version:1, scope, type_id:"workflow.prompt-resource", resource_id,
    data_schema_version:2, update_sequence, value:{enabled:true,members:[...]}
  }
```

item config 为既有 lifecycle member 全字段 `id/text/presentation/metadata/lifecycle/compaction`；group config 为 `{"members":[这些成员]}`。字段格式、member UUID 唯一、presentation 和 lifecycle/compaction 关系沿用严格 schema，不增任意业务 key。global record 使用 [global_resources.py:111](../../backend/src/phase1_agent/global_resources.py#L111) 的准确 envelope，identity 必须等于引用，value 使用现 prompt resource 2。

`config` 是实际当次正式读取的原材料依据，不是再次为整轮冻结配置。事实中无需另存可变 current ID、digest-only body 或产物副本。

node_run 仍 schema 5；其既有 reads list 只增加一种 strict pointer：

```json
{"schema_version":1,"kind":"prompt_source_read","fact_id":"<原读取事实 UUID>"}
```

指针由可信读取成功后提供，只用于关联，不建立授权。证明必须再核对真正持久化的事实 SQL 坐标、准确 stream、sequence、原 owner 及完整 body；节点手工 append 相同形状不构成已接纳读取。完整正文不重复放 node_run.reads，避免两份事实互为权威。

## 5. 新装配 envelope 与重建

### 5.1 两种产物共用的来源清单

新顶层 `assembly_sources` 的严格 schema 1 为：

```text
schema_version: 1
material_refs: array of exact {edge_id,output_id,order}
raw_prompt_refs: array of exact {edge_id,output_id,order}
configuration_refs: array of exact {edge_id,output_id,order}
read_fact_id: UUID | null
```

三组分别对应 producer 的真实静态材料口、raw_prompt 口、prompt_refs 口。每组按 `_artifact_refs` 排序；跨组不得重复 edge；`read_fact_id != null` 当且仅当 configuration_refs 非空。全组并集必须等于原 `source_output_refs`，不能留下未证明的 extra source。当前输入保留自己的原严格绑定，不混进材料来源清单。

- PROMPT@3 顶层精确字段为 `schema_version/kind/stage/items/assembly/assembly_sources`；version=3、kind=`workflow.prompt`、stage 只允许 assembled。assembly 精确字段为 `schema_version/kind/messages/manifest/current_input/placement_profile`，version=3、kind=`workflow.prompt-assembly`、placement_profile=`logical-floors-v1`，manifest 仍为 ordered_item_ids/source_output_refs/current_input_refs。
- PROMPT@7 顶层精确字段为 `schema_version/kind/stage/items/context/context_ref/current_input/current_input_ref/source_output_refs/messages/provenance/layout/once_pending_item_ids/placement_profile/assembly_sources`；version=7、kind=`workflow.prompt`、stage=assembled，要求 `placement_profile="logical-floors-v1"`。原值按 [prompt_depth.py:6](../../backend/src/phase1_agent/prompt_depth.py#L6) 的常量核对。原生没有 raw_prompt 口，raw_prompt_refs 必须为空。

两个 type 的 `references` 输出来源并集的 artifact refs；7 另含原 context_ref/current_input_ref，3 另含 current_input_refs。`artifact_bindings` 返回完整材料来源并集和相应当前输入绑定，现图边核验继续执行。read_fact_id 不是新通用 `fact` reference scope，只有下述官方 prompt proof 专用分支可推得准确读取事实。

两种新型不注册 content_transformer。旧转换器不能把它们当普通 PROMPT2，以修改后的 items 搭配未变来源 manifest。需要变量替换时，在静态材料/文本或既有 PROMPT2 阶段显式进行，随后重新正式装配；不增加“装配后丢掉证明”的转换路线。

### 5.2 唯一重建规则

输入 body、读取事实和固定声明到 items 的映射固定如下：

1. 静态 materials 使用真实 accepted `PROMPT_MATERIALS@1` 原 body，不重新解释节点今天的配置；按 `merge_lifecycle_prompt_materials` 校验完整来源身份。
2. node snapshot：item 作为一个 member、group 按正式 members。复用 `make_lifecycle_prompt_item(source node_binding_id, member.id, ...)`，source 精确为原 `prompt_item/prompt_group` 的 node_id/member_id/origin_item_id。
3. global snapshot：用引用产物的真实 global-resolve node_binding_id 和原 resource member.id 产生身份；source 为原 global_prompt 的准确 reference/member_id/origin_item_id。不是 assembler node ID，也不加 edit/resource sequence 到身份。
4. 所有生命周期材料合并仍按现业务字段去重、完整 origins 合并与 placement/depth/order/稳定 UUID 排序，见 [prompt_lifecycle.py:83](../../backend/src/phase1_agent/prompt_lifecycle.py#L83)。同 origin 不同业务或来源仍报冲突，不能最后一项覆盖。
5. 原生 7 直接使用这组 lifecycle items，复用现 context/current_input、logical floors、messages/provenance/layout/once_pending 的纯投影，见 [context_prompt_v6.py:69](../../backend/src/phase1_agent/context_prompt_v6.py#L69)。
6. 普通 3 保持单回答语义：将合并 lifecycle items 去掉 `lifecycle/compaction/origin_item_ids`，保留身份/source；与 raw_prompt 2 材料合并，再按原 ordinary assembly 规则重建 messages/manifest。普通 Chat 不生成 persistent once 台账，原实际 lifecycle 留在不可变读事实。

raw_prompt 2 只接现有效的 `stage=materials,assembly=null` 静态材料，不接已冻结 assembled 2；这沿用 [prompt_contract.py:74](../../backend/src/phase1_agent/prompt_contract.py#L74) 的真实聚合条件，不是新旧产品恢复 fallback。来自 tools.text/json-to-prompt、变量替换的静态 2 产物可进入该口。材料/body 格式不符或 stable ID 冲突直接失败。

最终要求重建所得全部 items 和装配投影逐字节 canonical 相等，不以独立 digest、自报 item IDs 或 messages 看起来相同代替证明。

### 5.3 once 身份

node_binding_id + member_id 继续决定 item 身份，见 [content_contracts.py:50](../../backend/src/phase1_agent/content_contracts.py#L50)。同身份可调正文/位置/配置序号变化不制造新 once 身份；global 同一 resolver/member 身份亦不随 update_sequence 改变。

已消费 once 不重新注入；已注入正文保留在原 context，装配时的 current read 可以记录新值但不追改它。删除再以相同 member UUID 加回仍是同身份；明确创建新 member UUID 才是新身份。restore 根据规定结果状态恢复 once 台账，不读今日配置改造原存档，也不因新会话重写原 origin。

## 6. 接纳与证明顺序

### 6.1 候选接纳前

assembler 取得正式 accepted 输入后，可信宿主的读取服务才可接纳 source-read fact。该权限来自真实 live invocation/输入与准确 service grant，**不依赖尚未发布的 prompt output**。

assembler 用原 fact body 和静态输入建立候选；宿主接纳该候选前执行严格 schema、图 artifact bindings、端口分组、官方 assembler identity、read pointer/stream/body 和完整 items 投影校验。可以将本次候选 value、真实 input_refs/inputs、trusted persisted read 传给专用纯 verifier；不能从数据库假装 resolve 一个尚未 accepted output。

随后才将 node_run succeeded、reads 指针、原 prompt workflow_output 和准确 output_refs 一起接纳。若后续产物接纳失败，已接纳的 source-read 仍是原运行事实，不删/改它；准确 retained candidate/retry_archive 继续接纳原候选，不再次读最新配置生成另一个正文。

### 6.2 Accepted consumer

建议内部准确 helper：

```text
prove_prompt_assembly(prompt_ref, authority)
  -> validated exact PROMPT@3 or @7
```

authority 从真实 accepted input 或 [30](30-历史事实闭包读取授权具体方案-2026-10-12.md) 的正式历史根建立。helper 不公开给 caller 任选 fact_id/source body；其中：

1. 解析原 prompt output、成功 producer、原 chain workflow/revision、准确 package/node/port/type；3 只接受 `prompts.assembly@3`，7 只接受 `context.assembly@5`。
2. 对比真实 producer input_refs 的完整端口分组与 assembly_sources，读取已授权相应原 artifacts。来源 refs 必须来自已注册清单，producer input_refs 本身不扩大通用闭包。
3. read_fact_id 非空时，核对原 node_run.reads 唯一 pointer，按原 `(session_id,chain_id,node_run_id,service stream,fact_id)` 查唯一 sequence=1 的原事实；SQL/JSON/真实 producer/全部 reference bindings 必须完全一致。
4. 校验读取 snapshot 的准确业务 schema 与原固定投影；历史仅用原冻结声明与原 read body，不调用 current configuration/global get。来源工厂、材料合并和投影按第 5 节重建，相等才成功。
5. 核对 7 的 context/current_input 与准确原输入；current_input 来源仍本轮 work reader 的 TEXT artifact，不把原 submitted input 冒充图 producer。再进入既有 executor/M2 全证明与真实 merge/CAS。

Agent/Lorebook 的节点入口复用 `artifacts:read`，新增准确内建 operation **`prove-prompt-input`**，request 为 `{"port":"prompt"}` 或 Lorebook 的 `{"port":"input"}`，response 仅 `{"validated":true}`；实际允许 port 由各组件声明/真实绑定决定，不返回原 fact body或任意闭包。没有该 port、不是正式运行 invocation、input 不相等直接拒绝。

models.chat 5 的 registered models 2.0.0 服务在读取其真实 prompt input 后内部调用同一 helper，再允许 prepare/dispatch；不增加 caller 自报 proof bool。context 4.0.0 read/validate/write 的 trusted proof callback 和 schema 2 executor/M2 proof 先调用该 helper，再重演/update/CAS。纯 PROMPT schema verifier仅证明形状及自身投影，不独自代表完整 accepted source proof。

### 6.3 历史与保留

30 的 HistoryArtifactAuthority 增加准确 prompt 专用分支；`resolve_detail` 保留原 config/input_refs，并提供原 node_run 的 reads 指针供该分支核对。类型 refs 先使 prompt configuration-ref producer artifacts 可达；该专用分支再推导准确 source-read fact，不能让任意 `fact_id` UUID成为读根。

准确受控 helper 为 `read_prompt_source_fact(connection, authority, prompt_ref)`；输入只能是已在内部正式根闭包中的准确 prompt_ref。它先核对 official assembler、完整 sources manifest、原 input_refs 和唯一 reads pointer，再从这些记录推得单一原事实坐标；无 configuration_refs 时返回 null。它不接受 caller 的 fact IDs/producer/stream，返回结果仅供本次内部 prompt proof，不新增 HTTP raw-fact 读取端点。30 已有 `read_context_update_facts` 的 executor/M2 分支保持原职责，在取得 frozen_prompt_ref 后先调用这个新受控分支完成原 prompt proof，不将引用中的 current/global 身份转成历史 current-read 权限。

原 prompt 输出、引用 producer、原读取事实、原静态 inputs、准确冻结定义及必要声明一起保留，按原 chain/workflow owner 和目标 session membership 核对。源 session 删除不能先删 source-read stream；fork/from-history 不复制或重拥有原事实，也不依赖源 current/Head。

历史读取继续单只读 SQLite snapshot、`mode=ro/query_only`，直接读取现表，不实例化带 DDL 的 RuntimeFactStore。内部读取证据/原 prompt/资源 body 不自动公开，`public_artifact_references` 不扩大，见 [host_sdk.py:469](../../backend/src/phase1_agent/host_sdk.py#L469)。历史 proof 前后 current-resource get、config read、fact accept、lease、prepare/dispatch/tool 调用计数均为零。
