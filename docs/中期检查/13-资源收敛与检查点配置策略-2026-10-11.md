## 1. 全局提示词与 Lorebook 管理收敛

### 当前读取与材料转换

两者通过已声明的资源身份授权，读取当前已保存的全局资源正文。当前存储读取只表示内容正文实时，不表示模型配置、已接纳节点输出或整个运行帧同时实时变化。

提示词解析直接保留条目的正文、角色、位置、深度、顺序、启用状态、生命周期及压缩策略，转换成 `PROMPT_MATERIALS@1`。Lorebook 则读取条目后，结合扫描用提示词和明确指定的变量，按关键词、概率、扫描深度及递归规则计算触发结果，再生成相同格式的材料。材料随后交给提示词装配和模型调用链路。

源码依据：

- [资源读取](../../backend/src/phase1_agent/graph_resource_host.py#L100)。
- [提示词解析](../../backend/src/phase1_agent/prompt_lifecycle_nodes.py#L154)。
- [Lorebook 读取和触发入口](../../backend/src/phase1_agent/tavern/lorebook_resources.py#L68)。

两者尚未完全统一的现状：

| 范围 | 当前差异 | 收敛方向 |
| --- | --- | --- |
| 前端控制器 | 已共享草稿和请求提交工具，但列表刷新、序号递增、保存请求构造分别实现 | 独立草稿工具退出；复用实际重复的管理流程，保留各资源字段校验与业务处理，不新建包办所有业务的平台 |

## 2. 检查点统一保存成功回合结果

### 当前机制

当前节点配置在工作流定义中，节点会话私有数据通过 `node_session` 保存，外层含 `data_version`，正文为带组件归属及格式版本的 `private_data.payload`。节点代码通过组件 ID/版本注册，与配置及运行数据分离；各节点正文结构由各自契约声明，并不是所有节点共用同一组业务字段。

当前 `_commit` 将当时的节点私有数据直接复制到 `state_snapshot.node_states`，并记录定义修订、变量数据修订和历史引用；会话对象状态另通过检查点 manifest 关联。因而当前检查点已经是“数据正文加历史引用”的组合，不能把节点 `data_version` 误解为恢复数据正文的唯一来源。

当前候选恢复还读取历史定义、变量和对象，再恢复会话状态并改绑历史定义；它与本页新的固定定义和可调提示词规则尚不相同。

依据：[节点私有数据保存](../../backend/src/phase1_agent/graph_service.py#L302)、[检查点提交](../../backend/src/phase1_agent/graph_service.py#L336)、[记录格式](../../backend/src/phase1_agent/graph_records.py#L23)、[候选恢复](../../backend/src/phase1_agent/graph_candidates.py#L160)。

### 已确定方向

节点负责当前数据处理，数据层负责正式持久化；工作流检查点机制统一负责成功回合规定结果的比较、保存和恢复。不再要求节点各自维护数据修订号或另一套历史版本链，检查点也不承担当前交互和未完成进度管理。

检查点是历史回溯的唯一权威，在逻辑上持有成功结束时规定的完整、可恢复结果。保存范围仅为节点明确注册且允许保存的内容，以及数据层中的上下文、变量和其他节点合规注册存储内容；不另设 once 台账、通用计数器分区或历史核验证据包。计数、聊天结果等只有本身属于上述注册内容才按声明保存。固定配置由工作流保存，可调提示词配置按第 4 节处理；“完整”不表示复制全部固定配置、全局资源或所有运行记录，也不表示持续跟踪当前交互数据。

恢复不依赖源会话 current/Head、原节点产物来源链、跨会话 history membership 或逐层 executor/M2 事实重建。检查点之外的不规范历史数据不补救、不兼容。正常运行的身份、格式、权限、真实写入冲突和结果接纳仍保留，不因此改写已发送请求或自动重放未知请求。

成功回合检查点的形成条件是：回合成功结束、助手消息闭合且工作流结束本次运行。该助手消息及其后面一条用户消息归属于该检查点；后续用户消息关联与成功结束状态快照分别表达，不能声称快照提前包含尚未提交的消息。执行中进度、失败和中止不形成成功回合检查点，但必要输入、进度和请求事实仍保存。初始基线、恢复、重来和候选操作的解释见 16 第 2 节。

用户进一步确认：用户消息本身只提供输入，不产生独立的计算后运行状态；回到历史助手消息或紧随它的用户消息都使用同一个检查点。例如 `assistant1` 和后续 `user1` 均恢复 C1，只有处理输入后生成 `assistant2` 并成功结束运行才形成 C2。这是已确认规则，不再标为待确认推导。

检查点类似存档：之后无论怎样交互、编辑或运行，都可以恢复规定的固定出发点。既有检查点不因未发送输入、工作流未启动时的修改或启动后的变化而更新；后续成功回合另建检查点。输入、运行进度和请求事实正常保存，但不由成功检查点管理，后续消息关联也不改写原快照。

物理保存采用程序判断的 diff：

1. 保留初始完整状态基线方向；具体初始检查点形成时点仍需随最小保存声明收敛，不将此前创建事务建议直接当作最终接口。
2. 后续检查点比较前一检查点与当前状态，只保存变化的数据和明确的删除项，并关联对应回合及父检查点。
3. 未变化内容复用既有数据，不重复保存同一正文；空变化仍可有回合或检查点关联记录。
4. 恢复时由基线和目标分支上的差异还原完整状态。分叉从明确父检查点开始，不把另一个分支的变化串入当前分支。

diff 是存储方式，不能变成仅保存零散消息、却无法恢复变量或对象的历史日志。节点条目 ID、格式版本、工作流身份、检查点身份与父子关系仍有用途；取消节点数据修订号不等于删除这些身份和格式约束，也不等于取消必要事务边界。

不取消检查点和同工作流内历史候选选择所需恢复。此前讨论过“不保存检查点”以减少实现，但未采用为本轮方向。历史结果查看与状态恢复是不同能力，分叉不承诺重现原模型输出，也不自动重放模型或工具请求。

## 3. 工作流、会话、回合与草稿退出

上层归属沿用工作流核心：

```text
工作流
  固定定义、节点身份和配置策略
  当前已保存的可调提示词配置
  多个独立会话
    各自的当前节点数据、已接纳输入及历史当前位置
    运行进度、节点执行记录、实际配置和请求事实
    回合及候选结果
    成功回合检查点：规定结果的固定恢复起点
```

历史回溯建立新会话时，拷贝整份历史检查点，形成同一工作流下自己的检查点和当前状态，之后与原会话独立变化；不是仅复用源会话的某个历史指针或来源证明链。同工作流节点结构和身份相同，不做节点映射、替换或跨版本迁移。可以记录出处，但不把新会话变成源会话内嵌的子会话或依赖其可变状态。完整复制的物理步骤、必要归属字段和存储表达仍需收敛，本文不指定算法。节点运行状态按会话隔离；同工作流可调配置由工作流共享，全局资源独立于工作流。

### 当前草稿怎样产生（待退出的实现）

提示词表单打开时复制节点配置并读取已有草稿，通常不因首次打开就新建表单草稿。输入变化后，监听器暂存 `{ basis, raw }`，约 200ms 后写入本机后端 `local_editor_drafts`；应用操作把表单副本写入工作流编辑文档，现有实现应用后还会更新依据并保留草稿。保存工作流不自动应用其他未应用表单。

工作台另有 `workbench:v1` 草稿，保存目录、工作流编辑文档和会话选择；没有记录时初始化工作台可能生成这类草稿，不能据提示词表单首次打开的行为推断整个页面不写草稿。

当前提示词表单地址是 `node:<工作流ID>:<节点ID>:prompt-members`，会话字段为 null；但是依据包含 SDK 生命周期，生命周期又含当前会话 ID。因此切换会话可能改变校验依据，却并未真正为每个会话建立独立提示词草稿。

完整现状与代码链见 [04：草稿调查](04-草稿保存与会话归属-2026-10-11.md)。

### 最新决定与退出边界

用户随后明确当前不做草稿机制，保存失败直接报错，并将独立草稿机制退出纳入规划。这一决定覆盖先前关于各会话草稿保留、共享表单按会话保存未提交副本和失败输入恢复的建议；草稿归属、地址和清除时点退出待论证事项。

| 内容 | 归属与后续规则 |
| --- | --- |
| 尚未进入后端的输入及数据编辑 | 页面临时内存，提交到所属节点；丢失不另建草稿或失败恢复 |
| 已通过 200ms 自动通信接纳的未发送输入 | 正式后端输入节点数据，可从节点重读；发送和启动运行另行调用，不是编辑草稿 |
| 工作流节点配置的未提交编辑 | 普通内存编辑，按原地修改或派生规则自动提交；切换会话不改变正式配置归属 |
| 已保存可调提示词 | 工作流共享，对接节点后续装配时求当前值，不自动变成会话私有配置 |
| 全局资源编辑 | 归全局内容模块，不随会话切换而代办保存 |

保存采用当前输入直接提交正式配置的主路径，失败报告原始错误和诊断信息，排查连接、数据库或实际写入问题；不另存草稿、生成冲突副本或建立输入恢复流程。前端表单现状已在 [15：表单检查](15-前端表单编辑与提交链路检查-2026-10-11.md)核对；表单直接编辑节点配置的职责已经明确，失焦、操作完成及复合配置整项提交仍是接口建议，不另开草稿归属讨论。

29 的 200ms 规则属于前端输入节点自身交互，不改变全局资源表单保存方式；后端正式输入的重读不是另一套草稿恢复。上下文与变量从数据层显式读取、引用或导入成为运行时内容，再由节点消费、编辑和写回；此处导入不等于暂缓的 JSON 导入导出能力。

独立草稿的持久化、恢复、依据冲突、已应用草稿同步及全部草稿保存门禁归第 3 步自动提交改造的退出范围。先由各自后端管理接口接管现有目录、定义和名称等数据，未决请求原始证据独立保留用于诊断和核实，依赖清零后删除草稿接口、存储表和专属旧测试。参考说明归档或标明失效，不保留可执行回退路径；具体范围见 09/R07。

## 4. 固定配置与可调提示词

用户确认的方案是由工作流内的节点配置持有固定/可调策略，恢复检查点时保留当前可调配置，不排除整个节点的合规保存内容。初期按钮仅对单条提示词条目开放，按节点注册机制在节点内部提供；不扩大到提示词组、所有节点参数或 Lorebook 触发配置。表单只是这份正式配置的编辑界面。

| 类型 | 有有效会话后 | 恢复检查点时 |
| --- | --- | --- |
| 固定节点配置和结构 | 后端判定需要派生，前端弹窗询问；用户同意后才创建不带原会话/历史的新工作流 | 使用所属工作流的固定定义 |
| 用户选为可调的提示词配置 | 可以编辑、保存，同工作流会话共享 | 不覆盖当前配置；后续尚未装配的内容在装配时求当前已保存值 |
| 节点注册允许保存的业务状态 | 按会话隔离并依注册声明进入检查点，不包括执行现场和未注册控制数据 | 按声明恢复规定业务内容，不能随可调配置一起排除 |
| 既有请求、实际配置与结果 | 保留真实执行依据 | 不改写，不自动重算 |

有效会话沿用未归档、未删除的定义，不以当前是否选中会话或是否完成首回合另设阈值。没有有效会话时允许原地编辑；归档仅留历史供查看，不提供恢复执行。

固定结构包括节点身份、类型、版本、增删、连线、端口、运行目标、对象和资源绑定，以及影响状态格式的设置。它们不能借“提示词可调”绕过派生规则。固定配置由工作流持有一份，不在每个检查点重复备份；已有历史仍须能解释原执行所用定义。

2026-10-12 用户指定通过节点上的按钮切换固定/可调，使用与节点注册相同的机制接入。按钮显示正式配置模式并走同一配置提交入口；不另设表单策略，不扩大到节点结构或运行状态，不追改已有历史。按钮切换本身是否触发固定修改派生确认，39 仍列为未决，不将旧“策略变化一律自动派生”建议作为已定规则。用户拒绝派生时不写入修改、不创建新工作流；当前编辑只留普通内存，不另建持久草稿。

可调提示词对其对接节点在装配时求当前已保存值；同一未完成回合中，后续尚未装配的内容也可采用新值，不要求等下一回合。内容进入装配后便不再受提示词节点控制，单次装配结果、已发送请求和已确认输出保留原事实。保存提示词不自动重跑装配，不使用草稿，也不回退到检查点保存时的配置。预先生成静态材料的现有链路需要按此边界核对，不能改写已接纳输出伪装实时。

例如，第 3 回合装配时采用 A，随后保存 B，再恢复第 3 回合成功检查点：上下文、变量和规定节点业务状态恢复到该点，当前提示词仍为 B，后续发生的新装配使用 B；旧回复仍记录为采用 A 的结果。这为调试保留空间，但不承诺重现原输出。

## 5. 仅注入一次的生效与防重复

`context_once` 可以保留，也允许作为可调提示词编辑；此前“仅允许 per_request 可调”的建议不作为最终规则。

### 当前批准方向

once 由提示词装配依据当前上下文实时检测，不另建检查点 once 台账或消费账本。检查点维护好规定上下文即可；恢复不追溯旧请求来重新证明 once，也不依赖逐层历史事实验证。恢复仍保留当前可调提示词，后续装配读取当前已保存配置，旧装配和请求事实不改写。

必要的上下文来源信息、同身份编辑及启停后的准确检测方式、压缩后的检测语义仍须在具体上下文契约中收敛。不能为了实现检测新增另一份存储台账，也不能把下面的旧 ID 台账字段直接登记为最终方案。

### 历史源码现状与已取消的沿用建议

以下步骤、操作表及代码链接记录旧实现，便于后续核对替代范围；其中 `once_injected_item_ids` / pending / 已消费记录路线不再作为新检查点或恢复方案的实施依据：

1. 提示词稳定 ID 由节点 ID 与成员 ID 生成，不依赖正文或资源修订号。
2. 装配读取当前上下文的 `once_injected_item_ids`。启用且未消费的条目才加入本次输入，并产生 `once_pending_item_ids`；合并材料按来源 ID 集合判断，已有来源命中时不再次追加该合并项。
3. 装配本身不修改持久记录。执行生成上下文更新，合并验证并被接受写入后，正文及已注入 ID 才成为会话持久状态。
4. 后续输入沿用持久上下文，不从配置重复追加同一条目；允许压缩的内容可被摘要，已消费身份仍保留，不能因此重复注入。

“仅注入一次”是向持久上下文追加一次，不是模型只接收一次；后续请求可能继续携带这段内容。生效判断是程序接受了上下文更新，不是判断模型理解或遵守了提示词。

| 操作 | 旧实现语义，仅供历史核对 |
| --- | --- |
| 同一成员 ID 修改正文、位置或顺序 | 已注入上下文不替换旧正文；尚未注入的上下文可使用新值 |
| 禁用，再启用同一条目 | 不重置已消费记录，也不删除原上下文内容 |
| 新建成员 ID | 新身份可再次注入，不自动替换旧身份的内容 |
| 新会话使用空上下文 | 没有消费记录，可以注入当前正文 |
| 恢复注入之前的检查点 | 消费记录和上下文一起恢复；后续适用装配求当前正文，已装配内容仍保持原值 |
| 恢复注入之后的检查点 | 恢复历史正文及其消费记录，不因配置可调再次追加 |

旧实现的消费记录属于会话内对应 Agent/上下文对象，不是全局标志。新规划改为依据各自当前上下文实时检测，检查点不另保存消费台账；这次文档整理没有删除或改造旧字段。

## 6. 后续实施与验证归属

本页不增加独立整改批次，后续安排统一由 40 承载。资源管理收敛归 B/MID-R07；配置策略和草稿机制退出归 C/MID-R02、03；检查点统一及上下文实时 once 检测归对应状态与 D 数据流工作。涉及 D、节点契约或调度改动，仍先收敛具体接口、数据格式和操作流程，再按确认范围实施。

必要验证方向：

- 两类资源保存、刷新和读取采用一致管理路径，Lorebook 触发规则及现有材料策略保持明确。
- 节点不维护数据修订号后，初始快照、修改、删除、无变化回合及分支恢复均可还原完整状态。
- 普通内存表单直接保存正式配置，不读写或恢复草稿；失败直接报告真实错误，目录和名称可正常保存重读，未决请求证据独立保留；会话选择不制造共享配置假冲突。
- 有有效会话时固定修改由后端判断并询问派生，同意后才创建新流；初期单条提示词可调按钮正式保存，策略切换分类待明确；恢复不覆盖当前可调值。
- 检查点仅在成功回合闭合时形成；助手消息和后续用户消息关联正确，后续消息关联不改写成功结束状态；失败进度不伪装成成功检查点。
- 后续交互、未发送输入、运行前编辑及执行中变化不修改已有成功检查点；恢复仍回到规定的固定结果，当前节点数据与未完成进度各自维护。
- 回到历史助手消息和紧随它的用户消息，恢复同一个检查点；用户输入本身不生成另一份运行状态检查点，再次处理输入不重复插入消息。
- 同回合中修改可调提示词，后续尚未装配的内容求新值，已装配内容和旧请求不变。
- 检查点恢复规定上下文，装配依据当前上下文实时检测 once；压缩后检测方式待契约收敛，不另保存台账或追证旧请求。
- 同流历史新会话拷贝整份历史检查点，之后独立；不做节点映射，不以 membership、原 chain 或源 current/Head 作为恢复条件。
- 历史实际配置、输入、请求和结果不被重写；保存配置或恢复检查点不自动重放外部请求。
