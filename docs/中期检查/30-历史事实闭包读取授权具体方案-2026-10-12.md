## 1. 最小结论

建议复用现有图记录、注册类型引用、对象读权限、原始事实表和纯证明，不建立通用“给 UUID 就读”的事实 API。新增一个可信内部历史读取上下文，负责从正式根建立闭包、解析准确原 producer 与冻结声明、读取其原始 executor/M2 事实。闭包是一次后端操作的内部授权对象，不是返回页面的可转交令牌。

四条界限保持：

1. 当前运行直接输入继续使用严格 live 授权；不能仅删除 `active/running` 条件，把 live reader 改成任意历史 reader。
2. 当前对象、成功存档和正式提交输入各有自己的可信读取根；后续用户消息关联不扩大先前存档的状态闭包。
3. 会话拥有状态、检查点链与历史 membership；工作流拥有不可变执行证据。新会话复用原事实身份与正文，不依赖源会话 current/Head。
4. 内部恢复/证明闭包与前端公开读取分开。普通 `references` 不是页面披露许可；不扩大官方来源白名单，也不生成可派发 lease。

已定的可调配置恢复、once 消费、固定存档、成功时点、独立会话、调度及三项默认值不在本文重新讨论。

## 3. 不可变归属与 membership

与 31 统一以下最小记录；字段和建表属于待审实现，不是当前库已有表。

```text
workflow_history_membership
  workflow_session_id
  chain_run_id
  workflow_definition_id
  fixed_definition_revision
  PRIMARY KEY (workflow_session_id, chain_run_id)
```

原 `chain_run` 本身就是执行归属记录，其 `workflow_definition_id/definition_revision/workflow_session_id` 三元组已由当前 transition 规则禁止修改。trusted run 创建事务当时核对真实 session 及固定定义，并保存原 chain；之后保留它即可核验原来源。普通回合与已有显式交互 event 都使用原 chain，不新增 `workflow_execution_owners` 或第二份 origin session 副本。

membership 由正式服务事务根据真实引用建立：本会话运行进度、成功检查点/历史路径、已有原执行 artifact 的正式 message links、同流 from-history 实际复制的前缀及必要闭包。它不是 caller 提交的一组允许 run UUID，也不是“同工作流就能任选所有会话事实”。恢复到旧点不删除仍属于本会话的后续历史 membership；读取某个固定存档仍只从该点的准确根出发。

D 建议 user 消息使用准确 `submitted-input` 类型引用唯一正式 `workflow_inputs` 正文，并由工作 input output 节点在运行中另产 TEXT artifact。提交前未发送 buffer 是 current 节点数据；提交后的原正文、input/entry 身份和接纳出处是 workflow-owned 不可变输入事实，PK 为原 `input_id`。尚未运行的输入没有 chain，不能借 `workflow_history_membership(chain_run_id)` 伪造授权：目标自己的正式 user message link/round 指向准确原 input row，作为该条输入的精确读取许可，不另加 input membership 表。from-history 事务建立目标关联，不复制正文；原输入仍保持原 workflow/session/instance/node/receipt 出处，源 session 删除不得删除其他目标关联所需原正文。这项新引用 scope 及精确字段由 31/32 一次审阅，不是当前 `validate_reference` 已支持的声明。

原 chain/run/output/runtime fact 的 session ID、run ID、fact ID、sequence、正文、时间戳、owner、签名和 request settings 不修改。事实自身不会因为 membership 增加而复制；源 session ID 表达原来源，不表达目标可派发身份。

bundle 验证分开处理：

- current state、Head、checkpoint 链、message links/rounds、目标 membership 仍必须有真实目标 session，并核对同 workflow/fixed revision。原 `workflow_inputs` 可保留已删除源 session 的出处，目标 link/round 与它的原身份、内容和接纳记录必须一致。
- workflow-owned chain/run/output/runtime facts 按原 chain 不可变三元组核对：run/output/fact 的原 session、chain、node/run 坐标逐项一致；原冻结定义和精确 binding/声明存在；成功 artifact 仍有成功 producer 与准确 `output_refs`。
- 源 session 还存在时可交叉核对它与原 chain 一致；源已删除时不装载其 current、不借其 Head、不造一个可运行的替身 session。原 chain 只证明保存时的原来源，不提供 resume/dispatch 权限。
- 原 executor/information source 的准确绑定证据若用于历史诊断读取，同属该 workflow-owned 证据组；不能按源 session 删除后再用当前注册“猜”原版本。

源 session 删除只清它自己的 current、目录、checkpoint/Head、links 和 membership。其他 session 仍正式引用的证据、原提交输入及原冻结定义必须保留；证据最终回收由无引用检查与现有 unknown-request 保护共同决定，删除会话不能声称同时清掉其他会话需要的证据。删除整个 workflow 仍按其明确范围和未知证据保护处理；本文不执行删除，也不增加自动 GC。

## 4. 谁建立可信根

建议内部对象名 `HistoryArtifactAuthority`，由图应用/数据层建立，持有一条连接、目标 workflow/session/fixed revision、正式根与必要冻结声明。构造器或 authority JSON 不对节点/页面开放；输入中的 root ID 仅是选择器。

| 场景 | caller 最多提供的选择 | trusted host 在同一事务读取的正式根 |
| --- | --- | --- |
| 活动节点直接输入 | input `port` | invocation owner、持久化 consumer `input_refs`、实际成功上游 output；保持现 live 原条件 |
| 活动节点读取历史对象 | `object_key`，明确读取历史 revision 时再给 `revision_id` | 本节点真实 `object_read` 回执/`context.reads`、binding readers/private owner、该对象 revision membership 与原值；不接受自报 object value |
| 历史查看/restore/select/from-history | 目标 `session_id` 与正式 `checkpoint_id`；entry/candidate 先由本 session 正式关联解析 | 同 session checkpoint parent/full-diff 链物化的规定状态、typed objects、history links；核对同 workflow/fixed revision。不是 caller 的完整 state JSON |
| 已提交输入及消息来源读取 | 本 session `input_id` / `entry_id` | 本 session 正式 user message link/round 指向的唯一 `workflow_inputs` 正文、原 workflow/session/instance/node/接纳出处与起点；assistant 来源仍为准确 artifact，不接受页面任意 source_ref |

第 4 行对应 D 的 `input.submit`：服务实际接纳后留下唯一不可变提交正文、稳定 input/entry 身份与原接纳出处。下一次运行、重来及历史显示由该准确记录取得原输入，不能用当前未发送 buffer 替换；工作 input output 节点按该次 chain_start 的 input_id 产生本轮 TEXT/USER_INPUT artifact 并保留正式输入 provenance。新会话实际复制自己的消息 links/rounds 后才能拥有对应读取根。

32 建议的 user-only 引用是 `{scope:"submitted-input", workflow_definition_id, workflow_session_id, input_id}`。本文不把它混成 artifact output_id；注册类型、host `validate_reference`、聊天/公开 reader 必须按审阅后的精确 scope 显式适配。原 `workflow_session_id` 表达输入事实的原出处，目标自己的正式关联赋予读取权；同工作流相等或知道此 JSON 本身均不授能力。

checkpoint 根只来自 31/D 共同审阅的成功结果投影。当前未发送输入、交互控制状态、后续 U1 以及正在执行的变化不会自动进入旧 C1 根。U1 可以凭自身正式提交/消息关联读取，但 `U1 -> C1` 只表示恢复起点，不把 U1 写入 C1 state 或 C1 证明闭包。

闭包建立算法：

1. 核对目标 session/workflow 的存在性、固定 revision、准确查询范围和调用权限；归档只读查询可以进入，恢复执行命令不可以。
2. 从上表正式根取得 typed values。对象读取须先验证 reader/private owner；涉及另一 session object revision 时继续核对目标 session、object_key、revision membership、类型与读者不扩权。
3. 只调用注册 `TypeRegistry.references` 提取精确引用；不扫描任意 JSON 字段中的 UUID，不把 `source.kind/model.request_id` 当成 artifact 路径，不读当前资源代替保存内容。
4. 每个 artifact 读取原 output、producer、chain 及原冻结 node/port/type。核对原 chain 不可变 workflow/revision/session、目标 workflow/fixed revision、实际 membership、成功 producer、原 output 坐标和 `output_refs`，再校验准确注册类型并沿其声明 refs 继续。正式 `submitted-input` 引用按本 session 准确关联与原输入 row 核验，不递归把任意输入 UUID 当成 artifact。
5. 原 producer 的 `input_refs` 用于证明来源，不能因此把它的所有输入加入通用可读集合。只有已注册 refs、准确 context proof 所需固定输入及其核对通过的专用分支可以读取；普通 unrelated output/producer 附带 UUID 没有能力。
6. 保留当前 artifact 闭包 8192 项、注册引用 4096 项等现有界限；缺失类型、引用越界或超过界限直接报错。对 proof 所需 lineage 单独检查循环，不能把 `seen` 去重等同于合法 lineage。

`HistoryArtifactAuthority.resolve_detail(reference)` 内部结果建议沿用已有写 resolver 的 shape，并补充可核对坐标：

```text
value, output_id, producer,
component_id, component_version, config, input_refs,
workflow_definition_id, fixed_definition_revision
```

`config` 用原 node_run 实际消费 config，固定投影须与原定义/声明一致；不能拿当前可调值改写历史证明依据。原声明用于类型/权限/固定部分检查。结果复制隔离，不直接返回可变 DB row 或 authority。

## 5. 模型与 executor 事实的准确内部桥

建议新增纯读取 helper：

```text
read_context_update_facts(connection, authority, update_ref)
  -> {
       producer,
       executor_facts,
       model_facts: {requests: [{request_id, settings_id, facts}]}
     }
```

输入 `update_ref` 必须已经在本次可信内部闭包；不提供 `producer`、`executor_ref`、`request_id`、`settings_id`、`fact_ids` 的 caller 自选入口。helper 的结果只供本次 context 证明，不新增公开 HTTP/consumer raw-facts 路线。

精确处理顺序：

1. 解析闭包中的原 Agent context update artifact；原 producer 必须成功，artifact/owner 与原 `output_refs` 一致。官方 source component/version 检查保留现有白名单；不可因为 packet shape 相似就授予新来源权限。最终新节点版本若需变化，由 D 列出并审阅，不由本 reader 自动放行。
2. 验证 receipts 2，取其中原 owner、准确 executor ref、完整有序 executor fact IDs 和全部有序 `model_requests`；generation 来自原 executor envelopes，receipts 2 没有该字段。取准确 `frozen_prompt_ref`、`model_ref`、policy ref，与原 producer 输入逐项一致。
3. executor SQL 限定原 `(session_id, chain_id, node_run_id, executor stream)`；返回仅 receipts 的全部 IDs，顺序一致，核对每条 envelope 原 owner/executor/sequence，generation 按现有完整证明的正整数、非递减规则核验。失败或其他 attempt 的 facts 不能补齐成功收据。
4. 模型 binding 读取原 accepted model artifact，并核对原 source 冻结声明/消费 config 和 resource binding。复用 live reader `_facts` 的原始查询与内容核验：准确 model service stream、request/attempt/outcome 三阶段、预分配 ID、sequence、request/settings/binding/purpose、原 producer input refs。请求清单从 accepted receipts 取得，discarded prepare、未接纳 outcome 或另一 binding 的 facts 均不能混入。
5. 用既有 `validate_execution_update_v2` / `prove_execution_facts_v2` 完成准确 snapshot、wire/settings/measurement、助手/工具闭合、压缩与 final 答案证明；之后再沿 native view lineage 做准确 read/merge 重演。纯 merge 或形状校验不是完整事实证明。

历史桥只替代 live reader 中“谁拥有这次历史根”的授权前段；原事实阶段校验不放宽。live `read-model-request-facts` 保留准确 active consumer/input/冻结 grant，不增加 `historical=true`、任意 producer 查询或遇拒绝改走历史的 fallback。

节点可见的逻辑入口继续复用：

| 入口 | 输入/输出 | 内部变化 |
| --- | --- | --- |
| `context:read / read-context` | `{object_key}` -> `{object, view}` | 从实际授权 object read 建立根，核对其必要历史 artifact/事实，再返回所属状态；不透出 raw facts |
| `context:validate / validate-context` | 现有准确 `view/view_ref`，可含 `context/context_ref` -> `{validated: true}` | 由真实 accepted input 建立根；历史 lineage 遇 schema 2 update 时内部读取完整事实并证明 |

## 7. 一致读取与失败语义

独立历史 query 采用绝对 DB URI 的 `mode=ro`、`PRAGMA query_only=ON` 和单个 SQLite `BEGIN`：正式根、checkpoint 物化、membership/精确 input links、原 chain 归属、冻结声明、artifact 与事实必须在同一快照中核对。传入 callback 只使用这一条连接，不另开服务连接读今日 current，也不实例化会写 DDL 的 store/service/RuntimeFactStore。

restore/from-history 的读验证与最终写事务按 31 的一个正式命令协调。预检读取不能单独授予持久能力；进入写事务时必须重核目标 session/Head/current revisions、目标固定定义与准确 checkpoint/link 身份，并在该事务内复核必要不可变记录/membership 后写入。发生并发变化直接报真实冲突，不缓存旧 authority 自动重试。

必要失败处理只覆盖核心路径：

- 输入字段/身份格式错误：400；根不存在或已删除：404；超出 session/membership/对象/官方来源权限：403。
- registered exact type/source 不可用、闭包界限、真实状态冲突：409，给出原 reason code 和诊断；不静默升级版本或返回部分可恢复状态。
- 被授权原记录缺失、原坐标/正文与存储不一致或证明失败：报告明确 storage/proof 诊断；不把有问题的状态当成空 context，不改写事实。
- SQLite/权限/连接错误保留真实异常，不改走可写连接、legacy reader、缓存或当前资源读。

任一必要证明失败，则历史恢复/新会话写操作不得部分落盘，页面不能报告成功。只读 query 不接纳新事件、不改 Head/checkpoint/CAS、不产生 lease、不调用模型/工具，不做未决请求重放；读取失败不改变 unknown-request 证据。

普通 public artifact 读取继续保持当前/原始 public 根及注册 direct export 双检查。内部 authority 的所有 `references` 不透给页面，也不自动把 private context、原 prompt、wire、executor/M2 facts 全部公开。

原事实接纳继续禁止同 ID 改正文，reader 保留原时间并按既有格式/顺序及交叉证据核验。本文不声称能识别管理员同时篡改所有互相依赖的 DB 记录，也不增加数据库外签名/时间锚；没有独立锚的合法时间值改变不能承诺必然可检测。
