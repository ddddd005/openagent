## 2. Key 实际接管

此前 backend 已有准确六字段非秘密 provider 请求、私有保存事务及原请求查询；缺口是公开 evidence 校验仍要求普通秘密命令的全部字段，组件仍借 draft 保留请求，前端只核对回执摘要格式。

| 文件 | 实际改动 |
| --- | --- |
| [request_evidence.py:52](../../backend/src/phase1_agent/request_evidence.py#L52) | 对 `provider.credential.save` 显式核对准确六字段公开身份，拒绝 `secret` 及空秘密占位；保留容量、原 UUID、秘密字段和摘要检查 |
| [providerCredentialEvidence.ts:7](../../frontend/src/adapters/providerCredentialEvidence.ts#L7) | 薄 channel 复用 `pending_commands`，准确 owner 为 `provider-credential / scope:resource_id`，save/delete 共用未决锁；原地 verified/archive，不复制请求 |
| [providerConfigurationApi.ts:72](../../frontend/src/adapters/providerConfigurationApi.ts#L72) | save/delete 用已确认落盘的原证据 digest 精确核对 command receipt，不再只检查 64 位 hex |

普通业务 command/query、provider service、私有 vault、DPAPI/HMAC、provider schema 3、application/credential/evidence schema 1、节点/包和实际 storage version 19 均未修改。没有新增补绑 mutation 或秘密哈希；完整 Key 只在原内存和一次业务保存命令中存在。

公开 digest 只证明准确公开请求身份，不声称能恢复或重新核对已经消失的秘密字节。原 provider UUID/正文、可信 vault 原 mutation receipt、准确代次和实际配置结果共同证明接纳；原证据缺失、partial/unresolved 或后来变化直接报告，不用当前 Key、空秘密、新 UUID 或新绑定补原请求。

“保存供应商”仍是一个动作：有新 Key 时提交当前完整供应商配置与 Key；Key 留空保持已有 local reference，不调用 Key save/delete。输入 Key 不锁住其他字段；提交或未决才锁 mutation。

## 3. 必要 Unknown 与退役边界

本批定向覆盖并复核：

- 初次 evidence write 丢响应时，保留原 UUID 和锁；先查准确证据，未确认落盘不派发 Key。
- 业务 unknown 只读原 provider/credential receipt；原记录不存在也不补发。
- verified/archive 已落盘但响应丢失时，当前 channel 按捕获的原 operation/UUID/正文/digest 只读收尾，不重发业务，也不改解释结案。
- 第二页面 evidence 写入明确被拒时，新 Key 不发送；只读实际同 owner 的原请求，不把被拒的新 intent 冒称已提交。
- 老 `management/intent/credential:<scope>:<resource_id>` 未删除证据只检查存在性并阻断新 mutation；身份/读取错误直接报错。旧正文不恢复、不迁移、不清空、不覆盖。

旧证据只读门禁是保护未知请求的退役前条件，不是旧保存 fallback。旧 draft 平台及其他消费者、旧 archive 和未知请求字节未删除；**整套 drafts 退出条件仍未满足**。这条接管不触发产品 data reset、workflow 清理或 Key vault 重置。
