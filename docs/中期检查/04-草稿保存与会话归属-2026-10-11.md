## 2. 会话实际挂在什么名下

会话属于工作流定义，创建时绑定一个明确的已保存定义修订，不属于提示词表单或酒馆展示节点。

```text
工作流 W
  已保存定义修订 r1、r2……
  会话 S1：绑定 r1，保存自己的运行历史与状态
  会话 S2：绑定 r1 或 r2，保存另一份运行历史与状态
```

同一工作流可以有多个会话；后端会话列表按工作流定义 ID 查询，不按定义修订过滤。会话容纳运行记录、节点私有状态、变量及会话对象。节点状态通过会话 ID 和节点 ID 区分，不是每个节点另有一个顶层会话。

前端各工作流条目分别保存 `session_id`。切工作流时，取该工作流条目上次选中的会话；同一工作流中切换 S1/S2 时，只改当前会话选择，不替换画布上的工作流编辑文档。

保存工作流定义也不自动改变已有会话绑定的修订；当前通过“采用已保存修订”明确重绑。酒馆展示节点使用当前工作流和会话作为入口参数，不拥有独立的聊天节点会话。

## 3. 表单和节点不是两套业务配置

以节点内的提示词条目为例，表单复制 `node.config.members` 到自己的 `members` 编辑副本。两者表示同一项配置的不同编辑状态，不是分别归属工作流与会话的两套提示词配置。

```text
节点当前正文为 A
  -> 在表单输入 B：表单副本为 B，节点配置仍为 A
  -> 点击“应用条目”：把 B 写入当前工作流文档的节点配置
  -> 点击“保存工作流”：保存修改后的工作流定义修订
```

这个副本机制用于暂存未完成、无效或想取消的输入。“表单配置”容易误导，更准确的名称是“待应用的编辑内容”。

当前有三个不同的保存或生效时点：

| 操作 | 当前实际效果 | 不代表什么 |
| --- | --- | --- |
| 自动保存表单草稿 | 保存输入及编辑依据，防止输入丢失 | 不代表节点配置已更新 |
| 应用条目 | 写入当前工作流编辑文档，并使其成为待保存的修改 | 不代表已保存为后端定义修订 |
| 保存工作流 | 保存当前工作流文档为定义修订 | 不会自动应用尚未应用的表单内容，也不会自动重绑已有会话 |

因此，输入正文后直接保存工作流，可以出现“表单输入已保留，但已保存节点仍使用原配置”。这不是两套业务配置，而是现有分段生效机制。

## 4. 草稿怎样产生和保存

### 提示词节点表单草稿

1. 打开表单时，复制节点当前条目，读取该表单地址已有的草稿。单纯首次打开不会新写一条提示词组草稿。
2. 修改正文、角色、启用状态、顺序或增删条目后，深度监听发现表单值变化，将输入暂存到前端内存。
3. 停止输入约 200ms 后，程序尝试把 `{ basis, raw }` 写入本机后端；切换页面或点击应用等操作还会主动等待草稿保存。
4. 再次读取时，将保存的 `basis` 与当前依据比较，一致才自动恢复，不一致则保留旧内容为冲突草稿。

`raw` 是表单输入；`basis` 是编辑时的依据。后端通过 `draft.save` 将记录写入 SQLite 的 `local_editor_drafts` 表，不依赖浏览器临时缓存作为主要保存位置。

应用成功后，当前实现不会删除表单草稿，而是更新依据并继续保存同一份输入。因此，有草稿记录不一定代表内容尚未应用。

### 工作台草稿与工作流编辑稿

工作台草稿是另一种本机记录，保存工作流目录、当前和选中的工作流，以及各工作流编辑条目；其中包含工作流文档和所选会话 ID。其地址固定为 `workbench:v1`，也采用约 200ms 的自动保存。

工作流编辑稿则是当前文档相对于已保存定义的编辑状态。新增节点、修改配置和连线等会改变该文档，不一定经过提示词表单的“应用条目”交互。

首次打开且没有工作台记录时，程序会创建空工作流并保存工作台记录。因此，“提示词表单首次打开只读”不能泛化为“打开整个页面不会生成任何草稿”。

## 5. 会话为什么会影响提示词草稿

提示词节点表单的实际地址为：

```text
scope: management
kind: form
key: node:<工作流ID>:<节点ID>:prompt-members
workflow_definition_id: <工作流ID>
workflow_session_id: null
```

其依据包含工作流 ID、节点 ID、节点版本、完整节点配置及 SDK 的 `lifecycle`。这个生命周期字符串又包含当前工作流、当前会话 ID 和可用前端扩展声明。

因此，“草稿属于 S1 环境”只是先前对校验依据的描述，不能当作数据归属：S1/S2 并没有分别保存一份提示词节点草稿，而是在同一表单地址上比较不同依据。

```text
工作流 W / 节点 N / 提示词表单的草稿记录仍是同一条
  -> 草稿依据记录了 S1
  -> 切换到 S2，节点配置可以完全不变
  -> 当前依据中的会话 ID 变化
  -> 旧草稿可能被判定为依据冲突
```

应用成功后仍保留的草稿也可能遇到这类冲突。没有现存或待保存的草稿时，单独切会话不必然产生旧草稿冲突。

点击应用还有另一道检查：先固定当前依据和输入，等待当前及其他表单草稿保存，再检查环境和编辑权限。等待期间发生会话切换、配置更新或扩展变化，可能中止应用。不同检查阶段可能产生不同提示，不能把它们都等同为同一个实际故障。

## 6. 后续重整范围与边界

后续已确定工作流编辑自动提交，取消独立“应用”与正式保存的两段生效步骤。用户进一步确认当前不做草稿机制，将独立草稿系统列入第 3 步自动提交改造的退出范围；草稿归属、会话草稿隔离、保存失败后的草稿恢复不再作为待设计接口或验收要求。

前端只保留普通内存表单编辑，直接提交对应正式配置。保存失败直接报告原始错误及诊断信息，排查连接或数据库等实际原因；不另存草稿、生成冲突副本或恢复失败输入。会话切换本身不改变共享节点配置归属，不建设按会话保存共享表单副本的机制。

退出范围包括持久草稿、自动恢复、草稿依据和冲突副本、已应用草稿同步，以及管理或编辑操作前等待全部草稿保存的流程。现有目录和名称等管理数据先接回各自后端管理接口；未决请求原始证据独立保留用于诊断和核实，不自动重发。调用依赖退出后删除草稿接口、存储表及专属旧测试；混合测试保留正常编辑、真实写入结果和请求证据的有效断言。
