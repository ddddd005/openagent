记录日期：2026-10-11，Asia/Shanghai。本页整理工作区画布工具栏调查及随后关于聊天展示职责的讨论，检查对象为当前 `develop` 未提交工作树；基础提交和检查限制见 [目录说明](README.md)。

## 1. 核心结论

- 系统已有节点执行顺序计算，完整执行计划由后端 `GraphCompiler` 生成。
- 前端负责构图、连线检查和部分依赖分析，目前没有独立的完整执行顺序预览入口。
- 执行顺序不是由“通用前端展示”或“会话对象绑定”计算的。
- 当前工作流不负责网页渲染，但确实承担了读取、追加和输出聊天展示记录的业务。
- 展示记录、模型上下文和节点执行顺序是不同职责，不能因为它们都关联会话就混为一件事。
- 把聊天记录维护交给独立的会话/聊天模块，是本轮讨论中的另一种分工；尚未确定实施范围和接口。

## 2. 术语和功能边界

| 名称 | 当前含义 | 不代表什么 |
| --- | --- | --- |
| 局部事件 | 在同一个会话中，提交具名事件和载荷，执行其声明的目标节点及依赖 | 不只是浏览器点击事件，也不保证完全不调用模型 |
| 通用前端展示 | 将已接受的节点输出组织为带角色、可持续读取的展示记录，并生成展示结果 | 不是执行排序器，不等于打开酒馆页面 |
| 会话对象绑定 | 声明对象键、确切类型、共享或私有范围、节点所有者及读写权限 | 不是选择会话，也不是将酒馆页面绑定到工作流或会话 |
| 展示读写节点 | 本轮解释使用的概括用语，指读取展示状态和追加展示记录的图内普通节点 | 不是独立调度机制，也不是界面上的统一正式名称 |
| 模型上下文 | 用于后续模型请求的上下文状态，由对应节点和模型协议处理 | 不等同于页面显示的聊天历史 |

“前端展示”按钮本身是已加载工作台扩展面板的入口。通用展示接线只是其中一项；供应商、提示词、世界书和酒馆等包也有自己的面板，不能把入口里的全部操作都解释为展示接线。

## 3. 当前节点顺序如何确定

```text
前端编辑节点、数据连线、前序依赖和运行目标
  -> 保存工作流定义
  -> 会话采用对应定义修订
  -> 后端从运行目标追溯所需依赖
  -> GraphCompiler 生成 ordered_node_ids
  -> 执行器按照计划执行节点
```

数据连线同时声明输入来源和执行依赖。例如 `A` 的输出进入 `B` 的输入，要求先执行 `A`。前序依赖即控制边，可以声明 `B` 必须等待 `A`，但不传递端口数据。

普通运行未声明局部事件时，目标取已登记的输出节点和显式运行目标；声明局部事件后，普通运行使用显式运行目标。事件执行则以事件声明的目标为准。编译器追溯数据边和控制边，检查循环、节点实现、输入端口、类型及权限，先收集依赖，再加入当前节点。

节点在画布上的位置和创建时间不是业务顺序。编译器会对目标与依赖遍历使用确定的排序规则，但这种排序不代替需要明确声明的业务先后关系。

前端也有循环检查、祖先关系和展示接线顺序分析；这些属于构图检查，不是页面拥有另一套完整执行引擎。

## 4. 展示读取、追加和输出的实际含义

当前通用展示链使用三个普通业务节点：

| 节点 | 作用 |
| --- | --- |
| `frontend.state.output` | 读取当前会话对象中已经保存的展示状态 |
| `frontend.state.append` | 将本次已接受输出按 `user`、`assistant` 或 `system` 角色追加到展示记录 |
| `frontend.presentation` | 从已接受的展示视图生成 `FRONTEND_DISPLAY@1` 输出 |

```text
读取已有展示记录 ----+
                    +-> 追加本次输出 -> 展示输出 -> 页面渲染
本次文本节点输出 ----+
```

“追加后写回会话”的准确含义，是由节点结算逻辑将新记录写入该会话的展示状态对象，经后端保存。不是再次发送模型 API，也不是自动把页面消息加入模型上下文。

底层并非只是把字符串复制到一份聊天数组里。展示条目包含 `entry_id`、`role` 和已接受节点输出的 `source_ref`；页面读取引用对应的内容再显示。追加节点校验来源，结算阶段写入对象并取得真实保存回执。

例如页面可显示为“用户：你好”“助手：有什么可以帮你？”，但这是角色和输出内容经页面解析后的呈现，不是这份对象直接保存的完整协议格式。

通用接线功能会加入读取、追加和展示节点、对象绑定及必要连线，也可能复用已有展示节点。这些都是图编辑操作，不会因点击接线按钮就立即执行或发送模型请求。

## 5. 为什么展示链需要对象绑定

当前实现选择将跨回合的展示记录保存在会话对象中。因此，读取和追加节点必须声明访问哪个对象，以及读取、写入权限。

绑定回答“数据属于哪份对象、类型是什么、谁能访问”；数据边和控制边回答“谁先执行”。对象绑定本身不会自动建立先后依赖。

例如两个节点访问同一对象，一个写、一个读，仅凭权限不能判断应读到写入前还是写入后的状态。当前编译器要求这类含写操作的访问之间存在明确依赖，否则报告 `graph_unordered_object_access`。纯读操作不要求因此人为排出业务顺序。

普通工作流执行不必使用通用展示链。不访问会话对象的节点也不要求非空对象绑定；`object_bindings` 可以为空。使用上下文、展示记录或其他会话对象的节点，则须满足其实际声明的访问契约。

因此，这种依赖来自当前节点的持久状态设计，不是因为系统缺少执行顺序计算。

## 6. 工作流是否必须负责聊天展示

不必须。需要区分网页渲染与维护展示记录：

- 网页渲染由前端组件及酒馆页面实现。
- 当前工作流节点负责读取、追加展示记录，以及生成供页面读取的展示结果。
- 后端会话对象存储负责实际持久化和访问校验。

这是当前职责分配，不是图执行框架的必然要求。不能把“工作流没有渲染网页”理解为“工作流完全没有承担聊天展示业务”。

本轮讨论中的另一种分工如下：

| 模块 | 候选职责 |
| --- | --- |
| 工作流及执行服务 | 接收业务输入、计算依赖、执行节点、产出回答及明确的结果信息 |
| 会话/聊天模块 | 保存用户消息和回答，维护供页面读取的聊天历史 |
| 聊天前端 | 读取消息、渲染列表、呈现状态和用户操作 |
| 模型上下文功能 | 组织模型请求所需历史和协议信息，与页面展示历史分别管理 |

采用这种分工后，普通聊天不再要求用户手工构建“读取记录 -> 追加消息 -> 展示”的图内链路。但现有酒馆结果契约、消息保存时点及所属模块需要先明确，不能只删节点或绕过校验来代替职责订正。

此表是讨论方案，不是本轮已经实施或已授权实施的架构。是否保留可选展示节点、普通聊天结果如何交给会话模块、失败和未决请求下消息如何记录，仍待后续裁定。
