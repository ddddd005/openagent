## 2. 原内核与请求边界

[runtime.py](../../backend/src/phase1_agent/runtime.py) 的 `SnapshotKernel.run` 显式接受 `request_bridge`。schema 2 必须使用准确 `ModelExecutionRequests`，不接受旧 adapter 或额外 token counter；schema 1 拒绝该桥。M2 的 result 3 转为现有 `ModelResponse`，随后复用原助手解析、工具队列、实际工具执行、final_answer 和暂停路径。

[model_execution_requests.py](../../backend/src/phase1_agent/model_execution_requests.py) 增加原 `model_result` 事件并保留原结果。普通和摘要统一统计：`request_count` 是原请求登记数，`attempt_count` 是每个原 dispatch 首次进入数。原事件或 outcome 的接纳重入只重交原 ID 和正文，不增加计数、不重新通信；新路径不进入旧四次模型重试。

`KernelCheckpoint` 增加原桥身份和业务请求边界序号，纳入 HMAC 校验，并核对桥的准确 snapshot 和计数。模型桥失败保留真实诊断码与同进程 checkpoint；事件接纳失败保留 `event_id/kind/cause_code`，不递归尝试发布另一错误事实。unknown 重入不改 key、不重新派发。

摘要成功后、下一普通请求前可以暂停。checkpoint 保留原边界，原桥保留已接纳摘要、替换操作和结果；继续时仅准备下一新普通请求。工具后暂停保留已完成工具结算，后续请求读取当次新设置，不重复执行工具。

这些是同进程、同桥的暂停继续能力，不是生产历史恢复或从 durable 事实重新构造可派发 lease。

## 3. 执行器与上下文候选

[agent_executor.py](../../backend/src/phase1_agent/agent_executor.py) 的 schema 2 分支核对准确 immutable 输入，注入可信模型 host callback 和释放回调。原事实缓存保留 ID、正文及 `created_at`；ack 成功后才将 ID 记入执行收据，并只记一次。

receipts 2 的有序模型请求清单来自已接纳 `model_result.result.fact_refs`，不包含 discarded 准备的预分配事实。terminal 成功先保留实际 kernel result 和原 terminal fact，终态 ack 丢失后 `recover_acceptance` 只接纳原事实并构建输出，不再运行 kernel。释放失败保留状态，仅重试可信 release。

[contracts_v2.py](../../backend/src/phase1_agent/contracts_v2.py)、[agent_receipt_contract.py](../../backend/src/phase1_agent/agent_receipt_contract.py) 和 [context_update.py](../../backend/src/phase1_agent/context_update.py) 增加显式 schema 2 校验分发。schema 1 保留给当前仍安装的消费者；没有按字段猜版本或自动升级节点。

上下文授权顺序必须保持：

1. executor 从实际 kernel 的操作和 effective messages 构造候选 packet 2。
2. producer 输出被接纳后，consumer 才能从 live 已接纳输入调用模型事实 reader。
3. consumer 用准确 executor 事实及 reader 返回的有序模型事实完成纯证明。
4. 纯 merge 核对准确原 view/ref/basis；生产写入与安装接线留在 D。

executor 构造候选时不调用依赖该候选已经被接纳的 live reader，避免循环授权。候选形状校验和纯 merge 重演不能代替完整事实证明。

## 4. 完整证明与生命周期投影

新 [execution_facts_v2.py](../../backend/src/phase1_agent/execution_facts_v2.py) 的 `prove_execution_facts_v2` 核对原 host envelope、owner、executor reference、generation/sequence、准确终态及 snapshot。每个 request/result 必须与真实 M2 request/attempt/outcome、settings、wire 和原输入一致。

完成回合的状态机逐项核对：

- 原始助手文本、工具 `raw_arguments`/解析参数、固定工具版本、canonical call remap 及签名元数据。
- 实际 dispatch、准确 tool execution ID、settlement、accepted message 的闭合顺序。
- final_answer 的原 control/result、答案 schema、终态计数及收据的全部有序请求。
- 压缩 trigger decision、原 summary result、同设置普通 O 的前后测量、准确替换范围和下一有效上下文。

新 [context_update_v2.py](../../backend/src/phase1_agent/context_update_v2.py) 分离 `make_context_update_v2` 候选构建、`build_execution_update_v2` 证明后重建、`validate_execution_update_v2` 完整核验。证明不读今天的配置、不获取 Key/lease、不通信。

[context_v4.py](../../backend/src/phase1_agent/context_v4.py) 提取共享生命周期投影，保留 view 4、once 消费台账、fixed 材料不进入持久历史、current 变成实际回合 history 的规则。普通最终回答按原 final pair 显式投影；带协议签名的 final pair 继续保留，不剥离签名。纯 merge 要求准确原 view/ref/basis，重复消费拒绝。

没有扩大官方来源白名单、历史 fact UUID 读取范围或生产 CAS 写权限。

## 5. 实际联合验证

新 [test_model_kernel_integration.py](../../backend/tests/test_model_kernel_integration.py) 使用实际 `RuntimeHost`、`PublicAgentExecutor`、`SnapshotKernel`、M2 服务、资源 SQLite 和 `RuntimeFactStore`。测试显式注册临时 executor 2，注入合成已接纳 prompt/policy 输入；这不是已安装的生产图宿主。

真实 callable lookup 在执行后修改临时当前配置，三次离线通信为：

1. normal 1 输出上限 `32000`，解析 lookup 并实际执行、结算工具。
2. 触发准备输出 `16000`，decision 后普通 O 改为 `12000`；摘要实际输出 `1024`。
3. 摘要后当前输出改为 `8000`，normal 2 使用新值并执行真实 final_answer。

consumer 从 live reader 读取三次原模型事实，完成整个更新核验和准确原 basis 的纯 merge；核验不增加资源读取、lease 或通信。once 台账、fixed 退出、lookup call/result 和最终回答投影均经过断言。

联合专项另覆盖工具后暂停、摘要后暂停、terminal ack 丢失只重交原事实、unknown 不输出 context，以及 owner、请求顺序、结算和候选篡改拒绝。

本批没有访问产品数据库或用户 Key、重置产品数据、启动产品服务、调用真实模型、提交、合并或推送。
