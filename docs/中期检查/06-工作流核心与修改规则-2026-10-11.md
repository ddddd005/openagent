## 1. 核心方向

以工作流为核心，工作流管理会话。会话及其运行数据、历史属于对应工作流，不作为可以自动跨工作流延续的独立运行时主体。

先只做正常工作流，不引入独立调试模式、测试会话模式或另一套会话核心运行架构。后续调试便利性不能成为同时维护两套所有权、保存和恢复规则的理由。

同一工作流可以管理多个独立会话。新建工作流不创建会话；运行时没有选定会话才自动创建，有选定会话则在该会话内运行。从历史新建会话也是新的独立会话，不强行放进原会话下作为子会话。

工作流下存在未归档、未删除的会话信息时，修改固定执行定义由后端判定需要派生，前端弹窗询问，用户同意后才创建新工作流；未同意前不写入这次修改，不静默派生。原工作流和会话不改，新工作流不携带原工作流的任何会话或历史检查点。第一版只允许预先选为可调的单条提示词业务配置在原工作流保存，后续尚未装配的内容在装配时求当前值，不随检查点回溯；固定结构不在此例外中。

工作流下没有这类会话信息时，在原工作流内修改，不额外复制。删除或归档全部会话后，同样按无会话工作流处理；不是只看当前前端是否选中了会话，也不额外建设初始化占位或数据量阈值判断。

## 2. 节点修改与数据修改必须分开

| 操作 | 后续处理原则 |
| --- | --- |
| 没有未归档、未删除会话时修改执行定义 | 原地修改，保留工作流身份，不额外派生副本 |
| 存在未归档、未删除会话时修改固定执行定义 | 后端判定需要派生、前端询问，用户同意后才创建新工作流；原工作流和会话不改，新流不携带原会话或历史 |
| 存在有效会话时修改预先选为可调的提示词 | 原工作流保存，后续装配求当前值，已装配内容不变，检查点恢复不覆盖配置 |
| 在派生的新工作流尚无会话时继续编辑 | 继续修改这个新工作流，不为每次编辑反复复制 |
| 改名、移动节点等纯展示操作 | 不因此派生工作流，不改变原会话归属 |
| 非运行期间修改会话内容、上下文或节点运行数据 | 作为数据修改处理，弹窗告知范围与影响，不混同于节点定义修改 |
| 运行期间手动修改会话或节点运行数据 | 不允许；正常节点执行写入不属于手动编辑 |
| 编辑全局供应商、模型配置或内容 | 在各自模块完成，不因此派生工作流或清理会话 |

节点配置中的提示词、参数等属于执行配置；其中预先选为可调的提示词采用上述例外，其余固定。运行中积累的上下文、消息、私有状态等属于数据，按会话和节点归属保存；成功回合规定需要保存的结果进入检查点，当前交互及未完成进度另由节点、数据层和 runtime 维护。不能因为两者都显示在节点面板里，就采用同一种保存或删除行为。

执行定义修改包括节点增删、替换或版本变化、节点内提示词及参数、数据连线、执行依赖、运行目标、对象读写绑定等影响执行的内容。不能只按节点 UUID 是否改变判断；用户先前提出的 UUID 唯一判断已收回。

改名和画布位置等纯展示操作不属于执行定义修改。全局资源的内容变化不等于工作流定义变化；改变节点所引用的资源或对象绑定则按执行定义处理。

本轮不采用“只有节点增删才派生，其余配置均可原地修改”的规则。可调例外初期只覆盖明确选择的单条提示词业务配置，不覆盖节点身份、类型、版本、连线、端口、绑定和状态格式。策略切换不能追改已有历史；按钮切换本身是否触发派生确认，仍须在最小契约中明确，不直接沿用现未安装基础的固定修改分类。归档和删除先停止相关运行，不能通过假定会话为空来跳过尚未结束的运行或未核实请求。

固定配置由工作流持有一份，不在每个检查点重复备份。检查点在逻辑上保存成功回合规定的完整可恢复结果，物理存储采用初始完整快照及程序比较生成的差异，关联回合和父检查点；取消节点自身的数据修订号，不取消条目身份、格式版本、必要写入约束和实际执行事实。详见 13 第 2、4、5 节及 29 第 6 节。

检查点是唯一权威的历史回溯机制，只保存两类内容：节点明确注册、合规且允许保存的业务内容，以及数据层中的上下文、变量和其他节点合规注册存储内容。不增加独立 once 台账、计数器分区或历史核验证据包。once 在提示词装配时依据当前或恢复后的上下文实时检测，检查点维护好上下文即可；压缩后的最小检测语义在 40 所列具体契约中收敛。

同工作流从历史建立独立会话时拷贝整份历史检查点，目标拥有自有检查点、必要 full/diff 依据和当前状态，源会话删除不破坏目标。相同工作流不做节点映射、迁移或改绑。历史读取按所属检查点处理，不以原 chain、membership、artifact 闭包或逐层模型事实证明为恢复条件；检查点之外的不规范历史数据不做兼容或补救。

成功回合检查点只在该回合成功结束、助手消息闭合且工作流结束本次运行时形成。助手消息及其后面一条用户消息归属于该点。执行中进度和请求事实不等于成功检查点；随后用户消息的归属与成功结束时的状态快照分别表达，具体恢复、重来和候选解释见 16 第 2 节。

用户消息本身只提供后续执行输入，不独立形成计算后的运行状态或新检查点。因此回到历史 `assistant1` 或紧随它的 `user1`，都恢复 C1；处理该输入并生成 `assistant2`、成功结束本次运行后才形成 C2。助手消息与其后续用户消息不各存一份检查点。

成功检查点类似存档，唯一职责是保存成功结束时规定需要保存的结果，使之后能够回到固定出发点。检查点形成后不随交互、未发送输入、工作流未启动时的修改或启动中的数据变化更新；当前数据和暂停/失败进度由所属节点、数据层及 runtime 维护。内部内核暂停现场不等同于成功回合存档。

## 3. 新工作流只复制定义，不继承运行数据

从工作流 A 派生工作流 B 时，允许复制节点、连线、节点配置及全局资源引用等执行定义。

B 不继承 A 的：

- 会话身份或会话选择；
- 聊天消息、agent 上下文及会话上下文；
- 会话变量、共享对象和节点私有运行状态；
- 运行记录、节点输出及未完成执行位置；
- 会话历史、历史当前位置或历史恢复关系。

B 从自身配置声明的初始值开始。派生 B 本身不创建会话，运行时按第 1 节规则创建或选择会话。

“不携带旧数据”是对新工作流的初始化规则，不是删除 A 的会话数据。A 的定义、会话、历史和运行均保留在 A 下，不因派生 B 被清除。

不进行自动改绑、节点状态迁移、跨工作流历史接续或隐式上下文复制，也不自动重放旧模型和工具请求。

## 4. 工作流编辑自动提交后端

工作流编辑后自动提交后端，不再要求用户依次操作“保存本机草稿 -> 应用条目 -> 保存工作流”。后端是保存责任方，不建设与正式定义并行的另一套用户可见本机保存路径。

节点内表单和节点配置表达同一项业务内容，不维护两份需要用户手动同步的生效配置。切换会话不是节点配置编辑依据变化，不能单凭会话选择变化拒绝定义编辑。

固定/可调策略由节点配置持有，表单不另设一套策略。文本失焦、选择和开关操作完成提交、复合配置整项提交及后端按变化分类，是 [15：表单检查](15-前端表单编辑与提交链路检查-2026-10-11.md)第 4 节的接口建议；自动提交方向已确认，具体触发、粒度和 SDK 返回契约尚待方案审阅。

2026-10-12 用户进一步指定策略入口：初期只做单条提示词条目，通过节点注册机制在节点内部提供固定/可调按钮，复用节点扩展和宿主承载能力，不推广到提示词组或任意节点。按钮走统一正式配置提交入口；节点身份、类型、版本、连线和资源绑定保持固定。策略切换本身的派生分类待最小契约明确，不因提供按钮就允许追改已有历史。

普通工作台和各节点前端实例接同一配置应用层，分别提交自己负责的结构或注册字段。应用层复用原请求证据、真实结果和归属隔离基础，但须先订正静默派生。迟到回执只归原工作流/节点，未知请求只核实准确原请求、不自动重发；这不是草稿恢复或另一套历史权威。

提交成功后刷新应读回已保存内容；失败直接报告实际错误和诊断信息，不假报成功。当前仅保留普通内存表单编辑，不建设持久草稿、失败输入恢复、冲突副本或会话草稿隔离。字段提示、提交排队和真实写入冲突不能重新包装成多套产品保存步骤。

前端用户输入按 29 作为节点自身的数据处理：200ms 自动通信并被后端接纳后，即使未发送也已成为正式节点数据，发送和启动运行是另一动作。尚未进入后端的内容仅在页面临时内存中，崩溃或刷新丢失是正常机制，不建设独立草稿或浏览器恢复副本；不据此改变全局资源及 Key 的既定保存方式。

独立草稿机制纳入自动提交改造的退出范围。先将其承载的目录和名称等管理数据接回所属后端接口，独立保留未决请求原始证据用于诊断和核实；随后删除草稿保存、恢复、依据校验、全部草稿保存门禁及对应接口、表和专属旧测试。旧调查与说明只作明确标注的历史参考，不成为可执行回退路径；当前计划不再论证草稿归属。

当前以开发和调试为目标，代码和功能采用简洁实现，支持暴露程序问题以定位根因。在考虑兜底机制或额外错误情况前，先明确回答：是否可能掩盖更深层报错；程序没有这个机制是否无法正常运行。正常运行不需要的机制不添加，连接中断或数据库失败直接排查原始原因。此原则已写入 `AGENTS.md`。

全局供应商、模型配置和内容在各自模块保存，工作流自动提交不顺带提交其他资源。供应商仍按既有规则使用一次“保存供应商”提交整份配置和新填写的 Key。

保存工作流不要求它已经可运行。未接完连线、未选模型、缺少运行输入等未完成状态允许保存，不在保存时做完整执行编译、模型可用性探测或上游试调用。

保存只保留写入所必需的格式、身份、权限及真实覆盖冲突检查，不假报写入成功；执行所需的缺失输入、循环、资源可用性等问题在实际运行流程中检查并报告，不提前阻止正常构图。

## 5. 数据修改采用弹窗告知

用户修改已有会话内容、上下文或节点运行数据时，通过弹窗报告本次修改的范围，以及对后续输入、输出和上下文一致性的影响。

提示应描述实际影响，不只显示 UUID、修订不一致等工程信息，也不笼统把任何修改描述为必然导致模型性能下降。

运行期间不允许手动修改会话和节点运行数据。独立全局内容和配置保持可编辑；可调提示词只对对接节点后续尚未装配的内容实时生效，装配时求值后不再控制已装配内容。此边界也适用于同一未完成回合，不替换已装配输入或执行事实。全局内容按工作流读取时生效，不为其增加整轮冻结或额外禁止修改的规则。

非运行期间的数据编辑应明确目标和影响范围。弹窗不是另一套草稿发布步骤，也不授权绕过待核实请求保护。

用户已确认：手动修改指定会话数据只影响后续运行，不自动删除后续楼层、不重新计算已有输出，也不追溯改写已发送请求和已确认运行事实。修改目标数据与重写历史执行记录是不同操作。

数据修改不应被偷偷转换为“复制全部会话并改绑到另一个工作流”。同样，工作流节点定义修改也不能被当成修改原会话数据，从而绕过新工作流规则。

## 6. 全局配置与通信边界

模型供应商模块集中管理提供商、模型和命名配置，运行参数界面只保留思考强度、上下文长度、压缩阈值、输出上限，不把这些配置交给每个工作流维护。模型选择、地址及 Key 等身份与连接信息仍归相应模块。三项默认值保持 `300000 / 0.85 / 32000`；压缩阈值是开始压缩的占用门槛，不是压缩后的目标长度。模型真实容量和协议能力校验仍据真实请求检查，超限直接报错，不猜测补全。

工作流仅指定模型配置引用，不设置第二套上下文/输出/压缩限额、调用配额或覆盖节点，也不换成隐藏限额。模型源传引用，不复制整轮设置；Chat/Agent 每个新请求准备时拉取当前已保存配置，已准备或发送的请求不追改。必要的非限额压缩行为收回上下文模块，准确最小字段和本期配置范围另行审阅，不增加模型第五项参数。通信层只负责 API 协议、内容发送和接收，不承担工作流目录、会话、草稿或全局内容管理。

全局配置和内容由工作流实时读取。当前运行后续调用也可以采用已保存的新配置，不要求等下一次运行，不保存一份整轮冻结的供应商配置。例如模型欠费后，用户可以修改全局模型配置，再明确继续未完成运行。

已发送请求及已确认结果仍是事实记录，修改全局配置不改写它们，也不自动重发模型或工具请求。单次请求记录不等于工作流拥有另一套全局配置。

同一模型配置引用下允许切换模型协议或能力，后续新请求采用当前设置及相应协议；已接纳请求保留原设置。引用指节点所指向的模型配置资源身份，不是工具调用。更换所引用资源本身仍是固定节点绑定变更。正常请求授权及消费者成组适配按 40 收敛，不原样安装 12/19/34 的旧限额或历史来源追证提案。

### 左侧栏薄基底

左侧栏是应用壳中的薄基底，只负责布局、收起、导航和组件承载。工作流、模型供应商、全局提示词和世界书等内容以独立业务组件接入，不由其中任何业务持有左侧栏，也不由一个业务替其他业务保存、校验或管理状态。

各组件持有自身业务数据和操作，分别调用对应后端模块。可以复用通用存储、传输和界面基础能力，但不建设包办全部业务的左侧栏后端或新的通用管理平台。组件化不代表拆除共享基础设施或重复建库。

## 7. 失败处理与暂停恢复

失败调用不自动删除已记录的用户输入，也不一概把未完成工作流判为不可继续。用户可以中止或继续；想重新开始本回合时，通过明确的“回合重来”操作处理。

“重试失败节点”和“回合重来”不是同一动作。继续保留已确认执行进度；回合重来是用户主动操作，不能由失败处理隐式触发，更不能把未知结果的工具请求当作失败后自动重放。

用户在清理审批中要求保留与 roll 回复相关的能力。同一固定工作流内的候选回复选择及必要状态恢复保留，不因取消跨流迁移就整删候选模块；但不能保留跨工作流、跨执行定义改绑或归档会话恢复。回到历史 `assistant1` 或紧随它的 `user1` 均恢复 C1；按此规则，重新生成 `assistant2` 从 C1 加已有 `user1` 开始，不重复插入输入。选择已有 `assistant2` 候选采用其对应 C2，选择本身不调用模型。恢复归属已经确认，具体命令、消息关联和节点接线仍须形成 D 的方案，创建/酒馆操作流程在 E 整合。审批依据及调用核对见 [09：清理审批](09-清理候选与审批清单-2026-10-11.md) 的 P02。

本次用户说明当前没有所讨论的外部工具调用，相关副作用回滚、重来时重复执行及外部工具恢复策略暂时占位，不在本轮建设或作为完整验收前提。占位不表示已经实现工具回滚，也不取消原请求结果未知时不得自动重放的保护。

工作流 A 的暂停运行属于 A，恢复时继续使用 A 的固定节点定义和原执行进度；全局配置独立实时读取，可调提示词对后续尚未装配的内容在装配时求当前保存值，不重写已经装配、发送或完成的输入和结果。

修改节点产生 B 后，B 是另一个工作流，没有 A 的会话数据和暂停位置。B 不参与 A 的恢复，也不存在 A 接受 B 新配置的问题。

因此不增加“节点修改后丢弃旧运行数据”的自动处理规则。仅仅创建或编辑 B，不自动终止 A 的暂停任务，不清理 A 的已保存数据。

用户明确中止、归档或删除是独立操作，不与派生新工作流混在一起。

## 8. 归档、删除和管理操作

会话归档停止相关运行，只保留历史数据供查看，不提供恢复、取消归档后续跑或采用新图的功能。归档记录不参与“是否允许原地编辑工作流”的会话判断。

会话删除停止相关运行并移除该会话的所属数据。归档和删除对工作流编辑权限的效果相同，数据处理不同；删除、归档全部会话后，原工作流可以继续原地编辑。

工作流归档或删除同样先停止所属运行。工作流删除清理所属会话、历史和运行数据，不连带删除引用的全局模型配置、内容资源或私有 Key。

归档保存失败不得当作归档完成，删除也不得掩盖未核实请求。保留原请求证据不等于让会话继续运行，不借此建立自动重放机制。

运行 A 不应阻止切换或新建 B；操作和保存只影响其目标对象，不先保存所有无关表单、不锁住整个应用。归档后的查找入口布局后续细化，本轮不建设归档恢复能力。

管理流程采用目标操作直接提交并返回真实结果的主路径。移除无关表单保存、图宿主就绪和执行可运行性等相互嵌套的前置条件；将真实写入、运行错误交由责任模块直接报告，而不是提前通过跨业务流程锁定阻止操作。必要的归属检查、真实写入冲突、失败结果和未知请求保护仍保留，不把“简化”变成吞错。

## 9. 聊天、上下文和节点前端

读取、装配、内核调用和更新由工作流节点表达，采用“读取上下文 -> 提示词装配 -> agent 内核 -> 上下文更新”的模式。原始读取结果可以同时连接装配、内核和更新节点，不反复读取同一记录来追加用户、再追加助手。

聊天消息由统一聊天输出组件连接下游追加节点，追加节点处理后与工作流数据层交互，替换旧的追加后重新读取补线机制。前端输入、输出、展示所需数据和交互能力由节点声明，通用宿主承接节点扩展，不再靠应用壳逐项硬编码酒馆业务；页面展示本身由前端负责。现有扩展机制可复用，不把它描述为完全不存在。

Agent A、B 的上下文分别独立，不规定“Agent B -> A 上下文写回 -> B 上下文写回”，也不规定所有上下文必须先于聊天追加写回。更新节点按实际数据依赖和工作流 runtime 调度执行；A 的上下文写回排在全部数据写回末尾也成立。助手消息闭合且工作流成功结束后形成检查点的规则保持，不以固定跨节点先序代替成功条件。

2026-10-12 进一步确定：大部分节点保留，部分端口承担的前端运行能力提升为节点。每个后端节点绑定自己的前端实例，复制节点后新实例绑定新节点身份；不共享实例业务状态，不将操作或迟到结果发送到原节点或其他当前对象。通用组件、类型声明、传输和渲染宿主可复用；全局供应商、模型和内容管理仍独立。具体端口转节点及实例清单先形成方案，创建及酒馆入口在前端节点化后整合。

架构职责按 29 划分为应用壳与通信、工作流与会话管理、定义与能力注册、编译与 runtime、节点业务、工作流数据、成功回合检查点、交互、外部资源与宿主服务九项。Agent 执行器与内核是节点内部实现，不单列工作流层；前端注册、用户输入、运行开关、重 roll、分叉和功能映射通过节点接入。前端页面不持有正式业务数据，后端节点维护以数据层为基底、每回合更新的展示上下文，页面负责呈现。

上下文和变量从数据层通过显式引用、读取或导入成为运行时内容后，才能消费或编辑，结果通过明确写回保存；取得的值不因存储后续变化而被追改。这里的导入不等于第 11 节暂缓的 JSON 导入导出功能。

节点维护图内的数据处理；会话负责归属和持久化。不能将节点化理解为会话独立于工作流，也不另建一条无工具、无节点的酒馆执行路径。

酒馆从所属前端节点入口打开时带上当前工作流和会话；具体前端注册节点与旧聊天展示入口的对应关系随 D 清单落实。若尚无会话，按运行时创建规则处理，不在新建工作流时提前创建。

## 10. 节点激活与执行顺序

运行入口及连线由 runtime 统一确定普通执行范围，上游依赖优先。无上下游的节点由 runtime 判为孤立节点并排除，不因为被随意选为运行目标就进入执行；各节点执行器不重复编写连接、孤立或激活判断。

写入节点可以没有输出端口，上游连接足以表达其激活和顺序；不能把“写后返回空结果”本身认定为错误。

变量赋值按此通用规则执行：无上下游时不执行，是因为 runtime 未将其纳入执行范围；进入范围后节点只负责赋值处理及数据写入。

第一版对依赖关系未区分先后的同批就绪节点按节点序号串行运行，不按 UUID 或画布位置排序。变量更新和读取同时就绪时也遵循该顺序，不要求用户另配一层显式先序才能运行。

节点序号从工作流中的节点创建开始分发，仅负责顺序，不承担唯一身份；UUID 仍用于节点身份。本轮未要求新增手动改号界面。

变量注册与初始赋值改为用户主动触发的工作流交互节点，不要求连接到普通执行链，不再作为自动独立初始化例外。具体交互入口及目标数据归属在 D/E 方案中对接既有规则。

节点统一声明工作/非工作类别，runtime 按黑名单语义排除普通执行中的非工作节点，同时保留显式交互调用。前端注册、运行开关、重 roll、分叉等按交互职责分类；类别过滤与孤立排除分别由 runtime 负责，节点不重复判断。具体注册字段及节点名单在 D 方案中给出。

世界书直接访问工作流变量数据，读取执行当时的值；不因访问同一变量就添加对注册、赋值节点的先序，也不自动激活这些节点。正常的数据线依赖、缺失输入和循环检测仍由执行计划负责，不以串行序号代替依赖计算。

后续重整旧手动先序交互和冲突校验，不仅因节点访问同一对象就强制补先序，不为普通流程再建设一套必须手动使用的控制线体系。对象归属、读写权限、真实写入冲突及接纳校验仍由相应数据和执行边界负责。

## 11. 上下文复用后续单独处理

上下文复用的后续候选能力是：

- 将选定的 agent 上下文或会话上下文导出为 JSON；
- 将导出的上下文显式导入目标工作流的会话。

目前不实现上下文导出、导入，也不通过复制工作流提前提供隐式继承。

以后若实施，应作为独立内容转移能力定义格式、导入目标和影响范围，不视为完整会话恢复、节点状态迁移或旧执行续跑。是否提供无工具文本化导出等细节留待该能力立项时讨论。

## 12. 规则示例

| 场景 | 应有结果 |
| --- | --- |
| 新建 A | 只创建工作流；首次运行且未选择会话时才创建 S1 |
| A 尚无会话，连续修改多个节点 | 始终修改 A 并自动提交后端，不反复创建副本 |
| A 存在未归档会话 S1，修改固定节点配置或连线 | 后端判需派生并询问；同意后才产生 B，A/S1 不改，B 没有旧会话或历史；不同意则不写入 |
| A 存在 S1，修改选为可调的提示词 A 为 B | 原工作流保存 B；回溯恢复状态但不覆盖 B，后续尚未装配的内容在装配时采用 B |
| 已注入 context_once 提示词后修改同一条目正文 | 已有上下文不被替换，装配依据当前上下文检测 once；不新增独立台账，新上下文可读取新正文 |
| A 存在 S1，仅改名或移动节点 | 不因此派生工作流 |
| B 尚无会话，又继续修改节点 | 仍修改 B，不额外创建 C |
| A 的全部会话已归档或删除，再修改执行定义 | 原地修改 A；归档仅留数据，不恢复旧会话 |
| 保存尚未接完连线或未选模型的 A | 正常保存，执行可用性问题在实际运行时报告 |
| 非运行期间修改 S1 中的已有上下文 | 弹窗告知，修改只影响后续运行，不删除后续楼层或重算已有结果 |
| S1 正在运行，手动修改运行数据 | 禁止修改；全局内容和配置仍可正常修改 |
| 模型欠费后修改全局配置并继续 | 后续调用读取新配置，不改写已发送请求、不自动重放工具 |
| A 暂停后派生 B，并运行 B | A 的暂停任务仍属于 A；B 从自己的初始数据开始 |
| 从 S1 的历史起点新建会话 S2 | 整份复制历史检查点；S2 自有且独立，不成为子会话，删除 S1 不破坏 S2 检查点 |
| 想把 S1 的上下文用于 B | 当前不自动支持；后续通过明确的 JSON 导出、导入实现 |

## 13. 历史清理与实施关口

后续开发只以新架构为准，不同时维护新旧数据路线。实际开工前确认本轮整改所用的数据目录和开发/测试数据库，清理其中此前留存的全部历史产品数据，包括：

- 模型供应商、命名模型配置及旧参数配置；
- 全局预设及关联提示词、世界书等旧内容；
- 历史工作流、会话、运行记录、节点状态及所属历史；
- 历史产品归档内容，以及旧工作台、表单草稿和管理标签。

清理不是将旧数据转移到一套兼容归档继续保留。不为旧内容开发兼容读取器、迁移、回退或自动换版；后续持久化、重读及接口一致性只围绕新架构产生的新内容验证。这里的产品归档不指 Git 历史或本目录的检查文档。

代码编辑过程中创建的中途验证工作流及其关联会话、历史、测试配置，记录明确身份，在对应验证阶段结束后删除；失败也须记录尚未完成的清理。新架构下用户创建的正式验收内容不自动视为临时夹具或旧内容反复删除。

本轮计划登记不立即执行清理，也不扩大到无关稳定库、私有 Key 库或未知请求证据；沿用既有保护边界，普通历史产品归档与未知请求证据分别识别。清除供应商配置不等于新增一个私有凭据维护入口。

删除与归档汇报规则：

- 删除或归档后移除是正常的减负手段。对过期、无效、重复内容主动思考并提出清理建议，不因回避删除而保留多套架构、旧接口或无效逻辑。
- 对未获明确授权的删除，先汇报涉及哪些代码、模块、接口、节点、文档、测试或数据，为什么建议删除，依据和依赖影响是什么，以及直接删除还是先作参考归档；用户确认后实施。相关内容可以按批次汇总，不要求逐文件重复汇报。
- 前文已经明确列出的历史供应商、模型配置、全局预设、工作流、会话、历史产品归档和旧编辑记录，以及已授权的临时验证数据删除，无需再逐项汇报或请求确认；在对应开发阶段开始后按既定范围执行，并汇总实际清理结果。
- 免重复汇报不扩大到额外代码、节点、接口、文档或无关数据；原有路径、数据保护和节点论证关口保持。参考归档不得成为可继续执行的旧架构、兼容读取或回退入口。

实施优先级与关口：

- 简化代码逻辑，先完成已确认的核心链路，不把单项功能的异常情况穷尽作为推进下一项的条件。只实现已经确定的业务分支，不预设大量可能情况来追加状态、兜底、重试框架或抽象。
- 保存以“提交当前内容 -> 必要写入 -> 返回实际结果”为主路径，不再叠加多种应用、确认或发布机制。数据归属、真实写入结果、Key 保护和未知请求不自动重放等必要底线保持，但不围绕它们提前建设完整异常恢复体系。
- 开发验证聚焦核心路径与必要回归。非核心问题在实际测试中记录复现、影响及所属模块，经人工论证形成定向联调规划，再补充实现；不在原任务内持续堆积未确认逻辑。
- 直接阻断核心流程且原因明确的问题，做范围内最小修复；涉及新行为、跨模块职责调整或节点优化时先汇报，不自行扩大实现范围。
- 先整改已明确的后端所有权、供应商配置与通信、内容管理等问题，再进行对应现有界面的必要接口对接。
- 前端新增或适配更多节点、工作流顺序优化、节点职责或契约优化，先调查实际范围并提交报告，说明问题、修改依据、方案、影响和验收方式；用户确认后才实施。
- 上述节点和顺序关口同样覆盖需要改动的后端契约或调度代码，不能因为先改后端文件就绕过论证。
- 批次 D 的节点执行与聊天数据流、批次 E 的创建与酒馆入口均保留后续人工参与：先呈现具体方案、节点接线和用户操作流程，经人工讨论确认后实施，并进行对应人工验收。E 不因复用现有节点就自动进入实施；本轮三并发只读勘察不越过该关口。
- 不将此前确认的方向视为本次新增节点或优化的直接开工授权，不在明确问题的后端批次中夹带这些改动。
