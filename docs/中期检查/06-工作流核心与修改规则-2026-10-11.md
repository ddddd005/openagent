## 1. 核心方向

以工作流为核心，工作流管理会话。会话及其运行数据、历史属于对应工作流，不作为可以自动跨工作流延续的独立运行时主体。

先只做正常工作流，不引入独立调试模式、测试会话模式或另一套会话核心运行架构。后续调试便利性不能成为同时维护两套所有权、保存和恢复规则的理由。

同一工作流可以管理多个独立会话。新建工作流不创建会话；运行时没有选定会话才自动创建，有选定会话则在该会话内运行。从历史新建会话也是新的独立会话，不强行放进原会话下作为子会话。

工作流下存在未归档、未删除的会话信息时，修改执行定义直接派生为新工作流；新工作流不携带原工作流的任何会话数据。

工作流下没有这类会话信息时，在原工作流内修改，不额外复制。删除或归档全部会话后，同样按无会话工作流处理；不是只看当前前端是否选中了会话，也不额外建设初始化占位或数据量阈值判断。

## 2. 节点修改与数据修改必须分开

| 操作 | 后续处理原则 |
| --- | --- |
| 没有未归档、未删除会话时修改执行定义 | 原地修改，保留工作流身份，不额外派生副本 |
| 存在未归档、未删除会话时修改执行定义 | 派生新工作流，只复制定义和配置，不携带原会话数据 |
| 在派生的新工作流尚无会话时继续编辑 | 继续修改这个新工作流，不为每次编辑反复复制 |
| 改名、移动节点等纯展示操作 | 不因此派生工作流，不改变原会话归属 |
| 非运行期间修改会话内容、上下文或节点运行数据 | 作为数据修改处理，弹窗告知范围与影响，不混同于节点定义修改 |
| 运行期间手动修改会话或节点运行数据 | 不允许；正常节点执行写入不属于手动编辑 |
| 编辑全局供应商、模型配置或内容 | 在各自模块完成，不因此派生工作流或清理会话 |

节点配置中的提示词、参数等属于执行定义；运行中积累的上下文、消息、私有状态等属于数据。不能因为两者都显示在节点面板里，就采用同一种保存或删除行为。

执行定义修改包括节点增删、替换或版本变化、节点内提示词及参数、数据连线、执行依赖、运行目标、对象读写绑定等影响执行的内容。不能只按节点 UUID 是否改变判断；用户先前提出的 UUID 唯一判断已收回。

改名和画布位置等纯展示操作不属于执行定义修改。全局资源的内容变化不等于工作流定义变化；改变节点所引用的资源或对象绑定则按执行定义处理。

本轮不再采用先前讨论过的“只有节点增删才派生，其余节点执行配置修改直接作用于原会话”的分段规则。归档和删除先停止相关运行，不能通过假定会话为空来跳过尚未结束的运行或未核实请求。

## 3. 新工作流只复制定义，不继承运行数据

从工作流 A 派生工作流 B 时，允许复制节点、连线、节点配置及全局资源引用等执行定义。

B 不继承 A 的：

- 会话身份或会话选择；
- 聊天消息、agent 上下文及会话上下文；
- 会话变量、共享对象和节点私有运行状态；
- 运行记录、节点输出及未完成执行位置；
- 会话历史、历史当前位置或历史恢复关系。

B 从自身配置声明的初始值开始。派生 B 本身不创建会话，运行时按第 1 节规则创建或选择会话。

“不携带旧数据”是对新工作流的初始化规则，不是删除 A 的会话数据。A 的定义、会话、历史和运行均保留在 A 下，不因派生 B 被清除。

不进行自动改绑、节点状态迁移、跨工作流历史接续或隐式上下文复制，也不自动重放旧模型和工具请求。

## 4. 工作流编辑自动提交后端

工作流编辑后自动提交后端，不再要求用户依次操作“保存本机草稿 -> 应用条目 -> 保存工作流”。后端是保存责任方，不建设与正式定义并行的另一套用户可见本机保存路径。

节点内表单和节点配置表达同一项业务内容，不维护两份需要用户手动同步的生效配置。切换会话不是节点配置编辑依据变化，不能单凭会话选择变化拒绝定义编辑。

提交成功后刷新应读回已保存内容；失败应说明真实原因并保留当前输入，不假报成功。网络请求中的暂存、无效字段提示、提交排队和真实写入冲突属于实现细节，不能重新包装成多套产品保存步骤。

全局供应商、模型配置和内容在各自模块保存，工作流自动提交不顺带提交其他资源。供应商仍按既有规则使用一次“保存供应商”提交整份配置和新填写的 Key。

保存工作流不要求它已经可运行。未接完连线、未选模型、缺少运行输入等未完成状态允许保存，不在保存时做完整执行编译、模型可用性探测或上游试调用。

保存只保留写入所必需的格式、身份、权限及真实覆盖冲突检查，不假报写入成功；执行所需的缺失输入、循环、资源可用性等问题在实际运行流程中检查并报告，不提前阻止正常构图。

## 5. 数据修改采用弹窗告知

用户修改已有会话内容、上下文或节点运行数据时，通过弹窗报告本次修改的范围，以及对后续输入、输出和上下文一致性的影响。

提示应描述实际影响，不只显示 UUID、修订不一致等工程信息，也不笼统把任何修改描述为必然导致模型性能下降。

运行期间不允许手动修改会话和节点运行数据，只能修改独立的全局内容或配置。全局内容按工作流读取时生效，不为其增加整轮冻结或额外禁止修改的规则。

非运行期间的数据编辑应明确目标和影响范围。弹窗不是另一套草稿发布步骤，也不授权绕过待核实请求保护。

用户已确认：手动修改指定会话数据只影响后续运行，不自动删除后续楼层、不重新计算已有输出，也不追溯改写已发送请求和已确认运行事实。修改目标数据与重写历史执行记录是不同操作。

数据修改不应被偷偷转换为“复制全部会话并改绑到另一个工作流”。同样，工作流节点定义修改也不能被当成修改原会话数据，从而绕过新工作流规则。

## 6. 全局配置与通信边界

模型供应商模块内完成提供商、模型、命名配置、上下文容量、思考强度、温度等管理，不把这些配置交给每个工作流维护。容量仅手动配置；超限真实报错，由用户处理，不猜测补全。

工作流只引用和调用已配置能力。通信层只负责 API 协议、内容发送和接收，不承担工作流目录、会话、草稿或全局内容管理。

全局配置和内容由工作流实时读取。当前运行后续调用也可以采用已保存的新配置，不要求等下一次运行，不保存一份整轮冻结的供应商配置。例如模型欠费后，用户可以修改全局模型配置，再明确继续未完成运行。

已发送请求及已确认结果仍是事实记录，修改全局配置不改写它们，也不自动重发模型或工具请求。单次请求记录不等于工作流拥有另一套全局配置。

### 左侧栏薄基底

左侧栏是应用壳中的薄基底，只负责布局、收起、导航和组件承载。工作流、模型供应商、全局提示词和世界书等内容以独立业务组件接入，不由其中任何业务持有左侧栏，也不由一个业务替其他业务保存、校验或管理状态。

各组件持有自身业务数据和操作，分别调用对应后端模块。可以复用通用存储、传输和界面基础能力，但不建设包办全部业务的左侧栏后端或新的通用管理平台。组件化不代表拆除共享基础设施或重复建库。

## 7. 失败处理与暂停恢复

失败调用不自动删除已记录的用户输入，也不一概把未完成工作流判为不可继续。用户可以中止或继续；想重新开始本回合时，通过明确的“回合重来”操作处理。

“重试失败节点”和“回合重来”不是同一动作。继续保留已确认执行进度；回合重来是用户主动操作，不能由失败处理隐式触发，更不能把未知结果的工具请求当作失败后自动重放。

用户在清理审批中要求保留与 roll 回复相关的能力。同一固定工作流内的候选回复选择及必要状态恢复保留，不因取消跨流迁移就整删候选模块；但不能保留跨工作流、跨执行定义改绑或归档会话恢复。选中已有完成候选不等于调用模型生成新回复，具体 roll 生成及用户流程留到 D/E 人工讨论，本次不扩建历史回滚体系。审批依据及调用核对见 [09：清理审批](09-清理候选与审批清单-2026-10-11.md) 的 P02。

本次用户说明当前没有所讨论的外部工具调用，相关副作用回滚、重来时重复执行及外部工具恢复策略暂时占位，不在本轮建设或作为完整验收前提。占位不表示已经实现工具回滚，也不取消原请求结果未知时不得自动重放的保护。

工作流 A 的暂停运行属于 A，恢复时继续使用 A 的节点定义和原执行进度；这不意味着冻结独立的全局供应商配置或内容。

修改节点产生 B 后，B 是另一个工作流，没有 A 的会话数据和暂停位置。B 不参与 A 的恢复，也不存在 A 接受 B 新配置的问题。

因此不增加“节点修改后丢弃旧运行数据”的自动处理规则。仅仅创建或编辑 B，不自动终止 A 的暂停任务，不清理 A 的已保存数据。

用户明确中止、归档或删除是独立操作，不与派生新工作流混在一起。

## 8. 归档、删除和管理操作

会话归档停止相关运行，只保留历史数据供查看，不提供恢复、取消归档后续跑或采用新图的功能。归档记录不参与“是否允许原地编辑工作流”的会话判断。

会话删除停止相关运行并移除该会话的所属数据。归档和删除对工作流编辑权限的效果相同，数据处理不同；删除、归档全部会话后，原工作流可以继续原地编辑。

工作流归档或删除同样先停止所属运行。工作流删除清理所属会话、历史和运行数据，不连带删除引用的全局模型配置、内容资源或私有 Key。

归档保存失败不得当作归档完成，删除也不得掩盖未核实请求。保留原请求证据不等于让会话继续运行，不借此建立自动重放机制。

运行 A 不应阻止切换或新建 B；操作和保存只影响其目标对象，不先保存所有无关表单、不锁住整个应用。归档后的查找入口布局后续细化，本轮不建设归档恢复能力。

管理流程采用目标操作直接提交并返回真实结果的主路径。移除无关表单保存、图宿主就绪和执行可运行性等相互嵌套的前置条件；将真实写入、运行错误交由责任模块直接报告，而不是提前通过跨业务流程锁定阻止操作。必要的归属检查、真实写入冲突、失败结果和未知请求保护仍保留，不把“简化”变成吞错。

## 9. 聊天、上下文和节点前端

读取、装配、内核调用和更新由工作流节点表达，采用“读取上下文 -> 提示词装配 -> agent 内核 -> 上下文更新”的模式。原始读取结果可以同时连接装配、内核和更新节点，不反复读取同一记录来追加用户、再追加助手。

聊天消息采用同样的读取、处理、更新思路。前端输入、输出和展示能力由节点声明，通用宿主承接节点扩展，不再靠应用壳逐项硬编码酒馆业务。现有扩展机制可复用，不把它描述为完全不存在。

节点维护图内的数据处理；会话负责归属和持久化。不能将节点化理解为会话独立于工作流，也不另建一条无工具、无节点的酒馆执行路径。

酒馆入口挂在聊天展示节点，从节点打开时带上当前工作流和会话；若尚无会话，按运行时创建规则处理，不在新建工作流时提前创建。

## 10. 节点激活与执行顺序

运行入口及连线确定执行范围，上游依赖优先，孤立节点不因为被随意选为运行目标就进入执行。

写入节点可以没有输出端口，上游连接足以表达其激活和顺序；不能把“写后返回空结果”本身认定为错误。

第一版对依赖关系未区分先后的同批就绪节点按节点序号串行运行，不按 UUID 或画布位置排序。变量更新和读取同时就绪时也遵循该顺序，不要求用户另配一层显式先序才能运行。

变量注册是允许独立初始化的明确例外，已有会话继续运行时不反复重置变量。正常的数据线依赖、缺失输入和循环检测仍由执行计划负责，不以串行序号代替依赖计算。

后续重整旧手动先序交互和冲突校验，不为普通流程再建设一套必须手动使用的控制线体系。

## 11. 上下文复用后续单独处理

上下文复用的后续候选能力是：

- 将选定的 agent 上下文或会话上下文导出为 JSON；
- 将导出的上下文显式导入目标工作流的会话。

目前不实现上下文导出、导入，也不通过复制工作流提前提供隐式继承。

以后若实施，应作为独立内容转移能力定义格式、导入目标和影响范围，不视为完整会话恢复、节点状态迁移或旧执行续跑。是否提供无工具文本化导出等细节留待该能力立项时讨论。

## 12. 规则示例

| 场景 | 应有结果 |
| --- | --- |
| 新建 A | 只创建工作流；首次运行且未选择会话时才创建 S1 |
| A 尚无会话，连续修改多个节点 | 始终修改 A 并自动提交后端，不反复创建副本 |
| A 存在未归档会话 S1，修改节点配置或连线 | 产生 B；S1 及其内容仍属于 A，B 没有会话和旧数据 |
| A 存在 S1，仅改名或移动节点 | 不因此派生工作流 |
| B 尚无会话，又继续修改节点 | 仍修改 B，不额外创建 C |
| A 的全部会话已归档或删除，再修改执行定义 | 原地修改 A；归档仅留数据，不恢复旧会话 |
| 保存尚未接完连线或未选模型的 A | 正常保存，执行可用性问题在实际运行时报告 |
| 非运行期间修改 S1 中的已有上下文 | 弹窗告知，修改只影响后续运行，不删除后续楼层或重算已有结果 |
| S1 正在运行，手动修改运行数据 | 禁止修改；全局内容和配置仍可正常修改 |
| 模型欠费后修改全局配置并继续 | 后续调用读取新配置，不改写已发送请求、不自动重放工具 |
| A 暂停后派生 B，并运行 B | A 的暂停任务仍属于 A；B 从自己的初始数据开始 |
| 从 S1 的历史起点新建会话 S2 | S2 是同一工作流下的独立新会话，不成为 S1 的子会话 |
| 想把 S1 的上下文用于 B | 当前不自动支持；后续通过明确的 JSON 导出、导入实现 |

## 13. 历史清理与实施关口

后续开发只以新架构为准，不同时维护新旧数据路线。实际开工前确认本轮整改所用的数据目录和开发/测试数据库，清理其中此前留存的全部历史产品数据，包括：

- 模型供应商、命名模型配置及旧参数配置；
- 全局预设及关联提示词、世界书等旧内容；
- 历史工作流、会话、运行记录、节点状态及所属历史；
- 历史产品归档内容，以及旧工作台、表单草稿和管理标签。

清理不是将旧数据转移到一套兼容归档继续保留。不为旧内容开发兼容读取器、迁移、回退或自动换版；后续持久化、重读及接口一致性只围绕新架构产生的新内容验证。这里的产品归档不指 Git 历史或本目录的检查文档。

代码编辑过程中创建的中途验证工作流及其关联会话、历史、测试配置，记录明确身份，在对应验证阶段结束后删除；失败也须记录尚未完成的清理。新架构下用户创建的正式验收内容不自动视为临时夹具或旧内容反复删除。

本轮计划登记不立即执行清理，也不扩大到无关稳定库、私有 Key 库或未知请求证据；沿用既有保护边界，普通历史产品归档与未知请求证据分别识别。清除供应商配置不等于新增一个私有凭据维护入口。

删除与归档汇报规则：

- 删除或归档后移除是正常的减负手段。对过期、无效、重复内容主动思考并提出清理建议，不因回避删除而保留多套架构、旧接口或无效逻辑。
- 对未获明确授权的删除，先汇报涉及哪些代码、模块、接口、节点、文档、测试或数据，为什么建议删除，依据和依赖影响是什么，以及直接删除还是先作参考归档；用户确认后实施。相关内容可以按批次汇总，不要求逐文件重复汇报。
- 前文已经明确列出的历史供应商、模型配置、全局预设、工作流、会话、历史产品归档和旧编辑记录，以及已授权的临时验证数据删除，无需再逐项汇报或请求确认；在对应开发阶段开始后按既定范围执行，并汇总实际清理结果。
- 免重复汇报不扩大到额外代码、节点、接口、文档或无关数据；原有路径、数据保护和节点论证关口保持。参考归档不得成为可继续执行的旧架构、兼容读取或回退入口。

实施优先级与关口：

- 简化代码逻辑，先完成已确认的核心链路，不把单项功能的异常情况穷尽作为推进下一项的条件。只实现已经确定的业务分支，不预设大量可能情况来追加状态、兜底、重试框架或抽象。
- 保存以“提交当前内容 -> 必要写入 -> 返回实际结果”为主路径，不再叠加多种应用、确认或发布机制。数据归属、真实写入结果、Key 保护和未知请求不自动重放等必要底线保持，但不围绕它们提前建设完整异常恢复体系。
- 开发验证聚焦核心路径与必要回归。非核心问题在实际测试中记录复现、影响及所属模块，经人工论证形成定向联调规划，再补充实现；不在原任务内持续堆积未确认逻辑。
- 直接阻断核心流程且原因明确的问题，做范围内最小修复；涉及新行为、跨模块职责调整或节点优化时先汇报，不自行扩大实现范围。
- 先整改已明确的后端所有权、供应商配置与通信、内容管理等问题，再进行对应现有界面的必要接口对接。
- 前端新增或适配更多节点、工作流顺序优化、节点职责或契约优化，先调查实际范围并提交报告，说明问题、修改依据、方案、影响和验收方式；用户确认后才实施。
