# 外部 Agent 接入工作流使用说明

2026-11-04 · 第 5 步 S5-01 交付（对应 Q11-1/Q11-2/Q12 决定，见 `docs/工作流优化执行规划-2026-11-04/06-验收与执行记录.md` §10.10）

本文面向"外部代码 Agent"（Codex、dsh 等 harness）：它们通过**现有本地接口**完成一次完整的工作流循环——发现契约 → 读取基线 → 编辑 → 预演 → 保存 → 运行 → 按诊断修复 → 再次保存/运行。**本步不新建平台、调度器或认证体系，也没有新增业务代码**；下面的示例由 `backend/tests/test_external_agent_loop.py` 用隔离临时库实际跑通并校验。

---

## 1. 接入方式

| 方式 | 入口 | 说明 |
| --- | --- | --- |
| 现有 HTTP（本地可信） | `GET /api/graph/application`；`POST /api/graph/commands`；`POST /api/graph/queries`；以及 `/api/graph/definitions`、`/api/graph/sessions` 等 REST 包装 | 产品服务本身的路由（`backend/src/phase1_agent/graph_http.py`）。命令/查询统一为 `{"operation": ..., "parameters": {...}}`。 |
| Codex / dsh 等 harness | 把上述 HTTP 调用映射为各自已有的工具执行能力 | 不新增 MCP/平台层；harness 自己负责把工具结果回填上下文。 |
| 进程内（等价） | `GraphApplication(service).command(name, parameters)` / `.query(name, parameters)` | 与 HTTP 路由共用同一 dispatcher，测试与嵌入式调用用它，不需要起服务。 |
| 远程接入 | **未来另议** | 当前边界是"本地可信调用"；本步不建设远程认证/来源白名单。 |

一次接入只需要两个地址：命令 `POST /api/graph/commands`、查询 `POST /api/graph/queries`；`describe()`（`GET /api/graph/application`）给出完整命令/查询清单与参数表，**不要离线硬编码清单**。

## 2. 身份与信任前提

- 调用方必须是**用户信任的本地 harness**：`describe().boundary.caller == "trusted_local"`，`remote_plugin_authentication == false`。用户"信任某个 harness"是使用前提，接口不为此建设认证系统。
- management scope 拥有完整工作流编辑/调试能力；consumer scope 只读原始回执与草稿（`for_consumer()`）。本说明默认 management scope。
- `node_id`/`workflow_definition_id` 等身份是**可信 management 输入**：它们不替代图内对象权限检查，对象读仍按节点声明与授权校验。
- 所有写命令都要求 `idempotency_key`（1–128 字符，建议 UUID 或稳定字符串）；同一 key + 同一请求重放返回原回执，不会重复写。

## 3. 能力矩阵（操作 → 参数 → 语义 → 权限 → 前置）

完整清单以 `describe()` 为准（当前 22 个命令 / 45 个查询）。下表是外部 Agent 最小操作集；"权限"列是 `application_operation_authority` 的服务分档（不进入 describe）。

### 3.1 命令

| 操作 | 必填参数（另有 `session_id` 的按路由提供） | 成功 | 主要错误 | 权限 | 前置条件 |
| --- | --- | --- | --- | --- | --- |
| `definition.update` | `workflow_definition_id`、`document`、`expected_edit_sequence`、`idempotency_key`（可选 `confirm_derivation`） | 200，`outcome=saved/unchanged/derived/confirmation_required` | `stale_edit_sequence`、`stale_revision`、`configuration_run_locked`、`workflow_modification_busy`、`graph_invalid_*`、`session_object_*`、`graph_storage_busy` | management | 结构合法；双 CAS 匹配；非 G21；互斥空闲；幂等键；有有效会话且改 fixed 时需确认 |
| `definition.copy` | `source_workflow_definition_id`、`expected_source_definition_revision`、`expected_source_edit_sequence`、`target_workflow_definition_id`、`target_name`、`idempotency_key` | 200，`outcome=copied`（新身份、revision=1） | `graph_definition_conflict`、`stale_revision`、`stale_edit_sequence`、`not_found` | management | 源有当前配置；目标三处无记录；源计数匹配 |
| `definition.archive` / `definition.delete` | `identity`、`expected_revision`、`idempotency_key` | 200，`archived/deleted` | `stale_revision`、`workflow_archived`、`management_pending` | lifecycle | 修订匹配；归档定义只读；删除为破坏性动作 |
| `session.create` | `workflow_definition_id`、`definition_revision`、`idempotency_key` | 201，完整 session 视图 | `stale_revision`、`not_found` | management | `definition_revision` 必须等于当前 fixed 修订 |
| `session.archive` / `session.delete` | `expected_revision`、`idempotency_key`（`session_id` 由路由/参数给出） | 200，`archived/deleted` | `stale_revision`、`session_archived`、`execution_stop_unconfirmed` | lifecycle | 修订匹配；归档会关闭该会话未完成链（动作显式） |
| `run.start` | `expected_revision`、`idempotency_key`（可选 `inputs`） | 202，prepared 视图 + `active_chain_run_id` | `stale_revision`、`package_missing_dependency`、`invalid_request`、编译/准备阶段错误（400/409，**不留 run 记录**） | execution | 会话修订匹配；无活动链；包可用；inputs 为 dict 且不含保留键 |
| `run.control` | `action`、`expected_revision`、`idempotency_key` | 200，session 视图 | `stale_revision`、`invalid_state`、`failed_retry_unavailable`、`recovery_unavailable`、`execution_stop_unconfirmed` | execution | 动作合法；当前链状态允许（`available_actions`）；`close` 需显式调用，不自动 |
| `event.submit` | `workflow_definition_id`、`definition_revision`、`event_id`、`event_schema_version`、`payload`、`expected_revision`、`idempotency_key` | 202，事件链视图 | `graph_event_not_declared`、`graph_event_payload_invalid`、`stale_revision` | execution | 事件在固定修订中声明；会话修订匹配；无活动链 |
| `request.abandon` | `workflow_definition_id`、`target_operation`、`target_idempotency_key`、`target_request_digest`、`idempotency_key` | 200，`outcome=committed/abandoned` | `request_arbitration_unavailable`、`request_evidence_conflict`、`idempotency_conflict` | management | 必须已有该原请求的证据行（`request-evidence.write`）；否则无法仲裁 |
| `request-evidence.write` / `.resolve` | `operation`、`idempotency_key`、`owner_kind`、`owner_id`、`request` / `request_digest`、`resolution` | 200，证据行 | `request_evidence_conflict`、`request_evidence_capacity_exceeded`、`request_evidence_secret_disallowed` | management | 单 owner 单 pending；证据不强制用于业务写 |

| 查询 | 参数 | 用途 | 权限 |
| --- | --- | --- | --- |
| `document.contract` | 无 | 版本化文档契约：JSON Schema、上限、保存语义、诊断字段、错误码目录（**部分覆盖**，见 §9） | 只读 |
| `catalog.node-types` | `protocol_version=2`（v1 仅兼容） | 节点契约：端口/类型/配置 schema/可调声明/对象访问/包锁 | 只读 |
| `platform` | 无 | 包锁、执行包锁、数据类型、执行器、pause 支持、服务与包诊断 | 只读 |
| `definition.summaries` | `include_archived?` | 定义目录窄行：名称/修订/编辑序号/节点数/会话数/是否有当前配置 | 只读 |
| `definition.read` | `identity`、`revision?` | 不带 revision 返回合成后的当前文档（含 `edit_sequence`）；带 revision 返回该固定修订原文 | 只读 |

| `definition.inputs` | `document` | 编辑期外部输入声明与 `required_for_run`（编译错误收在 200 的 `diagnostics[]`） | 只读 |

| `session.read` | `session_id` | 完整会话视图：状态、`can_submit`、`available_actions`、节点诊断、chains、outputs、对象/变量 | 只读 |
| `session.actions` | `session_id` | 窄视图：`status`、`can_submit`、`available_actions`、`start_operation`、`control_operation` | 只读 |
| `run.read` | `session_id`、`chain_id` | 链/节点运行记录、重试尝试、inputs/outputs、runtime_facts、manifests | 只读 |
| `output.list` / `output.read` / `output.history` | 会话 + 定义/端口参数 | 读取节点 `public_outputs` 声明的正式输出与历史 | 只读 |
| `checkpoint.list` / `checkpoint.read` | `session_id`（+`checkpoint_id`） | 定位检查点（read 只有 header，不含状态） | 只读 |
| `receipt.read` | `operation`、`parameters`（**完整原请求**，含 `document` 等该命令全部必填字段） | 用原请求核实未知结果：`matched/unresolved`；`unresolved` 不代表未执行，见 §6.6 | 只读 |
| `request-evidence.read` / `.pending` | owner + 条件 | 前端 outbox 证据读取（窄读/分层初始化，S4-01） | 只读 |
| `object.*` / `information.read` / `manifest.read` | 会话 + 授权/边界参数 | 运行内数据面（对象需节点授权） | 只读 |

### 3.3 明确不由外部 Agent 直接操作

`packages.configure`（全局包装载）、`object.write`/`checkpoint.fork`（运行内数据动作）、`draft.*`/`consumer.*`（前端草稿层，`draft.save` 已退役）、前端轮询/画布坐标/UI 锁。工作流内 Agent 节点自修改**不在本步范围**（其工具体系只有 `inspect_text`/`final_answer`，没有图编辑工具）。

## 4. 现有缺口（不新增业务代码，接口与 Q11/Q12 不冲突）

| # | 缺口 | 影响 | 当前处置 |
| --- | --- | --- | --- |
| G-1 | 没有修订历史/差异查询（`definition.read(revision=N)` 只能按号猜读） | 回退、对比需要试错 | 记录，属后续能力，不影响完整循环 |
| G-2 | 运行输入没有独立契约查询，只能用 `definition.inputs` 的 `required_for_run`（编译失败时为 `null`） | 失败后需先修编译 | 记录；`definition.preview` 可先给出编译结果 |
| G-3 | 没有结构补丁，`definition.update` 只收完整文档 | 大图每次全量重传 | 设计如此（整文档提交天然支持批量改）；记录成本 |
| G-4 | `request.abandon` 需要先有原请求证据（前端 outbox 协议）；未写证据时返回 `request_arbitration_unavailable` | 纯 Agent 流程无法"终止未知请求" | 记录；Agent 只能用 `receipt.read`（完整原请求）核实 + 同 key 重提来**继续执行/确认结果**，这不是终止；终止需证据（见 §6.6） |
| G-5 | `checkpoint.read` 只有 header；诊断多错只报首个；无时间戳/耗时 | 深入定位受限 | 记录，属后续增强 |
| G-6 | 前端扩展字段接管清单只在浏览器侧 | 画布显示对齐 | 只影响 UI，不影响保存合法性 |
| G-7 | 无远程认证 | 仅本地可信接入 | 未来另议，本步不建 |

## 5. 只读、预演与编辑锁

- **读取、分析和 `definition.preview` 不占编辑锁**：它们不获取每工作流互斥资格（modification gate），只做读快照。
- **只有真正的修改才占锁**：`definition.update`/`definition.copy`/`patch` 通道在写事务前取得该工作流的进程级互斥资格；忙时立即 409 `workflow_modification_busy`，**不排队、不自动重试**。锁在命令事务提交或回滚后释放，不等前端接纳或证据结案。
- 因此 Agent 可以长时间思考/调试而不占住工作流；也不要为了"占住"而提前发写请求。
- 只读范围（不占锁）：`document.contract`、`catalog.node-types`、`platform`、`definition.read/summaries/preview/inputs`、`session.read/actions/summaries`、`run.read`、`output.*`、`receipt.read` 等。

### 6.5 显式关闭（释放 G21 占用）

```json command
{
  "operation": "run.control",
  "parameters": {
    "session_id": "00000000-0000-4000-8000-000000000031",
    "action": "close",
    "expected_revision": 7,
    "idempotency_key": "agent-close-0001"
  }
}
```

`close` 是**显式控制动作**：失败的运行会一直占用 `active_chain_run_id`（G21），调用方必须自己 `run.control(action="close")`；接口不会因为保存被拒、G21 或超时而自动 close。`pause/resume/retry_*` 同样是显式动作。

### 6.6 核实未知结果（只读，不重放）

核实必须传**完整原请求**：`receipt.read.parameters.parameters` 就是首次 `definition.update` 提交时的完整参数（含 `workflow_definition_id`、`expected_edit_sequence`、**完整 `document`**、`idempotency_key`）。实现会用 `validate_parameters(spec, parameters, stored_evidence=True)` 校验这个内层请求；缺任何必填字段（例如漏掉 `document`）都只会得到 `outcome=unresolved`、`reason_code=invalid_request`，无法核实保存结果。

下面的示例与 §6.1 的 `definition.update` 是同一次请求（文档内容也必须一致）：

```json query
{
  "operation": "receipt.read",
  "parameters": {
    "operation": "definition.update",
    "parameters": {
```

**必须与首次提交的原请求内容完全相同（逐字段一致，含 `document` 全文）**，否则无法匹配到回执。回执身份基于规范化 JSON（`application_command_digest`），所以 JSON 键序/空白不影响，但字段、值与 `document` 内容必须一致。

- `outcome=matched`：该请求已接纳，返回正式 `result` 与原始 `receipt`，**不要重放**。
- `outcome=unresolved`（如 `reason_code=invalid_request` 缺字段、`application_identity_missing` 无身份、`receipt_invalid`、`storage_unavailable`）：**只表示本次核实未成功，不能证明该请求未执行，也不能证明它已执行或被取消**；核实本身是只读的、不写任何记录。此时必须显式选择下面两条路之一，二者语义完全不同：
  - **a) 继续执行 / 确认结果**：用**同一原请求 + 同一 key** 重提。这是幂等继续：若此前已执行，返回既有结果并证实；若此前从未执行，这次会**首次执行**该请求。**它不是取消**，也不会撤销任何已发生的执行。
  - **b) 终止请求**：只有在已有该原请求证据（`request-evidence.write` 写入的 pending 行）时，显式调用 `request.abandon` 做事务内仲裁（见下）。没有证据时只能保持"结果未决"。
- **警告**：同 key 重提**不能替代**终止（重提是继续执行，可能真的把请求执行掉）；不得把"同 key 重提"当作终止的替代；不得把 `unresolved` 当作"未执行"或"已取消"的证据；未核实成功前不能向用户报告成功或失败。

若需要**终止**一个明确定义的未知请求（已有原请求证据时）：

```json command
{
  "operation": "request.abandon",
  "parameters": {
    "workflow_definition_id": "00000000-0000-4000-8000-000000000001",
    "target_operation": "definition.update",
    "target_idempotency_key": "agent-edit-0002",
    "target_request_digest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "idempotency_key": "agent-abandon-0001"
  }
}
```

- `target_idempotency_key`/`target_request_digest` 必须来自该原请求的**证据行**：digest 是 `request-evidence.write` 返回的 `request_digest`（原 application 命令 `{"operation": ..., "parameters": ...}` 的规范化 SHA-256），示例中的 64 位占位值必须替换为真实值；`workflow_definition_id` 必须与证据 owner 一致，否则得到 `request_arbitration_unavailable` 或 `request_evidence_conflict`。
- 已有业务回执：返回正式结果，不重新执行。
- 无回执：写入持久终止事实，返回 `outcome=abandoned`；之后同一请求的迟到重放被 409 `request_abandoned` 拒绝，**不会执行**。
- 无原请求证据：`request_arbitration_unavailable`，结果保持未决（不得谎称已取消）。

## 7. 保存与编辑规则

1. **双 CAS**：`expected_edit_sequence` 必须等于当前 `edit_sequence`（否则 409 `stale_edit_sequence`）；文档 `revision` 必须等于当前 fixed 修订（否则 409 `stale_revision`）。旧基线**只会被拒绝**，不会自动覆盖新版本。
2. **互斥**：同一工作流同一时刻只允许一个真实修改；第二个立即 409 `workflow_modification_busy`（不排队）。
3. **G21**：工作流定义下任一持久会话仍有 `active_chain_run_id` 时，任何配置保存都 409 `configuration_run_locked`，诊断带 `occupying_sessions`。先 `run.control close`（或显式归档该会话）才能改。
4. **幂等**：同 key + 同请求重放返回原回执；同 key 不同请求 409 `idempotency_conflict`。
5. **证据**：业务写不强制走 request-evidence；前端 outbox 用它做"未知结果恢复"。外部 Agent 建议每次写生成新 key，并在结果未知时用 `receipt.read` 带**完整原请求**核实（`unresolved` 只是核实未成功，不能证明未执行/已取消）；"同 key 重提"是继续执行而非终止，终止必须显式 `request.abandon`（需原请求证据），语义见 §6.6。
6. **派生**：存在未归档会话且改动含 fixed 类字段时，不确认 → 200 `confirmation_required`、**零写入**；`confirm_derivation=true` → `derived`，返回**新的** `workflow_definition_id`（revision=1、edit_sequence=1）。Agent 必须显式选择，不能假设原地保存。
7. **display-only / unchanged**：只改名称/标题/位置 → `saved` 但只推进 `edit_sequence`、不产生新修订；无实际变化 → `unchanged`。
8. **结构校验**：保存是结构/引用硬约束（含普通边端点存在性、声明引用非悬挂、ACL 一致性）；保存**不编译**，能否运行要用 `definition.preview` 或运行验证。保存后即为正式基线：`definition.read` 读到的最新文档 + `edit_sequence` 是下一次写的唯一基线。

## 8. 运行与控制语义

- `run.start` 是异步启动：202 返回 prepared 会话视图，**不等于运行成功**；最终状态轮询 `session.read`/`run.read`，终态为 `succeeded/failed/archive_failed/recovery_unavailable/closed`。
- 失败会落 `chain.diagnostic`/`node_run.diagnostic`（`code/message/node_id/port_id/edge_id/phase/path/expected/actual`）并可重复读取；准备阶段失败不产生 chain/node_run，**调用方要保留本次错误响应**（`run.start` 的 4xx 就是唯一记录）。
- `close` 必须显式调用；`retry_*` 是显式动作；请求结果未知时**先核实、不自动重放**。
- 只读窄视图：`session.actions` 给 `available_actions`；完整诊断在 `session.read`/`run.read`。
- 真实模型调用：按 Q12 属于"用户启用的调试接入范围"，Agent 可调用已配置好的模型节点；接口不做每次弹窗，但模型配置与工具权限继续生效。**本步交付的隔离测试不调用真实模型**。

## 9. 诊断与契约发现

- `document.contract`（v2）集中提供：GraphDocument JSON Schema（结构）、容量上限、保存语义、诊断字段、错误码目录（`errors` 为**部分覆盖**：覆盖本步 save/compile/prepare/run/settlement/storage 链路实际可达码；notes 声明了边界与扩展方式）。`errors` 不是全集，调用方仍以实际返回的 `reason_code`/`diagnostics` 为准。
- 诊断字段：`code`、`message`、`node_id`、`port_id`、`edge_id`、`dependent_outputs`、`phase`、`path`（RFC 6901 JSON Pointer）、`expected`、`actual`；G21 额外有 `occupying_sessions`。外层错误信封：`{status, code, reason_code, message, diagnostics}`，`DiagnosticError` 下 `reason_code == diagnostics[0].code`。
- `catalog.node-types`（`protocol_version=2`）+ `platform` 是节点/包/数据类型的唯一目录；`document.contract` 不覆盖节点可用性与编译/运行约束。

## 10. 限制

- **工作流内 Agent 自修改不在范围**：本说明是外部 harness 通过本地接口接入；工作流内 `agents.execute` 节点的工具体系没有图编辑工具。
- **G21**：运行未完成（含失败/暂停）期间不能改图；必须先显式关闭/归档。
- **单 pending**：request-evidence 同一 owner 只允许 1 条 pending；`request.abandon` 依赖该证据，纯 Agent 流程可能不可用。
- **读取新鲜度**：`run.read`/`session.read` 无时间戳、无分页、多错只报首个；长会话/大图响应较大。`definition.read` 只能按修订号读历史，无 diff。
- **不保证预演=提交**：预演成功不保证提交或运行成功。
- **网络/服务**：本文假设本地可信 HTTP；远程认证未来另议；本步未启停服务，示例均用隔离测试库验证。
- **真实模型**：按 Q12 属用户启用调试范围，接入说明明确即可；本步验收不实际消耗模型。
