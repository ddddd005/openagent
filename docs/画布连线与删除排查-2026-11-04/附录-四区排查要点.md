## A 区：取消 / 断开连线的交互与状态机

### A.1 `<VueFlow>` 配置逐项

| 配置 | 实际值 | 对取消路径的影响 |
| --- | --- | --- |
| `:delete-key-code="null"` | 显式 `null` | 正确禁用 Vue Flow 内置删边（`useKeyPress(null)` 恒不触发），删边只剩应用自己的入口，避免两套删除分叉 |
| `connect-on-click` | **未设置 → 默认 `true`** | 允许“点一下 handle 就开始连线”的隐性模式；应用未订阅 `clickConnectStart/clickConnectEnd`，形成不可见 pending |
| `:connection-radius="28"` | 28（默认 20） | 只影响拖拽**目标端**的吸附，不影响起点身份；句柄坐标缓存失真时会放大误吸附 |
| `:is-valid-connection="validConnection"` | 函数 | 拖拽中写 `connectionMessage`；对“已存在边”直接放行以保留显示 |
| `:nodes-connectable` | `!graph.editorLocked` | 锁定态同时禁用拖拽与点击起线 |
| 其它默认 | `connectionMode=Loose`、`edgesUpdatable=false` | 任意 handle 可互连，端口角色只靠应用层 `graphConnectionIssue` 拒绝；无重连手柄 |

### A.2 应用侧状态

```ts
const connecting = ref<OnConnectStartParams | null>(null), connectionMessage = ref("");
onConnectStart(...) { connecting = start; connectionMessage = "" }
onConnectEnd(...)   { connecting = null }              // 消息不清
onConnect(c)        { graph.connect(...); if (accepted) connectionMessage = "" }
```

| 时机 | Vue Flow 行为 | 应用状态 |
| --- | --- | --- |
| handle mousedown | `startConnection` + `connectStart` | `connecting=start`，消息清空 |
| 拖拽移动 | 调 `validConnection` | 写消息、端口描边（依赖 `connecting`） |
| mouseup | 合法发 `connect` → `connectEnd` → `endConnection` | `connecting=null`；消息**不清** |
| handle click（单击） | `connectOnClick` 且无 pending → `clickConnectStart` + `startConnection(..., true)` 设 `connectionClickStartHandle`；**不发 `connectStart`、不画线** | **应用零变化** |
| 再点另一个 handle | 合法 `connect`、非法丢弃 → `clickConnectEnd` + `endConnection(..., true)` | 合法走 onConnect；非法**零反馈** |
| Esc | Vue Flow **无** Escape 取消 | 应用只 `menu.close(); selectNodes([])` |
| 点空白 | pane onClick 只对 `connectionStartHandle` 早退；不清 `connectionClickStartHandle` | 只清选择 |
| 点节点 / 点边 | 发 nodeClick / edgeClick | 只改选择 |
| 切换工作流 | 组件按 `:key` 重建、store 重建 | 唯一“清干净”的路径 |

### A.3 三条取消路径

| 路径 | 拖拽 | 点击连线 | 判定 |
| --- | --- | --- | --- |
| 点空白 | 不适用（mouseup 才是结束） | 不清 pending | ❌ |
| Esc | 无效 | 无效 | ❌ 完全缺失 |
| 点另一个 handle | 语义是“完成” | 唯一能清 pending，但会建边 | ⚠️ 语义错误 |

补充：拖拽唯一真实“取消”是**松开鼠标**（Vue Flow 的 `onPointerUp` 无条件 `connectEnd` + `endConnection`），不会残留连接状态；但会残留 `connectionMessage`。

### A.4 缺陷清单

| # | 判定 | 缺陷 |
| --- | --- | --- |
| A-D1 | ❌ | 无任何显式取消连线入口（按钮/命令/右键/提示）；Esc 不取消 |
| A-D2 | ❌ | connect-on-click 默认开启且应用未订阅 clickConnect* → 不可见 pending |
| A-D3 | ❌ | pending 不被 pane click / node click / Esc 清除；只有第二次 handle click |
| A-D4 | ❌ | `connectionMessage` 取消/失败/结束都不清，无超时无关闭 |
| A-D5 | ❌ | 点击连线非法完成零反馈 |
| A-D6 | ⚠️ | Loose 模式 + 所有 handle 可作起点，端口角色错误被应用层以误导文案拒绝 |
| A-D7 | ⚠️ | 删边只有键盘（依赖焦点）与垃圾桶；`keyboard()` 未排除 button/a，焦点在按钮上按 Backspace 会误删 |
| A-D8 | ❌ | 无 replace/reconnect/断开单 handle；`multiple=false` 只能先删整条边 |
| A-D9 | ⚠️ | undo/redo、删除失败不清理 `selectedEdgeId/selectedNodeIds` |
| A-D10 | ⚠️ | `GraphWorkbench` 无交互级测试 |
| A-S1 | ✅ | 拖拽 mouseup 必结束，无状态残留 |
| A-S2 | ✅ | `delete-key-code=null` 正确禁用内置删边 |
| A-S3 | ✅ | 键盘 Delete 与垃圾桶走同一个 `removeSelection` |
| A-S4 | ✅ | 切换工作流清空连接状态与消息 |

### A.5 与画错线的边界

连接身份链（DOM `data-handleid` → `onConnect` → `store.connect`）**不读坐标缓存**，所以 A 区不存在“把 receipts 存成 result”的路径；锚点错误属 C 区。A 区的贡献是：错误观感出现后无法取消，且隐性 pending 让“下一次点击从哪个 handle 开始”不可解释。

## B 区：删除节点的文档变更顺序

### B.1 `removeSelection()` 顺序表

| 步骤 | 过滤依据 | 说明 |
| --- | --- | --- |
| `nodes` | `selectedNodeIds` | 先删节点 |
| `edges` | 引用被删节点 或 `edge_id === selectedEdgeId` | 与选中边合并处理 |
| `control_edges` | 同 `edges` 规则 | |
| `event_bindings` | 仅 `ids` | 先删目标再丢空绑定；只保留非空目标 |
| `object_bindings` | 仅 `ids` | 先删 owner/registrar 失配绑定，再清 ACL |
| `session_preloads` | 过滤后 bindings 的 `object_key` | **唯一跨步骤依赖，方向正确** |
| 选择清理 | `editable()` 返回真才清 | 失败/锁定/无变化时残留 |

### B.2 `editable()` → `edit()` 顺序

1. `entry` 不存在或 `canEdit=false` → 静默返回 `null`
2. clone 文档
3. `change()`；签名无变化 → 静默 `null`
4. **只有 schema 2** 才同步 `isGraphDocument`
5. 会话稳定性门槛（prepared/running/pausing/paused 时拒绝）
6. `acceptDraft(...)`：配置应用已安装时**异步提交、立即返回**（本地文档不变）

### B.3 顺序敏感性结论

- 文档层：单次 clone 内顺序正确，整体替换，无中间可渲染态。
- 真正的顺序风险在**跨请求**：唯一危险是“先删节点保存、后删普通边”（静默悬挂）；安全是“同批级联”或“先边后节点”。

### B.4 操作对连线的影响

| 操作 | 影响 |
| --- | --- |
| `duplicateSelection` | 只复制两端都在选区内的边，新 edge_id；config 引用重映射；私有对象换新 key |
| `replaceNode` | 保留原 node id，重置 config；**旧边一律保留**（注释：never guess port mappings）→ 可能留下端口不存在/类型不兼容的边 |
| `undo/redo` | 整份快照恢复（节点与边 id/顺序一致）；配置模式下是异步提交，不是本地回滚；不修剪选中 |
| `reorderEdge` | 只改同一 target+port 兄弟边的 `order`，不动结构 |

### B.5 缺陷清单

| # | 缺陷 |
| --- | --- |
| B-D1 | 乐观成功 + 异步落盘；失败只弹无字段定位通知 |
| B-D2 | schema 3 同步校验缺失；整单失败会把无关脏数据算进来 |
| B-D3 | 选中清理与失败判定不一致；失败/锁定/无变化时残留 |
| B-D4 | 删除不清理 `config_node_references` 与 object_access `object_key(s)` |
| B-D5 | 前端 schema 不校验普通数据边端点存在（对照 control_edges 校验） |
| B-D6 | 文档整体替换不修剪选中（undo/redo/外部接纳/刷新） |
| B-D7 | 在途保存窗口内操作被静默吞掉（`canEdit` 含 submitting/locked，无提示） |
| B-D8 | 双选择器并集：`addNode`/`locate` 只设节点不清边，删除会连带删无关边 |
| B-D9 | `replaceNode` 保留旧边且保存不阻塞 |
| B-D10 | `removeSelection` 不调用 `prepareGraphEdit`（旧格式文档只做部分清理） |
| B-D11 | 删除路径缺生产分支测试（多为无配置应用的 schema 2 fixture） |

## C 区：句柄坐标缓存与端口行来源

> 本区修复由另一 agent 执行；此处保留机制与证据，供验收与回归使用。

### C.1 端口行来源链

```
GraphWorkbench.nodes computed
  data.inputs  = edges.filter(target_node_id===node).map(target_port_id)
  data.outputs = edges.filter(source_node_id===node).map(source_port_id)
        ↓
GraphCanvasNode.ports(direction)
  known = nodePorts(definition, node, direction)      // 目录/模式声明
  extras = data[direction] 里不在 known 的端口（data_type="?"，仅由边推导）
  行 = [...known, ...extras]，:key=port_id，Handle :id=port_id
        ↓
Vue Flow handleBounds（Handle.onMounted 登记 / updateNodeDimensions 重算）
```

### C.2 首帧时序与失真条件

1. `activate()`：先 `ensureDefinitionEntry`（装文档）→ 再 `loadCatalog()`（取目录）。首帧节点**没有 definition**。
2. 首帧 Agent 节点：输入列由 3 条入边得到 3 行；输出列只有 `receipts` 一条出边 → **1 行**（`result` 尚未出现）。
3. 目录到达：输出列变 `[result, receipts]`；Vue 按 `:key=port_id` **复用 receipts 的 Handle 实例**（挪到第二行），`onMounted` 不再执行 → 不重新登记坐标；新出现的 `result` Handle 才在第一行登记。
4. 节点高度由**输入列**决定（3 行更高），输出列 1→2 行**不改变节点总高度** → Vue Flow 的 `updateNodeDimensions` 因 `dimensions` 未变而跳过重算（`doUpdate` 条件）。
5. 结果：`handleBounds` 里 `receipts` 的 y 仍等于第一行 → 画线/起线都落在现在 `result` 的位置。

### C.3 需要区分两种时序

| 时序 | 端口行是否变化 | 是否会产生陈旧坐标 |
| --- | --- | --- |
| 首帧（目录晚于文档） | 是（定义缺失→到达） | **会**（本案例） |
| in-session（目录已加载） | 声明端口稳定，删边不会减少声明行；仅 `replaceNode` 改类型/版本或目录外端口时可能变 | 若行数变且节点高度不变（另一列更高）仍可能；一般会随尺寸变化重测 |
| 切换工作流 | VueFlow 按 `:key` 重建 | 重建后回到首帧语义 |
| 删除节点 | 被删节点消失；其他节点端口不变（声明列稳定） | 通常不会；但 pending 连接状态不受文档替换影响（见 A/B 交界） |

### C.4 Vue Flow 内部依据

| 主题 | 位置（`frontend/node_modules/@vue-flow/core/dist/vue-flow-core.mjs`） |
| --- | --- |
| 句柄重算条件（宽高变化或 forceUpdate） | 6300-6330（`doUpdate` 在 6321） |
| Handle.onMounted 自登记坐标 | 7012-7035 |
| 按 `data-handleid` 收集句柄 | 4665-4685 |
| 边端点按 id 取坐标 | 4293-4298、8898-8911 |
| ConnectionLine 按 id 取起点 | 9097-9145 |
| click-connect 起线（position 存 Top、id 来自 DOM） | 5396-5413 |
| 点击连线完成/作废 | 5415-5454 |

### C.5 可用 API 与修复方案对比

- 库**不导出** `useUpdateNodeInternals`；正确入口是 `useVueFlow().updateNodeInternals(nodeIds?: string[])`（`store.d.ts` 276，注释即“若句柄边界不正确就用它”），以及组件事件 `@update-node-internals`。

| 方案 | 覆盖 | 风险 |
| --- | --- | --- |
| A. `GraphCanvasNode` 内 watch 端口列表/标签 → `nextTick` 调 `updateNodeInternals([nodeId])` | 首帧 + in-session 端口变化 + replaceNode | 每次端口变化触发一次尺寸重测；节点很多时需合并 |
| B. `GraphWorkbench` watch `graph.catalog` 加载完成后对全部节点强制重算 | 首帧为主 | 全量重测成本；目录刷新时重复触发 |
| C. `activate()` 先 `loadCatalog()` 再装文档 | 只覆盖首帧 | 首屏变慢；不覆盖 replaceNode/端口变化 |
| D. 让回退端口不参与布局或固定首行顺序 | 部分 | 只绕过特定组合，不能根治 |

推荐：A（根治）＋ B（兜底首帧）；C 可顺带做但不作为唯一手段。

### C.6 复现/验证

1. 保存一条 `receipts → receipts` 边后刷新页面；
2. 点击 Agent 节点 `receipts` 句柄：连接线应从 `receipts` 行起；
3. 保存的边应画在 `receipts` 行；
4. 若条件允许，在 devtools 中观察 `.vue-flow__handle` 的 `data-handleid` 与节点高度变化（可选）。

## D 区：保存 / 重载 / 删除顺序的后端契约

### D.1 保存路径顺序（22 步摘要）

1. HTTP `POST /api/graph/definitions/update` → 应用命令 `definition.update`（先算 receipt digest，再派发）。
2. `_save_configuration_update`：
   - UUID/edit_sequence 形状 → `validate_graph_document` → schema 3 → `validate_session_item_registrations` → `validate_session_preloads` → identity → edit_sequence 相关字段 → 归档/管理挂起 → 未完成 run 锁 → current edit_sequence → legacy 拒绝 → `effective` 计算 → 逐节点 `validate_node_configuration` → 修订号 → `previous` 重组成视图 → 分类 display/adjustable/fixed → （有 effective 且 fixed 且未确认 → 返回 `confirmation_required` 不写）→ 修改/派生/不写 → `save_fixed_revision`（fixed 时）→ `_write_configuration` → 重读 actual 返回。
3. `save_fixed_revision`：再校验一次 → 期望修订检查 → 逐节点 `node_binding` → `workflow_definition_revision`（bindings + edges + document）。
4. `atomic`：`BEGIN IMMEDIATE` → 幂等回执查询/重放 → change → `_validate_changes` → 写回执 → `COMMIT`；任何异常 `ROLLBACK`。
5. 保存路径**不写** request evidence（由前端提交前单独写入并在成功后 resolve）。

### D.2 校验边界（保存 vs 编译）

| 校验项 | 保存时 | 编译时（run.start / `definition.inputs`） |
| --- | --- | --- |
| 字段形状/UUID/order | ✅ | — |
| control_edges / event_bindings / object_bindings / session_preloads 引用存在 | ✅ 硬拒 | — |
| 普通数据边端点存在 | ❌ 不校验 | `graph_missing_node` |
| 必需输入齐全 | ❌ | `graph_required_input_missing` |
| 端口声明/类型/单端口多边/order 冲突/环 | ❌ | 对应 `graph_unknown_port` / `graph_type_mismatch` / `graph_input_cardinality` / `graph_input_order_conflict` / `graph_dependency_cycle` |
| `config_node_references` 目标存在/类型 | ❌ | `graph_missing_config_reference` / `graph_config_reference_type_mismatch` |

### D.3 删除在后端的硬/软要求

**硬（违反即 400/409，整单回滚）**

1. control_edges 两端必须存在。
2. `event_bindings.target_node_ids` 非空且都存在。
3. `object_bindings` 的非空 owner/registrar/readers/writers 都存在；provider 的 registrar 绑定必须保留。
4. `session_preloads` 必须能匹配到精确 object_binding。
5. `expected_edit_sequence` 与 `document.revision` 必须匹配当前；有 effective session 时 fixed 变更要二次确认（并会派生新 workflow id）。

**软（静默接纳，留下隐患）**

6. 删节点必须同时删普通数据边（唯一会静默悬挂的引用）。
7. 单端口 order 建议 0..n-1 唯一（前端已维护）。
8. 保存前可调用 `definition.inputs` 取编译诊断，但后端不强制。

### D.5 缺陷/风险清单

| # | 风险 |
| --- | --- |
| D-R1 | 普通边端点不校验 → 前端偶发疏漏会被静默固化并跨修订存活 |
| D-R2 | 保存不编译 → 不可运行图可保存、可建会话，一跑才 400 |
| D-R3 | order/重复边不校验 → 运行期才报 |
| D-R4 | 读路径不提示悬挂边（编辑器/目录都看不到坏边） |
| D-R5 | `confirmation_required` 返回的是**提交文档**而非当前文档（前端需识别 outcome 并忽略 document） |
| D-R6 | 当前视图依赖定义契约存在（`graph_missing_node_type`），包/契约变化会影响首屏重载 |

### D.6 后端契约对前端的接口结论

- 后端文档里**只有 nodes 与 edges**（端口以 `source_port_id/target_port_id` 出现在边上），没有端口行/句柄/坐标概念；编辑器把边归到哪个端口只取决于边的端口 id。
- 因此“保存进库的边正确 → 后端不会把线指向 result”；指向错误只能是前端“句柄 id ↔ 端口 id ↔ 坐标”的映射问题。
- 删除的正确顺序要求：**同一份提交内级联闭环**；若必须拆单，顺序为“先边与引用、后节点”，绝不可“先节点、后边”。

## 附：四区交叉结论

1. **保存正确性 ≠ 画布正确性**：身份链（存哪个端口）与锚点链（画在哪）是两条独立链路，本次故障只在后者。
2. **“取消不掉”与“画错锚点”会互相放大**：锚点错使点击起点看起来是 result；pending 点击连线又让下一次点击的起点不可解释；且没有替换机制，只能删整条边重来。
3. **删除本身是原子的**：这次不是删除顺序造成的；但删除的“提交与选择”顺序确有真实缺陷，会让操作表现为时好时坏。
4. **后端是保真但宽松的**：不编译、不查普通边端点，会把前端偶发疏漏固化为正式修订——建议补硬校验 + 非阻断诊断，同时保留“草稿可保存不完整”的语义。
