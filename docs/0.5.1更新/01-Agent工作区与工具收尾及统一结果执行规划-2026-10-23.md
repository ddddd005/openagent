## 1. 目标与已确认决定

本期目标是让 Agent 在一次调用期间加载和持续使用有运行中数据的工具；模型完成后，由程序收尾工作区，并将模型内容与工具导出内容组合为节点的最终结果。

首个目标工具是地图工具。它承载位置、设定、NPC 和角色状态、行为链等内容；模型通过命令查看地点、移动对象、构建正式移动命令。工具可以运行在另一个进程中，同一次 Agent 调用内的多条命令需要访问同一个运行实例。

| 事项 | 用户已确认方向 |
| --- | --- |
| 数据生命周期 | 每次调用从数据层加载，工作区持有本次运行态；持久业务数据由数据层保存 |
| 模型结束 | 有效 `final_answer` 结束模型循环，后续由程序继续收尾 |
| 工具保存 | 工具接到程序的正常结束命令后，按自己的逻辑读取、提交和保存数据 |
| 节点结束 | 工作区正常收尾、结果组装和关闭完成后，结束节点调用 |
| 输出 | 模型提供的内容与工作区导出内容合并到现有 `result`，暂不增加对外输出端口 |
| 模型报错或用户终止 | 停止执行，不对未完成运行态执行正常结束保存；仍需释放本次资源 |
| 上下文与地图数据 | 不要求同一次提交，工具自行负责数据存取；上下文沿用现有职责 |
| 历史回合 | 依托检查点返回历史回合；工具数据是否已被采集和正确恢复必须验证 |

本期不建设统一业务提交事务、跨工具原子提交或自动补偿机制。已有工具按次提交的数据不会因为新工作区机制自动撤销。工具自行保存仍应通过所属领域的数据层接口，不表示获得任意 SQL、文件路径或跨会话访问权限。

## 3. 职责划分

以下为已讨论方向的实施拆解。准确方法名、参数、配置载体和记录格式在 P0 确认。

| 承载 | 职责 |
| --- | --- |
| Agent 内核 | 驱动模型循环、校验命令、生成调用身份、接收工具返回；有效 final 后停止模型调用 |
| Agent 执行器 | 装配本次工作区和工具；协调正常收尾、合成结果与节点返回；保持原始执行记录 |
| 工作区 | 持有本次加载的能力实例及进程句柄，路由调用，按确定顺序通知正常结束并关闭资源 |
| 工具能力 | 地图业务、进程通信、运行态、对模型的查询结果、正常收尾导出及通过数据层自行保存 |
| 数据层 | 根据工具所属领域的权限、类型和写入规则接纳持久数据 |
| 上下文与检查点模块 | 保持原始消息来源；按现有职责保存上下文、采集及恢复已准入工具数据 |

首版围绕一个地图能力及明确的加载、收尾顺序完成闭环。工作区先承载本次调用的能力生命周期，任意现有图节点直接进入工作区执行不属于已确认契约。

工具给模型的逐次返回、给最终结果的导出内容、需要持久化的数据可以不同。实施时由工具明确提供哪些内容参与最终合成，不能把全部持久状态自动拼入 `result`。

## 4. 执行路径

### 4.1 正常路径

```text
按本次固定依据准备工作区及工具声明
    -> 初始化 Agent 执行器和本次工作区
    -> 工具经数据层加载数据，取得本次地图进程实例
    -> 装配模型、上下文、提示词和可调用工具
    -> 模型连续调用，工作区路由至同一个工具实例
    -> 有效 final_answer：结束模型循环，保留原始 final
    -> 程序按顺序通知工作区能力正常收尾
    -> 工具按自身协议完成导出和保存
    -> 程序合成模型内容与工作区导出内容
    -> 关闭工作区，返回现有 result 及执行回执
    -> 沿用后续图层结果校验、接纳和上下文保存流程
```

准备工具声明与执行业务加载应分开：准备阶段核对声明、准确来源和依赖；取得业务数据及进程资源放在实际调用生命周期中。

本方案不要求等待图层提交节点结果后再保存工具，因此不增加图层提交后的工作区保存确认机制。关闭与工具保存的具体实现仍需核对现有释放路径，避免正常关闭和 `dispose()` 重复操作同一个进程。

### 4.2 结果及来源

概念上，节点结果调整为：

```text
result = 合成（模型提供的内容，工作区正常收尾导出的内容）
```

现有 `result` 类型为 `TEXT@2`，本期先维持这一内容出口。段落、命令文本等准确合成格式在 P0 确认，不在本规划中新增端口或固定 JSON 封套。

模型原始 final、真实工具调用和返回继续作为原始执行证据。程序合成的内容不能伪装成模型生成的消息。合成结果是否追加到下一轮模型上下文尚未确认；实施前先核对事实、回执、上下文及显示消费者，不能只替换文本后就宣称整条链路完成。

### 4.3 异常、终止与既有接纳再入

| 情形 | 必须保持的边界 |
| --- | --- |
| 工作区加载失败 | 给出具体失败阶段，释放已取得的本次资源，不带着缺失能力继续正常运行 |
| 模型报错或用户终止，尚未进入正常收尾 | 停止模型和工作区执行，不发送正常结束保存命令，清理本次资源 |
| 终止发生在工具提交前后 | 停止不等于撤销已经提交的数据；进程停止及提交状态必须据实际结果报告 |
| 工具导出或保存失败 | 明确失败工具、阶段和已知提交事实；不自动重跑模型或工具，不伪称最终结果已成功完成 |
| 工具已保存，随后合成、关闭或图层接纳失败 | 保留已保存事实；不能将节点失败描述为所有工具数据均已回滚 |
| 既有结果接纳再次进入执行器 | 复用本次已完成的收尾产物，不能再次调用工具保存或重跑模型 |
| 既有同进程暂停 | 与用户终止分别核对，不能误触发正常保存；若接入需要改变控制契约，先报告并确认 |

这里的“收尾一次”指一次调用的正常完成逻辑不会因既有结果接纳再入而重复执行业务保存，不承诺进程崩溃后具备通用的恰好一次提交机制。

多工具收尾失败后的后续执行、释放失败的错误表达，以及提交期间终止的交互细节属于 P0 待确认项。本文不预设继续保存、自动重试、超时强杀或补偿回滚策略。

## 5. 分步实施规划

各步骤当前均为未实施。以下是建议顺序，P0 收口后再按确认范围进入代码施工。

| 步骤 | 工作内容 | 交付及结束条件 |
| --- | --- | --- |
| P0：局部契约确认 | 确认工作区配置来源、能力声明、工具实例取得方式、进程协议、收尾顺序、导出与合成格式；检查数据准入、原始事实和版本影响 | 形成局部契约及准确改动文件清单；已定方向不重开，未定字段不以示例代替决定 |
| P1：工作区与调用接入 | 建立一次调用的工作区持有关系；增加工作区工具准备和调用路径；复用准确包来源、调用身份及参数校验；连续调用使用同一实例 | 用离线工具和受控进程样例证明加载一次、多次调用共享运行态、隔离不同调用；不产生逐地图命令修改内核的分支 |
| P2：正常收尾与统一结果 | 内核 final 后进入程序收尾；工具自行保存并导出；合成现有 `result`；处理正常关闭、异常释放及结果接纳再入 | final 后无新增模型调用；保存和导出不重复；原始 final 可重读；合成结果经正式节点结果路径消费 |
| P3：地图目标接入 | 按真实工具协议接入地图进程、数据读取及保存；验证地点查询、移动、正式命令导出和下一次调用重载 | 完成地图代表链路；明确实际工具版本、配置和数据类型。若真实工具尚未提供，只记录样例验证，不能报告地图产品已接入 |
| P4：检查点与联合验收 | 将工具保存的数据纳入准确检查点路径；验证历史回合恢复；执行相邻回归并更新开发及包使用文档 | 原会话不被恢复操作覆盖；目标会话加载所选回合工具数据；交付实现回执、实际测试结果和剩余限制 |

实现规模按中等评估，主要成本在工作区持有关系、收尾与既有接纳路径的衔接、进程退出及数据历史一致性。真实地图协议和数据形状未确认前，不给出固定人日承诺。

### 5.2 检查点接入要求

1. 先确定地图持久状态的准确类型、会话归属和对象绑定，再判断现有普通预加载对象采集路径是否已经适用。
2. 单独设置 `checkpoint_admission=True` 不代表所有工具数据会自动采集；收集与恢复两端都要有证据。
3. 保存到数据层之外的进程本地文件不能直接宣称受现有检查点保护；如真实工具依赖此类内容，先报告缺口及需要确认的接入范围。
4. 验证至少两个成功回合的差异：恢复较早检查点后，地点内容、角色及 NPC 位置、行为链均与所选回合一致。
5. 沿用现有恢复到独立目标会话的语义，不把历史回合恢复实施为覆盖原会话业务数据。
6. 工具自行保存与检查点保存分开记录事实；没有完成 P4 前，只能报告保存链路完成，不能报告历史回合恢复完成。
