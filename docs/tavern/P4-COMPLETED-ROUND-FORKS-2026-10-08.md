## 1. 范围与身份

- 唯一新增聊天历史操作是从实际完成检查点分叉到新会话；不做当前会话回退、候选选择、消息编辑/删除或有效上下文编辑。
- 复用平台 `list_graph_candidates / fork_graph_candidate` 和已有检查点、对象继承、历史、CAS、事务与幂等机制。
- 酒馆节点和数据契约仍为 `workflow.tavern@1.2.0`。新增能力是消费者应用操作，不新增或改写节点版本；页面依据应用目录检查支持，不向旧宿主偷偷调用管理接口。
- 首版消费者只接同一工作流身份内的检查点，包括旧定义版本与继承的祖先回合。跨工作流身份的历史目标继续仅由管理端处理；不增加多工作流请求日志迁移。
- ST 模板、交互、适配和来源清单仍在酒馆包内。公共客户端只补明确的分叉契约、原请求保护和实际子会话接纳。

## 2. 受限协议

- `consumer.candidate.list` 使用精确父会话、工作流身份和定义版本，提供可用完成检查点及当前 CAS 依据，不导出私有对象/上下文正文。
- `consumer.candidate.fork` 使用父会话、候选 ID、会话/数据/head revision 和原幂等键。拒绝不稳定、不可用或范围外目标，不公开管理候选选择。
- 成功操作回执关联实际子会话及父会话/候选/完成运行/目标定义版本。子采用检查点上的定义、对象与历史，不混入父会话后续状态。
- 原请求结果未知时保留原 body/key 和父身份；重开和核实只读持久回执，不重发 fork，不创建第二个子会话。

候选响应严格为 `workflow.consumer-candidates@1`：父工作流/定义版本/会话/会话 revision，加 `data_revision / head_revision / status / can_fork / candidates`。活动或不可用会话的候选列表为空；暂停在途时与消费者统一显示 `pausing`。每个候选只有 `candidate_id / chain_run_id / source_session_id / source_workflow_definition_id / source_definition_revision`。

分叉使用现有命令信封，只接受 `session_id / candidate_id / expected_revision / expected_data_revision / expected_head_revision / idempotency_key`，不丢弃多余字段后计算 digest。成功结果为 `workflow.consumer.receipt@1`，基础回执加 `fork_source`，同时提供实际子消费者观察。`fork_source` 包含父会话、候选、完成 chain、目标工作流和定义版本。冻结的接纳回执为新子 `session_revision=1 / status=succeeded / chain_run_id=null`；成功状态来自继承的完成运行，不表示分叉调用了模型。

只读核实结果仅为 `{receipt}`，不携带新消费者或私有状态。读取在只读 SQLite 事务内证明 native 回执、独立应用请求身份、完成 commit、源 snapshot、实际子会话与 seed/初始 snapshot 的对应关系，不初始化 Runtime、不创建缺失数据库。管理端或直接 native 的同键回执不能代替消费者请求来源；已接纳消费者原请求则可在父子后来变更后核实或重放，不创建第二个子会话。

## 3. 酒馆交互

- 通过每条实际 `TEXT@2` 产物的 producer 关联完成运行，不把累计展示节点的最近 run 当成所有旧消息的来源。
- 同一完成回合的用户与多个 Agent 展示条目关联同一检查点，不按消息索引截断。
- 只对实际可用目标提供分叉，确认明确回合边界，接纳后按真实子身份加载。
- 原请求待核实期间禁止新修改及会话切换；迟到查询/回执不能覆盖当前身份或清除未知请求。
- 接纳后的浏览器存储失败保留父会话和原请求归属，后续只能通过真实回执恢复子会话。候选目录失效或不在当前消费者完成历史中时不能发出新分叉。
