## 1. 结论（三问三答）

### Q1 前端编辑与后端异步同步是否带来逻辑冗杂？

**是。** 且冗杂的核心不是"画布乐观状态"，而是"把每一次画布微编辑当成一次需要可恢复的持久化命令"。

置信度：**高**（代码路径 + 数据库实测 + 5 个独立分区交叉一致）。若被推翻，最可能是"用户所指的异步层不是当前生产路径这一层"（见 §3）。

### Q2 主要是哪里产生的？

按贡献排序（详细证据见主报告 §3、附录 A–E）：

1. **原请求证据 / 幂等 / 回执核实 / 恢复层**：单次编辑 5 个串行 HTTP、≈6 行/≈28 KB 永久数据、2 次"返回该 owner 全部历史证据"的读取；同一状态机前端独立实现 4 遍；约 3,300 行实现 + 4,232 行测试。
2. **多副本仲裁**：约 10 份前端"真相"（document / saved_document / saved_revision / latest_published / 旧 pending / history / accepted Map / channel 状态 / workspace 目录行 / 组件草稿）+ 7 类后端记录；一次 `connect` 要维护约 30 个状态槽位，一半只为"请求在途/证据/重放"存在。
3. **整份文档 PUT + 客户端重实现服务端语义**：每次编辑整篇上传/下载；后端同一文档校验 4 次、前端回执校验 4 次；`isGraphConfigurationResult` 把服务端保存语义再写一遍（约 50 行）。
4. **双版本号 + display/adjustable/fixed 分类 + 派生确认**：因为"编辑可能发生在有会话/运行时"而存在；开发库 103 次保存里 59 次只改展示、不产生修订；派生/确认分支 0 次触发。
5. **在途门锁与静默丢弃**：保存窗口内后续编辑被 `canEdit` 拒绝后 `return null`，无提示、无队列。
6. **历史遗留叠加**：已退役的 `saveWorkflow`/`workbenchPersistence`/`localDraft.save`、只删不写的 `session_document`、生产只写 null 的旧 `entries.pending`、schema 1/2 升级分支。

成因链：改一下就存 → 每次微编辑成为整图持久化命令 → 浏览器无法判定是否生效 → 写前留证 + 只读核实 → 幂等/身份/回执/接纳仲裁 → 有会话时拆分固定修订与覆盖层 → 前端可编辑副本需要仲裁与投影。每层单独合理，叠加成"一次 1 条边的编辑 = 5 请求 / 6 行 28 KB / 30 个状态槽 / 两次全历史读取"。

置信度：**高**。

### Q3 假如卸除，会不会对整个运行产生优化？

分层结论：

| 层 | 结论 | 置信度 |
|---|---|---|
| 执行循环（prepare/compile/execute/settle） | **几乎没有收益**。运行请求不带前端文档；prepare 读 1 篇固定修订 + 1 行当前配置、执行期再读同一篇再编译一次；证据/幂等表不在运行读路径 | 高（代码） |
| 运行入口（run.start / run.control / session.create / event.submit） | **有收益**。这些命令也走管理原请求证据通道，一次约 6 次证据调用；首次运行还会先 createSession（两轮） | 高（代码）；本库未观察到该通道的 run.start 记录，属潜在成本 |
| "编辑→可运行"路径 | **有收益**。保存事务与运行准备抢同一把 SQLite 写锁与服务 `RLock`；保存越重窗口越长 | 中高（代码）；未做运行时计时 |
| 数据/库容 | **有收益**。证据+幂等占开发库 67%，每次编辑 +28 KB 永不清理；证据读随编辑次数线性增长、累计 O(n²) | 高（实测） |
| 运行正确性 | **不依赖该层**。真正依赖：会话固定修订绑定、G21 运行期禁写、prepare 冻结节点配置、`expected_revision` CAS、运行 basis 冻结（全在后端） | 高（代码） |

附带发现：业务保存已成功、仅证据结案失败时，配置通道 `locked` 仍挡住运行——纯损失，可独立修。

## 4. 方法与流程（可复核）

1. 主代理先读装配与保存主链（`App.vue` → `useWorkflowFrontendHost` → `workflowGraph` → `workflowEditing` → `workflowConfiguration`），确认生产路径分支。
2. 5 个只读子代理分区并行：
   - A 保存流水线与每编辑请求数（`save-pipeline`）
   - B 原请求证据/幂等/恢复层（`save-reload-contract`）
   - C 后端 `definition.update` 写放大与锁（`save-backend-cost`）
   - D 运行路径依赖判定（`run-path`）
   - E 重复状态/重复校验账本（`node-delete-order`）
3. 主代理交叉复核：直接读关键函数（`acceptDraft`/`submitConfigurationDocument`/`submit`/`_save_configuration_update`/`_prepare_run`/`request_evidence.read`/`resourceOutbox`/`management requests`），并用只读 sqlite 独立取数（行数、均值、库容、owner 分布）。
4. 三份报告中的数字互相校对；不一致处以主代理直读代码为准。
5. 子代理只读合规：5 个成员均未修改任何文件（本轮 diff 增量已核对到另一位 agent 的改动来源）；只读 DB 查询未造成 mtime/size 变化。

## 5. 不能当结论的部分（未确认边界）

1. **未做运行时测量**：保存端到端延迟、锁持有时间、Vue Flow 在保存失败后的视觉回退，均未实测；49.4 ms / 80.9 ms 是纯解析实测下界，不含 HTTP/SQLite 提交。
2. **回执丢失/半截请求的真实发生率无法测**：无日志；发生过的 pending 会永久留存，开发库为 0 不能证明从未发生。
3. **多客户端并发写同一工作流是否有真实需求**：未找到产品侧证据。
4. **开发库 0 session**：`derived`/`confirmation_required` 分支只有代码证据，无本机执行证据。
5. **仓库外是否有客户端直接 POST `/api/graph/definitions/update`**：无法排除（路由仍存在）。
6. **工作台是否真的从管理证据通道发起 run.start**：代码路径存在，但本库 `pending_commands` 无 run.start 记录，所以运行入口的 6 次证据调用是"代码可证的潜在成本"，不是本库实测。
7. **`_settle_node_result` 用固定修订文档 config 算端口、而执行用 prepare 冻结的 current config**：可调字段影响端口时二者是否可能不一致，未验证。
8. **削减各方案的实际 diff 大小与测试改造量**：只给了量级估算（例如前端 250–320 行），不是逐文件 diff。
9. **用户所指"异步"的版本**：若指更早的本地草稿模型（git 初始提交 `00970f7` 曾同步 `persist()`，`c8af63e` 改为 fire-and-forget），需要用户确认；本报告只对当前工作树成立。
