## B 区：原请求证据 / 幂等 / 恢复层

### B.1 机制

写业务命令前先把 `{operation, idempotency_key, owner_kind, owner_id, request, request_digest}` 存入 `pending_commands`（同 owner 仅一条 pending，部分唯一索引）；业务完成后 `resolve` 置 verified；结果未知时刷新后按坐标找回，仅只读核实回执、**绝不重发**；接纳结果后再结案。每个命令另有 `graph.application.command-identity.v1` 幂等行。

### B.2 规模

- 实现：前端 ≈1,980 行；后端 ≈1,339 行。
- 前端 **4 份独立实现**同一状态机：`application/resourceOutbox.ts`（通用，199）、`application/workflowConfiguration.ts`（画布保存内联，342）、`adapters/providerCredentialEvidence.ts`（98）、`backend/src/phase1_agent/static/frontend-node-client.js`（555）。
- 测试：18 个专职文件 ≈4,232 行（后端 6 文件 1,568；前端 12 文件 2,664），另有 30+ 测试经 `testUtils/requestEvidence.ts` 间接依赖。
- 复用面：配置、复制、管理（9 操作含 `run.start`）、资源 5 类、Key、内容名、会话名、frontend-node 通道 → **不是插件/扩展公开能力**（`workflow_capability.py:357-372` 明确标注 `carrier="existing-operation"`，后端无包调用 `host.request_evidence`）。

### B.3 后端自身不依赖它

- `workflow_capability.py:357-372`：注释写明只在"前端管理 outbox 路径"上，后端命令不强制。
- `tests/test_configuration_run_lock.py:52-55`：直接 `service.update_definition(...)`，无证据。
- `graph_receipts.py:58-106`（只读回执）全程不引用 `pending_commands` → 未知结果核实只需 key + 原请求 + `receipts/read`。

### B.4 它保护的真实故障 vs 它引入的故障

| 故障 | 人类画布场景 | 后端是否有独立兜底 | 判定 |
|---|---|---|---|
| 业务已提交、回执丢失 | 会 | 有：全量文档 + `edit_sequence` CAS + 幂等回执；刷新 `definition.read` 即真相；重发同文档会 `stale_edit_sequence` | 证据层只是把"需刷新确认"变成"自动核实"，**非正确性必需** |
| 半截请求（证据已写、业务未发） | 会 | 无 | **证据层无法恢复它**，只会永久锁死（无 abandon） |
| 多标签/并发 | 少 | 有：409 `stale_edit_sequence` | 友好预检，非必需 |
| 同 key 不同请求 | 少 | 有：digest 冲突 | 非必需 |
| 刷新后未结案提示 | 依赖上两条 | 面板可被"刷新即重载"替代 | 有用但非必需 |

### B.5 永久锁（最大风险）

证据写成功、业务未发出/回执未达 → 该工作流 pending 且无回执；配置/复制/管理三个通道端口未提供 `archivePending`，因此没有 `resourceOutbox.abandon` 那种"放弃并解锁"出口（`resourceOutbox.ts:157-182` 仅资源/凭据用；`workflowConfiguration.ts:24-29`、`workflowManagementRequests.ts:16-25` 无）；`guardManagementWrite` 又用配置通道锁拦管理命令（`workflowGraph.ts:709-733`）→ 编辑器、运行、归档、删除全锁死；UI 只有"核实原请求"按钮，核实失败无出路。

- 测试固定该锁定：`application/workflowConfiguration.test.ts:234-246`、`stores/workflowConfigurationStore.test.ts:240-259`。
- 可验证：现网只读查 `pending_commands WHERE resolution='pending'` 即可知道是否已发生；开发库为 0。

### B.6 对运行的成本

- 管理通道（含 `run.start`/暂停/关闭/归档/删除/建会话/事件）走 `resourceOutbox.send`：`write` → 读 → 业务 → 2×读 → 读+`resolve` ≈ **6 次证据调用**（`resourceOutbox.ts:74-123` 两次 `current()` + `workflowManagementRequests.ts:86-118` 两次确认）。
- 证据读也走 `SqliteStore`（`request_evidence.py:205`），每次 `BEGIN IMMEDIATE` + 全量 DDL + 版本检查（`storage.py:44-105`）→ 每次保存多 4 个初始化写事务。
- 全量历史读：`read_evidence` 无过滤/不分页（`request_evidence.py:203-209`），实测 103 行 = 728,411 B / 81 ms 校验；每次保存读 2 次、每次打开读 1 次；累计 O(n²)。
- 存储：每次保存 6 行/≈28 KB，永不清理；开发库证据+幂等 ≈67% 库容。
- 启动只有 1 次 `request-evidence.pending`（`useWorkflowFrontendHost.ts:41-46`），无证据轮询（`schedulePoll` 是会话轮询）。
- 但打开任一工作流必须先读完证据历史：`locked = !initialized || busy || pending`（`workflowConfiguration.ts:132`）→ 编辑/启动按钮不可用。

### B.7 可验证的替代路径

| 路径 | 存在 | 差异 |
|---|---|---|
| 直接 `POST /api/graph/commands` `definition.update` | 是（当前传输层） | 少 2 写 2 读；未知时无 key/body 可回读（key 生成即丢）→ 需最小本地留底 |
| 只读回执 `POST /api/graph/receipts/read` | 是，且不依赖证据 | 简化恢复的核心 |
| frontend-node 窄补丁 `patch_exact_configuration` | 是，但同样走私有证据 | 非画布保存的简化替代 |
| `draft.save` / `definition.save` | **已退役** | 不可用 |
| 插件/扩展写入 API | **不存在** | 删除不破坏插件 |

### C.6 可简化清单

1. 保存前证据三段式（write → 2×read → resolve）：每次多 2 写 2 读 + ≈17 KB。**风险**：多 owner 共用，只能按 `owner_kind` 收窄。
2. 只读回执 `receipt.read`（`graph_receipts.py` 619 行）：同步阻塞保存且无需断线核实时可退役。**风险**：copy/resource/session 也用。
3. 两次全历史扫描改 `MAX(revision)`：**零契约风险**，省 ≈49 ms/次。
4. display-only 保存合并/轻量化：59/103 次是它。**风险**：undo/redo 与 `edit_sequence` 语义要重定义。
5. `confirmation_required`/`derived`（前后端约 70 行）：本库从未触发；但属产品规则，**删除需产品决策**。
6. `edit_sequence` 双号：只有在 4 落地后才能合并。
7. 每请求 28 条 DDL + `BEGIN IMMEDIATE`：与编辑协议无关的通用存储层问题。

### D.4 卸除方式对运行的影响矩阵

| 改法 | 运行行为 | 是否破坏 |
|---|---|---|
| 改阻塞保存 | 请求内容/后端路径不变；编辑更串行；运行链不优化 | 不破坏 |
| 每次编辑直接同步落库 | **现状已如此**（每次编辑一次整图 update） | 无变化 |
| 去掉"乐观层"（若指先清选区/先推历史/先报成功） | 运行不受影响，失败更早暴露 | 不破坏 |
| 连保存一起去掉（只留内存编辑） | 固定结构编辑无法进入运行；会话钉在旧修订 | **破坏"运行当前编辑"** |
| 只去掉前端保存门 | 运行与保存并发，SQLite 决定顺序；后端不撕裂，但"运行即所见"语义丢失 | 不破坏执行机制 |
| 只去掉证据 pending/closure 门 | 运行可在业务已保存、证据未结案时发起；后端读已提交数据 | 不破坏运行，破坏保存请求完整性 |
| 去掉会话固定修订/CAS | 检查点、历史、事件作用域、运行 basis 的一致性前提被移除 | **破坏**（后端契约） |
| 去掉轮询/catalog/session_document | 执行不变；UI 状态推进变差，可手动刷新 | 不破坏执行 |

### D.5 额外发现（耦合缺失，值得单列）
