# 项目整体架构：当前代码完全未涉及部分

日期：2026-10-16，Asia/Shanghai。

性质：总设想中的产品能力空白清单，不是施工计划、接口定稿或未来能力已批准实施的声明。

源码基准：本地 `main` / `develop` 共同提交 `4c67bbb0e416092ce7ebd1aef1e8a42c8940bfa7`。

总设想见[61](61-项目整体架构总设想-2026-10-16.md)，凡已有相关代码的部分均归[62](62-项目整体架构当前代码已涉及部分-2026-10-16.md)。

## 1. 严格收录口径

本文的“完全未涉及”指：本次在当前产品有效代码中，没有发现承担该项具体能力的实现或正式接线。不是说仓库内不存在任何相关文字、通用基础或可复用接口。

已有内容管理、模型配置、工作流编辑、能力包加载和命令查询入口，都不能因为尚不符合总设想而放入本文。其架构升级与职责重整属于 62 号中的差异。

本文也不将整个未来系统的缺失扩大为每个基础零件都不存在。例如，尚无智能沙箱，不等于没有配置校验；尚无项目 MCP 接口，不等于没有业务命令。

## 2. 项目内部管理的 MCP 入口

对应设想：项目底层内部管理能力通过 MCP 提供给智能操作者，采用严格约束。

本次没有发现正式的项目 MCP 服务入口、工具暴露和调用接线，使智能操作者可以通过 MCP 管理本项目。

这一空白具体指“通过 MCP 使用项目内部管理能力”，不包括已经存在的普通 HTTP API、同进程命令和查询接口。

后续尚需决定：

- 哪些内部业务能力可以暴露，哪些操作必须禁止或另行确认。
- 调用者身份、可操作对象和权限由哪里核实。
- 如何沿用各业务的修订依据、原请求身份和结果核实规则。
- 只读、配置修改、删除及产生外部效果的动作如何区分。

以上是待讨论问题，不在本文提前编造完整 MCP 工具清单或权限系统。

## 3. MCP 与模型管理的连通

对应设想：项目功能配置相关部分后续考虑通过 MCP 连通模型管理。

当前未发现为该方向建立的 MCP 连接、能力映射与模型管理接入链路。

用户原始表述尚未明确连通方向：是对外提供本项目的模型配置管理，还是连接外部 MCP 能力供模型使用，或两者分别建设。本文保留这一区别，不把其中一种解释当作已确认需求。

若最终指对外暴露模型管理，它属于第 2 节的一组管理能力；若指连接外部工具，则需要另行确定连接和工具使用职责。不能将一个未确定方向拆成两套已经获准建设的系统。

## 4. 项目内置的 harness 智能管理系统

对应设想：项目内部有独立智能操作者，管理项目并协助工作流创作。

本次没有发现该系统的产品入口、任务组织和管理调用闭环。其缺失不是现有 Agent 节点缺失，而是“项目级智能管理者”这一具体产品能力尚未接入。

它不同于：

- 工作流中消费输入并产生输出的 Agent 执行节点。
- 页面提交一次工作流操作。
- 当前协作开发所使用的外部编码助手或桌面工具。

后续需讨论它管理什么、如何接受用户任务、哪些动作可自主进行，以及何时转交用户确认。是否复用现有 Agent 内核或另作任务控制，本次未决定。

## 5. 工作流创作的沙箱代码环境

对应设想：智能操作者可以在沙箱内用代码自由创建和编辑节点内容、组织工作流。

本次未发现与项目产品接通的代码沙箱执行环境，也没有“进入隔离工作区编程并将成果提交工作流”的完整入口。

此处空白是沙箱编程能力，不是图编辑本身。现有工作流配置、节点实例和连线修改已归 62 号；它们可以成为后续讨论的业务基础，但不等于已经提供沙箱操作体验。

需要先区分两种不同需求：

| 需求 | 具体含义 | 当前归类 |
| --- | --- | --- |
| 用代码组合已有能力 | 在沙箱中生成或修改由现有声明组成的图 | 尚无沙箱创作接入 |
| 编写新的节点逻辑 | 运行用户或模型生成的代码，形成新的可执行节点能力 | 尚无该类不可信代码节点的隔离执行接入 |

后者不应通过直接把生成代码装入当前可信 Python 插件宿主来冒充沙箱支持。采用哪种隔离技术、允许哪些依赖及如何保存结果，本次不选型。

## 6. 智能管理与自由创作的联合产品路径

对应设想：内部管理与工作流创作采用不同的开放程度，但处于同一个项目智能管理体验中。

当前没有把“内置 harness、受限 MCP 管理、沙箱创作、成果提交”连接起来的产品路径，因此也没有这一路径下的正式权限分工和操作闭环。

这里指的是整条新路径，不是宣称已有后端校验、对象授权、配置修改规则或结果回执不存在。那些机制已有代码，必须在 62 号解释。

后续需讨论的最低边界：

- 哪些活动只发生在隔离副本，哪些会修改正式数据。
- 创作结果怎样进入正式配置入口，谁核实其目标和版本依据。
- 模型派发、工具外部效果、共享内容修改等动作如何获得相应权限。
- 代码生成结果、正式保存结果与实际执行结果如何分别呈现。

“沙箱中可以自由创作”不等于已经授权写真实业务库、读取 Key、改宿主源码或绕过运行规则。这里提出的是需要明确的边界，不据此新增一套实现方案。

## 7. 未涉及结论的核对范围

本次只读检查了当前产品的后端入口与宿主、能力包装配、工作流操作、前端工作台和扩展接口，并对 `backend/src/`、`frontend/src/`、`scripts/` 检索 `MCP`、`harness`、`sandbox` 及“沙箱”相关接线。

检索到的当前能力包说明明确指出其不是进程沙箱；未发现上述未来能力的正式接入。该结论结合入口阅读作出，不仅凭关键词缺失判断。

`vendor/smolagents/` 中可能保留的上游 MCP 或远程执行相关源码属于来源归档，当前内置能力装配不因其存在而获得这些产品功能。历史设想和测试内容也不视为产品接入证据。

本次没有运行测试或服务；“未涉及”是本次源码勘察结论，不是对所有可选环境和任意历史提交的穷尽证明。

## 8. 本次边界

本文不把尚未定稿的设想转成实施授权，不新增插件市场、Agent Team、微服务化或通用自动回滚等建设范围。

下一步若继续设计，应先明确 MCP 连通方向、智能管理任务边界以及沙箱究竟只组合现有节点还是还执行新代码。明确这些之后，才能讨论具体接口和工程计划。
