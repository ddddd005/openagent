## 2. 用户提出的项目理念

项目整体是母层。工作流、模型供应商配置、全局内容管理是并列子功能；工作流是当前核心功能，但不是项目唯一功能，项目整体不应绑定于工作流。

工作流以节点化为核心，鼓励用户自由组合和连接节点，在一定规则下创建插件和节点，搭建自己的 Agent 工作流。

整体采取解耦、模块化设计，各功能内部可按需要继续分解，但嵌套归属应明确，避免没有合理原因的跨层交叉耦合。

面向未来，项目不仅供人通过页面操作，也考虑内置智能管理系统：内部管理通过 MCP 进行严格约束的操作；工作流创作可在沙箱中通过代码完成，给予更宽松的创作空间。

以上是用户提出的方向，不表示已有完整项目平台、MCP 管理或代码沙箱实现。

## 3. 项目基底

项目基底承载各业务模块共同需要的基础能力，不以某一个工作流、节点或会话为前置条件。

从职责上包括应用启动与装配、本机服务与入口、基础校验与错误表达、持久化设施、必要的操作身份与结果记录，以及运行环境和进程生命周期管理。

基底不应解释具体 Lorebook 匹配规则、Agent 提示词策略或工作流候选选择语义。这些属于各业务模块。

这里是职责描述，不要求所有能力装进一个“基底类”，也不预先要求新建统一框架或拆成独立进程。

## 4. 面向用户的功能

用户目前归纳的三个功能方向为：

| 功能 | 功能定位 |
| --- | --- |
| 全局内容编辑器 | 管理可复用的全局内容，包括 Lorebook、全局提示词；设想中还包括预设管理 |
| 工作流工作台 | 创建、编辑、组织和运行节点化工作流，管理其会话、内容与运行结果 |
| 模型供应商配置 | 管理供应商、访问配置和命名模型参数，供工作流等功能使用 |

“预设管理”在这里属于总设想，不因存在全局提示词组就视为已有通用预设管理器；现行与退役范围由 62 号解释。

用户界面上的“工作台”是业务操作界面，不等于后端业务权威。某个编辑面板放在同一个窗口，也不意味着其业务属于工作流。

## 5. 项目整体架构设想

### 5.1 基础设施

作为项目地基，提供各模块可共同依赖的基础能力。项目级功能不应为了使用这些基础设施而先创建工作流或启动 Runtime。

### 5.2 多层数据管理

统一管理项目涉及的数据，包括全局内容、供应商配置、工作流目录、工作流定义、工作流会话及会话下的数据内容。

用户原述为“多层数据库”。本次建议将其理解为数据作用域、归属和管理职责的分层，不直接推导为多个物理数据库。物理拆库方式、事务范围和公开接口均未在本次定稿。

全局内容与供应商配置属于项目级资源；工作流引用资源，不因引用而拥有资源本身。会话内容属于相应会话，不应与全局定义或资源当前值混为一体。

### 5.3 模型供应商与 API 通信

负责供应商和模型配置，以及实际模型调用所需的请求与协议能力。

建议在同一业务域内区分配置管理、当次请求准备与授权、API 协议通信三种职责，避免将配置保存和模型派发视为同一个动作。如何形成项目级公共模型能力，仍需结合现有实现讨论。

### 5.4 内容工作台

面向全局提示词、Lorebook 及未来确认的预设等可复用内容，提供编辑与管理能力。

内容工作台维护资源，不替工作流隐式接线，不以编辑内容为由启动模型，也不持有某个工作流会话的运行权威。

### 5.5 工作流工作台

负责工作流的画布与配置编辑、会话与运行操作、结果与历史观察等功能。具体内部职责见第 6 节。

工作台前端应使用工作流的功能接口，不因为是画布或聊天页面就直接取得修改所有会话数据的权限。

### 5.6 功能和插件管理

加载插件、发现可用能力，向需要的功能提供相应节点、数据类型、执行器或界面扩展。

需区分项目能力的注册与某个工作流中节点实例的创建。可信宿主插件与未来沙箱中的用户代码也不能未经讨论就使用同一种加载方式。

### 5.7 项目功能配置与协作

用户设想该部分管理项目配置并协调不同模块的功能调用，后续考虑 MCP 与模型管理的连通。

建议在职责上区分“配置管理”和“应用协调”：前者管理启用项、参数和相关设置，后者组织一次具体业务操作。是否分为两个模块以及接口形态，尚未定稿。

跨模块协作应有明确契约，但不要求所有调用都必须绕母层中转。合法的接口依赖不等于无故耦合。

### 5.8 项目智能管理系统

设想内置 harness，让智能操作者参与项目管理和工作流创作：

- 对底层内部管理，通过 MCP 使用明确、受约束的管理能力。
- 对工作流画布，可在沙箱中使用代码创建和编辑节点内容。
- 内部管理采用严格约束，主要创作功能给予较宽松的操作空间。

此处 harness 指项目内置的智能操作与任务组织系统，不等于工作流里的 Agent 节点，也不是当前协作开发使用的外部编码工具。

建议将它定位为业务能力的操作者，而不是新的数据、权限或执行事实权威。代码创作可以自由，正式保存、模型费用与外部效果仍需遵守对应业务边界。实际沙箱技术、权限及操作契约均待讨论。

## 6. 核心功能：工作流

### 6.1 基础构建

加载工作流需要的内容与声明，准备依赖，初始化工作流或会话，使后续配置和执行能在明确依据下进行。

建议把它视为装配与生命周期过程，不让“初始化模块”长期包揽数据、编辑、执行等全部职责。

### 6.2 数据管理

按用户设想，涉及工作流数据库、定义库、数据存取与更新、检查点存档。

需要进一步区分声明与实际值：定义模块规定类型、能力和合法操作；数据存储保存配置、会话值、产物和事实。定义需要保存，不代表它只是普通数据仓库；登记某个数据项，也不等于持有其当前值。

### 6.3 配置管理

管理节点实例、连接、节点内部配置、内容修改及保存规则。

“节点注册”需要在后续文档中分别表述为节点类型/能力注册和图内实例创建，避免与插件加载职责重叠。固定配置、可调配置、运行冻结依据之间的关系应明确。

### 6.4 运行与功能操作

执行层负责 Runtime 执行、数据流转、与数据层交互及声明能力的调用。

启动、暂停、继续、关闭、候选选择和分叉等功能，不应仅存在于某个按钮或页面里。建议将可复用的工作流操作与执行引擎的职责分别解释，而非全部装进 Runtime。

## 7. 评估与待讨论调整

| 项目 | 本次评估 | 尚需明确 |
| --- | --- | --- |
| 项目母层、业务模块并列 | 合理，能避免整个项目被画布和 Runtime 绑定 | 公共能力范围及现有依赖如何逐步整理 |
| 模块解耦与嵌套归属 | 合理 | 区分业务模块、技术层次、数据归属，不把所有部分排成单一直线 |
| 多层数据库 | 管理目标合理，名称容易引起物理拆库误解 | 建议使用分域数据管理；不提前决定拆库 |
| 项目配置协调全部功能 | 有必要组织协作，但责任容易过大 | 配置与应用协调分清，避免万能管理器 |
| 供应商配置与 API 通信 | 可以属于同一业务域 | 内部职责分离，不由通信适配器负责项目业务 |
| MCP 严格、沙箱宽松 | 创作体验目标合理 | 约束取决于操作权限和影响范围，不只取决于通信或执行方式 |
| 自由创建插件和节点 | 符合核心理念 | 图组合、沙箱代码、可信宿主插件分别讨论 |

这些是本轮提出的解释与建议，不将其包装为用户已经批准的新契约。不新增微服务化、远程插件市场或通用自动回滚等未提出的建设目标。
