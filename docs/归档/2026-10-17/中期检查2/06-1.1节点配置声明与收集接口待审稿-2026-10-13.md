## 2. 唯一建议的声明表示

建议把声明作为 `NodeDefinition` 的静态注册描述，并由 `to_dict` 原样规范导出：

```python
checkpoint_save = {
    "config_paths": [
        ["mode"],
        ["options", "strategy"],
    ],
}
```

空声明统一写作 `{"config_paths": []}`，不省略字段、不用 `null`。路径段使用属性名字符串数组，单个路径不得为空。路径数组按段元组字典序规范排序；重复路径及同时声明祖先与子路径时注册失败。这样既保留父级整段选择，也避免一次配置被重复或冲突拼接。

路径注册校验只做一条静态 `config_schema.properties` 遍历规则，不做完整JSON Schema路径解释器：

- 每段必须是非空字符串，且是当前对象schema的直接 `properties` 键；路径只能由明确写出的属性段构成。
- 对象和数组属性都可作为终点整体声明；对象终点收取其经过固定策略投影后的整段值，数组终点收取其经过固定策略投影后的整段结果。
- 不穿过数组 `items`，不接受下标、成员ID、通配符、表达式或运行时查询。比如 `["members"]` 可选整段；`["members", "some-id"]`、`["members", "0"]` 不是合法路径。
- schema中不存在的属性、无法沿直接 `properties` 继续的路径、空路径、重复及父子重叠均在注册时拒绝。现有 `Draft202012Validator.check_schema` 与节点配置校验照旧，不另造schema平台或替代现有格式校验。

路径只定义开发者声明的静态字段范围，不由用户编辑，也不形成节点配置的第二权威。正常节点表单仍编辑和提交 `node.config`；未声明的配置字段不进入配置检查点。

## 3. 收集规则

建议收集器以已保存工作流定义的固定 `revision` 为输入，按节点绑定读取该版本的 `node.config`、精确组件描述及配置策略；不接受页面尚未提交的表单状态，不用节点默认值补齐缺项。仍在创建声明值前执行现有配置schema/格式校验。

对每个节点只走以下顺序：

1. 从该固定revision的已保存 `node.config` 计算现有 `fixed_configuration_projection`。
2. 在投影结果上按descriptor声明的属性段路径取值。
3. 只复制投影中仍存在的已声明值，组装成以 `node_binding_id` 定位的配置形状投影。

声明路径始终按原 `config_schema.properties` 判定；取值则始终来自固定投影。不得先从原始配置提取，再尝试从结果删去可调字段；不得把投影值重新还原为原始数组、写回 `node.config` 或作为新配置权威。全局引用按现有取最新策略处理：可收集固定配置中实际声明的引用身份，不沿引用额外读取并冻结全局正文。

宽路径的规则及空值语义：

| 情形 | 收集结果 |
| --- | --- |
| schema中没有声明路径 | 注册错误，不进入运行期收集 |
| schema路径合法，但当前有效配置没有该可选属性 | 该路径缺失，不补默认值、空对象、空数组或 `null` |
| 原配置存在该属性，但固定投影因既定可调/取最新策略移除了它 | 该值是“策略排除”，不是“配置缺失”或schema错误；不入点、不报数据缺失、不回退读取原值 |
| 宽路径部分保留，子字段有的固定、有的策略排除 | 仅收集投影后仍存在的子字段；绝不把被排除字段夹带进点 |
| 已声明路径在固定投影中存在且值为显式 `null`、空对象或空数组 | 保留实际显式值，不与缺失混同 |

因此，配置缺失与策略排除在收集判定中是不同原因；二者均不会生成配置值，也不需要在检查点中另存原因状态或包装成额外的通用状态schema。只要已有固定投影足以判断策略结果，就不新增字段屏蔽表、动态成员选择或通用查询机制。

当现有固定投影改变容器形状时，所声明路径仍直接指向投影后的值，不恢复可调数据。例如，适用成员身份投影的 `members` 如由列表变为身份键控对象，则以该投影对象为值；如果成员字段全部被既定策略排除、投影中没有 `members`，收集器就省略它，不伪造原数组、成员空项或成员字段。这里没有按ID挑选某个成员的附加路径语法。

## 4. 最小接口形状建议

建议用两个普通函数完成1.1的节点配置部分，不增数据类、表或错误平台。`normalize_checkpoint_save` 与 `NodeDefinition` / `NodeRegistry.register` 配套，`collect_checkpoint_configuration` 与现有 `GraphRecordStore` / `fixed_configuration_projection` 配套；具体模块位置仍按现有所有权放置。

```python
def normalize_checkpoint_save(config_schema: dict, declaration: dict) -> dict:
    ...

def collect_checkpoint_configuration(
    repo: GraphRecordStore,
    workflow_definition_id: str,
    fixed_definition_revision: int,
) -> dict:
    ...
```

`normalize_checkpoint_save` 接受且只接受 `{"config_paths": [...]}`，在给定 `config_schema` 上按第2节路径规则校验，返回新建的规范dict；它不接受缺省/`null` wire。`NodeDefinition` 的默认声明建议为 `{"config_paths": []}`。注册校验和 `to_dict` 导出共用该函数，让目录和持久descriptor使用同一规范形状；已有 `Draft202012Validator.check_schema` 继续负责schema格式本身。

`collect_checkpoint_configuration` 的 `repo` 是调用方现有 `_change` → `GraphRecordStore.atomic` 操作回调提供的仓储对象。收集函数不开始、提交或另开事务，只在该事务的同一连接内读取。它只按给定 `(workflow_definition_id, fixed_definition_revision)` 读取一条 `workflow_definition_revision`；现有 `GraphRecordStore.get` 会校验该记录，`validate_graph_record` 还会核对其嵌入document的工作流ID和revision。调用方负责选定本次操作所依据的固定revision；收集器不取最新revision、不读取 `workflow_current_configuration` 的可调overlay，也不使用页面未提交值。

对该固定document内的每个节点，收集器从精确 `(component_id, component_version)` 读取已保存 `node_definition` 描述，按其 `config_schema` / `checkpoint_save.config_paths` 和节点配置策略执行第3节流程。收集结果建议采用以下普通dict形状：顶层固定定义身份，`nodes` 按 `node_binding_id` 键控；每个值带精确组件身份及原属性嵌套的逻辑配置投影。比如声明路径为 `["mode"]`、`["options"]`、`["optional_note"]`，schema允许 `options` 内的 `strategy`，有效固定投影中 `optional_note` 缺失，而 `options.strategy` 显式为 `null`：

```json
{
  "workflow_definition_id": "11111111-1111-4111-8111-111111111111",
  "fixed_definition_revision": 7,
  "nodes": {
    "22222222-2222-4222-8222-222222222222": {
      "component_id": "example.node",
      "component_version": "1",
      "config": {
        "mode": "fast",
        "options": {
          "strategy": null
        }
      }
    }
  }
}
```

示例中 `optional_note` 因具体配置缺失而省略，`options` 仅含固定投影后保留的值；显式 `null` 保留。该示例定义返回身份和嵌套路径，不是新数据库record schema。没有固定声明值的节点可省略；即使所有节点均无投影，也允许返回空 `nodes`。不把路径改写成点号字符串，不给“缺失/排除”添加持久状态标记，不增配置overlay或独立收集表。

现有开发库18张表实测均为空，且已决定新descriptor与注册/收集消费者按新规范成组替代旧表示，不建兼容分支、不自动升包。新描述持久化后，同一 `(component_id, component_version)` 的完整描述仍须相同；实际出现冲突、遗漏消费者或未分类依赖时再报告，不为未发生的问题预建迁移、重试或恢复框架。
