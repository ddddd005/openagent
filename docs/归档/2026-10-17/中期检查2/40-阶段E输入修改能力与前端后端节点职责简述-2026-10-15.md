## 1. 职责归属

| 范围 | 职责与实施边界 |
| --- | --- |
| 工作流职责 | 统一配置修改模块受理合规修改，核对可修改的节点与字段、内容格式及配置版本，沿正式保存、可调规则和固定修改确认派生执行。节点负责调用，修改规则与保存权威属于工作流配置层 |
| 直接复用既有能力 | 类型/数据项登记、定义登记、数据读取和写入，以及已有运行控制和检查点分叉，由节点通过各自现成入口使用。定义模块维护声明，数据层维护当前值，runtime与检查点保持原职责 |
| 节点与外部交互 | 节点核对其允许的操作和准确目标，调用工作流配置、定义、数据、运行或检查点能力，并接纳实际结果。这部分需要独立明确的调用接口 |
| 节点内部功能 | 前端与其对应后端节点的通信、输入接收、展示副本、前端端口/入口注册、默认绑定及打开前端，属于该节点自身实现。这部分与节点调用外部能力分开开发 |

“节点内部”和“节点与外部交互”是同一个节点实现中明确的两部分。前端通信处理通过节点内部接口交给业务处理，再由外部调用部分使用工作流能力；各部分保持可识别的职责和依赖方向，不把通信、配置修改、数据读写及runtime控制混在一个处理函数中。

## 2. 工作流配置修改与输入节点

合规修改模块是工作流侧的可复用能力。首版规则名单可以只登记新输入节点的内容字段`text`，但入口、规则查询/校验及提交过程须与具体节点规则分离。具体节点身份、字段集合及格式校验放入集中规则条目，不在每个按钮、前端或调用分支里写死。

后续按定义模块的方式接续统一注册机制：其他节点通过统一入口登记可修改字段及规则，由修改模块统一查询和执行。首版应保留这个扩展边界，不将“修改输入节点”做成无法扩展的唯一接口，也不提前建设复杂插件平台。固定/可调声明与可修改字段的许可分别校验，不因允许调用而自动改变节点配置策略。

- 新输入节点负责保存输入文字并在运行时输出`TEXT@2`；具体身份尚未规定。现有`tools.current-input@1`读取运行请求的具名外部输入，现有`tools.text@1`直接输出配置`text`，可参考这两处最小实现。
- 首版建议只开放`text`，登记该节点的可信可调声明并默认可调。有会话时按当前可调配置规则保存；固定策略仍服从已有确认派生，不用输入操作绕过配置层。
- 这份可调输入沿现有工作流当前配置维护；会话上下文的数据项继续按会话隔离。运行准备取得本轮值，后续编辑不追改已准备运行。
- 200ms只是当前整体前端节点`frontend.node@1`内部拟定的输入更新时间，不是所有输入节点或配置表单的保存周期，也不是工作流核心机制。底层修改能力只负责实际校验及提交；发送前完成待提交输入再启动的顺序在该节点内部落实，不抽成通用保存框架。

## 3. 前端与对应后端节点

用户明确：每个前端对应自己的唯一后端节点，前端仅提交该节点允许的操作意图、接纳后端结果并显示。注册、修改、启动、暂停、分叉、重roll和候选等业务操作，由对应后端节点调用相关独立功能，操作权限及目标由后端核对。

```text
用户输入或操作
    -> 前端向其绑定的后端节点通信
    -> 节点内部接收、处理通信
    -> 节点对外交互部分核对归属、允许操作及目标
    -> 调用工作流统一能力或直接复用已有机制
    -> 配置层 / 数据层 / runtime / 检查点执行各自职责
    -> 后端结果返回对应节点和前端
```

输入的具体路径为：用户编辑文字，前端先将文字交给对应后端节点，由该节点调用合规修改能力写入准确的输入节点。回执须区分请求已收到和目标已保存；前端不得把本地输入当成已经提交成功的运行值。对应后端节点是否还保存一份输入、具体保存位置及失败呈现，留给该节点契约讨论，不预建第二份输入存储。

此前“多个前端复用修改入口”的建议按本轮订正为：复用在后端功能层发生，前端通过对应节点调用；新节点前端不获得通用工作流修改或管理能力。现有编辑器SDK仅作为实现勘察，不作为新前端直接操作工作流的设计依据。

## 4. 复用上下文登记、读写与展示

对应后端节点通过外部调用部分使用三项既有数据能力：登记自己提供的会话上下文及定义、向数据层显式写入或更新、从数据层读取内容。复用既有统一类型/节点定义、实例项登记和会话存储，不建立另一套上下文目录。节点负责发起与处理调用，不自行承担类型注册中心、定义维护中心或存储层。

类型定义统一登记；节点实例提供该类型下的独立项。自有项和读取的外部项均以准确类型、项键及会话归属区分，读写仍需要明确授权。绑定其他项进行读取不自动复制出一份同义业务状态；多个节点和会话的数据沿既有隔离规则。

```text
数据层中的已接纳值
    -> 后端节点显式读取
    -> 后端节点提供展示内容
    -> 前端保存临时展示副本
```

前端上下文副本用于展示，只接纳对应后端的新数据；前端不通过提交修改后的上下文副本覆盖数据层。输入文字是单独的交互请求，由后端处理后才形成正式配置或数据更新。加载输出仍表示读取时的一份值，后续数据变化需由后端再次读取并提供结果，不把前端缓存设成业务权威。

定义模块只管理定义、声明和登记信息，数据层维护当前值。类型登记、具体项登记、当前值写入与检查点准入分别处理；本简述不自动扩大聊天数据的检查点白名单，不把测试期`frontend-state@1`定为永久通用聊天格式。

## 5. 前端端口、默认绑定与UI

前端通信端口/入口的声明、注册接线及默认绑定，由对应后端节点的实现负责。工作流/宿主提供通用承载及校验，工作流配置层保存必要实例绑定；节点负责定义自己向前端开放的通信契约及默认归属。具体端口编号、路由形式和传输实现，等前端逻辑明确后再落实，不在本简述中定死。

每个前端始终绑定准确的后端节点实例，并携带相应工作流及会话归属；同类型多个节点各有自己的默认绑定。绑定由节点提供、由后端核对，浏览器不从全图唯一展示节点、当前选中节点或类型名自行推断归属。

节点上的按钮负责打开前端并带入该节点的绑定。节点的正常运行、数据维护及对外能力调用不以打开前端为前提；前端未启动时，节点仍可按正常图调度或已声明主动入口工作。关闭前端不停止后端运行。打开前端沿既定规则不提前创建会话，首次运行按需创建会话。

当前UI将前端节点作为一个整体呈现，暂不拆成多个读取、更新、输入和控制节点。内部实现仍按通信、展示/输入处理、端口与绑定、外部能力调用等职责有序组织，UI整体不等于代码混写。

## 6. 接续时需列清的最小契约

首批先落实工作流配置修改能力的可扩展规则入口及简单输入节点，再接节点内部输入通信与明确的对外调用。前端端口注册和默认绑定纳入节点职责，传输接线在前端逻辑明确后落实。需列清准确节点身份、允许操作、目标输入绑定、数据项读写授权及结果归属；后端不能仅转发前端指定的任意目标。

节点主动操作与普通图执行分别接入：暂停等控制须能在运行期间由后端节点调用既有控制能力，不能等待普通计划执行到节点。当前局部事件要求稳定会话并占用执行生命周期，不能直接充当全部操作的通道；具体入口在施工前确定。当前仍不增加能力连线或改造数据/控制边。

重roll、候选的具体业务语义尚未裁定，后续逐项讨论；本轮只明确其调用路径，不将失败重试替代重roll，也不恢复旧候选覆盖机制。更换前端时遵守对应后端节点的协议与能力边界即可。

当前源码差距：可调规则仍只覆盖提示词契约；现有编辑器SDK直接提交配置修改；`frontendWiring.ts`在前端侧生成读取、追加和展示三个节点，旧Tavern入口还有创建会话及全图唯一展示判断。这些只作为后续精确替换的勘察证据，不作为新前端节点的职责或UI模板。本轮不执行这些替换，也不改变用户已搭建工作流。
