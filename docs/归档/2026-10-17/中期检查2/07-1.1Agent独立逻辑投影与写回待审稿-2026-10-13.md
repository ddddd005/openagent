## 1. 建议范围

唯一候选根仍是源会话当前已接纳的 `session / workflow.effective-context / 4`。从正式对象读取当时的有效逻辑上下文；不要求目标解引用源 artifact、receipt、revision 或历史 merge/lineage 证明。对象未初始化或处于新类型正式空默认值时不入点，不补造 Agent 状态。

最小推荐是将必要逻辑值内联到目标自己的上下文对象，不新建表、全局消息库、artifact、merge/run 或来源账本。下列形状只说明语义白名单，不是已批准的 wire/schema：

```text
{
  messages: [
    {
      message_id, role, blocks,
      provider_metadata?, thinking_summary?
    }
  ],
  layout: [
    {kind, round_id, compaction}
  ],
  accepted_delta_ids,
  generation
}
```

- `messages` 保存已接纳的有序模型/工具上下文正文及其必要协议结构，沿用 `blocks` 字段名，只投影协议正文而不保留 `source`。`message_id` 是该上下文内消息身份；tool call/result 的 `tool_call_id`、调用顺序、结果状态及内容须保持闭合一致。它们是局部语义/协议身份，不解引用源记录，也不冒充目标新执行。
- Gemini `provider_metadata` 中原始签名 Content 和对应 `tool_call_bindings` 必须原样、成对保留；不能重建、删改签名段或仅按字段名排除。与该协议内容绑定的 `thinking_summary` 一并保真。一般说明性摘要、独立 run/event/fact 仍不因此成为上下文白名单字段。
- `layout` 沿用 `kind / round_id / compaction` 字段，保留 `history / summary / once` 生命周期、压缩资格及轮次分组关系，使既有上下文/压缩消费不丢边界。`round_id` 只作为不解引用的本地分组身份，不表示该运行在目标执行过。
- `accepted_delta_ids` 保留已消费 Agent 更新的完整有序身份集合；当前正式读取会把已应用更新折叠到持久对象的该集合。它是避免同一更新重复消费的状态，不是 once 来源账本，不得清空或改写。`generation` 保留现有上下文压缩代数。
- 不持久化 `owner`、`basis`、`derivation`、源 `view_ref` 或其递归 `input_view_ref / update_ref`。owner 与 CAS basis 由真实目标绑定和当前对象读取生成。
- 不因旧 `agent_message` validator 需要而复制整份 `source` 元数据。`prompt_id / revision / item_instance_id / group_instance_id / visible_message_id / output_id / request_id / tool_execution_id` 等旧来源/执行追溯字段不属于目标协议正文，不为满足旧 schema 保留。必要工具调用关联保留 `tool_call_id`，provider metadata 的协议绑定保留 `tool_call_bindings`；两者不能与 source execution ID 混同。
- 不收集 `private-state`、程序变量、整份 PROMPT、当前请求/临时材料、通用消息或独立摘要、Agent receipts/executor facts、输出 artifact 集合及 lineage。Agent 内部必要模型/工具协议消息不能仅因名称含 messages 而排除。

上述排除的是对旧对象/事件的来源证明依赖，不是抹去内嵌正文事实或协议关系。目标读取只消费自己的上下文值；其中保留的局部身份不授权访问源对象，也不声称相应请求或工具执行发生在目标。

现有 `CONTEXT_VIEW@4` 与 `workflow.effective-context@4` 校验均不接受上面建议的 inline value：前者要求 owner/basis/derivation 等旧 envelope，后者要求 `view_ref`。因此这不是可直接复用旧 schema 的小改名，而是已核实的真实表示冲突。当前 `context.output` 按旧 pointer 解析 `CONTEXT_VIEW` 是现状证据，不是新collector继续依赖 `view_ref` 或转换旧格式的建议。新collector读取正式绑定上的新inline值，不设旧format fallback；版本如何处理仅在正式 schema 不可同版本变更时由用户确认，不预先升版或伪造旧 producer。

持久历史去掉 `source` 不等于删除所有 live `agent_message/source`。后续新模型/工具消息及 Agent update packet 仍按真实 producer、message/call身份、frozen prompt/model输入和 executor facts 校验；实际 merge 入口现由 [`context_v4_nodes._merge`](../../../../backend/src/phase1_agent/context_v4_nodes.py#L55) 调用 [`validate_execution_update`](../../../../backend/src/phase1_agent/agent_executor.py#L128)。只退出“新目标必须保留并递归证明历史merge lineage”这一旧依赖，不削弱本次 live 接纳。

**2.1交接约束：** 持久 reader、`CONTEXT_VIEW`、既有 `PROMPT@6`、`context_update_v2`、Agent“读取已接纳历史”校验和压缩消费必须实际接受上述无旧 `source` 的逻辑消息；不能只改根对象 schema 后即报可用，也不能重建假的 `prompt/output/request/source` 字段绕过校验。建议先用现有 `CONTEXT_VIEW`/`PROMPT@6` 已承载的 `messages / context / layout` 及 `blocks` 消费逻辑正文和协议块，不加 prompt 字段或升版。若适配后确有现有字段不足，再报告真实冲突，不能静默选择新增字段/版本。正常新追加消息的来源身份验证仍保留。

## 3. 最小收集、校验与目标写入接口（待裁定）

建议的收集接口从源会话实际根对象binding读取当前自有inline值，返回非空 Agent 状态；目标不需要保留源引用：

```text
collect_agent_contexts_in_transaction(repo, source_session, document)
  -> {
       object_key: {
         agent_node_id,
         value  # source-free logical value
       }
     }
```

在 `document` 中按实际 `workflow.effective-context` 根binding及已有Agent归属配置定位对象；不要求 `context.output` 和 `context.merge` 成对存在作为额外图预检。对象不存在或为未初始化的正式空状态时省略，不补空值；对象已初始化时直接用该新类型正常reader取其当前inline值，经 `validate_agent_checkpoint_value(value)` 纯逻辑校验后投影为 `{agent_node_id, value}`。此collector不读取 `view_ref`、不解析 `CONTEXT_VIEW` artifact，也不兼容/转换旧pointer格式。纯validator只校验允许字段、消息/协议结构、布局、消费ID和generation；不接收repo、resolver、source owner或历史权限对象，不递归证明lineage。

目标写入建议为完整分叉事务内部专用步骤，签名候选如下：

```text
write_agent_contexts_into_target_in_transaction(
  repo,                       # 与外层分叉相同的repo/connection
  target_session,
  target_document,
  agent_contexts              # collect返回的映射
) -> {object_key: target_object_write_result}
```

writer应在目标正常初始化后，用传入的同一个 `repo`/connection读取目标对象真实当前revision，按其revision执行CAS并在同一外层事务内完成。**授权主体不是 `agent_node_id`：** 当前图定义把上下文对象的read/write声明给 `context.output / context.merge`，而 `ObjectBinding.writers` 是实际 `context.merge` 节点绑定；`agent_node_id` 只标识上下文归属。目标loader应从 `target_document` 找到此 `object_key` 对应的真实声明writer，核对该node仍绑定同一个Agent及对象，并据此确认对象binding声明了该writer权限；不能把Agent节点ID传给对象写入口。

这个内部写入不是执行 `context.merge`，不制造merge输出、node run或producer。纯 `validate_agent_checkpoint_value` 只能验证值，不能成为任意 `objects.apply` 写入该类型的授权。**新目标写入只由完整历史分叉事务的这个内部入口触发**：从目标document解析真实 `context.merge` writer node id，读取目标对象实际当前revision，构造目标CAS `WriteIntent`，再经普通 `objects.apply(target_session_id, node_id=context_merge_writer_id, writes=...)` 写入。其普通 `session_object_receipt` 只记录目标对象在已声明writer权限下的修改事实，不表示执行过merge或生成过run/artifact；`context.merge` node id是实际声明的对象权限主体，不是假producer。`graph.objects.update` 必须拒绝直接改写该受保护根类型，不能仅凭值形状绕过live接纳；正常live settlement仍由真实 `context.merge` 执行、走现有 host/settlement 链。这样无需另建通用authority平台、隐藏token或source写入账本。

**必须由用户裁定的选择：** 接受“目标正常初始化后的现有对象CAS + inline逻辑值”，并接受loader按目标文档声明的真实writer权限经普通 `objects.apply` 写入；其receipt仅记普通对象修改，不冒充merge执行。generic object update不凭纯shape改写该根类型；正常live merge只走真实执行接纳后的settlement。目标loader仍不制造artifact/run/merge，也不保留原 `view_ref` 或增加来源追踪平台。

## 4. 审阅出口

确认前保持以下事项为待定，不当作已安装/已批准：

- inline逻辑值的持久物理表示、当前 `@4` reader/writer/schema如何成组替代；
- 目标先正常初始化，再用对象绑定中真实声明的 `context.merge` writer身份与目标当前CAS写入；
- 2.1实际持久reader/`CONTEXT_VIEW`/现有 `PROMPT@6`、`context_update_v2`、Agent history validator和压缩消费者对无旧source消息的接入；新live消息身份校验继续保留；
- 目标普通object receipt记录该对象确实被写入，但不等价于live merge执行事实；generic `graph.objects.update`不改写此根类型。

方向性验收仅要求：已接纳Agent上下文按白名单独立读取；模型/工具协议顺序、call-result关联和provider签名内容不变；消费ID未清空；formal未初始化/空状态不入点；目标值不依赖源pointer/authority，使用目标真实owner、声明writer权限和CAS；generic object update不凭纯shape取代live接纳；整次新目标写入与检查点分叉同事务，源业务状态不写。详细真实写集合、事务伴随行和失败注入范围留给1.2在本契约审阅后核定。
