## 1. 一句话与一轮数据流

**当前机制是：读出Agent自己的上下文 → 装配本轮请求 → Agent内部维护工作上下文并输出更新包 → 独立merge节点验证和CAS写回。Agent成功不等于上下文已经写回。**

```text
Agent持久上下文根
    |
context.output@4
    | CONTEXT_VIEW@4
    +-------------------------------> context.merge@4 的 view
    |
context.assembly@4 <--- 提示词材料、当前输入
    | PROMPT@6
agents.execute@4 / @8 <--- 模型绑定、可选压缩策略
    | result: TEXT@2               | context: AGENT_CONTEXT_UPDATE@1
    |                              v
    |                       context.merge@4
    |                         验证、CAS写回
    |                         输出新view及真实commit回执
    v
其他下游业务，例如聊天追加

整个工作流可信成功后，再另行收集已接纳根状态形成成功检查点。
```

这是现有职责说明，不规定聊天追加与上下文merge的统一先后。两者按图的实际依赖和runtime计划执行；Agent A/B也没有固定的跨Agent写回先序。

## 2. 三种上下文不要混淆

| 对象 | 谁维护、何时变化 | 当前实际内容 |
| --- | --- | --- |
| 持久Agent上下文根 | 工作流数据层；merge节点成功接纳时变化 | `session / workflow.effective-context / 4`，inline逻辑值 |
| 本次Agent工作上下文 | Agent内核内部；每次接受消息或完成压缩时变化 | 初始`s0`、当前`effective_messages`及有序`context_operations`；不是每一步都写根 |
| 成功检查点 | 工作流可信成功收尾后固定存档 | 节点声明的固定配置及已接纳Agent根状态；不追踪运行中间变化 |

根值恰好是：

```json
{
  "messages": [],
  "layout": [],
  "accepted_delta_ids": [],
  "generation": 0
}
```

`messages`保存`message_id / role / blocks`，可选保留`thinking_summary / provider_metadata`；不保存执行`source`、消息`schema_version`或历史artifact指针。`layout`与消息一一对应，记录`history / summary / once`、`round_id`与压缩许可。

`accepted_delta_ids`防止同一个Agent更新重复接纳，不是once来源台账。`generation`随压缩次数增长，不是对象CAS revision，也不是每回合都加一。当前消息数及已接纳更新ID各有4096结构上限，压缩不清空更新ID。

依据：[逻辑根校验和投影](../../../../backend/src/phase1_agent/context_contract.py#L40)、[消息投影](../../../../backend/src/phase1_agent/context_contract.py#L77)、[正式类型登记](../../../../backend/src/phase1_agent/context_v4_nodes.py#L115)。

这里的`messages`是Agent根内部的逻辑字段，不是平台通用messages集合。它不推翻“通用messages不绑定会话、并非每会话必有、不自动纳入首版检查点”的已定边界。

## 3. 实际节点和端口

| 节点 | 配置与输入 | 输出与职责 |
| --- | --- | --- |
| `context.output@4` | `object_key`、`agent_node_id`；无数据输入 | 读取有权限的根，输出`CONTEXT_VIEW@4`；携带准确owner和`revision_id/head_revision`依据 |
| `context.assembly@4` | `view`；可选多输入`materials: PROMPT_MATERIALS@1`；`current_input: TEXT@2` | 输出`PROMPT@6`；组合历史、有效材料及本轮用户输入 |
| `agents.execute@4 / @8` | `prompt: PROMPT@6`、`model`；可选`compaction_policy` | `result: TEXT@2`与`context: AGENT_CONTEXT_UPDATE@1`；只产生真实接纳后的输出包，不写根 |
| `context.merge@4` | `object_key`、`agent_node_id`；`view`和`context` | 验证更新来源、同一冻结view、执行事实和结果，提交根CAS写入；输出新view和`CONTEXT_COMMIT@2` |

两种Agent component版本当前都使用同一个生产executor。`@8`表示Gemini节点组件版本，不表示schema2的新逐请求executor已安装。

节点登记依据：[context节点](../../../../backend/src/phase1_agent/context_v4_nodes.py#L136)、[Agent节点](../../../../backend/src/phase1_agent/agent_package.py#L47)。默认包包含`workflow.context / workflow.agents@1.0.0`，实际saved package selection仍可覆盖默认，见[builtin_packages](../../../../backend/src/phase1_agent/builtin_packages.py#L16)。

### 读取与装配

`context.output`从数据层读inline值，构成临时view。owner包括会话、对象键和Agent节点身份；basis保存当前对象的准确revision。

装配把当前输入转换为一条user消息，标为`current`且不可压缩；加入符合位置与深度规则的材料。Agent把装配好的消息冻结为本次调用的`s0`，内部后续模型轮次在这个基础上继续，不持续重读提示词节点配置。

依据：[读取](../../../../backend/src/phase1_agent/context_v4.py#L68)、[当前输入生成](../../../../backend/src/phase1_agent/context_prompt_v6.py#L39)、[装配](../../../../backend/src/phase1_agent/context_prompt_v6.py#L155)、[快照](../../../../backend/src/phase1_agent/agent_executor.py#L43)。

## 4. 追加、压缩与最终投影

### 4.1 Agent内部更新

内核接受assistant、tool及必要协议反馈消息时，保留原始执行事实，同时向工作上下文追加消息，并记录`append`操作。需要精简时记录`compact`操作，两类操作按实际发生顺序交织。

压缩只改变有效上下文，不改写已经接纳的原始模型/工具执行历史。工作更新完成后重放有序操作生成候选上下文，而不是再把“原始整轮消息”追加一遍。

依据：[接受消息](../../../../backend/src/phase1_agent/runtime.py#L560)、[有序重放](../../../../backend/src/phase1_agent/context_update.py#L146)、[构造候选](../../../../backend/src/phase1_agent/context_v4.py#L104)。

### 4.2 哪些内容会留下

- 当前user输入在成功候选中转成该回合的`history`。
- `per_request`材料标为`fixed`，本次请求使用，投影时不写入持久根。
- 已注入的`context_once`材料保留`once`生命周期；允许压缩的纯文本后续可被摘要替代。
- 正常assistant/tool协议内容保留；协议纠正反馈不作为新的用户历史持久化。
- 最后的`final_answer`控制调用和tool结果通常投影为一条可见assistant回答。携带供应商协议元数据时保留该真实协议对，不伪造或丢弃签名内容。

依据：[持久投影](../../../../backend/src/phase1_agent/context_v4.py#L126)、[Agent完成输出](../../../../backend/src/phase1_agent/agent_executor.py#L343)。

### 4.3 当前生产压缩策略

现有Agent可接`agents.compaction-policy@1`。默认策略为`enabled=true`、`trigger_tokens=0`、`keep_depth=2`、`summary_prompt=""`、`target_tokens=null`；空摘要提示词使用模块默认文本。

实际生产触发条件仍为：输入估算加输出预留达到容量的90%，或非零`trigger_tokens`提前触发。没有策略或策略禁用时不自动压缩，达到该水位会真实报容量错误。默认计量是序列化消息与工具的UTF-8字节保守估算，不是假称供应商精确tokenizer。

选取较早、声明允许压缩的user/assistant纯文本，保留最近`keep_depth`个历史回合。旧摘要和符合条件的本次新增assistant纯文本也可参加；当前输入、固定材料、工具调用/结果、协议反馈和带供应商元数据的消息不参加。工具调用批次必须先闭合。

摘要请求保留当前上下文并在尾部添加限定压缩范围的指令，通过模型通信能力发出；摘要结果要求非空、正常结束且无工具调用。摘要作为派生user消息插到被替换范围的第一个位置，其他消息次序不变。压缩后必须更短且降到90%水位以下，否则报实际错误。

源码中的`context_checkpoint`是这条**上下文摘要消息**，不是产品成功检查点。此次调查没有触发摘要请求。

依据：[策略默认值](../../../../backend/src/phase1_agent/context_compaction_policy.py#L43)、[计量](../../../../backend/src/phase1_agent/context_compaction.py#L92)、[触发](../../../../backend/src/phase1_agent/context_compaction.py#L126)、[范围选择](../../../../backend/src/phase1_agent/context_compaction.py#L146)、[实际维护](../../../../backend/src/phase1_agent/runtime.py#L731)。

## 5. once现在到底如何判重

当前汇总先对本次物料的enabled once条目按`(role, text)`去重；装配再扫描现有上下文纯文本消息，已有同角色、同正文就不注入，没有才注入，并在本次装配中立即占键。

所以它判断的是**当前内容是否存在**，不是追溯来源节点或永远只执行一次：

- 相同角色、正文，即使来自不同节点，也只注入一次。
- 只改变位置或顺序，不会因为节点身份不同再注入；正文或角色改变则可能成为新内容。
- 禁用条目只停止新注入，不会主动删除已经写入上下文的旧内容。
- 原文被压缩成摘要后，若当前上下文没有相同正文，下一轮允许重新注入。system once不允许压缩；user/assistant背景材料可声明允许。

持久根没有once来源账本。请求物料与live更新artifact仍有准确输入引用、来源和收据，不能把“根去执行来源”扩大成“全部运行数据无来源信息”。

依据：[汇总判重](../../../../backend/src/phase1_agent/prompt_lifecycle.py#L120)、[装配判重](../../../../backend/src/phase1_agent/context_prompt_v6.py#L70)、[system保护](../../../../backend/src/phase1_agent/context_contract.py#L63)。

## 6. 写回、归属与检查点

### 写回不是Agent自动动作

Agent节点成功只接受`result/context`输出artifact。没有执行`context.merge`，这次Agent工作上下文不会经这条生产路径写入持久根。

merge要求输入view正是Agent冻结使用的那份，更新owner、Agent节点、对象键和revision依据一致；它根据已接纳执行事实重建候选，再生成`WriteIntent`。

正式节点成功事务同时处理候选输出、对象CAS写入、真实commit回执及最终输出；失败不留下这个节点的半套接纳。下一轮读取新根和新revision，不拿旧view当新的CAS依据。

依据：[merge验证](../../../../backend/src/phase1_agent/context_v4_nodes.py#L55)、[CAS准备](../../../../backend/src/phase1_agent/context_v4.py#L248)、[settlement](../../../../backend/src/phase1_agent/context_v4_nodes.py#L94)、[正式事务](../../../../backend/src/phase1_agent/graph_service.py#L915)。

### Agent A/B隔离靠准确配置

A/B分别使用不同`object_key`，读取/写回节点准确绑定各自`agent_node_id`。身份不会因共用executor代码自动共用，也不会仅因叫“A/B”自动隔离；误用同一对象键会争用同一对象及CAS依据。

A结果传给B可形成数据依赖，但不由此推出“A必须先写回再写B”或“B结束后才允许写A”。具体图决定依赖，runtime决定实际顺序。

### 成功检查点只收已接纳状态

merge更新的是当前状态；工作流整体成功后，[收集器](../../../../backend/src/phase1_agent/checkpoint_collection.py#L205)才收取inline Agent根和声明配置，由[成功收尾](../../../../backend/src/phase1_agent/graph_service.py#L1107)写不可变full/diff点。

Agent内部压缩成功、Agent节点成功、merge节点成功和整个工作流可信成功是四个不同事件。不能由其中一个冒充另外三个；检查点不替代当前状态写回，也不作为通用聊天消息存储。
