## 1. 七项先序关系的处置

| 原盘点项目 | 后续已确认规则 |
| --- | --- |
| 1. 变量注册与初始赋值 | 用户主动触发的工作流交互节点，不要求连接到普通执行链；替代此前自动独立初始化例外。 |
| 2. 变量赋值 | 按上游连接进入执行范围；无上下游时由 runtime 判为孤立节点并排除，节点本身不重复判断连接或激活。 |
| 3. 世界书读取变量 | 访问工作流变量数据，读取实际执行时的值；不因访问同一变量就建立注册、赋值到世界书的先序。 |
| 4. 通用聊天追加 | 由统一聊天输出组件连接下游追加节点，追加节点处理后与工作流数据层交互。 |
| 5. 酒馆聊天追加 | 使用同一职责分配，不维持一套独立的先序补线规则。 |
| 6. 串行 Agent 写回 | A、B 上下文独立；没有固定的“Agent B -> A 上下文写回 -> B 上下文写回”业务规则。 |
| 7. 上下文写回与聊天收尾 | 各更新及追加节点按实际数据依赖和 runtime 调度执行，不从旧示例推导统一的跨业务写回先序。 |

## 2. runtime 与节点的责任

runtime 统一决定普通执行链的范围、孤立节点排除及执行顺序。变量赋值节点无上下游时不执行，是因为 runtime 没有将它纳入执行范围；不能在节点执行器中再写一套“孤立则不执行”的判断。

无输出端口的写入节点可以通过上游连接进入执行范围。进入执行范围后，节点负责自身数据处理和写入；runtime 负责依赖优先，同批没有明确依赖的就绪节点仍按创建序号串行执行。节点身份继续使用 UUID。

变量注册与初始赋值通过用户显式交互触发，属于与工作流交互的节点能力，不要求为普通消费者逐个补注册先序，也不自动插入普通执行链。具体交互入口、目标数据归属和运行中编辑约束在 D/E 方案中对接既有规则，不借本次订正另建一套执行引擎。

世界书访问变量时取得当时的值。注册、赋值不会因对象键相同就被自动激活或成为世界书的前置依赖；若实际图内已有数据连线，其依赖仍由 runtime 正常计算。

## 3. 聊天追加与独立上下文写回

通用聊天和酒馆聊天按统一的聊天输出组件连接下游追加节点；追加节点完成处理后与工作流数据层交互，数据层负责实际持久化及真实写入结果。

后续接线替换旧的“追加用户 -> 先序触发重新读取 -> 追加助手”补线机制。具体消息内容、端口和接纳契约在 D 中明确；不得直接把旧读取结果重复用于两个仍要求当前 basis 的旧写入，也不由本页擅自规定追加节点数量或新的事务格式。

Agent A、B 各自上下文分别更新。A 的结果传给 B 可以构成实际数据依赖，但不因此产生两个上下文写回之间的固定先序。写回时点只依据实际输入依赖和工作流 runtime 调度；若 runtime 将 A 的上下文写回排在全部数据写回的最后，仍按该计划执行。

同样，不把旧示例的“上下文写回 -> 聊天读取”控制边固化成普遍业务规则。成功检查点仍按 [16](16-检查点装配边界与前端节点化决定-2026-10-12.md) 的已定时点形成：助手消息闭合且工作流成功结束本次运行。检查点完成条件不等于必须硬编码 A/B 或聊天/上下文节点之间的顺序。

后续核心验收应覆盖：

- 用户主动触发变量注册及初始赋值，普通执行不自动触发注册。

- 世界书读取当时变量值，不自动激活注册或赋值；真实数据依赖仍生效。
- 统一聊天输出组件连接追加节点，消息写入、重读及真实回执一致，退出旧重复读取补线。
- A/B 上下文分别写回，遵循 runtime 计划，无固定跨 Agent 写回先序；A 写回排在末尾也可完成。
- 工作流成功结束后才形成成功检查点，既有失败、暂停及请求事实边界保持。
