## 1. 当前表单有不同的生效链路

| 表单范围 | 当前输入与生效 | 需要订正的部分 |
| --- | --- | --- |
| 通用节点字段 | 文字、数字和 JSON 先保存输入原文，`change` 时解析并修改内存图；选择和开关直接修改内存图 | 字段变化尚未直接保存正式定义；草稿读取、依据同步参与普通字段编辑 |
| 节点专用字段 | 提示词组、提示词引用、模型引用和 Lorebook 等复制配置到表单，点击“应用”前保存草稿 | 仍存在草稿落盘、应用到内存图、保存工作流三段链路 |
| 全局资源 | 供应商、命名模型配置、提示词、Lorebook 各有单次保存入口 | 保存前等待表单草稿，保存完成后也可能等待草稿确认；另有多份未提交草稿切换和恢复 |
| 名称等管理元数据 | 提示词显示名称由独立表单和管理标签保存；Lorebook 名称随资源保存 | 同一资源的名称与正文存在不同保存入口，管理数据仍借草稿层持久化 |
| 运行输入、事件和预算 | 各自编辑输入，应用或提交前保存对应草稿 | 移除草稿前置；区分执行定义编辑和提交到明确会话的运行命令 |

表单是业务对象的编辑界面，普通内存输入属于编辑过程；正式配置归节点所在工作流或对应全局模块。会话运行输入与共享节点配置分别提交，不因为都显示在前端就采用相同保存规则。

## 2. 节点 SDK 返回的不是后端保存结果

提示词组当前链路：

```text
复制 node.config.members 到表单
  -> 输入变化保存表单草稿
  -> 点击“应用条目”
  -> 等待当前草稿及全部表单草稿保存
  -> sdk.configureNode
  -> 修改内存工作流并持久化工作台快照
  -> 另外保存工作流定义
```

`configureNode` 的类型目前是同步返回 `{ workflowId, nodeId } | null`。`patchNodeConfiguration` 校验目标和扩展后调用 `editable`；`workflowEditing.edit` 接受编辑文档并调用工作台持久化，不直接等待正式定义保存。取消草稿工具后仍须接入后端原地修改或派生接口，才能让表单完成一次正式提交。

另一个耦合是 SDK `lifecycle` 包含当前会话 ID，专用配置表单将其纳入编辑依据。共享节点配置没有随会话选择改变归属，但会话变化仍可能触发表单重载或拒绝应用。后续配置提交应使用工作流、节点和必要配置依据；扩展身份及写入权限仍保留，会话选择不作为共享配置冲突依据。

## 3. 全局资源和数字字段仍有草稿职责

`useResourceFormDraft` 不只持有当前表单，还维护多个资源的未提交副本、切换列表和恢复操作；重新读取正式配置时，先将整份旧表单归档并验证落盘，再替换表单。这些职责按当前决定退出，保留当前对象的普通内存表单。

提示词和 Lorebook 保存前除等待整张表单草稿，还逐项等待数字原文草稿；资源请求得到回执后，面板完成回调仍调用 `localDraft.flush()`。`resourceOutbox` 会等待这个回调再标记完成，因此正式内容已经写入而表单草稿失败时，流程仍可能报告确认未完成。后续正式写入结果与草稿存储解除依赖，真实保存、刷新或字段解析失败各自报告来源。

`RawNumberInput` 已有两种用法：父表单传入 `rawValue` 时原文由父级控制；带草稿地址且未传入 `rawValue` 时则保存独立数字草稿。可复用现有原文与解析能力，移除草稿加载、恢复和冲突锁定；如 `-` 或未完成 JSON 等输入，只需留在当前控件内存并提示解析错误，不需要持久化或恢复。

供应商 Key 正文目前在专用编辑器的 `secret` 内存状态中，不放入通用表单草稿；草稿通道承载的是不含 Key 正文的请求证据。简化时保持一次“保存供应商”及私有 Key 保护，复用必要原请求证据和回执能力，不将其整删或新增通用恢复系统。

## 4. 表单职责与提交建议

已确认的收敛方向：表单编辑节点已有配置，固定/可调策略归节点，不增加表单配置或会话专属配置；自动提交正式后端，取消草稿和“应用后再保存”。全局管理及会话运行命令继续使用各自接口。按对象区分如下：

2026-10-12 用户指定固定/可调的入口为节点上的切换按钮，使用节点注册机制接入，复用扩展与宿主。第一步明确按钮声明及策略接口，后续自动提交阶段对接正式后端结果；按钮不另持有一份配置，不作为独立草稿或“应用”步骤。第一版可调范围及已有历史保护规则不变。

| 对象 | 编辑与提交归属 |
| --- | --- |
| 工作流节点配置及固定结构 | 普通内存编辑，完成一次有效修改后自动提交对应后端接口，由后端判断原地保存或派生；不另设“应用后再保存”阶段 |
| 全局供应商、模型配置、提示词和 Lorebook | 当前对象一个内存表单，通过对应模块保存；供应商配置与新 Key 一次提交。内容名称与正文的具体字段、复制和保存接口随管理收敛方案给出 |
| 会话运行输入、事件载荷和预算增额 | 当前内存输入在运行、发送或对应命令时提交到明确会话；不作为节点配置保存，也不保存输入草稿 |
| 未完成的数字或 JSON 输入 | 保留当前控件原文及直接解析提示，形成合法格式后才能提交；不新增持久草稿或错误恢复 |

具体自动提交触发及粒度已有以下建议，尚未逐项确认或实施：

| 编辑动作 | 当前建议 |
| --- | --- |
| 文本、数字及 JSON 字段 | 输入留在控件内存，失焦时提交合法内容；未完成或无法解析时直接提示，暂不提交 |
| 选择、开关及增删条目等完成一次修改的操作 | 操作完成后提交，不再增加“应用”步骤 |
| 提示词组等复合节点配置 | 一次提交整个节点配置，后端比较实际变化字段，统一决定原地保存或派生 |

建议后端在一次提交中按实际变化分类：完整配置里的未变化固定字段不触发派生；同时修改固定与可调内容时，有有效会话则整次修改写入派生工作流，不拆成两份保存。成功返回目标工作流及节点的正式结果，界面跟随该目标。具体字段、响应和 SDK 异步保存契约随配置接口方案给出，不把这些建议登记为已确认设计。

后端实际接纳结果返回后更新当前正式配置，保存失败直接暴露原始错误和诊断信息。切换目标后，旧请求结果仍属于原目标；必要对象身份和写入冲突检查保留。固定/可调策略决定是否派生与恢复行为，表单不另维护一套会话专属节点配置。

本次查看完成的是源码链路核对与讨论准备。实际草稿移除、表单提交和 SDK 接口改造均未实施；历史后端 377、前端 1177 通过只验证此前批次，不验证本文方案。
