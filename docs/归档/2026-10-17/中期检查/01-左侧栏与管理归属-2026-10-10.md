# 左侧栏与管理归属检查

日期：2026-10-10，Asia/Shanghai。检查对象为当前 `develop` 未提交工作树；基础提交和检查限制见 [目录说明](../../../中期检查/README.md)。

## 1. 总体结论

左侧栏位于应用壳和管理界面层，不属于工作流执行层。组件、状态库、服务和仓库已有拆分，但业务所有权及生命周期没有完整分离。

不能将现状描述为“完全没有后端支持”：当前有统一 `GraphApplication` 入口、图服务、供应商配置服务、全局资源仓库和本机草稿仓库。问题是这些入口及实现之间的归属不一致，而不是单纯缺少某个名为 Sidebar 的服务。

## 2. 前端层级

| 区域或功能 | 当前入口 | 状态与行为归属 |
| --- | --- | --- |
| 左侧栏布局、三个导航区域 | `App.vue` | 根组件直接组织界面与部分管理行为，没有独立工具栏或工作流目录组件 |
| 收起与展开 | `useWorkbenchSidebar` | 独立布局偏好，使用浏览器 `localStorage`；不是业务草稿，无后端调用 |
| 工作流目录、选中与打开 | `workspace` 状态库 | 管理条目投影、当前选中项、当前打开项及导航区域 |
| 图草稿、保存依据、会话、运行等 | `workflowGraph` 状态库 | 同时持有图文档、保存快照、会话引用与观察、历史、未决请求、节点及扩展目录等 |
| 会话列表和采用修订 | `GraphSessions` | 组件已拆分，业务状态和命令仍来自 `workflowGraph` |
| 供应商及模型配置 | `ProviderSidebar`、供应商插件面板 | 面板编辑逻辑已拆分，面板可用性依赖图宿主返回的包与扩展目录 |

## 3. 后端层级与调用

```text
界面组件 / 前端状态库
  -> 前端应用逻辑与 API 适配器
  -> HTTP commands / queries
  -> GraphApplication 分发
  -> 具体服务或 GraphWorkflowService
  -> SQLite / 私有 Key 库
```

`GraphApplication` 属于应用分发层，不持有执行状态或持久业务记录。供应商及凭据操作被分发给 `provider_configuration`，其余多数管理操作仍落在图服务上。

正常页面的图 API 请求先取得 `GraphWorkflowService`，再进入分发；专门的原回执读取有绕开该初始化的路径。因此不能把“供应商类可以独立初始化”外推为“当前页面配置入口已完全脱离图服务”。

源码依据：[graph_application.py:56](../../../../backend/src/phase1_agent/graph_application.py#L56)、[server.py:135](../../../../backend/src/phase1_agent/server.py#L135)、[server.py:358](../../../../backend/src/phase1_agent/server.py#L358)、[server.py:373](../../../../backend/src/phase1_agent/server.py#L373)。

## 4. 数据实际归属

| 数据 | 实际归属及存储 | 当前特点 |
| --- | --- | --- |
| 目录、所有编辑图、当前选择、会话引用 | 整份工作台快照，通用 `LocalDraftStore`，SQLite `local_editor_drafts` | 左侧列表不是独立后端工作流目录查询的结果 |
| 已保存定义、修订、会话、运行事实 | `GraphWorkflowService` 与 `GraphRecordStore`，图记录 | 与编辑目录、草稿存储不同 |
| 供应商及全局模型配置 | `GlobalResourceStore`，SQLite `global_resource_current` | 配置是共享资源，工作流模型节点仅引用 |
| Key 正文 | `PrivateCredentialStore`，独立受保护私有库 | 不进入通用草稿、图或公开资源；不是待合并到普通内容存储的对象 |
| 提示词、世界书 | `GlobalResourceStore` | 管理读写当前也经供应商配置服务转交 |
| 目录归档和会话显示名称 | `managementLabels -> formDrafts -> LocalDraftStore` | 属于前端解释的通用表单数据，后端无专门目录归档语义 |
| 左侧栏收起偏好 | 浏览器 `localStorage` | 纯布局偏好，与业务内容本机保存原则区分 |

工作台快照由 `capture()` 同时打包目录和全部图条目；启动读取草稿后恢复目录及图条目，而不是由后端独立列举工作流来组装左侧列表。

当前全局资源管理链路为：

供应商服务在图宿主组合中使用整个注册类型目录，因此这条路径也处理提示词和世界书。它并不因此调用模型 API，但通用内容资源管理被归到“供应商配置服务”名下，模块职责与命名不一致。

## 5. 已确认的待规范事项

| 编号 | 现状 | 需要规范的边界 |
| --- | --- | --- |
| MID-S01 | 工作流目录依附整份工作台草稿 | 明确目录、编辑草稿、已保存定义分别由谁管理，不再用一份编辑快照隐式承担全部目录权威 |
| MID-S02 | 导航、图编辑、会话观察与执行集中在大状态库 | 确立显式状态接口与操作责任；拆文件本身不算完成 |
| MID-S03 | 配置服务类可独立使用，但正常页面入口依附图宿主生命周期 | 应用层组合明确的配置管理与工作流服务，避免全局配置操作必须依赖执行宿主启动 |
| MID-S04 | 通用内容读写经过供应商配置服务 | 通用资源基础设施及内容管理有明确归属，供应商不承担无关内容业务 |
| MID-S05 | 导航及目录操作先保存全部表单和工作台 | 规定保存、切换与失败隔离范围，避免无关表单问题阻止其他管理操作 |
| MID-S06 | 归档及名称作为普通表单草稿解释 | 明确持久管理元数据与编辑草稿的区别；顶部及条目归档细节见 02 |

MID-S05 的直接证据是 `App.leaveEditor()` 调用 `persistence.flushAll()`，后者先保存所有表单，再保存整份工作台。任意保存失败可阻止切换左侧区域或打开另一工作流。

源码依据：[App.vue:86](../../../../frontend/src/App.vue#L86)、[workbenchPersistence.ts:129](../../../../frontend/src/stores/workbenchPersistence.ts#L129)。

这些事项是已经确认的结构和行为特点，不等于每项都已复现产品故障；当前也没有据此登记越权漏洞、无限递归或性能数值。

## 6. 酒馆入口关联问题

本轮此前已定位“所选会话与已保存定义不一致，刷新或明确改绑后打开”：

- 酒馆打开入口要求所选会话与工作台保存快照属于同一工作流且修订相等。
- 会话未读到、身份不匹配、归属错误及修订不同被合并为同一提示。
- 保存有变化的图会生成新修订，但不会自动采用到现有会话。
- 当前文档比较包含布局和名称，移动节点或改名保存也可能形成修订差异。
- 后端消费者能按会话绑定修订读取；入口额外要求其等于工作台保存修订。

这说明打开入口、编辑修订和会话生命周期存在不合理绑定。仅凭这句提示，不能确认用户当次命中了哪个条件；本次未读取用户实际会话数据。

源码依据：[chatLaunch.ts:45](../../../../frontend/src/plugins/tavern/chatLaunch.ts#L45)、[workflowManagement.ts:59](../../../../frontend/src/application/workflowManagement.ts#L59)、[workflowGraph.ts:412](../../../../frontend/src/domain/workflowGraph.ts#L412)、[graph_public.py:20](../../../../backend/src/phase1_agent/graph_public.py#L20)。

`tavern.chat.presentation` 节点本身确实存在，不能把“酒馆完全没有节点实现”当作检查结论。当前确认的是页面入口通过 URL 携带工作流与会话，并由额外版本条件决定能否打开；完整节点前端生命周期和后续会话变更策略仍需单独设计检查。

## 7. 已确认方向与未决设计

讨论已确认：应用管理层组织工作流管理、供应商与模型配置管理、内容管理。左侧栏只是展示这些能力，不以视觉位置决定业务所有权。

可共享 SQLite、通用校验、传输和 `GraphApplication`；不要求为了独立而拆成多个进程或重复存储架构。关键是每个模块明确持有数据、接受操作和承担故障的范围。

工作流目录及草稿接口、会话采用变更的规则、配置服务组合方式、模块依赖形态尚未裁定。本记录不授权直接删校验、迁移用户数据、重放请求或实施整体重写。
