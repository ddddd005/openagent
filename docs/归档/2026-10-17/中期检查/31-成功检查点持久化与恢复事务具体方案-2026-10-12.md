## 3. 规定结果的保存投影

### 3.1 保存什么

继续使用已交付 `workflow.runtime-state@1`，不增加第二份 context/counter/模型配置分区。调用者先从一份一致的正式读取得数据，再依**本次审阅的精确节点/对象保存名单**组成结果投影；不能直接把当前所有 objects/private 数据扫描进成功点。

| runtime-state 分区 | 保存内容 | 排除内容 |
| --- | --- | --- |
| `node_states` | 声明需要恢复的运行业务 private 正文，保留 `owner_component_id/schema_version/payload` | 输入 buffer、200ms 通信序号、页面/运行开关控制状态、执行现场 |
| `program_state.values/data` | 注册变量的类型、定义、值及共享业务数据 | 变量库 revision 和凭据 |
| `objects` | 已接纳 Agent 上下文、once 消费台账、业务 generation/计数器、规定聊天/展示结果及其他已审阅运行对象的 typed 正文/tombstone | 对象 binding、CAS head、`revision_id/revision` 存储包络、未发送输入对象 |
| `history` | 成功位置的 `selected_round_id/visible_entry_ids`，只含在此点实际可见的消息 | 未来 U1、所有后续候选或当前选中页面偏好 |

上下文对象可以保留准确 `view_ref`，但**必须同时证明并保留其注册 artifact 闭包中的真实正文**。闭包是不可变证据，不在 state 内重复复制成可写模型消息。缺少 view/正文/原 facts、错误 owner/schema、跨流引用或未接纳 producer 都直接失败。

注册 `references` 只表达内部保留及 provenance，不自动表达页面公开读权。[host_sdk.py:469](../../../../backend/src/phase1_agent/host_sdk.py#L469)的 `public_artifact_references` 是另一个边界。`checkpoint.read` 不公开返回完整 private state 或所有请求事实；页面只取得 checkpoint 元数据及声明可读的展示投影。可信内部 restore/proof 读取按 30 的正式 checkpoint/object root 授权，不能把 checkpoint UUID 当全局 capability。

### 3.2 当前输入与恢复默认值

32 推荐输入节点精确声明 `runtime_checkpoint: {include: false, restore: "reset-default"}`，这是**本次待审接口**。成功投影不保存未发送 buffer；恢复时清空该输入节点的当前 buffer/control 并回到注册默认值，回执明确报告 reset 的节点。已提交的 U1 在独立 immutable input/link 中保留，显式 restart 消费 U1，不把它写进 C1，也不因清空 buffer 删除 U1。

非工作类别只控制普通 runtime 筛选，不能替代 checkpoint 保存名单：主动变量注册产生的变量值仍属于 `program_state`；注册/运行开关本身的控制 private 不因此进入成功存档。前端 instance 身份来自固定 `(workflow,node,session)`，页面连接不进入 node_state，恢复后按当前固定配置查询/激活。精确声明复用注册/数据层，不建设任意 JSON 选择器或可执行投影语言。

### 3.3 初始基线与运行起点

新会话初始化 typed 默认对象、private 默认值及空 program/history 后，在**同一创建事务**产生一次 `kind: initial` 的 full C0 和 Head。C0 的 parent/round/chain/assistant 均为 null；不运行注册、赋值、模型或工具节点来制造初始基线。

之后用户主动变量注册、已接纳未发送输入或合法数据编辑只改变 current，不改 C0。第一次及以后每次普通 run 的 `chain_start` 必须另记真正开始的结果状态、已提交 input、起点 Head；不能声称当前编辑后的状态必等于 C0/C1。初始基线形成时点与投影清单作为此次具体审阅项；不把后续第一次成功延迟到未来输入出现。

`make_diff(materialize(parent), accepted_success_state)` 比较直接父点与这次成功结果。parent 是此次运行开始时选定的 checkpoint，不是按全库时间挑最近记录，也不是运行中的临时状态。恢复 C1 后形成新候选 C2'，其 parent 为 C1；空变化仍保存成功关联，旧 C2 不变。

| `workflow_rounds` | PK `(workflow_session_id, round_id)`；starting_checkpoint_id、input_id | 一个逻辑用户回合的准确起点，多个实际 candidate chains 复用；同 UUID 可在不同会话各有独立行 |

`workflow_rounds` 是候选分组及准确 reroll 起点的会话账本，不是第二套执行器。普通 chain 新声明 `round_id/input_id/starting_checkpoint_id`，替代 `base_commit_id` 的新产品用途；非聊天交互 event 不必有 round/input。这里只切换新 record 格式，原历史 chain 的 `base_commit_id`、input/body 及归属都不重写。新 schema 的精确版本随 32 一次声明，不能先安装临时版本后原地覆盖。

用户消息推荐的准确原正文引用为新待审 scope：

```text
{scope: "submitted-input", workflow_definition_id,
 workflow_session_id: <原提交所属 session>, input_id}
```

它直接指向唯一 `workflow_inputs` 正文；目标自己的 `workflow_message_links/rounds` 建立精确读取许可，不新增 input membership 表，也不把未有 chain 的提交伪装成 execution artifact。实际 `input.output` 在本轮运行形成真实 TEXT/USER_INPUT artifacts，以 input_id 和原 source_ref 保留 provenance。助手仍用 artifact source_ref。现有 `validate_reference` 尚未接受新 scope，准确 typed walker/公私读声明由 30/32 成组审阅，不在本文视为已安装。

当前运行状态没有新 `state_sequence` 或第二个 current-state 表。节点 private 去掉已批准退役的 `data_version`，当前数据继续分存现有 node/program/object 表。必要 `session_revision/head_revision` 和真实对象/变量 CAS 保留。

### 4.2 命令

查询和命令复用现有 GraphApplication/command/receipt 通道；新命名是待审建议，不另建恢复 REST 平台。所有 mutation 明确目标 session、`expected_session_revision`、`expected_head_revision`、`idempotency_key`；内部写入取得当前变量/对象 CAS，不要求客户端随恢复快照传历史 CAS。

| 操作 | 额外身份 | 行为 |
| --- | --- | --- |
| `checkpoint.read` | checkpoint_id | 同会话授权元数据/声明可读结果；internal materialize 使用另一可信范围 |
| `history.restore` | checkpoint_id 或 entry_id，二选一 | entry link 解到 C1；同一完整恢复事务，不执行节点 |
| `candidate.select` | candidate_id=成功 checkpoint_id | 同流当前固定结构核对后复用 restore；零模型/工具调用 |
| `session.from-history` | source session、checkpoint_id | 创建同流独立会话，不自动运行 |
| `round.restart` / `candidate.generate` | round_id | 同一内部 start 路径：原 starting checkpoint + 原 input_id，生成新实际 chain |
| `run.control resume` | 原 active chain | 沿原已接纳进度继续；不先 restore 成功点 |

restore/select/fork 回执至少返回实际 workflow/session、checkpoint_id、session/head revision、当前节点/对象读依据和 `reset_node_ids`；不混入整个原请求闭包。相同原请求返回原回执，不再次生成会话/存档、重置输入或调度运行。

## 5. 成功收尾与失败进度

### 5.1 D 的闭合证据

按 32 的少节点路线，推荐复用 `frontend.state.append@2`：一次处理本轮稳定 user input 和 assistant，settlement 实际写入后输出 `view/commit/closed_assistant`。**不额外新建成功节点**，也不硬编码 `B -> A写回 -> B写回` 或 `context -> chat`。

`ROUND_ASSISTANT_CLOSURE@1` 的待审字段与 32 一致：

```text
workflow_definition_id, fixed_definition_revision,
workflow_session_id, chain_run_id, append_node_run_id,
assistant_entry_id, source_ref, source_producer,
view_ref, commit_ref, object_receipt
```

全部来源于实际已接纳 artifact 和 object settlement；注册的工作流前端实例映射确定哪个 closure 是本回合收尾证据，不从任意最后 TEXT 输出猜助手完成。旧聊天 settlement 已有实际 receipt 依据，见 [chat_nodes.py:67](../../../../backend/src/phase1_agent/tavern/chat_nodes.py#L67)；旧 message 身份按 node_run 派生，见 [chat_contracts.py:180](../../../../backend/src/phase1_agent/tavern/chat_contracts.py#L180)，须由 32 的稳定 input/entry 接管，不能照搬造成 U1 重复。

### 5.2 一个完成事务

1. 核对 session 仍拥有该 active chain，固定定义一致，Head 仍为 run 的起点；完整执行结果与 retained 原 basis 一致。
2. 核对 runtime 纳入计划的所有 node runs 成功且输出已接纳，进度到末端；不要求未纳入普通图的非工作节点也执行。
3. 从已接纳 outputs 取得精确 closure，核对 append producer、助手 entry/source、typed view、commit 和实际 object receipt；核对所有结果写回，包括独立 A/B 上下文，都已按实际计划接受。
4. 从一致的当前正式读组成第 3 节规定结果投影，验证注册正文、同流权限和 30 的必要历史闭包。先将 history 指向这次成功 round/助手，再生成对直接父点的 diff。
5. 同一 `BEGIN IMMEDIATE` 写 immutable checkpoint、A1 -> C1 link、必要 membership、Head、chain succeeded、session revision/active=None 和本次成功 boundary，再写命令回执并 commit。

闭合证据缺失或任何真实写入失败就不产生 checkpoint/成功回执，不能出现 chain succeeded 但没有 C1 的半成功状态。node writes 已有各自接受事务，完成失败不伪装它们未发生，也不回滚外部副作用。

保留 [graph_service.py:1022](../../../../backend/src/phase1_agent/graph_service.py#L1022)的 retained completed result 和准确 finish key；成功存档落盘失败，`retry_archive` 只重交同一完成结果、闭合证据和 basis，不再执行 node、模型或工具。没有准确 retained 结果时直接保留错误和 `recovery_unavailable`，不从旧 C1 自动补跑。

### 5.3 U1 和未完成运行

输入保存仅更新所属输入节点。`input.submit` 的正式事务固定 input_id/entry_id 和唯一原提交正文，写 user-only submitted-input source_ref、U1 -> 当前 C1（首条输入 -> C0）及目标会话的正式引用；此时**不 update C1，不移动 Head，不启动模型**。run.start 精确消费已接受的 input_id，再由 input.output 形成实际运行产物；重复同一原提交或重来使用 U1，不产生第二个 entry，也不再持久化一份重复原正文。

pause、failed、budget exhausted、close 和管理停止只写原 progress/boundary。当前已接纳 node/object/变量结果保留，成功 Head 不动。现存 manifest 的 `chain_start/chain_boundary` 过渡职责要由一份逻辑 start/boundary 接管后才退出旧成功 snapshot 职责，不先删进度依据。

执行中的手工 session/runtime 编辑禁令保持，输入保存/提交同样不得新增“下一轮 buffer”例外。按 32 推荐，存在 prepared/running、暂停请求未确认、paused 等任何未完成 active chain，或本目标原 input.submit/run.start 请求未决时，直接拒绝输入 mutation；200ms 定时器不越过这个权限检查。不把其他独立全局表单未提交当成本节点门禁；始终不追改原 input、原 request 或既有 C1。

## 6. 同流恢复写事务

restore、candidate.select 和 restart 的恢复部分复用一个可信内部入口，不能使用现有跨定义 `_map_state/rebind`。先在同一读视图物化及验证，再在现有写事务内核对准确 session/Head 依据；注册声明与固定定义仍须精确相同。

1. 直接目标或 entry link 必须由目标会话拥有，且 workflow/fixed revision 与当前可执行会话一致。目标/workflow 归档或正在管理时只读；active execution 必须先显式停止并确认，不在 dispatch 中覆盖 current。
2. `materialize` 只加载目标自己的 parent 链；同时核对注册 private/body schema、typed object 保存名单、真实内容及 artifact/fact 闭包。调用者不能提交 state 正文、owner map 或未知 UUID 当恢复内容。
3. 事务内再次检查 `expected_session_revision/head_revision`、无 active chain、当前 binding 和必要原事实仍存在。原请求未决证据不删除；不能借恢复自动重新派发未知请求。
4. 将恢复正文写回当前私有节点、变量/shared data、typed objects/history；移除规定恢复范围内在目标状态已不存在的条目。固定对象 binding 不变，typed tombstone 与映射项 delete 分开。
5. 变量写入使用当前 CAS 后产生新的 revision；对象正文变化才保存新的 immutable value 并前移当前 CAS。不恢复历史 CAS/revision ID 或把旧事务序号写成 current。节点业务计数器、context generation/once 则按历史正文恢复。
6. 按注册声明 reset 输入/控制节点，移动 Head 到**现有** checkpoint，增加 session/head revision，写真实结果回执并提交。restore 不制造另一个成功 checkpoint，不删除后续分支、消息、outputs 或 runtime facts。

现有 [session_objects.py:349](../../../../backend/src/phase1_agent/session_objects.py#L349)的 restore 输入是 manifest revision refs，不能原封不动用在新逻辑正文。推荐在同一 store 中增加窄的 typed logical-value restore，复用 `_put_value/_grant_revision` 和 binding/CAS 检查；不包装旧 manifest 以伪装新状态，也不新增迁移服务。

恢复后 current configuration 完全未写：`workflow_current_configuration` 的 edit sequence、当前可调正文和 display 信息保持原值。上下文 once/已消费身份恢复到 C1；后续尚未装配读取当时最新配置，原已装配/request/result 仍读原事实。

restart 是用户明确的新运行，不是恢复旧请求。其完整服务命令先恢复所选 logical round 的起点，再消费其已提交 input，建立**新的** chain/node/request 身份并记录新的真实 chain_start。遇到仍未决原请求不自动重来；本批不设计外部工具副作用回滚或重启重放政策。

## 7. 独立历史新会话

### 7.1 一次同流 fork 事务

1. 核对 active source session/workflow、准确 session/head revision、选定 checkpoint 自己的链和同固定结构。归档来源只允许历史查看，不由 `from-history` 自动叉出可执行内容。
2. 可信内部取得从 initial 到选中 checkpoint 的**选中 parent 前缀**及其必要状态/消息/输入闭包；不复制整个源会话的全部候选或 current/unfinished progress。
3. 分配新 session ID 和每个目标 checkpoint ID；复制该前缀为目标自己拥有的链。目标根仍为 initial full，其余点按映射后的完整逻辑 state 重新 diff；parent/base/Head 全指向目标新 ID。
4. 保留稳定历史 entry_id/input_id/round_id，复制目标自己的 links/rounds；这些行中的 starting/checkpoint 指针映射为目标自己的点。`workflow_inputs` 原行和 submitted-input 中的原 workflow/session 坐标不改、不复制正文。源 checkpoint 之后那一条已正式提交 U 可按其独立 link 引用到目标自己的 C1，不写入先前 C1 state，绝不复制可变未发送 buffer。
5. 使用 `TypeRegistry.remap` 只处理注册允许的 session 状态引用；node UUID 和固定 binding 同流不变。必要 session revision 引用授予目标自己的对象 membership，并保留对应 immutable value，不能继续依赖源 membership 存在。
6. 复制精确结果状态/消息产物所需的 `workflow_history_membership`；如果实际 artifact 来自已接纳 interaction event，也纳入其必要证据，不只列成功 round chains。submitted-input 原正文没有 chain，不靠 history membership 授权，目标自己的 links/rounds 已给出准确原 input 读取理由。物化选中状态到目标 current，按输入默认规则 reset，写目标 Head 和独立回执。

出处放在 session.source 及原事实坐标，作为 `source_session_id/source_checkpoint_id` 参考；它们不是恢复父指针或继续运行许可。目标历史 round 账本复制本地起点映射，原 chain 的 source checkpoint ID 保持当时出处，真正原起始状态由 workflow-owned `chain_start` 证据保留；不因为源 checkpoint 后来删除而改写原 chain。

上下文具体复用：[context_contract.py:53](../../../../backend/src/phase1_agent/context_contract.py#L53)的 mapper 保留原 artifact refs；[context_v4.py:85](../../../../backend/src/phase1_agent/context_v4.py#L85)从持久对象和原 view 产生 target-owned 新读 view。不可为 fork 改原历史 view 的 owner，否则 [context_v4.py:321](../../../../backend/src/phase1_agent/context_v4.py#L321)的原 producer 证明会被破坏。

### 7.2 源删除及归属

保留原 chain/run/output/runtime facts 的原 owner 和定义坐标，将其保留责任归 workflow。原 chain 的 workflow/session/fixed revision 已受 [graph_records.py:440](../../../../backend/src/phase1_agent/graph_records.py#L440)的不可变字段检查保护，足以作为出处锚点，**不新增重复 `workflow_execution_owners` 表**。

bundle 改为：current node/session/Head/checkpoint 必须有活目标 session；历史 chain/run/output 以原 chain 的不可变三元组、不可变 definition/binding 和真实 producer 接纳核对，不再要求原 source session 必须存在。RuntimeFactStore 内层仍按原 owner 读，外层历史授权由目标自己的 root/membership 确定。

删除源 session 只移除其 current、checkpoint 链、links/rounds、Head、目录和 membership。仍被目标状态/消息/输入或其他必要证据引用的原 chain start/boundary、run/output/facts/typed revision 和原 `workflow_inputs` 正文不删除；尚未进入任何 chain 的已提交输入也按目标正式 link 保留。目标不再被 `session_history_in_use` 阻止独立使用。未决/未知请求保护照旧；删除结果必须如实区分会话数据已删除与仍保留的 workflow evidence。

首次实现不增加后台证据 GC。正常删除事务可精确处理已无引用且不受 unknown 保护的证据；删除 workflow 时核对范围、引用及 unknown 后处理整个同流内容。无需靠活 source session 或兼容 archive 来保住目标。

归档 target/session/workflow 只读，restore/select/restart/from-history 不可执行。目标已独立拥有的合法历史引用，不因原出处 session 后来归档或删除而丢失；这一规则不等于允许从尚未复制的归档来源建立新执行会话。

## 8. 成组切换与准确退役

审阅通过后，第一实施组可做历史授权、checkpoint repository、initial/restore/from-history 内部事务及合成闭合证据联调；只用独立临时 SQLite 和 fake artifacts，不能装临时 D 节点、把旧注册 fallback 当新成功证据或称页面功能已交付。

生产切换必须等待 32 的准确保存名单、输入及 closure、最终节点/包/声明和 runtime 筛选都可用，一次接入真实 finish，连同 bundle/源删除归属、消息关联和旧 progress 职责一起切换。不能只先改 Head，或先删 close commit 而丢失停止依据。

| 替代前提 | 退出范围 | 保留 |
| --- | --- | --- |
| 新 checkpoint/Head/逻辑 materialize+restore 可用 | 成功状态的旧 state_snapshot/workflow_commit/manifest 重复组合、旧变量历史指针恢复、node `data_version` | 类型/owner/schema、实际变量/对象 CAS、原 chain start/progress |

## 9. 核心验收与一次审阅项

最小验证用临时 SQLite、准确注册 fixture 和调用计数，不展开全面异常矩阵：

1. initial full、所有保存分区、业务 null/tombstone/delete 和 A/B parent 分支准确物化；注册正文/必要 artifact 缺失或越权直接失败且无部分写回。
2. 助手闭合后还有 A 上下文写回排在末尾时不提前存档；全部计划成功、真实 receipt 和闭合证据一起接受才 C1。纯管理 event、失败/pause/close 均不产生成功点。
3. U1/200ms buffer、手工稳定编辑和执行中结果不改变 C1；A1/U1 restore 都回同 C1，restore reset 输入明确可见，原 U1 仍可准确重来且不重复 entry。
4. Head 与 current/progress 独立；restore 保留当前可调 B，once/上下文回到历史状态，原已装配 A/request facts/ID/body/time 完全不变；恢复旧业务值取得新 CAS。
5. finish 写失败不伪报成功；准确 retained `retry_archive` 与已有 candidate.select/restore 均不增加模型/工具次数；原请求证据或未知结果不自动重放。
6. 同流 fork 拥有自己的 full/diff/Head/links/round/membership，引用唯一原 input 正文；原 artifacts/facts/input owner 不改。源编辑、归档或合法删除后目标可读/恢复/继续新请求，包含尚未有 chain 的 submitted input；跨流及归档直接 mutation 拒绝。
7. consumer 只读注册公开展示结果，不能通过 checkpoint/read/membership 请求任意 private artifact 或旧 fact UUID；历史 proof 不读 Key、不创建 lease/dispatch frame。

一次审阅只需确认以下具体接口，不重谈已定行为或三项默认值：

- 第 3 节精确结果投影、初始创建事务 full，以及 32 的 `include:false/restore:reset-default` 输入声明和 reset 回执。
- 新 checkpoint 表、唯一 `workflow_ref` Head 显式 schema、更换旧成功存储职责；session/head CAS、round/input/link/membership 的上述最小键和指针，原输入唯一正文及未安装的 submitted-input scope。
- 32 的 `frontend.state.append@2` 与准确 `ROUND_ASSISTANT_CLOSURE@1`，runtime 全部计划成功后同一 finish 事务，而不是独立成功节点或固定跨上下文先序。
- 与 30 一致的 workflow 原事实保留、session 独立链/引用；源删除不要求活 source、内部闭包证明不变成 consumer 全部读权。

以上为待审实现建议和目标验收，本轮没有运行这些测试。当前实际产品基础仍以 27 为准，默认生产 executor/schema 和旧生产状态路径尚未切换。
