## 2. 配置应用层

新 [workflowConfiguration.ts](../../../../frontend/src/application/workflowConfiguration.ts) 的 `createWorkflowConfigurationApplication(ports)` 实际组合 25 的 SDK 2、配置 adapter 和既有 `requestEvidencePorts`。使用：

```text
operation = definition.update
owner_kind = workflow-configuration
owner_id = 原 workflow UUID
```

应用层只维护正式配置观察值、目录与选择及必要未决请求状态，不持久化普通编辑草稿。先核对正式编辑依据，保存捕获的完整原请求证据，再单次发送 `definition.update`。证据未确认时不发送业务请求；unknown 或幂等冲突保持原请求和锁，其他工作流独立可用。

重开只加载原请求证据为 pending，不恢复为正式图或重新发送。核实只调用原 receipt read。有效拒绝报告原错误并结案证据；unknown 不解释为回滚。实际正式成功先留存 `lastResult`，视图接纳或证据结案失败仍保留原请求/锁并直接报错，不能把真实后端成功写成未保存。

保存接纳共享 current，保留后来选择的会话；派生增加准确目标目录、源保持不变，只有原选择序号未变化时才跟随目标且清空会话。迟到回执不能覆盖切换后的另一工作流或会话；更新的 current 编辑序号不被旧结果倒退。

普通生产工作台仍使用 host 1，本批没有注入新应用层、修改 manifests 或切字段组件。新应用的选择与目录是可接入接口，不能称页面端到端自动提交已完成。

## 3. M3 固定输入及纯证明

新 [model_execution_contracts.py](../../../../backend/src/phase1_agent/model_execution_contracts.py) 提供专用未安装校验及证明：

```text
validate_input_snapshot_v2
validate_agent_receipts_v2
prove_model_request
compaction_eligible_message_ids / expected_compaction_request
validate_compaction_proof
replay_model_context_operations
```

snapshot 2 移除整轮 `model_parameters`、容量和 transport projection 副本；保留准确 prompt/model/policy artifact、binding 5、canonical 初始消息、工具定义、输出 schema 和 layout。内核组件快照为 `public-3`、executor 为 `agents.snapshot-kernel@2.0.0`。这是新模块的专用校验，既有 `contracts_v2.validate_record` 尚未切 schema 分发。

receipts 2 在原字段上增加准确有序 `model_requests:[{request_id,settings_id,fact_ids}]`；每次只有实际接纳的 request/attempt/outcome 三项，准备或放弃的预分配 IDs 不能混入 accepted 清单。

逐请求证明核对 owner、binding、实际 service stream、原 request/index/settings、固定三阶段/预分配 IDs/单次 attempt、原 input refs、响应身份及原 wire/measurement。可信 resolver 只提供准确历史 projector/counter/version，证明不构造 transport 或 lease、不读取当前资源。M2 的 `intent_digest` 包含未公开逻辑 key，现有公开证据无法完整重算该摘要；不猜 key 或擅改 M2 留存格式，原正文/wire/身份核对及 reader 授权共同承担证明。

压缩证明保留原 normal trigger settings/measurement 和 discard；摘要使用自己的 settings/facts。普通上下文前后测量使用摘要设置中的普通输出预留 O，核对同 projector、estimator、tools，必须缩短且满足真实硬容量，不要求低于触发阈值。摘要请求允许 tools 为空，普通测量仍使用固定的普通 tools。

范围选择复用原 layout/keep_depth/闭合工具边界语义。accepted 增量必须是 canonical 原文、身份唯一且不能冒用初始消息 ID；不能以伪造 assistant 增量把 current 输入纳入压缩。回放按原接受消息与模型 facts 恢复操作顺序，不读今天的配置；普通 append 需要调用者提供已接纳 executor 消息依据，不能将任意输入直接称作已证明。

## 4. Live 模型事实读取

新 [model_request_fact_reader.py](../../../../backend/src/phase1_agent/model_request_fact_reader.py) 提供未安装的：

```text
model-facts:read / read-model-request-facts
输入 {port, producer, binding_ref, requests}
输出 {requests:[{request_id, settings_id, facts}]}
```

trusted host callback 从 consumer 的实际 accepted input 自行追溯 Agent 与 model binding；不接受客户端自报授权证据。reader 同一 SQLite 只读事务核对 active session/chain/consumer、准确成功 producer/model source、冻结节点声明、精确 service grant、binding artifact 及 accepted receipts 2 的完整有序请求清单。真实事实表进一步核对 owner、service stream、fact ID/sequence/stage、settings 和原 producer input refs。

读取只访问既有 graph records 与 `workflow_runtime_facts`，不实例化会执行 DDL 的事实库构造器，也不读当前资源/Key、取得租约或恢复旧可派发帧。结果和原事实复制隔离。本批仅实现 live 路径；历史 view/object artifact 闭包授权仍待后续，纯历史回放不代替历史读权限。

## 5. 请求边界调用桥

新 [model_execution_requests.py](../../../../backend/src/phase1_agent/model_execution_requests.py) 的 `ModelExecutionRequests` 消费严格 snapshot 2 和可信 M2 host callback，复用现有 `CanonicalModelAdapter._project`、消息校验及 checkpoint/replacement helpers。桥不执行工具、不注册新内核或节点。

一次 `advance` 消费闭合 canonical view 和冻结工具。普通 prepare 触发后先持久接纳 decision，再放弃未派发准备；摘要 prepare 读取当次新设置，dispatch 一次，前后普通测量使用这份摘要设置。纯文本摘要成功且缩短/硬容量通过后接纳 compact 操作，再重新 normal prepare 读取当前设置；这个准确压缩后 view 允许一次业务请求，不因低触发值再循环摘要。

模型请求事件引用 M2 真实 request/settings 与预分配 fact IDs；最终 result 必须准确接纳这些 IDs。事件 callback 使用固定原 event ID/正文，失败后仅重交原事件；原 outcome 接纳失败只重交原 M2 事实。成功摘要/结果缓存后再推进下一个阶段，不重发摘要。未知或未完成边界不能通过新逻辑 key 绕过；释放只阻止新请求和释放私有依据，不删除 durable facts。

完整工具解析/执行、final_answer 收尾、现有内核的暂停进度和全量 executor event history 尚未接这座桥。联合测试的工具闭合批次是合成 fixture，不是完整生产工具循环验收。
