## 3. 节点策略及第一版白名单

### 3.1 节点自有字段

建议使用 graph document `schema_version: 3`，`prompts.item/group` 的组件版本 `"3"`，`workflow.prompts` 包 `"2.0.0"`，前端扩展 schema `3` 与 host protocol `2`；这是待审推荐值，当前源码仍为原版本。新增节点字段：

```json
{
  "node_binding_id": "<UUID>",
  "component_id": "prompts.group",
  "component_version": "3",
  "configuration_policy": {
    "schema_version": 1,
    "prompt_mode": "adjustable"
  },
  "config": {"members": []}
}
```

`configuration_policy` 是节点配置的策略元数据，属于节点/工作流，既不是表单状态，也不是会话状态。它与 executor 的业务 `config` 分开表达，原因是现存 `object_schema` 为 `additionalProperties: false`，直接向每个业务 config 塞入策略会改变所有执行器 schema。下文列出的 `@2` 表示调查时现有组件，可调条目/组用新 `@3` 注册，其他未变节点可继续其准确原声明；不原地改写相同组件/包声明，不静默升级工作流。新图只用 schema 3，不加入 schema 1/2 产品兼容读取。

`prompt_mode` 只允许 `fixed` / `adjustable`；不支持该能力的节点显式固定。策略声明也由 `NodeDefinition` 提供，建议字段 `adjustable_configuration`：

```json
{
  "schema_version": 1,
  "policy": "prompt",
  "fields": ["members"],
  "member_identity_field": "id",
  "member_fields": ["text", "presentation", "metadata", "lifecycle", "compaction"]
}
```

这是需要新增的注册声明，不是当前 catalog 已有字段。对于提示词条目，`fields` 直接声明业务字段；对于组，后端按成员 ID 对照名单，不只凭顶层 `members` 变化就全盘放行。结构 schema、有效 ID、格式、大小和真实写入冲突检查仍保留；执行所需完整性检查留在运行路径。

策略本身属于固定配置。有有效会话后点按钮修改策略，按固定修改派生无会话新流；原流策略和历史不变。按钮在提交中或原请求未决时禁用，归档工作流只读。正常有有效会话不是全体配置编辑禁用条件，可调正文继续可保存。

### 3.2 建议首版准确范围

| 调查时节点 | 可调配置名单 | 固定部分和说明 |

建议沿用 `register_frontend_extension` 和可信本地实现表，新增精确节点目标槽 `binding.slot: node-actions`，对应最小 `kind: node-action`。节点卡片使用宿主按 component_id/version 解析出的组件，传入 node、document、正式编辑依据和 disabled；卡片不判断提示词业务或写出另一套策略逻辑。

声明示例，版本号和 entrypoint 为本次新增建议：

应显式升级宿主协议/SDK，替代当前同步 `configureNode`；不要把它继续叫做保存成功。注册扩展和 SDK 调整由接口审阅后实施，不在本轮暗中改变 host protocol 1。第 3 步实际接入时，所有受影响的现存字段编辑器声明/消费者一并适配 host 2 并按包声明约束显式升级，不添加 host 1 写配置的兼容支路；模型/酒馆准确节点和包升级清单在对应报告形成，本报告只给提示词首版明确推荐版本。

## 5. 一次保存、实际分类及无数据派生

### 5.1 最小命令和权威响应

建议以现有应用命令入口新增/替代 `definition.save` 为统一 `definition.update`，继续由 GraphWorkflowService 持有事务权限。直接 SDK 编辑节点时由宿主构造完整图提交；通用字段、节点/连线修改也走相同命令，不另外维护“先应用、再保存、再绑定”。

```json
{
  "workflow_definition_id": "<源工作流 UUID>",
  "expected_edit_sequence": 8,
  "document": "<包含完整节点策略与当前配置的编辑文档>",
  "idempotency_key": "<原请求唯一键>"
}
```

提交文档的工作流身份必须等于源身份；新工作流身份由后端在派生事务中产生。没有变更时返回 `outcome: unchanged`，不递增序号、不制造新流。

```json
{
  "schema_version": 1,
  "kind": "workflow.configuration-result",
  "outcome": "saved",
  "source_workflow_definition_id": "<源 UUID>",
  "workflow_definition_id": "<实际目标 UUID>",
  "definition_revision": 3,
  "edit_sequence": 9,
  "has_effective_session": true,
  "changed_categories": ["adjustable"],
  "node_id_map": {"<原节点 UUID>": "<目标节点 UUID>"},
  "session_id": null,
  "document": "<实际保存后的完整配置投影>"
}
```

`outcome` 为 unchanged / saved / derived。`session_id: null` 表示该配置响应不创建或搬移会话；原地保存时既有会话仍留在原流。派生返回 target document 和明确节点映射；建议节点 UUID 可在不同工作流中沿用，节点身份使用 `(workflow_definition_id, node_binding_id)`，映射仍显式返回，便于宿主跟随目标。若节点方案要求全局唯一新 UUID，应在同一派生操作中按注册引用 mapper 重写 config_node_references、对象权限和连线，并返回映射，不能用字符串替换。

建议保留定义修订解释不可变固定历史，另用 workflow `edit_sequence` 表示当前配置的真实写入冲突。它不是节点运行数据修订号，不参与历史恢复。保存可调值不让所有会话追逐一个新的固定定义修订。

### 5.2 后端分类与事务顺序

1. 核对请求身份、当前工作流归档/管理状态和 `expected_edit_sequence`；读取当前正式固定定义及当前可调值。
2. 比较实际变化，分为 presentation metadata、adjustable、fixed。名称/节点标题/画布坐标是显示管理数据，建议原地保存；不参与执行结构或状态回溯。图结构和白名单外 config 归 fixed，策略切换归 fixed。
3. 在同一 SQLite 写事务查询该工作流所有仍存在且未归档的会话，不能依据浏览器当前 selected session 或 can_submit。
4. 没有效会话：全部合法变更原地保存。有有效会话：仅 adjustable/显示管理变更原地保存；任何 fixed 变更将整次修改派生到新工作流。
5. 混合修改一次写入目标新流：不先修改源可调值，再把固定部分另存新流。源正式配置和会话/历史完全保留。
6. 写入目标及命令回执后返回正式投影。派生不写 source 的会话、node_session、上下文、变量、objects、input、chain/run、history、候选、检查点或未知请求证据。

保存门禁只保留格式、身份、权限及实际写入冲突。完整图缺少输入、不可运行、缺失包/模型不阻止合法存储，运行时直接报诊断；不得为保存访问模型上游。运行中可保存可调配置，固定编辑派生独立新流；运行中的原会话仍采用原固定定义。

当只剩归档会话后可原地改固定定义，但归档历史仍引用原固定修订，只可查看不能恢复执行；不覆盖原不可变定义。新会话绑定新修订。这使“无有效会话原地编辑”与历史可解释性同时成立。

### 5.3 固定与可调的存储建议

固定定义保存节点身份、策略及固定配置；工作流持有当前可调正文，按 `(workflow_definition_id, node_binding_id)` 保存，初始值来自该节点正式 config。只有一份可调值，不放在 session、checkpoint 或 form。

编辑读取接口合成完整 document；执行结构读取固定定义；装配求值读取当前可调字段并与该固定定义合成。历史请求和 node_run.config 记录当时实际被消费的配置，不要求永远等于固定 binding 中的初始可调正文。现存 [graph_records.py:273](../../../../backend/src/phase1_agent/graph_records.py#L273) 的冻结配置等式须替换为固定部分一致、可调消费事实独立校验。

这里的固定/可调是同一正式配置的职责划分，不保留两套生效架构或兼容读旧数据。固定历史继续使用现有 immutable workflow_definition_revision，graph document 使用本节推荐 schema 3；当前值建议表格式如下，不引入每节点 data_version：

| 新表建议 | 最小列/键 | 用途 |
| --- | --- | --- |
| `workflow_current_configuration` | PK workflow_definition_id；edit_sequence；fixed_definition_revision；display_name；node_presentation_json；adjustable_config_json | 当前正式编辑投影，adjustable 按 node UUID 存，name/位置/标题在显示管理部分；策略仍在固定节点定义中 |
| `workflow_session_metadata` | PK workflow_session_id；name；metadata_sequence | 会话名称；会话目录存在性来自 workflow_session |
| `content_resource_metadata` | PK `(scope,type_id,resource_id)`；display_name；metadata_sequence | ContentConfigurationService 的提示词 display name |

所有正式列写入仍由对应对象服务和现有 SQLite/receipt 事务处理，name 不同时另存到草稿表。`definition.read` 合成 document.name/position/title/current adjustable config；不可变历史 document 保留当时固定记录，运行结构不依赖当前显示名称。

### 5.4 表单提交建议

建议文本/数字/JSON 在失焦且合法时提交；选择、开关、增删及重排在操作完成时提交；提示词组一次提交完整 nextConfig。自动提交同对象串行，提交期间禁用其修改，不等待其他业务表单。未完成数字/JSON 原文只留内存并直接显示解析错误。

后端比较整项真实差异，完整配置里的未变固定字段不触发派生。成功后正式配置投影替换本对象依据；失败不制造草稿、冲突副本或恢复步骤。目标切换不代保存其他全局表单。上述触发、整项粒度与显示管理数据原地保存属于本次待审接口建议。

### 5.5 目录、名称及原请求证据的正式接管

当前 [managementLabels.ts:11](../../../../frontend/src/stores/managementLabels.ts#L11) 的 load/update 实际依赖 `useFormDraftsStore`，write 在 [41](../../../../frontend/src/stores/managementLabels.ts#L41) 经 stage/flush 写 `local_editor_drafts`；[ManagementLabelFields.vue:9](../../../../frontend/src/components/ManagementLabelFields.vue#L9) 又有一份输入草稿。因此 `managementLabels` 不是现成的独立正式管理 API，删草稿表前必须接管这两层用途。

建议最小正式归属如下，不新建包办三类业务的通用标签服务：

| 数据 | 正式权威与建议接口 | 不再保留的用途 |
| --- | --- | --- |

会话名称/内容元数据建议使用各自对象范围内的轻量正式 metadata 记录，保留必要 metadata_sequence 写入冲突与对象权限；它们与节点数据修订号不是同一概念。节点标题/画布坐标属于图编辑投影，经同一 definition.update 保存；会话选择不能触发名称保存。内容支线本轮只收敛现有控制器和复制，名称新接口尚未实施，不能登记为已接管。

明确推荐单独 metadata 查询，不给现有 resource.list/read/save/receipt 增加顶层字段。它们继续返回现存严格资源/回执 envelope；管理名称组件单独使用 `content.metadata.read/update`，结果为 `{reference, display_name, metadata_sequence}`，按精确 reference 与本地资源视图组合。不存在 metadata 行表示正式空名称和 sequence 0，不是恢复旧 label 草稿的分支。管理消费者及名称组件需要对应适配；执行资源读取不用名称接口。

原请求证据另行分离：当前 [workflowCommands.ts:86](../../../../frontend/src/application/workflowCommands.ts#L86) 的 entry.pending 经 workbench persistence 保存；[resourcePendingStorage.ts:5](../../../../frontend/src/adapters/resourcePendingStorage.ts#L5) 的资源 pending 也通过 `createLocalDraftChannel(kind: intent)` 写草稿表，其 [archivePending:21](../../../../frontend/src/adapters/resourcePendingStorage.ts#L21) 又使用 kind: form。它只有逻辑上独立的原请求用途，现有物理通道不能在 draft API/表退役后保留。

建议工作流、聊天、资源 pending 及其未知请求归档全部重接独立 `pending_commands` 诊断记录。最小列为 PK `(operation,idempotency_key)`、owner_kind/owner_id、request_json、request_digest、resolution（pending / verified / archived）。原 request/identity 写入后不可编辑，resolution 只能按准确原请求更新；归档保留 request 而不是删除 unknown 证据。证据服务建议 `request-evidence.write/read/resolve`：write 在发送前保存不含秘密的准确请求，read 按身份核对正文/摘要，resolve 以 verified/archived 及原摘要标记结案。它不提供 replay 命令。

客户端可以逻辑复用现存 `readPending/writePending/archivePending` ports，但要更换实现，删除 localDraftsApi/draft.* 依赖。复用现有 command receipt 核实原请求，不增加自动重放、修改请求或“恢复草稿”；准确资源 envelope/receipt 校验继续保留。resource pending/archives 与 workbench/chat pending 消费者均接管并核实后，才能删除草稿表。

该证据接口不代保存节点配置或管理数据。供应商证据沿用当前不含 secret 的私有凭据引用/结果，不能把 Key 正文放进通用 pending 记录、日志或公开响应。若证据持久化失败，直接报告且不发送无法留下依据的未知请求；正式业务回执已成功但后续本地显示失败时，保留实际成功事实，不将它说成产品写入失败。

草稿表删除前按消费者逐项证明：目录/名称正式 read/write 可用；工作流/聊天的准确 pending 请求在独立通道可核实；所有草稿持久化引用已退出。删除只按既有选定数据范围执行，不迁移或恢复旧产品正文。

## 6. 完整逻辑状态、基线和 diff

### 6.1 状态与执行事实分开

建议统一逻辑状态：

```json
{
  "schema_version": 1,
  "kind": "workflow.runtime-state",
  "node_states": {
    "<node UUID>": {"owner_component_id": "<组件>", "schema_version": 1, "payload": {}}
  },
  "program_state": {"values": {}, "data": {}},
  "objects": {
    "<object_key>": {"type_id": "<类型>", "schema_version": 4, "deleted": false, "value": {}}
  },
  "history": {"selected_round_id": null, "visible_entry_ids": []}
}
```

node_states 包含全部需要恢复的节点私有正文；program_state 包含既有变量和共享数据（包括类型/定义业务信息）。上下文正文、消费 ID、generation/计数器和聊天状态在其已注册对象或节点正文中保存，不再另建含重复内容的 `context`、`counters` 分区。逻辑恢复必须解析对象引用指向的上下文 view 和正文及其不可变 artifact 闭包，不能把一个缺失 artifact 的指针称为完整状态。

对象 binding、节点类型和配置策略是固定定义，不在每个状态重复复制；对象类型/schema envelope 保留以校验正文。对象 CAS head、变量库 revision、session revision 是当前写入并发依据，不是模型业务计数器；恢复历史值时取得新当前 CAS 依据，不伪造回退其事务序号。取消节点 `data_version` 不顺带取消会话/对象实际写入冲突、格式版本、UUID 或幂等键。

请求 settings、发送正文、已接纳输出、tool 结果、node_run、chain_run、runtime facts 是不可变执行事实；通过历史关联指向，不放进可回写正文的状态中。恢复改变选择及工作状态，不撤销或重写已发送事实。

### 6.2 最小物理记录

建议复用 checkpoint/Head 概念，替代当前重复 snapshot/commit/manifest。推荐新记录 `workflow_checkpoints`（PK checkpoint_id，workflow_definition_id、workflow_session_id、schema_version、parent_checkpoint_id、state_storage_json 及示例关联字段）、`workflow_session_heads`（PK workflow_session_id，checkpoint_id、head_sequence）；工作进度继续用 chain_run/node_run，不新增一套状态平台：

```json
{
  "schema_version": 1,
  "checkpoint_id": "<UUID>",
  "workflow_definition_id": "<UUID>",
  "workflow_session_id": "<UUID>",
  "fixed_definition_revision": 3,
  "kind": "successful_round",
  "parent_checkpoint_id": "<UUID>",
  "round_id": "<UUID>",
  "chain_run_id": "<UUID>",
  "assistant_entry_id": "<UUID>",
  "state_storage": {
    "mode": "diff",
    "base_checkpoint_id": "<同分支初始基线 UUID>",
    "upsert": {"node_states": {}, "program_values": {}, "program_data": {}, "objects": {}},
    "delete": {"node_states": [], "program_values": [], "program_data": [], "objects": []}
  }
}
```

初始基线 `kind: initial`，parent/round/chain/assistant 为 null，其完整存储格式为 `state_storage: {mode: "full", state: <第 6.1 节完整 runtime-state>}`，没有 upsert/delete/base 字段。diff 格式如上，base_checkpoint_id 为该分支初始 full，parent_checkpoint_id 为本次比较的直接父点；无变化仍可写四个空 upsert 映射、四个空 delete 数组，关联成功回合。

映射对应关系固定：upsert/delete.node_states 应用到 state.node_states；program_values 应用到 state.program_state.values；program_data 应用到 state.program_state.data；objects 应用到 state.objects。history 变化时在 upsert 增加可选完整 history 值，未变时省略，不用业务 null 或空对象表示“未变”。恢复完成仍得到第 6.1 节的一份逻辑状态。

最小 diff 按映射分区的键比较，变化正文整项替换，不首版递归生成任意 JSON Patch：

- 节点按 node UUID；变量/shared data 按注册名；对象按 object_key 比较规范 JSON。正文中数组视为原子值，顺序变化确实是变化。
- `upsert` 放完整新条目，`delete` 放明确删除的键，同一键不得同时出现；null 是有效业务值，不能代表删除。
- 对象“已删除”是有类型身份的 tombstone，可保留为 `deleted: true`；只有对象状态项本身不再存在才进入 delete。固定对象定义的增删按派生规则处理，不由 runtime delete 修改定义。
- history 是单一完整选择投影，变化时整项替换；新增真实事实仍写入原执行证据，不对旧事实生成删除 diff。
- 恢复只沿目标 parent 链，从其 base full 依次应用到目标；检查所有权、父链无环及固定定义一致。A/B 分支都以自己的明确父点比较，不能按全库时间顺序拼接。
- 比较时排除 created_at、事务修订等存储包络，但保留节点业务计数器、context generation 和消费记录。

恢复前在内存完整 materialize 并验证注册类型/权限及必要 artifact 存在，随后一个事务写当前状态、删除不再存在的节点状态、更新对象 current head 和 session cursor。失败不部分覆盖。首版不增加压缩链、定期重建、缓存、迁移读取或性能平台。

### 6.3 手动数据编辑

既有运行中手工数据编辑禁令继续使用。允许的稳定会话编辑只写当前工作状态，不修改成功检查点、后续消息、历史结果或已发请求。下次运行的 starting state 应按编辑后的完整工作状态登记在 `chain_start`/run progress，不能错误宣称仍与旧 C1 完全相等。恢复 C1 后自然得到 C1 状态；未恢复而继续下一次执行采用人工编辑值。前端编辑告知由第 3 步接入。

## 7. 成功检查点、后续输入和未完成进度

### 7.1 独立消息关联

建议新增 `workflow_message_links`（PK workflow_session_id/entry_id，下面示例列）和 `workflow_inputs`（PK workflow_session_id/input_id，source_ref、entry_id、starting_checkpoint_id）；这是 session-owned 关联，复用真实聊天 entry_id/source_ref，不在历史 entry 正文增加可变字段：

```json
{
  "workflow_session_id": "<UUID>",
  "entry_id": "<聊天条目 UUID>",
  "role": "user",
  "source_ref": {"scope": "artifact", "output_id": "<UUID>"},
  "checkpoint_id": "<C1 UUID>",
  "input_id": "<已提交输入 UUID>",
  "round_id": null
}
```

助手关联由成功结束写入，指向新 C1 和产出回合 R1；后属用户 U1 在输入接纳时写入关联，指向当前选择 C1，并拥有独立稳定 input_id。首条用户输入关联初始基线。`checkpoint_id` 表示恢复起点/消息归属，不表示该用户输入已经进入 C1 状态或模型上下文。

成功结束条件建议由注册成功收尾节点提供声明的闭合助手消息证据（确切 entry_id、source_ref、run_id/receipt）；服务完成事务核对本回合节点都已成功、对应助手条目已接纳闭合、上下文/对象更新已接纳，再一次写 C1、A1 -> C1 关联、session Head 和 chain succeeded。不能只以“页面已有字”或任意最后 TEXT 输出推定助手闭合。

当前服务没有这一正式消息证据，具体成功收尾节点/端口在后续 D 的清单/接线报告审阅；本报告规定字段与原子归属，不先修改 backend finish 绕过节点审阅。若没有助手闭合证据，这次执行不声称完成了聊天成功回合；纯管理 event 不产生聊天成功检查点。

提交 U1 的事务写入稳定输入及 U1 -> C1 关联，不更新 C1 state_storage 或延迟 C1 生成。下一次运行通过 input_id 使用原输入；重来/候选生成引用同一 U1，不重复创建 entry_id。即使 C1 的历史聊天对象尚无 U1，输入关联仍能读取已提交的 U1；实际写聊天/上下文节点应消费同一 input_id/entry_id，不用本次新 node_run_id 再制造第二条用户消息。现存 append 基于 node_run_id 生成条目身份的适配在后续 D 接线报告列出。

### 7.2 未完成进度

`chain_run`、node_run、已接纳 output/objects、next_node_index、input_id、starting_checkpoint_id、真实 request facts 和诊断构成未完成运行进度。节点结果接受时继续沿现存事务更新工作状态与进度；并未要求在每个节点产生成功回合检查点。

失败、pause、budget_exhausted、close、重启丢失执行帧保存原进度/结束事实；session successful checkpoint Head 不因此前移。close 的当前 `_commit(closed_execution)` 替换为 progress boundary。保留 same-process 继续、准确 result acceptance/checkpoint commit 重试和 `recovery_unavailable` 事实，不因检查点重构增加重启后自动重放。

即使完成结果已有而成功检查点事务失败，也不能误报成功；沿用现存 retained completed_execution + `retry_archive` 对准确已完成结果重试落盘，不重调业务或模型。未知结果请求只能核实和明确处理，不自动重来。

## 8. 恢复、继续、重来、候选及独立历史新会话

建议应用命令都使用现有 command/receipt 通道；共同参数为 session_id、expected_session_revision、expected_head_revision、idempotency_key，恢复/选择仍须明确目标属于同固定工作流且未归档。

| 建议操作 | 最小额外参数 | 状态行为 | 请求行为 |
| --- | --- | --- | --- |
| `history.restore` | entry_id 或 checkpoint_id（二选一） | A1/U1 解析成同 C1；恢复完整状态并移动当前选择，不覆盖当前可调配置 | 不运行模型/工具，不删后续历史 |
| `run.control` resume | 原 chain_run_id | 沿原已接纳进度继续，不能先恢复 C1 代替进度 | 保留现有可继续能力；不重发 unknown 请求 |
| `round.restart` | round_id（R2） | 从 R2.starting_checkpoint_id=C1 与原 input_id=U1 开始，创建新候选执行 | 明确产生新运行/请求，旧分支原事实保留 |
| `candidate.select` | candidate_id（成功 C2 的身份） | 恢复所选完整 C2，移动选择；保留该候选下一条输入关联 | 只选择已有候选 |
| `candidate.generate` | round_id 与 input_id | 与 restart 同一服务起点/命令实现，可在 UI 命名不同；不建另一套 roll 恢复 | 新运行，成功后新 C2 候选 |
| `session.from-history` | checkpoint_id | 同流创建独立会话，自己的状态基线、检查点/历史关联、Head 和会话 ID | 不自动运行；来源只为出处 |

活动执行必须明确停止并确认后才能历史恢复或整回合重来，不能在仍在 dispatch 的节点下覆盖状态。未决结果证据保留并直接拒绝自动重发；不建设外部工具回滚或通用重启恢复策略。已有原请求核实不由本报告删除。

人工修改的工作状态用于后续普通执行，并记录原 chain_start 事实；明确历史重来仍按已定 C1/U1 起点恢复，不把人工编辑变成另一份历史成功检查点，也不改写之前那次执行的实际起始依据。

### 8.1 真正独立的历史新会话

当前 fork 的 source/history_refs 指向源会话 run，且 delete 强制检查这些引用，所以现存 fork 不能登记为“独立所有权已完成”。建议实施以下明确归属：

1. 固定工作流拥有不可变执行证据（runs、outputs、模型事实及其 artifact 闭包）；保留 original workflow_session_id / run_id 表达当时来源，不为了新会话改写旧事实。
2. 每个会话拥有自己的可变状态、Head、输入及消息关联、候选选择和检查点路径。历史新会话复制选中历史前缀所需的关联/检查点为自己拥有的新身份，初始 full 与后续 diff 重新按映射后的完整逻辑状态计算；新 current state 物化到选中检查点。状态中的会话 owner 使用现存注册类型 mapper 合法映射。保留 provenance `source_session_id/source_checkpoint_id`，不将它们作为继续运行许可或父子运行关系。
3. 新会话的历史关联引用同工作流不可变证据，不依赖源 session current state 或 source Head。建议 `workflow_history_membership` 最少为 PK `(workflow_session_id, chain_run_id)`、workflow_definition_id，授权该会话引用本流准确事实闭包；事实继续使用原 chain_run/node_run/workflow_output/runtime fact ID。自己的 checkpoint IDs 和 parent 链可独立恢复；同一原消息可在不同会话以 `(session_id, entry_id)` 关联。
4. 删除源会话清掉其可变运行状态、关联、检查点与目录，不删除其他会话已拥有的状态链/关联所需证据，也不要求源会话继续存在。workflow-owned 证据保留至没有有效引用且符合未知请求保护的清理阶段；删除工作流时按该工作流范围处理。删除 session 不能伪报已同时删除共享证据。
5. 注册对象中的 artifact/exact origin/签名等引用保持真实来源，仅映射明确声明的会话状态 owner；复用 `TypeRegistry.remap`，不复用跨定义状态迁移、不按 JSON 文本替换 ID。验证新会话对象的全部必要历史/引用访问授权。

这需要调整当前 graph bundle 的“事实行必须存在活源 session”假设及删除归属，不只是修改 candidate 响应。方案复用不可变事实避免克隆请求 ID 和事实内容，不产生可执行兼容路线。此项是需要人工审阅的实质所有权选择；另一种做法是完整复制全部不可变事实并保留独立 origin 字段，但其 ID/签名/引用重写范围明显更大，本报告不建议首版采用。

归档 source/session/workflow 只允许历史查看，不借 from-history 执行归档恢复；归档只读规则不变。已定“同工作流独立新会话”不再待选，待审的是以上证据/状态所有权实现。

## 9. 提示词装配时求值与事实保留

当前 `prompts.group/item` 生成的是静态 PROMPT_MATERIALS，`context.assembly` 直接消费它。如果只让执行起始时读取新 config，后续装配仍可能拿到更早已接纳的旧材料，不符合已定行为。

建议最小求值方向是注册显式提示词配置引用输出，由对接装配节点在接纳本次装配前调用宿主读取当前节点可调配置并生成材料；引用最少包含 workflow_definition_id、node_binding_id、component_id/version 和声明的业务范围。结构/资源绑定用固定定义校验。建议新类型 `PROMPT_CONFIGURATION_REF@1`、宿主能力 `configuration:read` / 操作 `current-node-prompt`；准确 producer/consumer 端口和节点升级在后续 D 清单/接线报告列出并审阅，不冒充现有 PROMPT_MATERIALS 已支持惰性引用。

装配结果保存实际求得的正文、presentation、稳定 member IDs、lifecycle/compaction、该次配置 edit_sequence 和来源；已完成装配仍为不可变 artifact。单次装配在一份一致的当前读取中求值，不能正文和生命周期分别读不同保存结果。下一次尚未装配时再读取新值。

全局提示词引用仍按授权资源身份取当前保存正文；resource binding 固定。Lorebook 触发计算维持自身语义，不因新增可调引用随意重新触发旧扫描或抹掉结果。

once 继续使用 [stable_item_id](../../../../backend/src/phase1_agent/content_contracts.py#L50) 及上下文的 once_injected_item_ids；装配产生 pending IDs，context merge 被接受才消费。没有新 once 专用历史链，没有修改同身份正文后的强制重新注入；恢复上下文和消费记录作为同一对象内容。

## 12. 建议审阅结论边界

建议一次审阅以下具体接口决定：

1. 节点 configuration_policy 元数据 + 注册 adjustable_configuration；首版仅 item/group 及表中白名单，组成员增删作为可调业务配置；显式新组件/包版本。
2. node-actions / node-action 注册槽、host protocol 2 与 Promise 正式提交 SDK；不另建壳层提示词入口。
3. 完整文档 definition.update、edit_sequence、实际分类及混合派生响应；名称/位置等显示管理变更原地保存；上述表单提交边界及目录/会话名称/内容 display name 正式接管接口，准确原请求证据独立保存。
4. 分区映射整项 diff/full、明确删除与 immutable artifact 闭包；事务并发序号继续保留。
5. 助手成功收尾证据、独立 A/U 关联、input_id 与 progress；准确 restart/候选起点，后续 D 接线按对应报告审阅。
6. 工作流拥有不可变历史事实、会话拥有可变状态/关联/检查点链；from-history 物化独立身份，源 session 删除不阻断目标。

审阅通过表示允许实施这里明确列出的接口及其必要消费者替代，不表示产品已经实现，也不授权本轮启动服务、真实模型调用、重置数据、提交、合并或推送。已定行为维持 17 基线，不将接口审阅扩成再选一次整体规划。
