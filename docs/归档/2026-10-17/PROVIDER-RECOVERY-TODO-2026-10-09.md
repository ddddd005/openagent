## 用户订正的整改原则

用户明确将本次问题定性为严重的交叉引用 bug，主要问题在使用逻辑和模块职责，而不只是单个保存失败。后续整改必须满足以下三点：

1. **工作流只调用已配置能力，不管理底层配置。** 工作流不负责直接调用供应商 API、读取或发现模型、配置模型及其上下文容量，也不能修改底层 URL、Key、供应商或模型资源。工作流只能引用底层已经配置好的能力并发起业务调用；API 通信由底层执行，不得把通信与配置职责重新放回工作流。
2. **供应商通信模块只负责 API 收发，不负责工作流。** 它负责与上游通信、接收请求内容和返回响应内容，不应读取或修改工作流节点、连线、会话、编辑草稿或执行状态，也不负责工作流配置与恢复。底层供应商/模型配置管理和供应商通信是不同职责，不能因为同名“供应商”入口而混为一体；不得形成工作流与供应商通信模块的循环调用或循环依赖。
3. **错误必须有用户能理解的原因和可操作的恢复路径。** 用户应能知道哪一步失败、实际生效的是哪份配置、哪些修改尚未保存，以及下一步应去哪里处理。不能只显示“待核实”“配置无效”或错误码，让用户在多个入口间猜测；不能要求用户反复保存 Key、重配节点或依赖开发者清理后端才能继续使用。

用户在首次临时处理后再次触发同类故障，说明临时清理没有解决根因，不应归责于用户继续进行正常操作。字段顺序比较、过期表单和凭据绑定诊断是已经发现的具体缺陷；只修这些局部症状，不等于上述职责边界和使用逻辑已整改。当前尚未完成完整代码依赖审计，循环依赖的具体位置仍需核查，不能将整改原则写成已经完成的架构修复。

后续设计以以上原则为约束：底层配置入口负责配置与模型发现，工作流只选择和引用可用能力，供应商通信只处理收发。下文记录的“在模型节点获取模型、填写容量并应用配置”属于现有版本的现场操作与耦合入口，不作为目标使用逻辑或继续扩展该入口的依据。

## 因果链

1. 后端规范化 JSON 使用 `sort_keys=True`；前端 `resourceOutbox` 用 `JSON.stringify` 直接比较内存原请求与本机重读结果。
2. 字段顺序不同会使 `current()` 返回 `false`。成功分支因此不清 pending、不刷新资源；拒绝分支也提前返回，真实错误和解锁逻辑没有执行。
3. 核实已成功的旧请求可以清 pending，但供应商表单没有对应关闭或校准保存依据，旧 `s1` 表单继续留存。
4. 后续保存 Key 已成功；从过期表单提交其绑定时使用 `s1`，不能更新当前 `s2`。请求被留成待核实，成功回执不存在，反复核实无法解除。
5. 正式供应商仍引用缺失的环境 Key，模型列表获取在本地凭据检查阶段失败；已保存模型节点及未应用表单也未满足配置条件。
