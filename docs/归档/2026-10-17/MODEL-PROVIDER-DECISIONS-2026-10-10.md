## 1. 已确认规则

| 项目 | 用户裁决 | 后续设计约束 |
| --- | --- | --- |
| 配置入口 | 在“模型供应商（模型配置）”内直接完成，不再拆入口 | 同一入口创建提供商、配置模型、上下文容量、思考强度、温度等支持的参数 |
| 配置复用 | 同一模型允许多套命名配置，但必须是全局引用 | 配置由模型供应商管理；工作流只引用，不各自复制、维护或覆盖一套 |
| 更新采用 | 底层修改后自动采用 | 新运行自动解析所引用配置的当前生效值，不增加手动“采用新配置”步骤；已经发送的请求和历史事实不倒改 |
| 供应商保存 | 新建先进入草稿，一次保存提交整份配置，不分段保存 Key 和资源 | 只有“保存供应商”提交入口；完整字段与填写的 Key 一起保存，空 Key 保留既有 Key，输入时不锁定其他草稿字段；有效配置与私有结果均核实才报告成功 |
| 凭证路线 | 删除后端环境凭证及其选择入口，避免两套逻辑 | 只保留用户在页面填写保存 Key、独立私有库保护存储、`local:<UUID>` 引用；不删除安全存储，不把秘密移入浏览器草稿 |
| 真实模型验收 | 使用 DeepSeek，由用户启动页面并填写保存 Key | 不由开发代理启动服务、获取真实秘密或调用真实模型；在线验收仍待进行 |
| 进入主干时点 | 全部订正完成后统一验收合并 | 后续完整批次可离线验证，但不逐批进入 `main`；正式 BAT 保持稳定版 |
| 上下文容量 | 仅可手动配置，超上限报错，由用户处理 | 不从模型列表自动填充容量，不自动猜值、截短内容或调整预算以绕过错误；明确本地容量关系错误或上游容量拒绝 |
| 开发环境旧内容 | 新代码构建、底层更新或其他新一轮开发时，将以前存在的工作流全部移除，历史测试内容删除 | 不考虑对曾经工作流的支持，不做兼容更新、迁移或多套架构；不是日常修改 Key、温度、容量后删图 |
| 损坏后的测试重置 | 会话或历史损坏时，全部工作流和会话删除，清干净重新测试 | 不采用本轮建议的局部隔离保留方案；按已确认的开发测试范围完整清理工作流/会话关联记录，不留悬空测试引用 |

“模型供应商负责配置”指配置管理职责；供应商 API 通信模块仍只负责请求/响应收发及协议转换，不因此取得工作流、会话或草稿的管理职责。同一用户入口不要求把配置管理和通信实现放进同一个类。

自动采用发生在新的运行准备边界：一次已开始的运行仍使用其已冻结参数和容量，不在工具连续轮次中途替换配置。不修改历史冻结记录或已发送请求；凭据撤销/变更仍执行发送前保护。配置或历史协议不兼容时给出真实错误，不伪造签名、默改历史或自动重放。

手动容量属于用户配置，系统不声称能凭模型名称知道任意上游的真实容量。已声明的本地容量关系仍可校验；上游有更严格限制时按其实际拒绝结果报告，不自动修改用户配置。

上述开发清理规则不扩展成正式环境的日常删库行为。实施时核对明确选中的开发/测试数据库并清理旧工作流与相关测试记录，不误删其他工作区的库。不因“清测试内容”自动删除私有 Key、仍有效的独立资源或未知结果的原请求；未知结果记录仍先保留原始证据，不将缺回执视为可以重发。

## 2. 基线 Key 保存和绑定流程：已在开发版替换

这不是用户应当承担的业务决策，而是现有实现的交互拆分。密钥与公开配置隔离存储合理，但不要求用户分别完成两次保存。

1. 点击“保存 Key”后，`credential.save` 将密钥保存到私有凭据库；普通供应商资源不含密钥原文。入口为 `frontend/src/components/ProviderCredentialFields.vue:30`、`frontend/src/application/providerCredentialEditing.ts:89`、`backend/src/phase1_agent/graph_provider_host.py:29`。
2. 凭据回执及当前代次核实成功后，前端回调将 `local:<UUID>` 填入当前供应商表单的 `credential_ref`，但此时只修改未提交表单。定位：`providerCredentialEditing.ts:67`、`frontend/src/components/CurrentProviderPanel.vue:44`。
3. 还要点击“保存当前资源”，表单中的 URL、协议、启用状态和凭据引用才通过 `resource.save` 保存为供应商的生效配置。定位：`CurrentProviderPanel.vue:22`、`:95`。
4. 获取模型列表或执行模型时，后端读取已保存的供应商资源，按它的 `credential_ref` 取 Key，而不是采用尚未保存的表单。定位：`backend/src/phase1_agent/graph_provider_host.py:54`、`backend/src/phase1_agent/model_service.py:218`。

因此，“本机 Key 已保存”与“供应商已改为使用这个 Key”目前可以不是同一状态。此前现场发生过私有 Key 可读取，而供应商仍引用缺失的环境 Key；这解释了为什么再次填写 Key 没有解决生效配置问题，不归责于用户。

用户随后明确裁决：**点击“保存 Key”就直接完成生效绑定，不是先改未提交表单，再等待“保存当前资源”。** 程序负责私有凭据写入和供应商公开配置中的引用写入；两项都确认完成后才报告保存成功。不能只自动选中本机 Key 下拉框，冒充已经写入生效配置。

内部仍保留独立安全存储和精确回执；部分完成/结果未知时显示实际失败步骤，不伪装跨存储原子成功，不自动重发。绑定写入需使用对应供应商的真实版本依据，并保护其他未提交修改，不能为保存 Key 顺带覆盖供应商表单的无关编辑。

## 3. 已澄清的开发清理规则

用户对删除触发范围的进一步澄清：

> 删除相关工作流指的是，如果需要有新代码构建，计划底层更新，做其他开发时，将以前存在的工作流全部移除。不考虑代码对曾经工作流的支持，不做兼容更新和迁移，对于历史测试内容采用删除处理。核心目的是不转移工作重心，不将注意力放到对旧流的兼容。

> 避免同时维护多套架构。

规则按开发批次执行：

1. 新一轮代码开发或底层更新开始时，清理明确开发/测试范围内此前存在的全部工作流、关联会话、历史与测试配置记录，不限于“恰好不兼容”的旧图。
2. 当前架构是唯一运行路线；不为旧测试图补迁移、兼容读取、回退路径、自动节点升级或第二套执行架构。
3. 新批次重新创建当前版本的工作流验收。清理本身也是交付的一部分，不能只改源码而把旧流留到启动时报错。
4. 日常在当前版本中修改 Key、模型、温度、思考强度或容量不触发这类开发重置；现有全局引用在下一次新运行自动采用生效值。
5. 发生已确认的测试会话/历史损坏时，按用户裁决清理该开发/测试范围内全部工作流和会话，重新测试，不维持局部修补后的旧测试现场。

关联闭包清理不是旧流迁移。未知结果或损坏原文的必要证据归档也不作为旧架构继续运行，不增加兼容解码器。明确当前批次创建的验收流与日常有效全局配置仍须正常保存/重读；本次规则登记不立即删除现有数据。

## 4. 对原审查建议的订正

- 原建议“供应商、模型配置分两个页面”不采用，统一在模型供应商入口完成。
- 原建议“已有会话重要变更先确认采用”不采用，改为新运行自动采用。
- 原建议“被引用的配置阻止删除”和“损坏数据局部隔离”不作为本轮开发测试政策；新一轮开发前清理全部既有测试工作流，正常编辑全局配置不删图。
- 现有 Key 保存后再保存资源的双步骤退出；“保存 Key”自身必须完成生效关联。
- 本轮没有新增任意插件写入上下文的能力授权，Context/Agent 解耦仍保留现有生产者证明和权限，不用删除校验换取解耦。

本轮提问中的删除触发范围与 Key 保存行为已澄清；后续整改按本页裁决收口。本页不构成源码修复、服务切换或数据清理已完成的声明。

## 6. 供应商整份草稿统一保存

用户进一步裁决：**创建时进入草稿状态，点击保存后将整个配置保存。** 之前只合并“保存 Key + 生效绑定”、仍另留“保存当前资源”的实现不符合此交互要求；第 2 节“Key 保存不应用其他字段”只作历史解释，被本条覆盖。

- 新建与编辑只修改非秘密本机草稿；未提交 Key 只在内存，不进入草稿或原请求记录。
- 只有“保存供应商”一个正常提交入口，保存当前名称、协议、URL、启用状态及本次填写的 Key；已有 Key 留空保持不变。
- 填写 Key 时仍可修改草稿字段；同一归属、同一生效版本的草稿变化不重载或清空 Key。提交时固定整份请求，提交中或未知结果才锁定修改。
- 密钥与公开配置继续隔离存储，但这种内部边界不再体现为两个用户保存步骤。部分完成不声称原子成功；核实使用原整份配置和请求身份，不自动重放。
- Key 输入不标记为浏览器“创建新密码”字段；移除 `autocomplete="new-password"`，采用关闭自动填充的表单及密码输入属性。

本次承接同一开发批次，不再次清理本批验收数据，不合入 `main`、不改 BAT、不替用户启动服务或调用真实模型。
