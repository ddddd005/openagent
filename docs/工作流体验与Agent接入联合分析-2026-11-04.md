# 工作流体验与 Agent 接入：问题汇总与联合分析

日期：2026-11-04。核对基线：`develop`，HEAD `8bd2717`，包含用户当前未提交改动。

本文将画布、编辑同步与 Agent 接入三组勘察合并为一份分析入口，并订正交叉核对中发现的过度概括。按用户后续决定，推进顺序统一为“先优化项目自身逻辑，后整理外部 Agent 使用逻辑”。本文交付问题排序与预期订正方向，不代表业务修改已经实施，也不替代未定契约的确认。

## 1. 核心判断

当前工作流已经具备读定义、修改、保存、建会话、启动运行、查看结果和控制运行的基础能力。下一阶段的主要问题是：操作反馈与实际接纳结果不一致，逐次保存的协议成本偏高，以及保存和运行规则难以被调用方准确判断。

三组问题相互关联，但不能用“卸除异步”统一处理：

- 画布问题需要修正交互状态和显示，`receipts` 起线坐标错误已在上一轮修复。
- 编辑同步问题需要评估请求证据、接纳投影、锁和重复读取的实际成本。
- Agent 接入需要确定调用身份、目标工作流、写权限和未知结果处理方式；基础命令存在，不等于管理工具已经接入。
- 后台异步运行、会话固定修订、CAS 和运行冻结仍承担现有运行职责，不能随保存层一起精简。

推进顺序调整为：先打通前后端修改闭环，再修画布交互，再明确保存与运行规则及诊断，随后按测量精简项目内部成本，最后整理外部 Agent 接入。前四步服务于项目自身使用，不以 Agent 包装代替内部问题修正。

用户已明确修改流程的方向：前端提交期间自锁，后端先判断有无未完成修改，再判断提交基线是否与当前版本一致；成功响应接纳后，前端解除修改锁。具体锁实现、失败与结果未知的处理细节仍需结合现有机制确认，见第 8.1 节。

### 4.1 删除问题的准确归因

当前 `removeSelection()` 在同一份文档副本内删除节点、相关数据边、控制边、事件目标、对象绑定/权限及相应预加载，然后整体提交。没有证据说明本次问题来自“先渲染掉节点、后渲染掉边”的中间文档。

真正需要处理的是选择一致性、异步提交结果、未处理的配置引用，以及后端普通边检查边界。配置引用应清空、保留为待修复状态、阻止删除还是提示用户，属于节点行为决定，不能按字段名直接自动擦除。

### 4.2 哪些不是当前缺陷

- 正式配置允许保存尚未接完输入、暂不可执行的图，是现行规则。不能把“保存成功但缺必需输入”全部归为保存错误。
- fixed 修订、当前可调覆盖与会话修订表达不同事实，不能因数量多就合并。
- 组件编辑原文、撤销历史、目录摘要、服务端接纳文档并非全部是竞争的权威副本；应核对用途后再去重。
- 对象绑定声明和预加载值承担不同职责；重复同步点值得检查，不足以直接决定合并结构。

## 5. 三组材料共同揭示的关系

### 5.1 人与 Agent 可以共用已有保存能力

人通过画布修改文档，Agent 可以在获得授权后构造文档并调用相同命令。双方都需要准确的类型与版本、配置规则、引用关系、保存基线、诊断和运行结果。

因此，共用价值最高的是契约说明、可定位诊断、保存后果可见性和运行状态说明。为 Agent 另写一套不受现有保存规则约束的编辑逻辑，会增加需要维护的行为差异。

### 5.2 先优化项目内部，再让外部 Agent 复用

后端命令不强制先走前端 request-evidence 协议。Agent 直接调用应用命令，可以将多处修改合成一次整文档提交，避免逐个操作画布和逐次完成五段请求。

但相同的 `definition.update` 仍要检查 CAS、G21、配置策略和派生条件，仍有整文档校验、历史查询、修订与回执写入。Agent 也仍需观测后台运行及处理未知结果。不能概括为“绕开前端后只剩文档传输成本”。

精简保存协议的直接收益主要在请求往返、编辑吞吐和运行入口等待。证据历史不在执行循环的直接读取路径上，不能据此承诺模型调用或节点执行本身变快；实际端到端收益仍待测量。

因此，技术上存在直接调用入口，不构成提前推进外部 Agent 的理由。当前排期先解决人的修改闭环、内部诊断和实际成本，再让外部 Agent 复用整理后的规则。保存证据是否精简，仍需单独确认原请求保全政策，不能因接入顺序变化直接移除。

### 5.3 工作流内 Agent 自修改存在独立限制

本次后置接入明确面向外部 Agent。工作流内 Agent 管理另一份定义、修改承载自身的定义，是另外两种场景，不列为本次接入步骤的前提。

工作流内 Agent 修改自身定义在当前运行期间会命中 G21。即使接上管理工具，也不能完成同图运行中原地修改。不能借本次体验优化移除冻结规则，或让工具自动关闭自身运行以绕过限制。

若产品选择“只在副本上试验”，`definition.copy` 就需要提前进入接入范围；若选择直接修改正式定义，则必须处理有效会话下的派生确认。这些是不同授权范围，本文不替用户选择。

### 5.4 失败、关闭和可编辑是三个判断

运行状态为 `failed`，不表示 `active_chain_run_id` 已清空。`close` 只在允许的状态下执行，正在 `prepared/running` 的链不能直接按关闭处理。

关闭一条链也不保证整份定义立即可改：其他会话仍可能有 active run；关闭不会自动归档会话，之后 fixed 修改仍可能需要确认派生新定义。调用方应按当前会话状态、`available_actions` 与保存响应判断，不能把“失败后 close 再写”固定为无条件流程。

### 5.5 异步需要按实际行为讨论

| 行为 | 本文判断 |
| --- | --- |
| 画布提交后 fire-and-forget，再等待接纳 | 有反馈与编排问题，可以优化 |
| 网络中断后业务结果未知 | 人和 Agent 都会遇到，不能靠同步等待或 CAS 消除 |
| 运行后台执行，启动响应先返回 | 现有执行方式；调用方仍需观测完成与失败 |
| 多次查询响应到达顺序不同 | 单调接纳、generation/viewToken 等守卫仍有作用 |

“移除异步”不是足够明确的实施目标。更准确的目标是减少无效往返和重复状态，同时让请求中、已接纳、明确拒绝、结果未知这些状态可被调用方识别。

| Agent 不需要轮询或状态同步 | 可以不复用工作台的 350ms 轮询实现，但后台任务仍需观测；网络延迟也影响 Agent 闭环 |
| 工具内部自动重读序号、确认派生、失败后 close | 重读不能把旧文档自动附到新基线；确认派生和关闭运行涉及用户授权，不能默认自动化 |
| `definition.inputs` 没有正式 validate，就只能保存后试错 | 已有保存前结构检查、声明收集和编译诊断；缺的是完整预演与更好定位，而不是完全没有检查能力 |
| “两套校验/多份状态/前端零调用”即可优先删除 | 应先确定权威边界和调用用途；前端不使用的查询也可能供 Agent 或仓库外客户端使用 |
| 字段白名单可统一从 `adjustable_configuration` 派生 | UI 扩展字段归属、可调分类、完整配置 schema 和窄补丁准入含义不同，不能直接互相替代 |

另外，Agent 文档附录对内部 authority 的概括需要订正：当前 `object.write`、`checkpoint.fork` 列在 management 集合，`packages.configure` 列在 execution 集合。它们仍不因此获得对任意 Agent 的授权；内部服务分派与调用方权限不是同一概念，见 E09。

“没有机器可读契约”也应收窄：已有应用 `describe()` 提供 operation、参数名和作用域，节点目录提供配置 schema 与端口等信息；不足之处是完整 GraphDocument schema、保存协议语义及诊断位置，见 E09/E10。

## 7. Agent 接入的最小能力核对

下表保留为第 5 步外部 Agent 接入的需求核对，不是当前安装清单。先完成项目内部整理，再确定外部调用的承载方式、目标和权限；工作流内 Agent 接入不在本轮排序的实施范围内。

| 能力 | 已有入口 | 需要保留的判断 |
| --- | --- | --- |
| 发现操作和节点契约 | 应用 `describe()`、`catalog.node-types` v2、`platform` | 精确类型/版本、`accepted_types`、配置 schema、包可用性；v2 已含 platform 信息，避免重复全量拉取 |
| 读目标与编辑基线 | `definition.summaries`、当前 `definition.read` | 固定修订原文不含当前 `edit_sequence` 与覆盖值，不能直接当当前编辑基线 |
| 保存前检查 | `definition.inputs` | 结构错误可能为 4xx；编译错误可为 200 加 `diagnostics`。应检查诊断与 `required_for_run`，HTTP 成功不代表可执行 |
| 批量写配置 | `definition.update` | 捕获同一基线下的正文与序号，处理 saved/unchanged/confirmation_required/derived，不自动确认派生 |
| 核实未知结果 | 既有只读应用回执路径 | 保留原 operation、参数、key 与作用域；无匹配回执不证明业务未发生，不自动重发未知请求 |
| 独立试验 | `definition.copy` | 是否必须先复制由权限决定；复制与派生后的新身份必须用于后续操作 |
| 建会话与启动运行 | `session.create`、`run.start` | 前者绑定固定定义修订；后者 `expected_revision` 是会话修订。两种 revision 不可混用 |
| 观测与读取结果 | `session.read`、`run.read`、`output.list/read` | public 输出与管理运行详情不同；准备失败的原响应不能丢弃 |
| 关闭、恢复及重试 | `run.control`、会话 `available_actions` | 先确认允许动作和授权；重试能力并非仅由 action 名存在决定，不重放未知外部效果 |

`definition.inputs` 不检查本次保存的完整基线、全部运行资源和实际输入，也不预留保存权。即使将来增加正式预演，检查与提交之间仍可能发生状态变化，提交时的 CAS、G21 和资源校验仍需执行。

现有应用边界声明为可信本地调用，不是远程插件认证。把已有 HTTP 命令包装成工具，并不自动得到新的远程或模型调用权限边界。

## 8. 建议推进顺序与验收重点

前四步优化项目自身，第五步整理外部 Agent 使用逻辑。每步可分成小范围修改与验证，不要求一次大重构；处理范围与未决契约应在对应实施前明确。本次不包含业务实现或测试执行授权。

| 大步骤 | 对应问题 | 预期订正方向 | 完成时应可观察的结果 |
| --- | --- | --- | --- |
| 1. 统一前后端修改闭环 | S01、S03 | 前端等待提交结果；后端按“修改互斥、基线校验”接纳；成功后应用正式结果，再解除前端修改锁；明确失败和结果未知分别反馈 | 连续操作不能启动第二次未受控修改；旧基线不能覆盖；失败不表现为成功；业务已完成与证据待结案可区分 |
| 2. 修正画布操作与选择 | C02、C03、C04；C01 仅保留回归 | 依托第 1 步的接纳结果，统一连线开始/结束/取消、提示清理、节点与边选择、接纳后选择修剪 | Esc/空白按确认后的规则取消；取消后松手不意外建边；新增/定位后删除不连带旧选边；失败时选择和提示可解释 |
| 3. 明确保存、引用与运行规则 | S04、D01、D02、R01、R02、A01、O01 | 先确认保存结构边界与删除/替换策略，再对齐校验和可定位诊断；说明编辑基线、修订、派生、运行占用及可用控制动作 | 能分辨结构错误、编译错误、陈旧基线、运行冻结和准备失败；能定位节点/边/字段；保留未完成图的保存能力 |
| 4. 精简内部协议和重复工作 | S02、P01、P02、L01 | 在结果规则稳定后，按测量压缩保存往返、全历史读取、历史扫描和重复投影；仅精简已核实用途与替代覆盖的冗余 | 用同口径说明优化前后请求数、数据量与等待时间；原请求保全、其他会话刷新及历史准确性符合确认规则 |
| 5. 整理外部 Agent 使用流程 | A02、A03 | 复用前四步整理后的契约与命令；依次明确接入权限、读与诊断、批量编辑、授权运行及结果观测 | 外部 Agent 使用同一保存与运行规则；冲突不自动覆盖；未知结果不自动重放；派生身份和运行权限明确 |

排序依据：先保证一次修改有明确结局，画布才能准确表达成功与失败；再明确保存和运行的实际规则，之后才能判断哪些协议与读取确属冗余。外部 Agent 最后接入，避免把现有内部不确定性转移到工具封装中。

### 8.1 第一步的修改闭环与边界

用户已确定的是修改互斥、随后校验版本、前端提交自锁并等待后端成功的方向。以下细化为预期订正内容，其中待定项不在本文直接选型。

1. **前端先约束入口。** 会改变工作流定义的编辑入口采用一致的等待与反馈语义，覆盖节点配置、连线、删除、移动和撤销/重做等实际路径；提交期间禁止叠加第二次修改。不能只禁用某个按钮，而让其他入口继续修改。
2. **后端先取得修改资格，再核对基线。** 同一工作流的真实修改未结束时，第二次修改不能开始；取得资格后，在事务保护下核对版本并执行保存。版本校验是 CAS，不必另外维护一把长期“版本锁”。忙时明确拒绝还是等待、跨进程如何生效，需在实施方案中确认。
3. **成功以服务端接纳为准。** 前端收到成功后，先应用正式文档及基线，完成相应历史与选择更新，再解锁。请求已发出、未抛同步异常、得到 truthy 返回均不等于保存成功；`unchanged`、待派生确认等结果也须按实际含义反馈。
4. **明确失败与结果未知分别处理。** 明确拒绝或失败时，保留本次编辑内容并给出原因，结束对应前端提交锁；结果未知时保留原请求及 key，显示待核实状态。核实与解除阻塞的具体规则待确认，不能把断网直接当作后端失败或自动换 key 重发。
5. **区分不同锁的结束条件。** 建议后端修改互斥止于事务提交/回滚，前端修改锁止于结果处理完成；请求证据未结案与 G21 运行冻结各自说明，不能合成一个含义不明的“忙”。业务已接纳但证据结案失败时，允许哪些动作仍需决定。

已有服务 `RLock`、SQLite `BEGIN IMMEDIATE`、CAS 以及前端 pending/locked，并非从零新增锁。实施前应核对实际覆盖，再决定复用或调整。编辑基线应核对 `edit_sequence` 的覆盖，保留 fixed `revision` 的既有约束，不能仅凭固定修订未变化就认定编辑基线一致，见 E04/E06/E12/E16。

第一步优先让现有提交链正确等待并准确反馈，不预先删除证据协议。证据保全与传输精简放在第四步；真实运行的后台执行及 G21 冻结也不随配置提交一起改成同步。

### 8.2 各步进入条件与交付边界

- 第 2 步沿用第 1 步的提交结果，不再自行推断修改成功；点击连线是否保留、如何取消仍先确认。
- 第 3 步先明确 D01/D02 的保存与引用行为，再修改校验。A01 虽以 Agent 编号登记，此处先服务项目内部的契约、前端反馈和调试。
- 第 4 步以已明确的结果、证据与历史语义判断冗余；不为了减少代码行数合并全部写通道、凭据通道或对象结构。
- 第 5 步在前四步约定的内部目标完成并验证后推进。接入前列明仍保留的限制，不要求扩展工作流内 Agent 自修改，也不默认允许运行、派生、关闭或重试。

各阶段选择少量直接验证目标行为的检查，不恢复已经关闭的旧债测试矩阵，也不按旧测试反向安装旧架构。真实模型试跑、服务启停和业务数据改动仍需各自授权。
