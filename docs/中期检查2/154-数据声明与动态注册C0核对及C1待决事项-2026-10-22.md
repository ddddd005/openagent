## 1. 两个目标及当前事实

| 目标 | 当前已有 | 尚不能声称完成 |
| --- | --- | --- |
| 无会话维护数据项声明 | 注册节点配置保存名称、四种标量类型、可选初值及对象绑定；正式保存不要求先建会话 | 用户是否接受该维护载体；声明到多会话消费及变更规则的专项闭环 |
| 动态数据类型 | 可信包注册准确 scope/type_id/schema_version；目录、schema/default 校验、版本证据及 RunBasis 冻结 | 用户交互式新增/版本化/停用哪些类型、如何消费、是否开放给 Agent，尚无获批完整规则 |

“注册一个 score 变量”与“定义一种新的结构化数据类型”是两件事。前者使用已有类型建立会话数据项，后者改变可被配置与执行消费的类型来源。即使第一目标沿用已有节点完成，也不能据此标记动态类型已交付。

## 2. C0 实际链路

```text
无会话编辑注册节点名称/类型/初值及绑定
  -> 正式配置保存和独立重读
  -> 建会话：按固定修订创建隔离对象，变量仍是未注册空壳
  -> 管理事件执行注册节点：首次按声明赋名/定类型/可选赋初值
  -> 已获准节点或 Agent 操作当前值 -> 原 CAS/接纳
```

## 3. C1 建议与待决

以下前四项建议尽量保留现有行为；第五项需要明确首版实际用途。用户决定产品行为即可，表名、私有模块和测试夹具由执行方据此设计。

| 决策 | 建议，尚待确认 | 若采用其他方向，具体影响 |
| --- | --- | --- |
| C1-1 声明载体 | 首版沿用注册节点配置作为唯一声明来源，在无会话时即可维护/保存；注册节点仍负责显式首次注册 | 独立数据项管理界面可另行提供，但须先定其与节点谁维护 name/type/default，不能同时有两份权威 |
| C1-2 作用域与权限归属 | 声明属于当前工作流，值按会话隔离；沿用准确对象键与 readers/writers；名称冲突继续按实际获准消费集合校验 | 项目共享声明、工作流全局唯一名称、跨会话值共享都是不同新规则，不能从 shared 字样推导 |
| C1-3 初始化与历史 | 建会话仍建空壳，首次注册用初值；重复注册保持值。改名/改类型/改默认值走正式固定配置及确认派生，仅影响新依据，不重写旧会话 | 自动初始化会改变注册时点；让既有会话随声明更新需要明确迁移/生效规则。停用删除建议只限制未来使用，保留旧依据，但该新增管理行为仍须明确确认 |
| C1-4 用户与 Agent | 用户维护声明及首次注册；Agent 首版保持已授权当前值工具，不新增声明/首次注册/类型管理权限 | 开放任一 Agent 新操作都要指定准确目标、范围、生效时点及确认要求，再经正式业务入口装配；不能绕运行锁直接改 registry 或数据表 |
| C1-5 动态类型 | 先明确要支持哪类实际数据及其消费者；建议声明式 schema/default、新版本表达变更、旧版本留供历史解释 | 类型域、项目/工作流来源范围、用户维护入口、是否进入检查点与分叉均取决于用途，不能预设 content/session/global 三域全开；任意 Python 与特殊引用行为不自动开放 |

C1-5 并非要求用户设计 schema 解析器。需要的是一个首版使用目标，例如希望某个节点可保存并读取哪种当前无法表达的数据；执行方据此提出最小类型域、来源及消费者闭环，再形成局部契约。若用户决定只规范包提供的类型，交互式动态类型目标须明确后置，不能悄悄缩减后宣布第三阶段完成。

这些建议不推翻已定的声明/当前值分离、准确身份/版本、原会话保持和禁止隐式迁移；待决的是具体维护方式、新开放范围及其消费行为。
