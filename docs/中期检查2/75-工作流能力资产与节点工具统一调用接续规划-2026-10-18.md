## 3. 能力资产、节点和工具

### 3.1 不同维度

| 对象或维度 | 本轮含义 | 不应混同 |
| --- | --- | --- |
| 能力资产 | 可被多个工作流引用和复用的功能来源 | 不等于某个节点实例、某次运行或一条必须新增的数据库记录 |
| 能力实现 | 真正完成计算、查询、更新等业务的实现 | 不由工具提示词替代，也不为节点与工具各复制一份 |
| 节点类型与实例 | 类型描述可用功能及调用要求；实例表达工作流中的具体使用配置 | 类型、实例、运行继续分开；不因共用能力就共用实例配置 |
| Agent 工具入口 | 向模型描述可用操作，将实际工具调用接入绑定能力 | 不是另一份能力实现，不等于图上必须新增一个业务节点 |
| 节点包或能力插件包 | 提供能力及其可选工具入口的交付来源 | 不要求一节点一包，也不要求一业务族一包 |
| 菜单分类与内部模块 | 分别服务于展示和实现组织 | 分类路径不决定发布边界；算法、协议、数据适配不必全部暴露为节点 |

节点入口与工具入口可以有各自的参数呈现和转换，但必须指向同一真实能力及明确的调用契约。不能用“渠道统一”掩盖两份不同的业务实现、读写规则或结果语义。

### 3.2 工具绑定的要求

- 工具必须有可核对的能力来源、调用目标和真实实现，而不是仅凭描述文字声称拥有功能。
- 工具描述可以解释用途和用法，但修改描述不能凭空产生读取数据库、更新变量等功能。
- 能力来源可以提供普通节点入口及附加的工具入口；不推导出每项能力都必须向 Agent 开放。
- 如果通过工具节点向 Agent 提供工具，该节点可以很薄，但应提供已绑定能力的入口，不能只有提示词而没有对应执行能力。
- 如果功能本身就是提供或生成提示词，它仍是合法功能；不能把提供这段文字误写成已实现文字所描述的其他业务。
- 工具入口与实现是否必须同包发布、是否允许独立适配包依赖能力包，以及绑定的具体表示，仍见第 9 节。

本文主要针对赋予 Agent 业务功能的工具。现有 `final_answer` 等内核控制工具的定位需要另行核对，不能据本文强行将所有控制工具都改造成普通业务节点。

## 4. 共用调用渠道与执行分工

以下只表达已确认的调用关系，不规定类名、完整 API、消息总线或新的执行服务：

```text
工作流 Runtime 按图推进 -> 普通节点入口 --+
                                        +-> 共用能力调用渠道 -> 同一能力实现
Runtime 承载的 Agent -> 已绑定工具入口 --+
```

普通节点的调用依据来自自己的配置和上游输入；Agent 的调用依据来自提示词、上下文、已加装工具及其自身判断。共用能力不等于继承其他节点实例的参数和引用。

| 职责 | 本轮明确的方向 | 不应承担或推导的内容 |
| --- | --- | --- |
| 工作流 Runtime | 外层运行推进，承接本次运行所需能力的启动检查、加载与准备；工具所加载的节点按实际节点实例同等要求准备，以及既有运行控制和结果接纳 | 不接管 Agent 每一步思考与工具选择，不直接实现时间线等具体业务 |
| Agent 内核 | 根据自身输入选择工具、生成调用参数、消费结果并决定后续调用 | 不自行发展为脱离 Runtime 的另一套运行系统，不在每次调用时临时寻找和加载能力 |
| 共用能力调用渠道 | 让节点入口和工具入口取用已准备的对应实现，保留明确的契约、结果和错误 | 不是两套私有业务系统；不预定新增一个全局调度器 |
| 功能或能力实现 | 完成自身业务逻辑，需要持久数据时使用明确的领域存取通路 | 不因能被 Agent 调用就取得其他层的全部修改权 |
| 定义来源与目录 | 来源维护定义，目录提供只读消费视图，供启动检查及调用取用 | 不从注册或描述文字中生成另一套独立实现权威 |
| 数据管理与配置管理 | 数据管理承接领域存取、版本及事务；静态配置修改仍回配置管理 | 不因工具调用而绕过现有数据归属，或把静态配置当作会话当前值任意改写 |

72 号现有口径将“执行层”特指工作流 Runtime，Agent 内核归功能层。本轮明确了共同调用要求，但没有最终决定共同调用机制的完整层级归属、接口或代码组织。不能直接把 Agent 内核改归执行层，也不能用原有分类否定本轮已确认的启动准备与共同调用要求。

## 5. “激活对应节点功能”的准确含义

### 5.1 与实际节点实例同等加载

加装工具意味着对应节点功能进入本次工作流的加载与准备范围，即使没有对应的画布业务节点实例。后续制定节点加载规范时，应将实际节点实例与工具所加载的节点一起考虑，工具路径须满足同等加载要求，而不是另设一条只登记工具描述或预加载函数的简化路径。

后续局部方案必须说明：

1. 如何在启动准备阶段取得 Agent 已加装的工具清单及其真实能力绑定。
2. 如何按同等的节点加载要求核对来源、准确版本、调用契约及必要依赖。
3. 如何使工具所加载的节点完成与实际节点实例同等的加载与准备，使 Agent 开始使用时具备相应节点功能的调用条件，而不只是能够找到一个实现函数。
4. 缺少真实实现、绑定无效或必要依赖不满足时，如何在启动准备阶段明确报告，而不是拖到首次调用才临时寻找实现。

“启动范围不能只看图上的业务节点、避免逐次调用临时加载”是上述要求的一部分，不是全部。“没有画布实例”不构成减少节点加载步骤或要求的理由；具体哪些步骤适用，应对照实际节点实例的加载规范逐项说明。

具体检查项和准备接口须根据实际来源确认，不先建立完整加载平台。上游工具节点若在运行后才生成信息，如何提前获得准备所需绑定，仍须专门论证，不能通过首次调用懒加载绕开本要求。

同等加载不自动决定相同的画布位置、图调度关系、运行身份或状态共享方式。“激活”不等于额外执行一个画布节点，不创建隐形数据边或控制边，不恢复 `execution_roots`，也不改变孤立 working 节点不执行的既定行为。

### 5.2 调用阶段

Agent 使用按实际节点实例同等要求加载、准备好的节点能力；工具调用继续使用共同渠道，不逐次完成实现发现、注册或临时加载。

提前准备不取消对本次实际参数、数据引用和必要写入条件的检查。启动时能够检查的依赖与调用时才产生的具体参数分别处理，不能宣称所有业务数据问题都能在启动前查完。

### 5.3 不能据此推导的实现

- 不要求每个工具在画布上都配一个同类业务节点实例。
- 不要求把节点实例配置复制给 Agent，也不要求 Agent 借用另一个实例身份。
- 不要求所有调用共享同一个有状态实例或同一份持久数据。
- 不要求在每次工作流启动时重新导入全部已安装包，或提前执行工具业务、写入数据、发出模型请求。
- 不等于所有大型资源必须同时常驻内存；能力实现就绪与具体资源使用策略应分别论证。
- 本篇只确认启动时已加装工具的准备要求，不决定运行期间动态加装、热更新或自动卸载机制。

## 6. 持久数据：存储、引用和写回

持久性必须落实到可追踪的数据通路，不能只描述成“有副作用的函数”或向函数塞入一个笼统上下文。

| 要素 | 后续局部方案需要回答 |
| --- | --- |
| 存储 | 保存的是什么数据，由谁维护，位于哪个逻辑域及现有仓储 |
| 引用 | 一次调用如何定位准确的数据对象或集合，引用由何处取得，如何保留来源与归属 |
| 读取 | 读取当前值、固定修订还是本次运行的已有依据，缺失或陈旧时在哪里报告 |
| 写回 | 更新目标、版本条件、实际保存与重读路径，以及调用成功和持久化成功的关系 |
| 连续交互 | 同一 Agent 内多次调用能否读到前次更新，其他调用者何时可见 |
| 接纳与失败 | 写入在工具调用结束、节点接纳还是其他已确认边界生效，失败或暂停时哪些事实已经成立 |

Agent 不继承其他节点实例的引用，不表示能力访问持久数据时可以没有引用。实际数据目标如何通过工具参数、绑定或相应接口明确，仍需局部确认；不预定必须把所有内部身份字段直接暴露给模型。

必要的身份、权限、版本校验仍按既有数据边界保留，但这些校验不能代替上述存储、引用和写回说明。静态配置变更与会话数据更新继续分别走相应职责。

## 7. 时间线场景的用途

用户提出的时间线工具用于说明未来需求：Agent 使用时间线推算不同时间可能发生的事情，过程中可能多次读取数据、调用功能及更新变量。

它至少涉及两种业务组织方式：

- Agent 依次查询、推演、更新、再查询：是否继续调用由 Agent 内核判断。
- 一次时间线能力调用内部需要多次读写：领域流程由能力实现承担，实际存取通过数据管理。

两者都不能因跨越多个层级就全部交给工作流 Runtime，也不要求把所有内部步骤拆成画布节点链。

本例不批准建设时间线模块、定时调度器或后台任务，不决定预测算法、数据结构、事务策略及工具数量。具体选路仍应先依据实际对象和读写边界论证。

## 9. 尚待确认的实施决定

已确认“绑定真实能力、共同调用、与实际节点实例同等加载、启动准备、不要求画布业务实例”，以下只列仍未确定的具体方案，不重新讨论上述方向。

| 编号 | 待决项 | 为什么影响后续施工 |
| --- | --- | --- |
| Q01 | 能力与可调用操作的准确身份、版本，以及节点类型、工具入口之间的映射 | 决定绑定、查询、依赖和调用契约；不默认一能力一工具或一节点一包 |
| Q02 | 工具必须与实现同包，还是允许适配包通过明确依赖附加工具入口；如何声明和校验导出 | 决定发布与加载边界，不能直接新增 manifest 字段或插件格式 |
| Q03 | 共用调用机制的职责归属、接口、必要适配及其与现有宿主的关系 | 决定如何接通两类入口；不先建全局执行器，不自动改写六层定义 |
| Q04 | 已加装工具的清单、绑定和配置保存在哪里，如何在启动阶段取得 | 尤其影响来自上游工具节点的输入，不能用首次调用临时加载代替启动准备 |
| Q05 | 对照实际节点实例，明确同等加载的具体步骤，以及运行实例的生命周期、归属和共享方式 | 同等加载原则已定，具体步骤仍需落实；不能降格为仅检查函数可用，也不能直接推导为同一状态实例或相同暂停、继续与释放细节 |
| Q06 | 访问持久数据时的准确引用、目标和必要绑定如何表达 | 不能继承其他节点实例配置，也不能改用隐式“当前数据”来填补目标 |
| Q07 | 连续调用的写入可见性、接纳和事务边界，工具或节点失败后的事实 | 当前一次节点写意图不能直接满足多次提交；须先决定语义，再选择实现 |
| Q08 | 调用身份、结果、错误、暂停与事实记录如何与外层运行关联 | 不等同于每次调用创建一个完整图节点运行，也不能丢失实际调用事实 |
| Q09 | 哪些现有功能允许提供 Agent 工具入口，内核控制工具如何定位 | 不自动把检查点、重roll、分叉及所有内部 API 全部暴露给模型；原能力语义继续保留 |

69 号中可调配置、变量定义载体和初始化、生命周期事件、能力失败及检查点准入等未决事项不因本文得到默认答案。相关路径遇到依赖时先提交用户确认，不通过重试、回退、临时加载或直接访问表来绕开。
