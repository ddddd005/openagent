## 3. 本批范围与不变量

1.3 的问题是“谁根据什么依据提交了修改，结果如何被正确接纳”；1.4 的问题是“消费者实际取用的是哪个配置，以及产生了什么结果”。不能把两者缩成再跑一次保存测试。

共同沿用以下约束：

- 工作台完整保存与节点页窄补丁进入同一配置业务，但原请求、绑定、证据、operation、回执和结果投影分别保留。
- 配置读写继续经过已安装的功能接口、业务、数据接口和数据管理；不新增万能入口或第二套业务。
- 固定 `revision`、当前 `edit_sequence`、会话修订分别处理；当前配置、固定原文、历史回执分别读取。
- 请求证据仍独立于配置业务事务；未知结果不能自动重发，已提交事实不能因本地接纳失败被改记为回滚。
- 确认询问、取消、派生、unchanged、冲突和错误按现有行为保护，不借验证重新决定产品语义。
- 本批不建设通用权限平台、只读存储新机制、变量初始化、工具加载、生命周期机制或完整定义目录。

代码现状用于确定验证对象，不作为批准所有既有行为的依据。尤其“准备期 A、本轮 A、下轮 B”只是当前代表样本的兼容验证，不替其他能力、检查点或重roll决定最终生效规则。

### 5.2 执行步骤

| 子步 | 执行内容 | 涉及层 | 交付 / 关口 |
| --- | --- | --- | --- |
| 1.3-A | 固定 S1/S2、现有两种操作身份、原请求、预期版本与测试副作用 | 来源适配、配置、数据、必要定义 | 局部样本与文件清单；区分无运行用例和运行用例 |
| 1.3-B | 验工作台正式提交：先留原请求，再发完整配置，准确接纳结果和结案 | 前端来源、配置接口、共用业务、数据 | 成功、unchanged、确定拒绝、未知和接纳失败的分段证据 |
| 1.3-C | 验节点页：精确 owner / 类型 / 输入 / 对象绑定，进入同一业务；只返回自己的文本和后续绑定 | 节点来源、配置、数据、必要定义 | 不允许指定任意输入目标，不产生第二事务或第二回执 |
| 1.3-D | 同一临时库、同一工作流，用两来源交叉修改与冲突 | 两来源、配置、数据 | 共享编辑序号、陈旧修改拒绝、新依据修改成功、独立当前读取 |
| 1.3-E | 按确认范围补客户端到真实 Channel 的纯修改桥接 | 节点客户端、来源适配、配置、数据 | 仅 state/patch/receipt/accept，禁止 start/控制/模型调用 |
| 1.3-F | 汇总来源证据、当前读取、局限与残余项 | 跨层核对 | 分段联验与真正跨端证据分别报告，再进入 1.4 |

1.3-D 的最小交叉场景：

1. 保存初始 A，固定修订 1、编辑序号 1，两来源均捕获该依据。
2. 工作台将可调文本保存为 B，编辑序号到 2，固定修订仍为 1。
3. 节点页持旧编辑序号提交 C，得到原结构化 CAS 拒绝；当前仍 B，不出现部分写入。
4. 节点页通过当前状态取得新依据，以新的显式请求保存 C，编辑序号到 3。
5. 新管理对象读取当前 C、固定原文 A；工作台 B 的历史回执仍表示当时的 B。

再用相反先后顺序验证同一边界即可，不扩成所有字段与来源组合的穷举矩阵。不得自动替失败请求更换依据、重试或改写原请求。

### 5.3 必须分别保护的分支

| 分支 | 验证重点 |
| --- | --- |
| 非法 / 外来 / 陈旧 owner 与未绑定输入 | 在对应来源检查处拒绝；不得绕成任意节点 patch |
| 确定 CAS 拒绝 | 原错误可见，配置不被拒绝值覆盖；两来源证据按各自现有规则处理 |
| 证据写入失败或结果未知 | 不能未经确认派发业务；保留准确原请求及本来源的锁定范围 |
| 保存已成功、响应丢失 | 读取原回执并核实，不再次派发业务 |
| 结果接纳或证据结案失败 | 保留实际成功事实和未结案原请求，不谎报回滚 |
| 固定修改需确认 / 用户取消 / 明确确认 | 询问不改配置；取消不写；确认另有请求身份，保留原工作流和会话 |
| 固定修订推进或派生 | 节点页返回准确 `next_owner`，旧 owner 不得静默升级；工作台按自己的选择归属接纳 |
| 迟到结果 / 较新的本地正式观察 | 不覆盖新依据、不抢占已切换的工作流或会话 |

工作台 `reconcile()` 读取的是原回执，不是今日当前配置；节点页 `receipt` / `accept_receipt` 也不能替代新的 `state`。前者保留历史事实，后者读取此刻状态。

## 6. 1.4 验证使用结果

### 6.1 消费顺序

```text
1.3 已核对的保存结果
-> 新一次当前 / 固定读取
-> 编辑器和节点页状态消费
-> 运行准备采用配置
```

### 6.2 执行步骤

| 子步 | 执行内容 | 涉及层 | 交付 / 关口 |
| --- | --- | --- | --- |
| 1.4-A | 用 1.3 已接受修改，重新加载 current 和 fixed，核对编辑器、配置应用和节点页状态 | 来源消费者、配置、数据 | 当前值、固定原文、编辑序号与显示一致；不以旧回执覆盖当前 |

| 1.4-E | 检查残余路径的兼容结果并汇总 | 配置消费及现有依赖 | 仅代表范围收口，不宣布全项目存取统一 |

1.4-A 应验证重新构造前端状态并从正式查询加载，而非只检查提交后内存。前端测试替身与后端真实独立读取仍分开记录；不得将两组独立通过改称它们之间已经实际串通。

1.4-C/D 优先复用 [test_editable_input_runtime.py](../../backend/tests/test_editable_input_runtime.py) 的 `test_prepared_input_stays_frozen_while_next_round_uses_new_saved_text`，不要因此运行同文件的检查点 / 分叉场景。既有样本通过公开窄补丁方法改值，只能证明配置消费；要覆盖生产来源，应分别接工作台命令、绑定节点页通路进行受控保存，而不是只重跑该测试便宣布两来源结果均验证。

该既有用例直接断言的是 `node_run.config` 和会话中的节点输出；虽然声明了 `public_outputs`，它未直接断言公开输出查询。若按本规划验证公开输出结果，还须补原有 `output.list` 查询与相应持久输出依据的断言，区分本轮 A 与下轮 B，不新建发布或查询机制。补验前不得声称既有用例已覆盖公开发布结果。

时序 gate 必须有明确进入信号、释放和等待结束，失败也清理本次测试运行；不以任意 sleep 代替准备期依据。所有执行仅在临时库中使用内置无模型节点，不启停现有服务、不访问业务数据。

### 6.3 当前发现的一项待验证风险

静态核对发现，`frontend/src/stores/workflowGraph.ts:212` 的 `loadDefinitions()` 使用 `mutationGeneration` 和固定 `revision` 接纳目录文档；`:228` 允许同固定修订的文档覆盖 `entries.document/saved_document`。配置应用另有独立 Map，`frontend/src/application/workflowConfiguration.ts:51` 按 `edit_sequence` 拒绝旧观察。

因此需要验证：目录请求先捕获 A，随后可调保存 B 被接纳、固定修订不变，最后旧目录 A 才返回时，Store 文档与配置应用是否仍一致。

**这是未复现的静态风险，不是已确认缺陷，也不是 78 号核心接线主张已失败。** 已有应用层旧观察测试不能替代 Store 竞态测试。若复现，应汇报两个状态的实际值、版本依据、受影响代码及最小修正建议；未经相应范围确认，不重构所有前端状态管理或更改修订语义。

## 8. 冲突、取舍与汇报

| 发现情况 | 处理 |
| --- | --- |
| 来源路径绕开既有接口，或同一修改出现两套配置规则 | 在已定链路内提出最小接线修正；不新增统一通信平台 |
| 验证需要嵌套事务、改变原 operation / 摘要 / 回执身份 | 停止受影响修改，报告与 76/77 号冲突 |
| 业务保存成功但客户端投影或结案失败 | 保留真实接受事实，核对原回执；不重发、不改记回滚 |
| 需要改表、补历史 current、迁移业务数据或修改默认库 | 不作为测试修复；报告准确路径、对象与迁移影响，另行决定 |
| 执行结果依赖尚未决定的可调范围、检查点或重roll语义 | 停止相关扩展，不以当前实现或旧测试批准新规则 |
| 只有前后端各自 mock 通过，缺真实交互证据 | 如实写明证据缺口，不能扩大验收结论 |
| 新测试需要 HTTP / 浏览器 / 真实模型或启停现有服务 | 与离线验证分开申请，不从本规划推导许可 |
| 范围外残余路径影响代表样本 | 给出最小依赖、受影响模块和备选范围，等待用户决定，不绕行 |

汇报应包含：实际事实与定位、失败或缺口、冲突要求、影响范围、建议及代价、仍可独立继续的工作。测试失败不自动授权架构改造，移除测试也不等于问题解决。
