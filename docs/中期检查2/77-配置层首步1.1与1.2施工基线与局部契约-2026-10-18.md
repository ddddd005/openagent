## 2. 本批代表对象与操作

- 对象：`tools.editable-input@1` 单节点的 `text` 配置，覆盖工作流身份、固定修订、节点投影和当前覆盖。
- 写路径一：工作台 `definition.update` → `GraphApplication.command` → 配置功能接口 → 配置业务 → 配置数据接口 → 数据管理 → 配置仓储。
- 写路径二：独立节点页 `graph.frontend-node.patch-input` → `BoundFrontendNodeOperations.patch_input` → 同一配置业务与数据通路，外层事务和回执身份保持不变。
- 读路径：`get_definition(identity)` 当前配置合成、`get_definition(identity, revision)` 固定修订读取；保存结束后通过新一次读取独立重读。
- 不纳入：变量定义与初始化、节点组、包选择、检查点可调值、布局折叠、项目资源正文、删除/归档/复制等项目管理，以及 Runtime 准备和执行改造。

## 3. 局部接口契约

### 3.1 配置功能接口

新增 `configuration_service.WorkflowConfigurationService`，作为配置层功能接口，持有对服务的引用，只负责受理、操作形状检查、分发和协调，不承载分类、派生或存储规则。

| 方法 | 受理内容 | 保留的结果/错误 |
| --- | --- | --- |
| `update_definition(document, *, workflow_definition_id, expected_edit_sequence, idempotency_key, confirm_derivation=None)` | 工作台完整 schema 3 文档保存 | 原 `graph.definition.update` 回执、原请求摘要、四类 outcome 和结构化错误 |
| `patch_node_configuration(*, workflow_definition_id, node_binding_id, component_id, component_version, changes, expected_edit_sequence, idempotency_key, confirm_derivation=None)` | 公开窄补丁意图，保留现测试调用面 | 原 `graph.configuration.patch-node` 回执；本批不新增生产入口 |
| `patch_exact_configuration(data, *, workflow_definition_id, node_binding_id, component_id, component_version, changes, expected_edit_sequence, confirm_derivation=None)` | 节点页在外层事务内调用同一窄补丁业务 | 不新开事务、不产生第二份回执 |
| `read_configuration(identity, revision=None)` | 当前配置或固定修订读取 | 原 `not_found`、当前合成和固定原文语义 |
| `list_configuration_definitions(*, include_archived=False)` | 定义目录投影 | 原最新固定修订、当前合成和归档过滤语义 |

`GraphWorkflowService.update_definition`、`patch_node_configuration`、`get_definition`、`list_definitions` 保留原签名并委托本接口，保证现有应用命令、查询和测试调用面不改变。

### 3.2 配置数据接口

新增 `configuration_data.WorkflowConfigurationData`，由服务装配；它向配置数据需求提供事务内会话 `ConfigurationDataSession`，并按需打开新的读取会话。

`ConfigurationDataSession` 只提供本批有限领域操作：

| 类别 | 方法 |
| --- | --- |
| 读取依据 | `current_configuration(identity)`、`definition_revisions(identity)`、`all_definition_revisions()`、`definition_sessions(identity)`、`session(session_id)`、`archived(kind, identity)` |
| 当前/固定合成依据 | `configuration_view(identity)` 返回当前行与对应固定文档；`fixed_document(identity, revision=None)` 返回精确固定修订或最新修订 |
| 保存结果 | `save_fixed_revision(document, expected_revision)`、`save_current_configuration(value)` |

该会话不提供 `rows`、`get`、`put`、表名、SQL、数据库路径、连接、通用 repo 或任意回调能力，也不自行决定可调/固定分类、确认或派生。

### 3.3 数据层管理接口

新增 `configuration_data.WorkflowDataManagement`，作为数据层管理受理口。本批只实现配置域：

- `configuration_transaction(records)`：把数据会话绑定到调用方已有的 `GraphRecordStore` 事务；
- `read_configuration()`：由数据管理内部构造 `SqliteStore`/`GraphRecordStore` 并提供只读会话，供保存后的独立重读。

数据管理内部可以使用原 repo；配置业务和来源适配只取得有限会话。数据管理不替代配置业务决定修改类别或派生，也不新建事务体系。

### 3.4 配置仓储与数据库适配

新增 `configuration_data.ConfigurationRepository`，承接固定修订、节点投影和当前覆盖的记录映射：

- 当前覆盖继续复用 `GraphRecordStore.current_configuration` / `put_current_configuration`；
- 固定修订和节点投影写入从原 `_save_definition` 移入仓储，仍使用 `repo.put` 以保留 `_changed_definitions` 和 bundle 校验；
- `workflow_current_configuration` 的 DDL 从 `workflow_configuration.py` 移到 `configuration_data.py`，`storage.py` 改为从数据层初始化；表结构、列名和存储版本不变；
- 不新增表、不迁移历史数据、不建立第二份配置权威。

### 3.5 原事务适配

`GraphWorkflowService._configuration_change` 保留原事务持有者：

```text
_configuration_change(operation, key, request, callback)
-> GraphRecordStore.atomic(operation, key, request, ...)
-> BEGIN IMMEDIATE
-> 回执重放检查
-> ConfigurationDataSession 绑定同一个 GraphRecordStore
-> callback(data) 执行业务
-> _validate_changes
-> 原生回执 + 应用身份行
-> COMMIT / 异常 ROLLBACK
```

- 工作台路径：功能接口构造与原实现完全相同的 request，`_configuration_change` 开启 `graph.definition.update` 事务。
- 节点页路径：外层 `graph.frontend-node.patch-input` 事务不变；`patch_exact_configuration` 只转发业务，不调用自带事务的公开方法。
- 来源核对、配置依据读取、编辑序号和固定修订检查仍在事务内、写前完成；配置业务判断分类/确认/派生后经数据接口保存。
- 前置请求证据仍是独立事务；回执身份、请求摘要、错误码和回退行为不改变。
- 保存后独立重读通过新的 `read_configuration()` 打开新存储读取，不复用保存阶段合成对象、回执缓存或前端内存。

## 5. 验证与证据边界

获准施工后按以下顺序验证，不自动运行全量：

1. 先运行第 1 节五个文件的现有测试，确认行为基线；
2. 增加小型接口调用检查，证明两条真实来源进入同一配置业务和配置数据接口，且保存后通过新一次读取取得配置；
3. 静态检查 `workflow_configuration.py`、`configuration_service.py` 不含 `GraphRecordStore`、`SqliteStore`、`self._change(`、`self._store(`、`.rows(`、`.get(`、`.put(` 等直接存取形态；
4. 复用现有陈旧编辑拒绝、`after_configuration_write` / `before_commit` 回滚、回执与当前读取分离断言；
5. 记录实际命令、basetemp、退出码、通过/失败/跳过、残余旁路和未执行项。

测试只使用临时 SQLite、合成注册和受控故障注入；不使用默认业务库、真实凭据或真实模型，不启动服务。

## 6. 停止与汇报

出现下列情况时停止受影响部分并报告，不用回退、双写或透传 repo 继续：

- 配置业务在同一事务内必须取得通用 repo 才能工作；
- 节点页接线会嵌套事务、改变外层回执或需要改写来源证据；
- 必须修改 operation、请求摘要、应用身份或证据结案语义；
- 需要改表、新增持久事实、提高存储版本或访问业务库；
- 所需查询跨入项目管理、变量、检查点或运行生命周期且无法以有限读取完成；
- 发现更晚文档决定或外部修改影响本批边界。
