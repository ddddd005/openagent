## 2. 已确认：配置固定与运行时求值

用户以“打开盒子才能知道结果”说明可调配置的求值时点，确认以下语义：

1. 当前运行期间存在配置修改锁。可调配置允许在启动前调整，启动后本次运行中的配置同样固定。
2. 节点可以到实际被调用时才对本次所需的值求值。实时求值可能仅参与内部运算，也可能直接形成输出。
3. 一次节点调用完成后，该次输出固定；不能把这次已完成调用解释成一个持续随外部变化更新的输出。
4. 启动时配置固定，不要求所有动态值在启动时提前求出；也不要求每一种节点都采用动态求值。
5. 后续通过配置层在运行期间修改配置属于另一个议题，本轮不展开。

“打开盒子”是求值时点的类比，不引入随机计算、缓存或惰性求值框架。具体取值仍由节点功能及既有读取规则决定。固定工作流修订不自动扩大为冻结全部项目资源或所有后续外部请求。

本轮已确定的是上述语义；具体配置项与现有准备、调用、继续路径的映射，留待第三批勘察核对。

## 3. 已确认：节点、Runtime 与数据的职责

| 位置 | 负责的内容 |
| --- | --- |
| 节点或具体功能 | 接受调用、获取输入、维护自身内部功能实现、按节点编排输出或回报；业务未成功时向 Runtime 抛错 |
| Runtime | 在既定调用关系下激活和调用，传递输入，接收输出或错误，维护执行位置并推进、中止或按既有条件继续 |
| 数据管理 | 承接相应领域的读取、写入、版本与并发条件校验，完成约定的持久化和事务 |
| 基础支持 | 运行目标、状态、会话指向及错误对外传递等薄口职责，具体接线仍需核对 |

节点不负责在未激活时自行启动，也不负责自己的输出在后续引发哪些变化。后续功能由 Runtime 根据定义和明确调用关系推进，节点无需获知或接管后续消费者。

节点负责自身业务是否成功，数据存取仍按已定接口和事务配合。当前存在“节点产生写入意图，执行侧将写入、输出和运行记录共同接纳”的路径；节点内部业务规则与执行侧接纳职责分别保留。本轮没有决定将所有节点改为自行开启数据库事务，或将节点业务成功统一改由 Runtime 重新裁决。

本篇不改变 [75 号](75-工作流能力资产与节点工具统一调用接续规划-2026-10-18.md) 关于节点与 Agent 工具绑定真实能力、共用调用渠道、同等加载和准备的要求；具体工具调用机制、实例准备及数据接纳仍待相应局部论证。

## 4. 已确认：错误中止、继续与已完成内容

用户确认现有错误中止与继续逻辑已经体现：

- 后续节点错误，不影响之前节点已经完成和接纳的内容。
- 继续可以按已有条件从当前中断位置接续执行，不将整个工作流自动从头重跑。
- 节点维护自己的功能和必要数据交互，成功后输出或回报，未成功则抛错。

例如：

```text
A 已完成并接纳 → B 已完成并接纳 → C 错误中止
```

A、B 的已接纳结果保留；C 的接续和错误处理沿用已有明确机制。本篇没有新增重试、跳过、恢复或补偿策略，也不将“继续”解释为任意节点均可安全自动重做。

对于自由实现的节点，抛错只能表示调用没有成功返回，不能据此推断其内部从未写入数据或产生外部效果。Runtime 只承诺自身明确管理的接纳和继续边界，不额外保证任意扩展内部都能回滚或重放。这是承诺范围的说明，不是增加强制控制机制的理由。

## 5. 已确认：已有业务结果分步成立，整轮最终汇总

用户认可按已经明确的业务动作分步形成结果，最后汇总整轮调用。一次业务调用可以包含：

```text
前端发起
→ 后端进行必要数据操作
→ 输入节点或相应入口完成可调输入写入并请求激活工作流
→ 工作流执行
→ Runtime 根据定义依次调用后续功能
→ 整轮业务调用结束
```

该示意表达已有业务可以组合的方向，不冻结 HTTP 路由、触发协议或调度器。输入节点接受激活后执行相应功能，不表示未激活节点可以自行启动；其输出后续如何被处理仍由调用关系决定。

工作流可以是整轮业务中的一步，后续功能调用也可以是一步。工作流执行完成和整轮业务结束可以分别表达。

例如，在已经有明确结果的部分：

```text
输入保存成功 → 工作流完成 → 功能甲完成 → 功能乙失败
```

可以如实报告前三项已成立，整轮调用在功能乙处中断。后续按已有接续规则处理，已完成结果不因更晚错误自动失效。

### 5.1 步骤粒度保持自由

本轮最新明确要求：

- 节点执行采用弱约束、强自由的方向。
- 已有明确业务结果的部分保留各自结果；尚无明确结果的内部过程，不强行补建。
- 不要求穷举整轮业务的全部步骤，也不要求给节点内部每一步建立正式业务结果。
- 用户自定义节点和功能依靠作者意愿及约定组织，不为强制规范增加代码负担。
- 保留现有调用约定和有实际需要的规则，不由本篇引入逐步回执、统一内部步骤声明或全节点结果登记机制。

此前讨论中“对每个步骤明确输入、结果和失败位置”的建议，在本篇按上述要求收窄：用于已有明确结果的框架路径及实际需要论证的动作，不作为所有节点、所有内部操作的强制准入清单。

### 5.2 业务步骤与事务分别描述

一个业务步骤可以包含多个必须共同成功的写入。模块业务归属可以分开，必要的共同事务不因此被拆开。

当前成功结算包含运行终态、聊天候选绑定、会话提交记录、成功检查点及结束记录，已有同一事务约束。可以将这组动作理解为一个明确的结算步骤；本轮没有批准改成工作流先宣告结算成功，再异步补写检查点。

节点已完成前缀与最终结算分别处理。最终结算失败不自动撤销全部已接纳节点；反之，节点计算完成也不能代替最终结算成功。

`run`、业务轮次、批次用于解释不同业务范围，不预设固定三层结构。当前未明确的业务概念不因名词存在就新增实体、状态机或批次调度器。
