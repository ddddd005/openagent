### 2.1 P2-1 异常生命周期细化

- 语义：同一 chain 的 `_execution_errors` 是“最新一次执行调用”的上报，不是整条链历史的累积；新调用（resume/retry_archive/retry_acceptance/retry_failed_node 都经 `_execute` 入口）开始时旧上报作废。
- 不变量：本次调用若业务提交后通知失败，仍按 G12 抛 `CommittedNotificationError`；若本次调用成功且通知成功，`wait()` 返回 `None` 且不再携带旧结果；失败/超时语义不变。
- 范围：不新增状态表或版本字段，不改变 `wait()` 形式、超时行为或节点级失败表达。

### 2.2 P2-2 来源身份与结构细化

- 只允许同链 `chain_start` 作为 released-basis 结算的 package_lock/global_resources 来源；状态、变量修订、对象、私有态、历史引用仍取真实已接纳数据。
- 缺失、身份不符、结构损坏均为 `storage_contract_violation`/500：Q11 close 整体回滚（无 close 回执、无 head/commit/manifest 变化）；Q10 异常收尾同样回滚，调用方仍见原异常（未改变错误政策）。
- 行为收紧：旧库或旧版本写出的 `chain_start` 若缺 envelope/kind/身份字段，后续 close/unconfirmed 收尾会显式失败而不是补造来源；这是 119 §6 承诺的实现，不属数据迁移。

### 2.3 P2-3 诊断脱敏细化

- 通知失败项形状改为 `{stage, outcome, reason_code, error_type}`；`reason_code` 为固定 `notification_stage_failed` 或产品 `DiagnosticError` 的受限 reason code；不再有 `message` 字段。
- 诊断记录失败路径：`notification_diagnostic_recorded=false` 时 `notification_diagnostic_error` 为 `notification_diagnostic_failed: <受限 error_type>`，不复制异常文本；此时持久诊断不写 `round_notifications`，业务成功事实不变。
- 等待异常与持久 `chain_run.diagnostic.round_notifications` 使用同一份安全表达，避免两处泄露不一致。

### 2.4 P2-2 补充：损坏 JSON 解码边界（复核追加）

- 现象：`chain_start` 的 payload 被存成不可解析 JSON 时，`loads_strict` 在 `_prepared_boundary` 读取前抛出裸 `ContractValidationError("Invalid JSON input")`；事务会完整回滚，但异常无 `reason_code`/`status_code`，HTTP 按 `server.py` 既有规则落 400/`invalid_request`，与 119 §6 承诺的 `storage_contract_violation`/500 不符。
- 修复：`_prepared_boundary` 的两条 manifest 读取分支（settlement 与 repo）各自 `try/except ContractValidationError` → `DiagnosticError("storage_contract_violation", "The prepared boundary for this execution is unreadable", status=500)`（新增 `_unreadable_boundary` helper），原解码异常保留在 `__cause__`；合法 manifest、身份/结构不符、缺失等既有分类与回滚行为不变。
- 回归：close 路径断言错误分类/500/文案与回滚（以原始 records/manifests/idempotency 对比），Q10 断言回滚与 wait 原异常；独立复验另以进程内 HTTP 实测同一状态返回 500（非 400），并以敏感性对照证明去掉转换会退回 400/`invalid_request`。
- 范围限制：本窄修复只覆盖 prepared-boundary 结算读取；`get_run` 等公开读取若遇到同一损坏 payload 仍会抛无 reason_code 的解码错误（见 §6），不在本次扩大范围。
