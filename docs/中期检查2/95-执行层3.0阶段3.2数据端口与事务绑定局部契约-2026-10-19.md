## 2. 局部契约

### 2.1 数据管理分发

在现有 `WorkflowDataManagement` 上增加执行领域分发：

- `execution_transaction(records, *, basis)`：把执行领域端口绑定到调用方已有的 `GraphRecordStore` 和本次 `RunBasis`，要求 `records.store._connection.in_transaction`，不打开、不提交、不回滚新事务；
- `read_execution()`：为宿主读取、事实读取和事务后独立重读打开新的 store，只提供读操作，不作为写路径；
- `accept_fact(...)`：运行事实保持自己的独立事务，不并入执行主事务，也不由 `execution_transaction` 代办提交。

`WorkflowDataManagement` 仍是唯一的数据管理入口；新增的只是执行领域分发，不是可执行任意 `get/put/rows` 的上级万能入口。

### 2.2 事务作用域的运行数据包

`_start_run`、`_execute`、控制回调和宿主桥接不再直接持有 `repo`/`GraphRecordStore`。在 `_change` 的回调边界内构造一个只含有限领域会话的 `RunData`：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `records` | `ExecutionRecords` | session、chain、node_run、output、workflow_ref/commit/snapshot、私有态 |
| `state` | `ExecutionState` | 程序变量、会话对象及对象写集 |
| `settlement` | `ExecutionSettlement` | 结束 manifest、commit、成功检查点 |
| `type_evidence` | `ExecutionTypeEvidence` | 本批唯一可写的类型证据核验 |
| `configuration` | `ConfigurationReadSession` | 固定修订文档、当前配置覆盖的只读读取 |
| `chat` | `ExecutionChatData` | 仅主链使用的聊天绑定、冻结输入/调用和检查点读取 |

`RunData` 由数据管理入口在同一事务内装配，只暴露上述命名会话；不提供 `store`、`connection`、`repo`、`atomic`、`get`、`put`、`rows` 或通用回调。

### 2.3 有限领域会话

| 会话 | 允许的操作 | 明确不提供 |
| --- | --- | --- |
| `ExecutionRecords` | 按 session/chain/run/output 身份读取；写 session、chain、node_run、output；读写私有态；读 Head/commit/snapshot | 任意 record 类型、任意 owner 过滤、bundle 校验、事务控制 |
| `ExecutionState` | 读当前变量态；以原 `expected_revision`、幂等键和请求写入变量态；读当前对象；按对象写意图应用写集；读检查点对象 | 通用 `ProgramVariableStore`、`SessionObjectStore`、SQL 或连接 |
| `ExecutionSettlement` | 保存 chain/state manifest；执行原 commit；追加成功检查点；读最近检查点 | 任意表写、改变检查点准入、拆分共同事务 |
| `ExecutionTypeEvidence` | `check_registry(types)`，沿用原 `TypeContractStore.check_registry` 的 savepoint/外层事务语义，允许首次登记 | 只读定义口、`check/register` 的任意业务调用、绕过事务 |
| `ConfigurationReadSession` | 固定修订文档、当前覆盖行、定义修订存在性 | 配置保存、定义保存、编辑序号推进 |
| `ExecutionChatData` | 聊天绑定、单条聊天对象、冻结 round 输入、调用记录、最近检查点、成功候选绑定 | 聊天候选规则、select/fork/reroll 全量迁移、通用对象仓储 |

对象和私有态的校验仍使用本次 `RunBasis` 的 `registry`/`data_types`；端口方法接收本次 registry，不以 `self.registry` 为默认值。

### 2.4 特殊边界

- **类型证据写入**：`ExecutionTypeEvidence.check_registry` 是执行领域内的显式可写适配，内部仍调用 `TypeContractStore.check_registry`，保留“已有声明比对、缺失时在所属事务登记、嵌套 savepoint”的原语义。定义数据口仍是只读，不新增 `check/register`。
- **bundle 历史校验**：`GraphRecordStore(store, definition_registry=self.registry)` 仍由 `_change` 装配并调用 `atomic`；执行端口不接收 `definition_registry`，不暴露 `_validate_changes`，也不因端口写入而取消历史修订的 bundle 校验。
- **节点接纳事务**：`_node_event`（含 `_settle_node_result`/`_save_effects`）在节点接纳的 `atomic` 事务内共同保存该节点的输出、约定写入、`node_run`/`chain` 进度和会话修订；接纳完成即提交，是整图事务的已接纳前缀，不是整图事务。
- **最终结算事务**：`finish` 的最终结算事务共同保存运行成功终态、`_commit`、成功检查点和结束 manifest，四者不拆开。端口只承接各自事务内的有限读写，不自行 `BEGIN`/`COMMIT`/`ROLLBACK`，也不把节点接纳并入最终结算。`after_checkpoint_write` 故障只回滚本次最终结算；此前已接纳节点的输出、变量、对象、私有态和进度必须保留。
- **检查点收集**：`collect_checkpoint_state`/`collect_agent_contexts_in_transaction` 改为接收精确固定文档、`ExecutionState.checkpoint_value` 和本次 `types`/`registry`，不再接收 `GraphRecordStore`；`_append_success_checkpoint` 从 `RunData.configuration`/`RunData.state` 传入。收集规则、准入和 diff 仍留在检查点模块，检查点端口不调用配置或对象仓储。
- **运行事实**：`ExecutionFacts.accept` 仍以独立 `BEGIN IMMEDIATE` 打开新 store，完成 owner 检查和事实写入后提交；不接受 `RunData`，不与节点接纳合并事务。
- **管理关闭**：失败链已释放绑定后的管理关闭仍可按 3.1 已允许边界使用当前来源；该路径不继续执行、不重放业务。执行异常收尾仍按 P2 修正复用同链 `chain_start` manifest。
- **历史与公开读取**：`get_session/list_sessions/get_run/list_checkpoints/read_checkpoint`、`GraphPublic` 输出/历史观察和 `GraphInformation` 独立历史查询可保留原只读实现；本批只验证它们读到真实持久结果，不宣称这些旁路已迁移。

### 2.5 已决边界

下列问题在第 2 批施工前定案，不留到实现中临时选择：

1. **`_stable` 与 `_view`**：`_stable` 仍是命令前置校验，读取 session 通过 `RunData.records.session`；`_view` 仍是事务内的响应投影，可使用 `RunData.records`/`RunData.configuration` 的只读方法，但不在其中写库、不重取运行依据。`get_session`/`list_sessions` 的管理投影保留原实现。
2. **独立读连接**：`read_execution()` 沿用现有 `store_factory`，不新造 SQLite `query_only` 连接；“独立”指新 store、事务后读取，写入禁令由端口方法保证。宿主只读桥接同样走该入口。
3. **`_execute` 输出读取**：第 2 批保留现有全量 `workflow_output` 读取语义，端口提供具名的 `all_outputs()`；不趁迁移收窄为精确 ids，避免改变缺失输出时的错误码。收窄需另立行为决定。
4. **类型核验适配**：对象会话的 `_check_type` 与准备路径的 `check_registry` 共用同一个 `ExecutionTypeEvidence`，底层仍是 `TypeContractStore.check/check_registry`。`GlobalResourceStore` 的 `allow_legacy=True` 历史读取保持原路径，不在本批统一；本批选中链不经过它。
5. **聊天范围**：第 2 批选中普通 round，但没有参与聊天项，因此只迁移 `_prepare_chat_run` 的文档/绑定读取与早退、`_bind_chat_success` 的空调用读取；参与聊天项的 `save_chat_round_inputs`/`save_chat_invocations` 与成功候选写入留第 3 批。聊天候选规则不迁移。
6. **资源读取**：准备期资源预检仍在原事务内，使用期内容资源仍按 3.1 的本次类型读取；本批只登记、不迁移提供方资源管理。选中链不经过资源节点。
7. **`_execute` 装配事务**：装配阶段沿用现有显式 `BEGIN` 和 `closing` 回滚，不由端口提交；读会话绑定到该已打开事务。`read_execution()` 只用于装配完成后的独立重读和宿主读取。
8. **manifest 失败回退**：manifest 端口只接收已解析的 `package_lock`/`global_resources`，不接收 registry。`_save_manifest` 在无绑定时通过 manifest 读端口取得同链 `chain_start` 的值再写入，保持 P2 的“不重算、不取当前定义”语义。

## 4. 代表主链

第 2 批选择 **普通 round 成功主链** 作为代表主链：

```
GraphWorkflowService.start
  -> _start_run（捕获一次 RunBasis）
  -> _prepare_run（配置读取、类型证据、编译、prepared 记录、chain_start manifest）
  -> _execute（begin、状态装配、图推进）
  -> _node_event / _settle_node_result / _save_effects（输出、变量、私有态、对象）
  -> finish（chain/session 终态）
  -> _bind_chat_success（无聊天项时为空读）
  -> _commit（快照、提交、Head、变量绑定、state_snapshot manifest）
  -> _append_success_checkpoint
  -> _save_manifest("chain_end")
  -> 提交后通知与独立重读
```

选择理由：

- 它是产品真实入口和最常用的执行路径，不是测试直接调用私有函数；一条链即覆盖准备、执行、节点接纳、共同结算和结束读取。
- `_commit`、成功检查点和结束 manifest 是 round 成功的必经步骤。第 2 批必须带上这些**在链上的最小片**，否则选中路径仍会为了完成结算回到旧 `repo`，无法证明“业务内部撤出直连”。
- 第 2 批不迁移 round 之外的聊天候选写入、`chat_select`/`chat_fork`、控制路径、事实/产物宿主桥和剩余 3.2-B/C；这些留第 3 批。选中测试使用无聊天项的 `text_graph`，因此 `_bind_chat_success` 只走空调用读取，不触碰参与聊天项的写入。
- 现有 `test_success_checkpoints` 已提供事务后独立重读、检查点故障回滚和结束回执重放，适合作为共同结算未被拆开的保护证据。

第 2 批完成证据：

1. 真实 `start` 用 `test_graph_service.text_graph` 成功执行；事务后通过 `read_execution()` 独立重读 chain、node_run、output、变量、私有态、对象、commit、checkpoint 和 manifest，结果不是保存响应或内存缓存。
2. 端口接线探针至少记录 `records`、`state`、`settlement`、`type_evidence`、`chat` 和 `configuration` 的实际调用；选中路径的准备、接纳、检查点和结算函数不再接收 `GraphRecordStore`，不是只新增类而继续走旧 `repo`；控制、历史和管理的兼容分支单独列出，不混入本项声明。
3. 类型证据：准备路径在缺少证据时写入 `registered_type_contracts`，回滚时不留行；已有证据仍比对原声明，不重定义；对象 `_check_type` 复用同一适配。
4. bundle 校验：构造一个只通过端口写入、但 bundle 不完整的变更，仍在 `atomic` 提交前被 `storage_contract_violation` 拒绝；执行端口没有绕过 `_validate_changes`。
5. 事务：在 checkpoint 写入后注入 `after_checkpoint_write` 故障，只回滚本次最终结算，不出现半套 commit 或结束 manifest；此前已接纳节点的输出、变量、对象、私有态和进度保留。原 `checkpoint_commit_pending` 和 finish 回执精确重放保持。
6. 独立重读与原有 `test_success_checkpoints`、`test_graph_service` 同时通过；没有新增表、存储版本、历史迁移或前端协议变化。

## 6. 未决项与停止线

本契约没有把下列事项留作实现时自行决定：

- 不新增表、存储版本、历史迁移或业务数据清理；
- 不拆分最终结算事务（运行成功终态、commit、成功检查点、结束 manifest），也不把节点接纳并入最终结算或以最终结算失败撤销已接纳节点结果；
- 不把运行事实的独立事务并入主事务；
- 不向功能层交出通用 `GraphRecordStore`、连接、`atomic` 或任意 `get/put`；
- 不让定义只读口获得 `check/register`，不取消或缩小 bundle 历史校验；
- 不改变节点参与、配置固定/调用期求值、检查点准入、暂停/继续/重接纳权限；
- 不启动真实模型、产品服务或依赖安装，不新增前端协议。

若实现中发现需要改变上述任一边界，停止受影响部分并报告；不以临时默认、旁路、双写或回退继续。
