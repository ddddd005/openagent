## 4. 实现思路与职责分开

### 4.1 四种对象不能混成一个

| 对象 | 维护方与作用 | 不能承担 |
| --- | --- | --- |
| 能力定义及实现 | 来源包维护准确节点契约、原生 executor 或宿主引用；定义目录只读提供查询 | 不保存某 Agent 私有选择，也不由提示词生成实现 |
| 普通节点实例 | 配置层维护自身类型、配置、连线、对象绑定 | 不成为 Agent 可以直接继承的一套实例参数和身份 |
| 工具绑定/加载锚点 | 配置层表达 Agent、附带工具入口与真实能力的关联，以及明确的访问配置 | 不等于提前执行业务，不创建隐形画布业务节点 |
| 工具提示词声明 | 提示词功能组织说明、参数展示及位置顺序，引用准确绑定 | 不独立授予权限，不允许改段说明就获得另一能力 |

这些是职责，不要求四张新表或四个新服务。优先用现有配置保存与只读定义查询；新增字段、端口、节点版本及序列化方式由局部契约明确。不要未经确认直接把新字段塞入现有严格 `input_snapshot` 或 manifest。

### 4.2 变量首版局部契约与实现建议

本节对应 4.0-2 的具体化。首版只操作当前会话中已经注册的 `workflow.variable@1` 对象；变量对象沿用现有配置、初始化与注册流程。不给 Agent 新增变量注册、删除、跨会话访问或运行期类型注册。范围、Agent 自身授权及逐次写入接纳已确认；其余具体接线为单一实现建议，不并行建设多套机制，也不据此开始产品施工。

#### A. 三类操作，复用两个真实节点

| 面向 Agent 的操作 | 真实能力目标 | 参数及结果 |
| --- | --- | --- |
| 读取，例如 `score_read()` | `tools.variable-to-content@1`，`mode=json` | 无模型参数；校验真实节点输出后转换为变量值结果 |
| 写入/替换，例如 `score_set(value)` | `tools.variable-assign@1`，`operation=set` | `value` 按该变量已经注册的标量类型声明 |
| 数值修改，例如 `score_add(value)`、`score_subtract(value)` | 同一 `tools.variable-assign@1`，分别为 `add`、`subtract` | 仅数值变量提供；复用现有算术、已赋值检查与写意图，不在工具侧再算一遍 |

“写入”和“更改”不是两套存储 API：`set` 同时承接首次赋值与替换已有值。字符串、布尔变量只生成读/写工具。为每个显式绑定的变量生成固定类型工具，可以沿用当前 callable 的标量参数限制，不引入通用 JSON 参数协议，也不让模型填写内部对象键、权限或 expected revision。

当前赋值节点输出为空；工具的写入成功结果应来自接纳后的对象重读，而不是伪造该节点有变量输出端口。读取节点只做内容到工具结果的转换，不另外实现一份变量读取业务。

#### B. 一个真实加载锚点，配置表达 Agent 和变量引用

建议在现有 `workflow.tools` 来源内附带变量工具适配和一个明确导出的加载节点，不首建独立适配包、通用工具导出协议或工具注册数据库。新增导出须记录准确包版本；不得用同一个已发布包版本表示不同契约。

加载节点使用显式配置引用目标 Agent；候选配置意图如下，不是现行可直接保存的 schema：

```json
{
  "agent_node_id": "<真实 Agent 节点实例 UUID>",
  "variables": [
    {
      "alias": "score",
      "object_key": "variable/score",
      "operations": ["read", "set", "add", "subtract"]
    }
  ]
}
```

该节点是图上真实存在的能力加载锚点，不是隐藏的变量业务实例。建议其职责为声明与准备，不排入普通业务节点执行顺序；实例引用复用现有配置节点引用校验。由参与运行的 Agent 收集其显式绑定的加载声明，不让无关锚点激活额外能力。该连接方式是本方案建议，不默认为已经有工具输入端口或数据边。

工作流启动从正式配置读取这些绑定，在本次 registry 中解析准确目标与来源，核对变量存在、已注册类型、可用操作及权限，再冻结生成的工具清单与适配。类型在启动检查，具体值按每次调用读取；不提前执行变量业务。

工具提示词节点引用同一绑定生成说明与参数材料，两类材料仍可分别排布。别名冲突、无真实绑定或声明不一致时明确拒绝，不静默删工具。配置经现有配置接口保存并独立重读，不依赖进程内临时列表。

#### C. Agent 是授权主体，工具调用另有追踪身份

首版已确认使用目标 Agent 的真实 `node_binding_id` 承接对象 ACL；所绑定变量必须显式允许该 Agent 读取，写工具还须显式允许写入。加载节点不自动取得变量权限，也不向 Agent 转授其他实例权限。

每次调用另外保留 `tool_call_id`、`tool_execution_id` 和加载绑定引用，用于事实、操作身份和故障定位，不把它们冒充节点 UUID。适配器只从启动时固定的允许集合中选目标，内部构造受真实能力声明及该绑定共同约束的调用上下文；不把变量目标的完整权限并入 Agent 总权限。

内核当前只调用 `execute(arguments)`，因此落实时必须增加有限的内部调用桥，把已产生的工具调用/执行身份送到适配器。不能只在闭包里捕获模型参数，也不能使用全局“当前工具”变量推断身份；模型本身不提供这些执行身份。

#### D. 已确认逐次接纳，写入成功再返回

每次变量工具写入独立接纳，正式保存并独立重读后才返回成功。具体实现建议每次调用使用新的有限能力调用上下文，操作键由本次工具执行身份和目标对象共同确定。该上下文用于权限、读取与写意图，不创建新的画布节点或完整 `node_run`。

```text
Agent 选择 score_add(value)
→ 内部桥传递本次工具绑定和调用身份
→ 确认父 Agent / chain 仍可执行，取得本次固定准备结果
→ 经数据入口读取准确对象及当前修订
→ 调用同一 tools.variable-assign@1 实现，形成写入意图
→ 执行侧经有限接纳入口校验 owner、许可和 CAS
→ 在该次接纳事务保存变量变更及准确业务关联
→ 事务结束后独立重读目标对象
→ 返回实际值及修订；随后才发布工具成功并交回 Agent
```

读取工具同样使用真实目标实现和最新正式对象值，但不创建写事务。首版串行调用，顺序沿用 Agent 内核当前工具派发顺序，不新增队列或并行写入。

本批已确认采用这一新增语义：`set → add → read` 可以在一个 Agent 调用内连续使用最新正式值；后续工具或 Agent 失败不撤销此前已正式接纳的变量变更。每次调用的新上下文仍遵守“该边界同对象一次写”，不删除现有限制。

新增的变量接纳使用明确有限操作，不把仓储或事务对象交给 Agent。对象写回、执行关联和必要会话修订在本次边界一致保存；现有事实独立事务与整图最终结算不被合并。不能直接把普通 `_node_event(succeeded)` 当作工具接纳，否则会提前完成 Agent 节点并推进图。

已逐次接纳的工具写集不能在 Agent 最后成功时再次提交。执行侧还须同步本次运行的对象视图与后续接纳依据，保证 Agent 后面的普通节点读到新值；不以跳过 basis/CAS 校验解决旧快照问题。接纳失败、独立重读失败或暂停/关闭竞争均显式停止；已提交事实保留，不自动再执行 `add/subtract`。

#### E. 首版验证与修改位置

建议接线位置为：`tool_package.py` 提供附带映射与加载锚点，配置/定义校验承接准确引用，准备阶段固定清单，有限共同调用适配调用现有变量 executor，`agent_executor.py` 与内核边界传调用身份，执行数据接口承接逐次接纳和重读。文件名可按现有结构选择，不创建覆盖全项目的万能能力服务。

最小验收链：普通节点写值 → Agent 读取 → Agent `set(10)` → `add(2)` → 再读为 `12` → 下游普通节点读为 `12` → 重开存储仍为 `12`。另测第二次调用失败时第一次已接纳结果保留、越权与类型错误不写、缺准备不执行、成功后不重复提交。变量注册与其他能力不纳入本批。

用户已确认 Agent 自身权限和每次变量工具写入独立接纳，不再重复询问这两个边界。显式配置锚点的具体表示、包导出版本及有限接口继续按施工局部契约明确；本次只将已定语义落文，不代表产品实现或测试已完成。

### 4.3 共用调用目标通路

```text
来源包提供真实节点能力及附带工具映射
→ 定义/注册核对准确身份、版本、来源和实现
→ 配置保存 Agent 工具绑定、加载锚点及提示词引用
→ 工作流启动：从图和配置收集普通节点需求 + 工具绑定需求
→ 本次 RunBasis 下完成适用的同等检查和准备
→ 普通节点入口 / Agent 工具入口
→ 共同能力调用适配
→ 同一 RegisteredNode 的原生 executor / executor_ref
→ 输出、读取事实、写入意图、诊断
→ 执行侧依约接纳，经所属数据端口保存
→ 工具结果返回 Agent；普通节点输出交图执行推进
```

这里的“共同”是相同能力解析、调用规则与通信边界，不要求取消原生/宿主两种实现，也不要求把全部逻辑塞进 `RuntimeHost`。执行侧组织调用，功能层实现业务；Agent 内核仍只选择工具、形成参数和消费结果。

### 4.4 模块拆分与依赖

| 位置 | 本批职责 | 必须留在别处的逻辑 |
| --- | --- | --- |
| 功能/能力包 | 真实业务操作、工具到能力的可信参数及结果适配 | 工作流调度、通用数据库通信 |
| 配置业务与 `configuration_service.py` | 校验 Agent 绑定、锚点及提示词关联，处理保存与独立读取 | 节点算法、包导入、工具实际执行 |
| 定义目录、`NodeRegistry` 与包适配 | 准确引用解析、来源及实现关联 | Agent 的运行选择、会话当前值 |
| 工作流准备与 `RunBasis` | 收集需求，消费同源依据，建立本次调用所需准备结果并负责释放 | 启动前执行工具业务、动态猜测工具 |
| 共同调用适配与节点执行 | 参数校验、上下文和授权衔接、调用真实 executor、结果检查 | 第二套能力实现、Agent 思考调度 |
| `agent_executor.py`、内核边界 | 将已准备绑定适配成模型工具，传递准确调用关联，保持暂停与保留结果 | 直接取得 registry 写权限、通用 repo 或连接 |

候选共同调用小模块的文件名由施工方选择；只有确有重复的契约和调用逻辑才提取，不为统一命名建立万能服务。

## 5. 核心实现与次要实现

### 5.1 核心一：准确绑定，而不是名称查 callable

一条业务工具绑定至少应能核对：工具入口准确引用、真实节点准确引用、母包及准确版本、适配来源、所属 Agent/加载锚点、必要访问绑定。这里列的是必须回答的信息，不冻结完整 JSON 格式或新增独立能力 ID 体系。

工具名称只服务模型选择；不能通过同名猜测节点、取最新版本或从当前全局目录兜底。参数转换允许不同，但必须接受真实能力的配置、端口、类型和数据边界检查。禁止把另一业务实例的配置直接转交 Agent。

参数 schema 来自真实可执行绑定。位置和顺序可调不等于能任意改变调用契约；若要允许用户编辑参数契约本身，先明确合法变更与实际适配方式。

### 5.2 核心二：同等准备不等于把工具塞进图排序

准备收集应区分“图上需要执行的实例”和“Agent 已绑定的能力”。工具锚点提供声明依据，不自动把目标能力变成图中的另一个 scheduled node，不添加隐形数据边/控制边，不恢复 `execution_roots`。

当前 `RunBasis` 只包含冻结 registry 和同源定义目录；服务实例/路由在 `_service_runs`，资源在 `_resource_frames`、`_workflow_frozen_resources` 等位置，`RuntimeHost` 由 `_host_for_chain` 按需构造。“共享准备结果”要求这些实际消费者遵循同次来源和生命周期，不表示它们已经全部存进 `RunBasis`，也不要求把所有运行对象搬进这个值。新增包附带工具映射也须与 registry、manifests 同次发布并固定捕获；不能先冻结节点 registry，调用时再从当前工具目录取得另一份映射。

对每个工具目标对照实际节点逐项列出：定义和包依赖、配置与参数边界、类型、executor、资源、服务声明与路由、对象访问、宿主生命周期及释放。逐项说明哪些在启动检查、哪些依赖调用参数；不以“registry 里存在”代替同等准备。

启动能确定的目标必须在 Agent 执行前准备。若某设计只有执行上游业务后才知道目标能力，停止并报告绑定表达缺口；不能首次工具调用才加载。启动不提前读完所有动态业务值，不调用模型，不写工具业务结果。

普通节点与工具共享本次准备依据；它们不必共享有状态实例、私有态或输入输出。实例共享、私有态归属、宿主 continuation 和释放若涉及新增语义，须先在局部契约中确认。

### 5.3 核心三：调用、写回、返回分别有边界

共同适配接收准确目标、已准备依据、实际参数及调用归属，复用真实节点调用所需校验。原生目标仍调用原生实现；宿主目标按准确 `executor_ref` 和已准备宿主调用。不为每次工具调用编译一张临时工作流图。

输出给模型前需要明确：

- 哪些是实际能力输出，怎样转换为模型可消费结果。
- 哪些是读取事实、写入意图，哪个接纳点使其成为正式数据。
- 哪些是调用过程事实；它们可以先持久成立，但不代替对象保存回执。
- 发生错误、暂停、关闭或接纳失败时，哪些结果保留，哪些尚未正式成立。

写回仍经执行侧与数据管理的有限端口；功能或工具适配不直接持有 `GraphRecordStore`、仓储和连接。不是要求所有能力都返回写意图：纯计算可只返回输出，已有明确持久边界的业务须如实对接，不强制内部步骤逐项落回执。

### 5.4 核心四：调用身份与权限不是一回事

复用现有运行和 Agent 调用事实，至少能追踪：

```text
workflow_session_id → chain_run_id
→ Agent node_binding_id / node_run_id
→ tool_call_id → tool_execution_id
→ 准确工具绑定 / 真实能力引用 / 对应结果与诊断
```

[`InvocationOwner`](../../backend/src/phase1_agent/runtime_hosting.py#L25) 和内核已有工具执行 ID 是接线基础；不是全部已经打通。若能力调用需要子身份，必须说明父子关系、授权、事实 owner 及生命周期，再决定是否增加身份载体。不得直接把工具名称或一个关联 ID 当作对象权限。

不得把每次工具调用谎报成完整画布节点执行；也不能只保留最后一条模型消息，丢掉前面已发生的调用与写回事实。

### 5.5 次要实现

节点目录展示、表单控件、工具说明排版、诊断展示可随核心协议补齐，但不先做工具商店、自动发现、批量迁移或复杂配置编辑器。新节点需要可实际保存、重读和使用的最小配置入口；“次要”不等于只留后端私有函数而没有真实消费者。

工具定义与 Agent snapshot 当前版本、参数限制、内核控制工具兼容均须按实际受影响面修改；新增结构化参数不能用未经论证的 JSON 字符串包装绕过现有 schema 限制。

| 4.0-4 共同调用 | 普通节点与工具适配共用真实实现和通信；接 Agent 内核入口、运行关联、暂停/关闭边界 | 执行、功能、数据 | 两入口命中同一真实能力；不临时加载，不复制业务；输出和诊断正确 |
| 4.0-5 变量样本与跨层联验 | 按首版变量范围验证读、set、add/subtract、连续交互、事实、持久接纳与独立重读 | 功能、执行、数据、配置/定义消费 | 两入口共用变量能力、连续值与下游一致、实际持久重读；不宣称动态类型注册或其他能力完成 |

### 6.1 哪些可一起做

- 4.0-0 与 4.0-1 可以合并勘察，配置、调用和数据三线可并行调查，但共同身份、契约和事务由一处协调。
- 4.0-2 契约通过后，配置保存、提示词引用、定义查询的内部实现可在相同契约下并行；涉及同一文件由一个负责人落改。
- 4.0-3 与 4.0-4 可在同一批局部实现，但必须先有“准备完成且尚未执行业务”的证据，再接真实 Agent 调用。
- 4.0-5 的纯计算两入口探针可以提前准备，不能据此跳过有持久写回的数据样本验收。

### 6.2 哪些必须先审核再继续

1. 4.0-2 的 Agent 自身权限、逐次接纳和失败保留已确认；具体变量锚点、配置/包契约和接口在施工前记录，新增未定机制再请用户决定。首版不等通用数据注册论证，不重复确认已定边界。
2. 4.0-3 的同等准备和缺失阻断先有回执，再把任意能力交给 Agent；不能只有 callable 可调用就扩大能力范围。
3. 持久样本的连续可见性、失败保留和接纳事务先审核，再扩到其他数据能力。只通过纯计算不开放批量写能力。
4. 首批共同通路验证后，逐领域迁移原调用旁路；每批列出已经迁移和明确留存，最后才进入图内多模块联合修整与验收。

以上是依赖关口，不要求每个内部 helper 都独立审批。已定业务内的小型私有实现和命名可由施工方选择；新增架构和行为不能自行决定。

## 7. 勘察发现的取舍与确认状态

以下分清已经确认的首版契约与尚需处理的接口或后续能力。已确认不等于代码已经具备；施工仍需准确记录新增实现与验证，不重新打开已定语义，也不擅自补齐其余未定机制。

### 7.1 连续写入：已确认逐次接纳

[`object_write`](../../backend/src/phase1_agent/graph_execution.py#L114) 仅追加意图，不更新读取快照；同一节点同一对象第二次写会报 `session_object_duplicate_write`。当前工具 callable 尚未接入对象写意图；若直接把工具写意图累积到 Agent 的 `NodeExecutionContext`，现有节点接纳路径也只能在整个 Agent 节点成功后沿 `_settle_node_result → _save_effects → data.state.apply_objects` 接纳。现有 `tool_settled` 和 `message_accepted` 是过程事实，不代表对象数据已保存。

因此直接复用一个 Agent 上下文会出现“第一次赋值后仍读旧值、第二次写被拒绝”。此前比较过以下两类方案；首版现已选择第一种，第二种仅保留取舍依据，不再是待选实现：

| 可选方向 | 需要补的机制 | 失败保留的区别 |
| --- | --- | --- |
| 每次工具能力调用独立接纳 | 子调用的准确写集、版本与操作身份，有限接纳入口，接纳后重读与工作视图更新 | 后续 Agent 失败不撤销已接纳的工具业务 |
| Agent 内部工作视图，节点末尾接纳 | 读己写、连续更新合并、CAS 依据和最终一次接纳 | 节点失败前的暂存写入不是正式数据 |

当前机制尚未支持所选的逐次接纳，需按第 4.2-D 新增有限接纳入口；不能为通过测试删除单节点重复写限制。现有默认对象操作键按 `node_run_id + object_key` 派生，不含 `tool_execution_id`，必须相应明确每次工具操作身份，不能复用该默认键冒充不同调用。每次变量工具写入是本批已定的正式接纳点，不据此强制工具内部每个步骤落业务回执。

首版按用户确认：逐次接纳变量工具写入，后续工具或 Agent 失败保留此前正式结果；不实现节点末尾统一提交作为另一模式。调用成功、接纳成功与过程事实仍需分别记录，不伪称当前代码已经支持。

### 7.2 授权主体：已确认使用 Agent 身份

对象 ACL 使用节点身份；[`变量注册实现`](../../backend/src/phase1_agent/tool_package.py#L153) 还要求 `registrar_node_id == context.node_binding_id`。[`validate_session_item_registrations`](../../backend/src/phase1_agent/graph_contracts.py#L686) 要求 registrar 是真实图节点且声明提供对应类型。

首版由真实 Agent 实例承接变量权限，不由工具加载实例或新建的子节点身份承接。工具调用身份只作追踪和操作关联。施工局部契约说明配置许可如何与实际目标取交集、如何随本次准备释放；不得冒用另一实例身份，或把目标能力的全部权限默认加到 Agent。

变量注册节点还是 `non_working`，不能通过改为 `working`、伪造 registrar、偷偷添加图边或隐形业务实例绕过现有门禁。需要改变提供者规则时，先报告影响的配置、定义、对象初始化、检查点与消费者。

### 7.3 模型“创建数据类”究竟注册什么

至少分清：

- 包提供的受信数据类型契约，即 `TypeRegistry` 的 `DataTypeDefinition`。
- 工作流配置中的对象定义、引用和许可。
- 会话中的数据类声明、对象或具体值的创建、注册和更新。

当前 [`TypeRegistry.register`](../../backend/src/phase1_agent/host_sdk.py#L349) 在冻结后拒绝注册，包加载结果及 `RunBasis` 都要求冻结。已有变量节点操作的是 `workflow.variable@1` 会话对象，还要求预建空壳；它不是通用数据类型创建接口。

用户最新已将首版收敛到变量读写，因此本项不再阻断首版接线，也不列入其验收。未来重启实时数据类创建时，再明确它是“稳定能力内部管理可持久化的数据类/结构声明”，还是确实要改变本次运行的受信注册结果。前者需要数据注册能力的领域契约和存取；后者涉及冻结依据和执行安全边界，不能自行解冻、重建 registry 或热更新。本篇不替用户选定通用 schema 数据系统。

本次变量读写是用户明确选择的首批范围，不是宣称通用数据注册已经实现。未来该能力若需要新表、引用协议或工作流对象提供者规则，提交单独局部契约并批准后再施工；不得把该能力凭空算作已有。

### 7.4 工具如何作为能力包的附带

“附带真实能力”已定，但物理上同包导出，还是准确依赖母包的适配包，仍未决定。现有 manifest 无工具导出种类；不能未经确认新增 manifest 版本、通用工具注册表或扫描插件目录。

施工前提交首批最小方案，说明声明放在哪里、如何核对母能力及包来源、如何被定义查询和启动准备消费。复用现有可信加载结果，不另造工作流私有包管理；将来项目级来源接入时替换来源适配，不重做调用通路。

### 7.5 新通路如何衔接现有错误分支

[`SnapshotKernel`](../../backend/src/phase1_agent/runtime.py#L927) 当前对普通异常终止，对 `ToolExecutionError` 形成 error 工具消息后继续，对 `ToolOutcomeUnknown` 关闭当前批后继续。这是实现现状，不代表新业务能力可以失败后默认继续。

本批不扩建错误分类或顺带改写全部既有内核分支。新共同调用的异常不得为了适配 callable 被一律包装成可继续错误；若无法保持已确认的“抛错中止当前业务调用链并显式报错”，先提交最小衔接方案。参数拒绝是否反馈模型修正、能力执行失败如何区分，按用户要求留待专门规则，不在此自行补齐。

## 8. 验证安排

遇到以下情况停止依赖施工：

- 必须改变第 7 节未决语义、权限主体、失败保留或既有控制政策。
- 需要新表、存储版本、历史迁移、修改公共 snapshot/包协议，或清理业务数据。
- 为共用调用需要复制业务实现、暴露通用仓储、让数据领域模块互调仓储。
- 必须取消 CAS、对象 ACL、同源依据、原子接纳或回执校验；用另一连接、异步补写或重放掩盖失败。
- 工具只能在调用时临时加载，或提示词能够声明未绑定的实际能力。

- 触及外层顺序注册、完整项目插件管理、运行期换包/热更新或 3.0 范围外迁移。

同一事务内继续绑定同一有限数据会话，不拆分已有节点接纳、事实独立事务和最终结算。本批已确认新增逐工具变量写入接纳边界，须准确新增对应接口与事务契约，不将其冒充旧事务原样不变。
