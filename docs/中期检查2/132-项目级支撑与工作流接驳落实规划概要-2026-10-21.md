## 3. 顺序细化时需要讨论的事项

以上是建议依赖顺序，下一轮再确认是否拆分、合并或调整：

- **步骤 1-2**：项目环境、服务持有、外来实例兼容和关闭责任先明确；基础框架可以随真实依赖分批接线，不要求各建一套服务。
- **步骤 2-3**：用当前工作流这一个真实消费者验证框架，不先建设完整定义平台。最小接入声明、公开取得入口和生命周期契约需先定案。
- **步骤 3-5**：可以围绕一条真实工作流路径迭代。先具备准确身份与正式结果读取，再扩大管理操作；本概要不决定准确 API 或前端页面。
- **步骤 4-5**：目录字段、归档过滤和一致读取范围，以及管理操作的版本条件另行细化；配置复制先确定来源基准、内部引用与并发条件。
- **步骤 6**：作为工作流内部独立专项规划，不摊入项目顶层能力目录。盘点可提前，真实执行接线需协调当前运行入口与依据；不默默改变结算和控制语义。
- **步骤 7**：各步先做必要定向验证，最后联验。测试集合、构建与运行环境验证在相应执行规划中明确，不由本概要预设全量执行授权。

每步按“必要简勘与局部决定 → 执行规划 → 获准落实 → 验证与回执”展开。涉及尚未确认的责任边界或契约，先交用户判断。

## 4. 落实时持续保留的边界

1. 项目不组织工作流内部组件，不跨域改表；沿用所属领域的事务、CAS、幂等、回执及独立读取。
2. 子能力来源维护公开声明与实现，项目汇集校验；不再建立同一业务定义的第二份可编辑权威。接入信息准确字段仍待确认。
3. 顺序注册只承载工作流大功能：`0000-0999` 构建准备、`1000-1999` 工作流执行、`2000-2999` 结束处理，其余预留。具体单元、序号、冲突规则与适用条件仍待确认；数字不代替权限、事务或失败政策。
4. 保留按需取得执行权威、冻结运行依据、业务提交与通知分开、已接纳前缀及必要释放；不新增默认重试、恢复、补偿或未知请求重放。
5. 供应商与全局内容的新增项目接驳、多实现共存/选择、跨实现数据迁移、插件市场和热替换后置；现有可用路径继续保留。配置复制不恢复旧 `session.copy`。
6. 127 号遗留项继续单列，遇到本批真实依赖再处理。真实库/凭据、既有服务启停、模型、依赖安装及提交推送不由本概要自动授权。
