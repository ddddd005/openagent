## 2. 产品窄修：事件读取诊断投影

只修改 `backend/src/phase1_agent/graph_events.py`（新增 `_public_event_diagnostic`，导入 `ROUND_NOTIFICATION_FAILURE`），`_read_event` 改为通过该投影返回公开 diagnostic。持久 `chain["diagnostic"]`（含 `round_notifications` 记录）**不删除、不改写**；读取本身无写入副作用。

| 存储中的 chain diagnostic | 公开 `event.read` 的 diagnostic | 说明 |
| --- | --- | --- |
| 无诊断 | `None` | 保持原行为 |
| 仅含成功的 `round_notifications`：`business_committed=true`、`business_status=succeeded`、通知列表非空且各阶段均 `succeeded` | `None` | 成功通知记录属持久存储证据，不再误投影为 `event_failed`；记录仍留在 chain 中 |
| 含 `round_notifications` 以外的其他诊断键（`reason_code`/`code`/`failure_retry` 等） | 保留失败投影：reason 取原 `reason_code`，其次 `code`，否则 `event_failed`；message 保持 `Event execution requires attention` | 不因成功状态清空真实诊断，覆盖“真实业务失败”等情形 |
| 业务成功但通知失败/未执行 | `{"reason_code":"round_committed_notification_failed","message":"Event execution requires attention"}` | 业务成功仍为成功，但通知失败可见；持久通知记录不删除 |
| `business_status` 非 `succeeded` 且无其他诊断键 | `{"reason_code":"event_failed","message":"Event execution requires attention"}` | 失败信号保留 |

- 投影只判断通知列表非空且已有各行均为 `succeeded`；**不校验通知阶段是否齐全、记录是否完整**。正常写入路径始终生成完整阶段列表；异常/缺失记录的完整性校验不作为本修已验收能力（审阅后收窄口径，见 §10）。

- 公开信封未变：仍为 `{reason_code, message}` 两键且 message 固定为 `Event execution requires attention`；前端 [workflowEvents.ts](../../frontend/src/application/workflowEvents.ts) 的 `readWorkflowEvent` 校验器无需改动即可接受。
- 管理读取：`service.read_event` 及 HTTP `event.read` 均使用同一投影；成功事件不再带失败 diagnostic，通知失败仍可见。
- “消费者读取”：当前 `consumer.event.read` 已属退役读取（见 `RETIRED_READS` 与 `test_consumer_entry_retirement.py`），没有需要改动的活动消费者读取契约；本轮定向复验保留该退役测试通过，未新增消费者读取面。
- 未改 `graph_service.py`、结算/通知持久化、run/chain 记录或 `round_notifications` 的写入逻辑。
