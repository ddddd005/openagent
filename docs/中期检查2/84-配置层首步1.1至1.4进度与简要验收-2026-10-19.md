### 3.2 未通过一：直接管理命令绕过配置锁

临时探针名：`82 A4: direct management commands must reject a configuration unknown`。

复现顺序：

1. 安装真实配置应用，经真实 Store 提交建立已保存配置。
2. 下一次修改注入响应丢失，配置请求保留 `pending`，`locked=true`。
3. `graph.manageWorkflow(id, "delete")` 返回 `false`，说明外层入口已有保护。
4. 对同一对象调用已公开的 `graph.management.commands.manageDefinition({ workflowId: id }, "delete")`。

| 状态 | 应有结果 | 实际结果 |
| --- | --- | --- |
| 直接管理命令 | 拒绝，发送 0 次 | 未拒绝，发送 1 次删除请求 |
| Store 条目 | 保留 | 被清理 |
| 配置待核实请求 | 保留且入口可定位 | 请求仍 pending，但 Store 条目已消失 |

定位：[管理命令 execute](../../frontend/src/application/workflowManagement.ts#L42)通过 `canSubmit` 门禁；[Store 提供的 canSubmit](../../frontend/src/stores/workflowGraph.ts#L597)只核对存活、对象存在与复制状态，没有配置提交/pending 门禁。外层 [manageWorkflow](../../frontend/src/stores/workflowGraph.ts#L666)的检查未保护直接命令调用。

影响：首批“配置 unknown 不能由归档/删除绕过”要求尚未全面落实。探针实际证明定义删除的前端门禁与清理行为，成功回执由替身提供，没有执行真实后端删除；同类归档及会话路径未在本轮逐项注入，不能扩大为已复现数量。

### 3.3 未通过二：管理进行中的旧目录可恢复已删对象

临时探针名：`82 A4: a directory requested during deletion must not restore a deleted workflow`。

复现顺序：

1. 经正常 `graph.manageWorkflow(id, "delete")` 发出删除，暂缓回执。
2. 删除进行中发出 `graph.loadDefinitions()`，目录捕获删除前配置，暂缓返回。
3. 先释放删除回执并成功结案，确认 Store 条目与 accepted 均已清理。
4. 再释放旧目录。

| 状态 | 应有结果 | 实际结果 |
| --- | --- | --- |
| 目录响应 | 失效，不恢复目标 | `loadDefinitions()` 返回 `true` |
| Store 条目 | 不存在 | 重新建立 |
| 配置应用 accepted | 不存在 | 重新接纳旧正文 |
| 工作区目录项 | 不存在 | 重新建立 |

定位：[loadDefinitions](../../frontend/src/stores/workflowGraph.ts#L238)捕获 `mutationGeneration`；[管理 commandState](../../frontend/src/stores/workflowGraph.ts#L596)仅在开始时推进代次，[最终清理](../../frontend/src/stores/workflowGraph.ts#L640)没有使进行中发出的目录失效。`forget` 清除 accepted 后，旧行又走首次接纳与建条目分支。

影响：当前应用内删除后的本地状态可被迟到观察恢复；这不是后端数据恢复，也不是刷新后自动发现能力。配置版本仲裁本身不足以判断已结束的对象生命周期。

两个探针均使用真实前端模块、内存证据与 mock 请求，不访问 HTTP 服务、业务数据库或模型。执行命令为 `npm test -- src/stores/configurationReceiptAcceptanceProbe.test.ts`；临时文件已于验证后移除，未把失败探针留入默认测试集。上述调用顺序、断言与实际状态是本次保留的复现记录，不能把探针失败改写成通过。
