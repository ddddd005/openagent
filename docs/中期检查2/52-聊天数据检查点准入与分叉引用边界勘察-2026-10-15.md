旧格式还有另一处实质缺口：它是只追加展示条目的记录，不表达“同一条用户消息的一组回复候选”或选中项。即使补齐引用授权，也仍须新增候选业务数据，不能把现有所有成功执行的列表当成同轮候选集合。

## 2. 推荐：数据层保存独立逻辑聊天值

最新语义下，优先增加明确版本的逻辑聊天数据类型，由既有数据层保存真实内容、候选集合和选中值。格式范围限于当前工作流聊天需求，不提前抽象未来全部聊天格式或renderer接口。

| 必要业务信息 | 职责边界 |
| --- | --- |
| 用户消息及其回合身份 | 同一回合的重roll不能追加第二条相同用户消息，不能用当前输入框的新文本替代已经提交的这条消息 |
| 同一回合的全部候选及稳定身份 | 五次成功生成的五条候选全部持久保存；正文为独立逻辑值，不能只留源产物ID或临时展示内容 |
| 当前选中的候选身份 | 是后端接纳、可读取、可存点的数据；不能由前端修改缓存来代表业务选择 |
| 候选与实际计算结果的准确关联 | 独立重roll/候选功能必须区分所选候选对应的上下文及变量结果；不能只切显示而沿用最后一次生成的计算状态 |

这里列的是必要信息，不固定一整套JSON协议、表结构或状态机。候选功能归独立工作流模块，聊天节点和前端页面只是允许的消费者。计算上下文和变量当前值仍留在各自已注册的数据项，不为了聊天显示在前端再维护一套权威值。

必要的新类型边界：

1. **不能静默修改`workflow.frontend-state@1`含义。** 新逻辑聊天值使用新准确类型/版本；具体标识由最小合同审阅确定。旧引用格式不能继续承担候选数据权威。
2. **正常写入合同一起改变。** 后端从实际已接纳的生成结果取得内容并写入新类型，仍核对真实输入、会话、项、CAS及原请求；逻辑值内联不等于允许浏览器上传一份上下文覆盖数据层。
3. **提供声明和实际消费者成组接续。** 登记新类型、准确节点提供声明、正常追加/候选选择、显式读写、展示快照及现有页面同时适配。每个提供实例仍登记自己的独立项，类型名不能代替项或会话身份。
4. **检查点只消费明确白名单。** 新聊天类型明确准入，收集完整已接纳逻辑值；配套完整/差量、校验、物化、准确目标CAS及新会话装载。检查点基础不依赖前端节点。
5. **展示以真实读取为准。** 后端写入后读取一份快照供前端展示；前端可以临时缓存，不能成为候选集合或选中值的唯一保存位置。完成切换后旧格式是定向退役对象，不长期维护两份聊天权威。

这条路径的当前合同改动比“增加一个检查点分区”大，但候选功能本身已经要求新的数据表达。与先为旧展示引用补跨会话授权、证据寿命，再另外建立候选类型相比，直接保存逻辑值的整体责任更少、更清楚。

逻辑聊天值装入分叉目标后，读取历史正文不再依赖源会话TEXT产物，不需为本需求先建设新的跨会话产物授权平台。原始运行证据及原请求仍保留原职责；这不承诺源删除后还能读取被删源的所有执行轨迹，也不改动既有凭据和不确定请求保护。

## 3. 原引用路径的成本与限制

以下保留原勘察，说明本页为何不再优先推荐该路；它不是已授权安装清单。

保存当前`workflow.frontend-state@1`，保留原始不可变引用，不复制或改写producer身份。

实施范围：

1. 在共享类型定义factory明确准入；收集完整已登记聊天项，包括空项，缺失或已删除的当前头明确报错。
2. 检查点增加`chat_contexts[object_key] = {type_id, schema_version, value}`；同步严格schema新版本、仓储建表约束、完整/差量、物化、新目标装载及CAS。既有产品库不自动迁移。
3. 从准确选定点及类型声明的引用提取闭包，只授予目标该对象相应的不可变产物；不把整源chain变成可读历史，不授予其他会话、同类型其他项或未选中后续回合。
4. 同步数据层装载、正常后续追加、显式对象产物读取及展示快照的核验。检查点功能本身不依赖前端节点；节点和其他外部消费者仍通过数据层读取准确项。
5. 明确被引用原产物的删除规则。引用授权与删除保护需同批验证，不能留下可保存但无法读取的半条链。

可复用[graph_runtime_host.py](../../backend/src/phase1_agent/graph_runtime_host.py)已有的类型引用闭包算法及对象读取ACL；不能仅放宽`_resolve_write_artifact`的会话检查，因为该函数还被写入证明核实使用。

### 源删除的具体关口

[workflow_lifecycle.py](../../backend/src/phase1_agent/workflow_lifecycle.py)当前只因其他会话的`state_snapshot.history_refs`仍引用源chain而拒绝删除，随后按源session整删`records`中的chain、node_run和workflow_output。它没有检查其他会话对象或检查点里的聊天引用。

坚持以引用格式承载新聊天数据时，还必须另外确定以下行为之一：

- **存在准确聊天引用时拒绝删源。** 沿用现有“历史仍被使用”的保护语义，扩大依赖检查到保留的对象/检查点引用。改动较小，但目标还依赖源的不可变证据，不能宣称删源后独立可读。
- **允许删源，继续保留被目标引用的不可变证据。** 需要明确产物、producer、chain、固定定义等必要证据的保留边界和删除后的准确解析，不是简单保留几个output行。禁止复制伪造producer或让目标执行记录冒充源记录。

第二项比当前保存/分叉基础多出实质的证据寿命职责。二者都不能补上候选集合和选中项的业务表达；本页不先安装任一引用授权或删除规则。

## 4. 同轮重roll还缺首轮前基线

`GraphWorkflowService._new_session`只建立初始化对象及首个commit/snapshot，没有检查点；`_append_success_checkpoint`是在整轮成功后才写首个完整点。因此首轮第一次回答前的准确状态，不能通过“取前一个成功点”获得。首轮之后的点也不能代替首轮之前。

已开始运行时的manifest、输入和node-run配置可以帮助核实实际读到什么，但没有因此成为正式历史装载入口，不能重新开放旧snapshot覆盖路径。

要满足已定语义，独立功能还需要明确的回合基线保存/取用职责，并与当前白名单收集、新目标初始化及成功收尾配套：

- 记录本回合已提交的同一用户消息及开始前状态，使候选C2不会把C1已写回的计算上下文/变量结果误作起点。首轮也须具备该起点，不伪装成一次成功执行。
- 生成C1至C5对应的结果S1至S5时，候选集合持续保存完整五项。不能通过回到较早保存点而丢掉后来生成的C2至C5。
- 选C1继续时，实际计算状态应对应S1，同时聊天数据仍保有C1至C5和选中C1。不能仅把前端选中值改为C1、后端却从最新S5继续。
- 检查点保存接纳时的完整聊天值和适当计算状态，分叉初始化保存值，不重放模型生成、不合并其他会话候选。

这些是实现必须补齐的缺口，用户无需再次确认“同轮/五条保留/选中续聊”的含义。本页不预定基线或候选关联表的完整协议，也不据此开放同会话历史覆盖、建设通用归档系统或提前安装新的产物授权。

## 5. 接续与核实

建议接续顺序为：先合订新逻辑聊天类型及回合基线的最小职责，再成组安装正常写入/选择/展示与检查点闭环，最后验证独立候选功能调用。不能只开聊天准入或升级schema，再把无法装载或候选丢失留到后续。操作入口补齐可独立交付，不冒充重roll/候选已经安装。

验收至少覆盖：同类型多项/多会话隔离、首轮及后续回合同一用户消息、五次生成五条候选全部真实保存、选择非末条后从相应计算状态继续、完整候选和选中值存点、较早点分叉/再次分叉、目标历史正文独立可读、错误类型/项/CAS拒绝、后项及最终commit故障完整回滚，以及原请求核实不重派发。

隔离离线核实已经复现此关口：使用正式`tools.editable-input -> frontend.node`运行产生一条真实已接纳消息，再向同一固定定义的新目标调用准确保存状态初始化，当前实现以`session_object_reference_denied`拒绝源产物引用；整个新目标事务回滚，数据库全量比较及源会话比较均保持不变。隔离库为[该次核实数据库](../../.local/test-runs/chat-reference-audit-5587422a0ba04be9b633f0e054122199/workflow.sqlite)。首次探索错误使用编辑投影而非持久固定定义，先被`checkpoint_target_definition_mismatch`拒绝；改用正式`_document`后才验证到真实引用关口，不将首次探索记为通过。

本页只写入勘察文档并执行上述隔离核实，未修改产品源码、操作产品数据库、启动服务、调用真实模型或提交更改。聊天检查点准入仍是未安装项。
