## 2. 与原规划的接续及用语订正

128 号原安排为基础装配之后先接提示词/Lorebook，再接供应商、模型及包注册。本轮讨论将首个真实接入对象调整为整套工作流能力，其他模块新增接驳后置。128 号原文保留为当时规划，后续局部规划按本文最新范围展开，不自动执行原资源接入顺序。

需要保留以下三次边界澄清：

1. “工作流整体”指工作流功能组件，不是每个工作流文档。后者仍是配置与数据，不因保存而安装一套功能系统。
2. 早先将“工作流功能构建”从工作流基础运行移到项目功能管理，是一次中间认识；用户随后进一步订正：项目也不应决定工作流内部的组件构造，项目接入的是子能力对外提供的整体入口。
3. 项目调用子能力提供的初始化、取得或关闭入口，并不等于跨域修改。需要避免的是项目自行掌握、选择或修改子能力内部业务组合、仓储及数据规则。

本篇提及的“加载、接入、初始化”不默认表示每次项目启动都立即创建全部服务，更不表示取得工作流执行租约或启动工作流。现有按需取得管理/执行服务的边界须在后续规划中明确保留或另行确认，不能由术语替换默默改变。

原 128 号排除的外层顺序注册，本轮已重新纳入后续论证路线，但仍是 127 号 N1 的独立工作流专项，不与项目基础装配混成一次无边界重构，也不表示已经获得产品施工授权。

## 4. 项目职责与子能力边界

本节是根据已明确方向整理的责任框架，不固定类名、工厂签名、表结构或完整注册格式。

| 职责 | 项目侧关注什么 | 不承接什么 |
| --- | --- | --- |
| 基础运行 | 项目环境、启动关闭、子能力接入与持有、适用的前端托管和连接支持 | 不据此掌握各子能力内部的业务构造和调度 |
| 数据与数据管理 | 统一存储环境、项目自有数据的有限操作、向子能力提供约定存储条件 | 不直接修改工作流节点、变量、对象或会话内部记录；不把数据访问入口当业务调度器 |
| 定义管理 | 对子能力公开接入信息进行汇集、校验和查询，保留其来源及实现关联 | 不集中重写或复制所有内部定义，不成为第二份可编辑业务权威 |
| 功能管理 | 组织项目级功能入口；本批主要承接工作流目录和整体管理请求，再交给工作流公开能力 | 不替工作流选择内部模块，不实现工作流自身配置、初始化与结算算法 |
| 执行管理 | 首版保留薄的项目级调用组织职责；与子能力公开入口接续，具体状态及返回方式待细化 | 不接管图内节点执行，不因存在此层就要求所有普通读写绕行，也不预建多引擎调度器 |
| 包与组件支持 | 区分来源供给、启用选择、可信装载与注册发布，作为明确职责承接 | 不与数据库读取混为一项，也不因需要扩展就另建第二套完整通用加载平台 |

项目与子能力可以共用存储、注册等基础设施，但不因此共用全部运行状态或获得彼此仓储的任意访问权。子能力对外使用的共享服务需要有明确契约；“内部自己负责”不等于可以自行绕过项目的环境、权限和生命周期约定。

## 5. 存储与工作流目录管理

### 5.1 三种接驳

| 接驳 | 目标 | 保留边界 |
| --- | --- | --- |
| 环境接驳 | 项目提供统一存储环境，工作流从中取得自身领域接口 | 既有领域存取、身份、事务、CAS、幂等和回执不因装配调整而重写 |
| 功能接驳 | 项目通过工作流公开入口发起增加、归档、删除、配置复制等管理操作 | 工作流负责内部规则与实际数据操作，项目不跨进仓储改表 |
| 查询接驳 | 项目取得工作流及会话目录、数量、摘要和必要管理结果 | 详细配置与会话数据由工作流解释，不维护两份权威状态 |

项目关注目录，并不意味着只返回一个数量。定位和管理至少需要准确身份、归属及适用的名称、版本/状态；这些仍属于目录级信息。摘要的准确字段、分页、归档过滤及一致读取范围由局部契约确认。

目录优先投影已有正式记录；不预设新增工作流成员表、持久计数或第二套归档状态。工作流数据管理可以纳入项目存储环境的装配，但仍是有明确归属的数据域，不是每个工作流再建一个独立项目或数据库。

### 5.2 管理操作

```text
项目工作流管理入口
→ 工作流公开管理能力
→ 工作流所属业务校验与协调
→ 所属领域数据接口
→ 同一 SQLite 中的真实存取与回执
→ 项目读取正式结果或刷新目录
```

项目不应先删除自己的目录记录，再异步等待工作流清理成功；不以重试、补偿或重放未知请求来掩盖未完成状态。归档删除继续保留当前运行、引用、历史证据及未知结果保护。是否以及如何收口当前生命周期跨领域调用，须按实际管理路径单列，不要求本批迁空全部仓储调用。

新增工作流的初始结构与新增会话的初始化由工作流能力承接，项目无需自己拼节点图或创建变量/对象。正式目录与尚未接纳的前端草稿也应分别表达，不能以本地出现一行视为后台资产已经创建。

### 5.3 第一版配置复制

已确认只复制工作流配置，产生新的工作流身份；不携带会话及运行历史，不因复制而重放请求或复制共享能力实现。

以下尚需在施工前细化：复制采用已保存的哪一份配置基准、是否允许未保存编辑、固定修订与当前覆盖如何取值、内部引用如何校验，以及并发修改时的版本条件。节点实例身份是否重建等细节不由本篇补定。

旧 `session.copy` 已退役，不恢复该入口；检查点分叉等已有独立操作不与“配置复制”混同。本轮用户确认的是复制范围，不是新的复制接口已经实现或验收。

## 6. 子能力接入与定义维护的补充论证

### 6.1 扩展面向什么

用户讨论的 A/B，是另一套工作流引擎、另一套供应商管理实现，或全新的功能工作台。不是多保存一份图配置或多增加一条供应商资源。

建议采用“共同接入与生命周期约定 + 各子能力自己的公开业务契约”，而不是规定所有子能力实现同一套业务方法。工作流、供应商管理和新工作台的业务入口可以不同；项目统一的是如何识别、接入、取得和管理它们。

### 6.2 如何避免定义细碎和重复维护

以下是本轮形成的候选收口方向，尚未冻结为公共协议：

- 接入声明由子能力来源维护并提供，项目汇集和校验，不在项目中心再手抄一份。
- 项目只关注身份/版本/来源、公开入口及契约引用、必要环境要求和生命周期边界；准确字段另行确认。
- 已有公开操作契约优先引用，不因项目接入重新登记每个参数、每个函数或每张表。
- 节点、类型、executor 等继续按所属来源登记；项目可以查询其公开视图，但不取得其维护权，也不再建立同一对象的第二注册权威。
- 工作流内部模块、算法和仓储不默认变成项目注册项；`0-9000` 大功能顺序也不摊入项目顶层目录。
- 当前可信固定装配可以作为第一版起点，不预建插件市场、自动扫描、任意导入、热替换或复杂依赖容器。

“加载”不默认表示网络下载；“有声明”也不表示代码、依赖或前端实现已就绪。现有能力包加载器与项目子能力接入可以复用基础，但复用到何种范围、由谁承载仍需局部确认，不能通过名称相同直接替换。

### 6.3 多实现的真正难点

声明条目增加本身不是主要复杂度。需要另行论证的是：

1. 同类 A/B 是否可同时启用，调用者如何选中准确实现。
2. 既有工作流和会话由哪个实现解释；相同功能类别不证明契约兼容，更不证明数据兼容。
3. 共用环境、执行租约、资源和生命周期如何避免相互干扰。
4. 前端入口、公开操作及错误结果是否适配，不能只替换一个实现名称。

第一版可先以当前工作流实现验证边界。多引擎共存、运行中替换、跨实现数据迁移及相应 UI 均未确定，不以“为以后扩展打基础”提前施工。

## 7. 工作流层级的大功能顺序注册

此项接续 [91 号 §5](91-执行层统一依据数据通路与大功能顺序注册确认-2026-10-19.md#L116)、[92 号边界](92-工作流业务对象与操作职责表及3.0边界整理-2026-10-19.md#L181)及 127 号 N1；既有数字方向与职责不重开。

| 顺序区间 | 已确认的大类 | 说明 |
| --- | --- | --- |
| `0000-0999` | 构建与准备 | 一次工作流调用的依据、环境、图计划及必要能力/数据准备，不是项目加载整套工作流子能力 |
| `1000-1999` | 工作流执行 | 包括调用整个节点图，图内顺序仍由图编译和图执行负责 |
| `2000-2999` | 执行结束处理 | 适用的业务结算、检查点、通知和资源释放；进入此区间不表示业务已成功 |
| 其余位置 | 预留 | 总方向为 `0-9000`、千位区间，尚不补定各预留位置用途 |

声明和位置归定义与注册管理；工作流基础支持承接启动、控制、目标与状态错误传递；流执行取得本次依据并组织实际调用；各功能模块实现自身业务。基础运行可以组织注册接入，但不代替定义管理维护全部规则，也不根据数字自行执行功能。

只登记工作流层级的大功能，不登记内部子函数、画布节点或 Agent 内部步骤。内置 `0、100、200...` 仅为留间隔示例，不是已冻结序号；首版插件不得覆盖或修改内置位置。

数字不能代替适用条件、事务、权限和完成判断，不能无条件从零遍历到末尾。round/event、暂停/继续/关闭须保持适用路径；节点接纳、工具写、事实及共同结算保持原事务。业务提交、通知和释放分别表达，错误中止当前业务链但不能据此省略既有必要收尾。具体内置注册单元、位置、同号冲突、开放区间和配置权限仍待确认。
