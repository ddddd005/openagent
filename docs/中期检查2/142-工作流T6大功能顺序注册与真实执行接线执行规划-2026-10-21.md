第一版建立一条明确、简薄、能对应真实调用的运行顺序线，便于后续维护，避免大功能继续散落在调用代码中。当前主要是组织规范，不以设计插件插入位置或搭建通用编排框架为目标。

入口为激活一次工作流运行的命令，主线为：

```text
运行命令受理
  → 本轮准备
  → 原准备事务提交与后台调度
  → 整图执行
  → 业务结算
  → 提交后通知
  → 结束释放
```

用户已确认的口径：

- 只注册大步骤；连续触发、紧密共享事务的内部动作不强行拆开。

- 顺序声明由真实执行消费；只登记描述而继续维护另一份实际调用顺序，不算本步完成。

| 顺序号 | 稳定身份 | 名称 | 承载范围及真实入口 |
| --- | --- | --- | --- |
| `0100` | `prepare` | 本轮准备 | `_start_run` 中捕获本次依据、准备事务受理与原失败清理；事务内继续调用原 `prepare(data, basis)`，保留 `_prepare_run` 整体 |
| `1000` | `execute_graph` | 整图执行 | 原 `_execute` 的 begin、读取已准备内容、恢复上下文、编译/图调用或取用保留完成结果 |

| `2100` | `notify` | 提交后通知 | 原通知阶段列表、独立窄诊断、结构化 wait 表达；不拆每项通知为外层注册 |

### 4.2 声明、校验与查询

建议新增工作流域窄模块 `workflow_run_order.py`，同时承载内置声明、汇集校验及可信内部只读查询，不建设一套新服务：

- 每项最少为 `step_id`、`order`、`name`、`entry_ref`。数据结构可用既有习惯的冻结 dataclass / 不可变 tuple，避免可变全局注册表。
- `entry_ref` 是显式绑定到可信本地执行闭包或私有方法的符号；不解释为模块路径，不动态导入，不开放任意反射执行。
- 汇集时校验非空身份/入口、整数顺序（排除 bool）、本批阶段范围、重复身份与同号冲突；同号直接安全诊断错误，不通过排序或覆盖消解。
- 返回确定性升序只读结果；原声明输入顺序不决定执行顺序。执行前完成结构与所需绑定校验，不能写入业务后才发现同号。
- 普通内部读取无建库、租约或业务副作用；声明属于工作流，不逐项注册到项目定义管理，不混入 `NodeRegistry` 或内部节点包 schema。

首版只有静态内置五步。不新增公开注册/改序 HTTP、前端编辑器、持久顺序表、包加载规则或热替换；也不为以后可能出现的复杂依赖增加字段和调度机制。静态顺序表可直接复用同一不可变结果，不扩 `RunBasis` 或新增每链顺序状态。

## 5. 真实执行接线与必须分开的逻辑

### 5.1 两段实际调用

同步准备与后台推进共用同一份声明，但保持原物理边界：

```text
原 start / event / reroll 命令
  → 原校验和 _start_run
  → 顺序声明的准备段（0100）
      → 原捕获 RunBasis
      → 原 _change → prepare(data, basis) → 同事务 prepared / chain_start / 回执
  → 回放直接返回；新受理才按原条件提交后台任务

原后台 _execute / 续跑入口
  → 顺序声明的执行段（1000）
  → 顺序声明的结束段，升序调用（2000 → 2100 → 2200）
  → 原后台调用返回 / 原 wait 观察
```

执行层以声明筛出的有序步骤迭代调用显式绑定，不在别处再写一份 `prepare → execute → settle...` 的硬编码顺序数组。准备段和后台段分开消费是原事务/线程边界的接续，不要求一个从 0 跑到末尾的统一循环。

可把原连续代码提成局部闭包或少量私有方法，再用按 `entry_ref` 查得的可信绑定执行；绑定表只关联实现，不另维护顺序。输入、结果和 `finish_key` 使用原局部数据或小的私有承接对象，不建立通用大上下文、结果存储或新的重试协议。

`_start_run` 对 event/chat 的原 `prepare(data, basis)` 形状保留。0100 应包含原捕获与准备受理整体；不能在登记调用之前已经做完整准备，再调用一个无实际作用的注册入口。后台四步同理，登记入口必须拥有相应真实动作，不能只追加一条 trace。

### 5.2 成功与其他路径

| 边界 | 保持要求 |
| --- | --- |
| 准备失败 / 幂等回放 | 原准备失败回滚和已建资源清理保持；回放可进入 0100 受理外壳查回执，但不执行事务 change/内部 prepare、不重建资源帧或排队后台任务，不为追求入口计数归零改变原查回执位置 |
| 普通成功 | 五步实际接通；2000 业务提交成功后才通知，2200 执行原释放；进入结束区间不等于提前成功 |
| event | 同一大步骤，内部使用原 event 分支，不增加 round 的 commit/成功检查点 |
| 图内失败 / paused 返回 | 共享提取出的现有 helper 时继续按原结果结算、通知、释放或保留；不能因只规划成功线而删掉这些既有行为 |
| 抛异常 / 未确认收尾 | 原 `_execute` 的 try/except、错误记录、未确认收尾事务及必要释放保留；不另登记失败序列、不包装成成功、不增加自动重试 |
| resume / 显式 retry | 从原后台入口接续 1000 及适用收尾，不重做 0100；保留 next_node_index、已接纳前缀与原同次 basis；有完整保留结果时不重跑图 |
| close / 管理归档删除 | 继续原控制/生命周期入口，不因为也会结算/释放而强行走完整成功序列；原确认、停止等待和释放不变 |
| 业务已提交但通知失败 | 保留已提交事实、结构化 wait 错误、独立诊断与后续释放；不得用顺序迭代的统一异常处理阻断原应到达的释放 |

最后一项尤其注意：当前通知函数会汇总失败，调用方记录错误后仍继续处理资源。新调度不能把已知通知失败简单改成向外抛出并跳过 2200。原本真正抛出的其他错误仍交原异常路径，不发明吞错或重试。
