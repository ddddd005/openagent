## 2. 已确认的施工顺序

| 顺序 | 当前施工重点 | 模块内部工作 | 跨层接通结果 |
| --- | --- | --- | --- |
| 1 | 配置数据盘点 | 列出配置层需要维护和保存的内容、定义、节点配置及引用，明确数据归属 | 每项都有来源、维护方、消费者和现有存取路径 |
| 2 | 配置与数据薄口 | 配置入口统一接入并分发配置操作；数据入口统一接入并分发领域存取请求 | 选定真实配置路径经过两个入口，内部先转发现有实现 |
| 3 | 配置数据存储 | 在数据管理内部整理配置数据仓储及数据库适配，承接配置数据的读写 | 配置保存后可经数据入口重读，实际错误和原有事务边界得到保留 |
| 4 | 定义消费视图 | 从持久配置及其他定义来源中提取、解析和提供定义，整理注册与查询关系 | 配置、Runtime、检查点等消费者取得准确的只读定义视图 |
| 5 | 执行 / Runtime 接入 | 整理配置、定义、基础支持信息及会话数据的消费，整理运行产出 | 运行数据经数据管理落入会话域；配置修改请求回到配置管理 |
| 6 | 功能与能力接入 | 依次整理具体功能及检查点、重roll、分叉的数据依赖和业务规则 | 能力通过已建立的数据与定义接口工作，与 Runtime 的接线得到验证 |

顺序表达施工重心。配置创建和校验所需的最小节点类型定义查询，应在第 2–3 步复用或补齐；第 4 步集中整理完整的定义消费关系。每步仍采用“局部论证 → 极简骨架 → 内部填充 → 跨层验证”，按已确认路径逐步扩大。

节点与插件扩展继续作为后续建设主线，待本轮必要接口可用后选择代表性接入流程论证，不在此预建完整插件平台。

工作流基础支持只承担运行相关的启动、恢复、抛错、当前状态和会话指向。现有应用入口、宿主或前端壳承载的项目管理操作只作依赖参考，不因共用入口就转为工作流基础支持职责。节点实例编辑、运行所需数据初始化及已定能力语义继续按相应契约核对。

## 3. 首步：配置层需要存储什么

先按实际对象盘点，下表是清单范围，不预定数据库表或新建模块数量。

| 数据类别 | 需要核对的内容 | 归属说明 |
| --- | --- | --- |
| 节点实例与配置 | 实例身份、准确类型版本、节点参数、配置值 | 工作流定义数据，由配置管理维护 |
| 静态内容 | 节点静态内容、工作流内保存的提示词内容 | 区分工作流自有内容和项目资源引用 |
| 工作流内对象定义 | 变量名称、类型、默认值、作用范围、允许操作等 | 定义可独立于会话建立；当前值另归具体会话 |
| 工作流结构 | 端口关系、数据边、控制边、节点组、绑定 | 与节点类型定义的来源和实例使用关系分别记录 |
| 资源与依赖依据 | 提示词等资源引用、package lock | 引用保留来源，项目级资源继续由原模块维护 |
| 画布与派生内容 | 位置、折叠、前端映射及其他派生内容 | 区分需要保存的编辑结果和可由定义、配置生成的视图 |

每项至少写明：对象种类、定义来源、维护方、存储归属、消费者、读写入口、必要身份与修订条件。配置层维护的内容和引用全部列清；包提供的节点类型、功能、能力定义另记来源。

会话变量当前值、上下文、聊天、候选和运行记录进入会话数据清单。配置中的默认值与会话中的当前值分别描述；会话临时覆盖必须有明确归属。

## 4. 两个薄口与配置仓储的位置

| 位置 | 承担的职责 |
| --- | --- |
| 配置薄口 | 统一接入配置操作并分发给对应配置模块，返回配置结果或错误 |
| 配置模块 | 判断修改目标、配置合法性、作用范围及派生规则，提出领域存取请求 |
| 数据薄口 | 统一接入领域数据请求，分发给对应数据模块，保留明确的身份、归属和读写条件 |
| 数据管理内部的配置仓储与适配 | 将配置数据保存到数据库，读取、修改相应记录，承接原有版本和事务条件 |

```text
配置修改
→ 配置入口
→ 对应配置模块
→ 数据入口
→ 配置数据仓储
→ 数据库适配 / 共享 SQLite
```

用户已确认“配置层对应的存储模块”放在数据管理内部。“配置层数据库”表示共享 SQLite 中相应的逻辑数据区；配置业务模块通过数据入口使用它。

薄口保持转发与分发职责，配置规则留在配置模块，领域存取和数据库细节留在数据管理内部。接口表达保存配置、读取会话对象等领域意图，调用方不取得任意表操作能力。

“配置存储通路接通”应有保存、重读和错误返回证据；仅新增入口或仓储文件不足以说明配置存储问题已解决。

## 5. 定义、Runtime 与能力如何接上来

### 5.1 定义层

定义层通过数据入口读取配置数据，从中整理工作流内的变量定义、节点实例与类型的关系、绑定等必要定义信息。节点类型、功能和能力还可以由基础包、插件及相应来源模块提供定义。

来源继续负责维护定义，定义目录提供统一的只读解析与消费视图。需要具体配置值或正文时，经相应数据接口读取；定义视图保留必要信息及来源关系，避免派生出另一份独立权威。

```text
配置数据 → 数据入口读取 ─┐
其他来源提供的定义 ─────┴→ 定义目录 → 只读定义视图 → 消费者
```

注册表示将已有定义纳入可查询、可取用范围。内部注册表示形式、查询接口及存储方式在对应局部步骤确认。

### 5.2 执行 / Runtime

| 消费或产出 | 交互方向 |
| --- | --- |
| 配置数据 | 经数据管理读取明确作用范围和修订依据下的配置 |
| 定义视图 | 从定义目录取得节点、数据类型、功能和能力等所需定义 |
| 基础支持信息 | 使用工作流当前状态、会话指向及启动 / 恢复目标；上下文内容按会话数据访问 |
| 会话数据 | 经数据管理读取具体会话的变量当前值、上下文等 |
| 运行产出 | 经会话数据接口保存运行事实、结果、状态和错误 |
| 配置修改意图 | 调用配置入口，由配置管理判断并经数据管理保存 |

因此，Runtime 可以产出需要改变配置的结果，正式配置变更仍走“执行侧 → 配置管理 → 数据管理”。保存成功与当前运行何时采用分别判断，现有可调配置的范围、生效时点和重roll基线继续按待决项处理。

### 5.3 功能与能力

具体功能和节点通过执行 / Runtime 层消费相应数据。检查点消费会话数据、定义及准入规则，按需读取允许的配置视图，再通过数据管理保存或装载。

检查点、重roll、分叉按不同调用时机接线。Runtime 负责通用执行与生命周期通知，各能力维护自身业务；检查点最终准入和版本仍依据现有 contract 核对。
