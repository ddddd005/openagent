## 2. 已确认语义与前轮契约的订正

以下按用户最新决定执行，不重新作为待决事项：

1. Agent 活动在 Runtime/执行层内，不意味着 Agent 内核必须直接对接图执行模块。内核继续选择工具、形成参数和消费结果；执行侧适配承接调用与接纳。现有图宿主适配器的存在本身不是职责违规。
2. 工具加载锚点与工具提示加载在画布上合为一个节点；加载声明与提示材料生成仍由各自逻辑承担。
3. 该节点只有一个输出，承载工具提示。工具提示保留“工具列表 + 对应工具参数”的成对结构，不能仍靠两个独立文本输出拼接。
4. 上下文装配新增接收工具提示的接口。列表与参数分别沿提示词条目的上下文前、中、后语义组织，位置和顺序可以独立调整；默认列表在前、参数在后。不是相对另一段提示词的简单前后关系。
5. 工具绑定仍保存在工作流配置。启动从正式图与配置收集工具需求，按本次冻结依据准备，不等第一次调用再装载。
6. 工具使用真实 Agent 节点身份经过对象 ACL，加载节点不取得变量权限，也不借用另一节点实例的配置或身份。
7. 普通节点与工具使用同一真实变量 executor；每次工具写入独立接纳、独立重读后才返回成功，后续失败保留已接纳结果。
8. 不扩建错误分类策略；未处理错误中止当前业务调用链并显式报错，不为了让模型继续而吞错、删工具或重放未知写入。

因此，103 号第 2.2/2.3 节的“两节点、两输出”及对应默认位置是首轮已实施形式，不能再作为最新目标。103 号有关真实能力、权限、运行依据和逐次接纳的有效边界继续保留；104 号仍证明其准确记录的历史改动和测试，不改写原始结果。

## 4. 核心实现参考

### 4.1 单节点中的两个阶段

当前注册规则见 [graph_contracts.py](../../backend/src/phase1_agent/graph_contracts.py)，`tool_binding` 必须对应无 executor 的 non_working 节点。直接把旧提示词 executor 塞进旧锚点会被拒绝；仅删掉这个检查也不足以证明准备与执行已分开。

建议按已有原生节点模式实现一个可参与图执行的工具加载节点，同时携带可信的加载声明。具体身份和版本先按 B0 记录，不在本文伪定已注册名称。

- **启动准备阶段**：从正式配置提取 Agent、变量和操作；校验包来源、目标 executor、类型、ACL、目标边界，生成本次准备帧。只读准备，不运行该节点的提示生成 executor，更不调用变量 executor、模型或写入变量。
- **图调用阶段**：真实数据边使加载节点参与计划时，其 executor 从已准备帧取得自身绑定对应的声明，生成一个工具提示输出。它不重新装载能力、不从服务当前表重建工具，也不产生变量写入。
- 提示输出经上下文装配接到 Agent，自然数据依赖决定该输出先于消费者生成；不新增调度根、隐藏节点或专用排序器。
- 工具声明的启动收集仍依据参与本次运行的 Agent 及正式绑定，不把提示输出是否展示、是否启用，解释成授予或撤销工具权限。
- 兼顾同一 Agent 已有多个加载声明的情况，继续做 Agent 范围的别名、工具名和总量检查；不能在单个加载节点内计数后遗漏其他声明。

注册校验须保留可信适配器、准确 Agent 引用及本轮目标限制；不得因合并形式就放开任意节点自称工具加载器。若实现需要新增公开节点种类、调度器或通用注册平台，按第 8 节停报。

### 4.2 单输出与上下文真实消费

结构化输出至少需要回答以下内容；这是语义清单，不是已批准的完整 JSON 字段表：

| 内容 | 要求 |
| --- | --- |
| 配对身份 | 工具列表项与参数项可按准确工具名及所属绑定核对，保留其 Agent / 加载来源关系，不能靠两个数组恰好同位置对应 |
| 工具列表 | 由本次准备声明投影工具名称和说明，不另维护可任意指向实现的人工目录 |
| 工具参数 | 保留对应工具的结构化参数 schema；不能只剩不可校验的 JSON 字符串 |
| 展示配置 | 列表与参数各自保存 presentation，默认 before / after；middle 的 depth 和 order 沿用既有上下文定位规则 |
| 内容边界 | 只输出可展示声明及必要来源，不输出 callable、存储句柄、对象当前值或额外对象权限 |

上下文装配先校验成对结构，再将列表与参数分别投影到既有提示材料和消息布局。对模型渲染参数文本是展示步骤，不能以此代替结构化数据或模型工具 schema 的校验。缺项、重复项和声明不一致要保留明确诊断，不静默截断或删除一侧。

沿用既有 prompt lifecycle、compaction 和深度规则；工具材料仍按当前受保护的逐请求材料处理，不引入另一套前中后算法。改变 presentation 只改变布局，不改变 Agent 可调用工具及访问范围。

新输入必须保留接受后的真实 artifact 引用。现有 `assemble_native_context_prompt` 已接收 `source_output_refs`，Agent 也会按真实 prompt artifact 核验；接线须追踪工具提示输入，不能在转换为旧材料时丢弃源输出身份。优先复用现有 `PROMPT@6` 消费和校验；若其封套或来源证明不能表达新输入，先报告具体缺口，不擅自放宽校验或制造引用。

当前提示词是独立支路：

```text
tool-prompt → tool-summary → prompts.assembly → tools.output
原 context.assembly → Agent
```

第二轮的最小真实链应为：

```text
正式配置 → 本次 RunBasis 下的工具准备帧
                ├→ Agent 的真实可调用工具
                └→ 一个工具加载节点 → 成对结构化工具提示
                                          ↓
上下文视图 + 普通提示材料 + 当前输入 → 上下文装配 → Agent → 受控模型
```

不要求 Agent 内核直接理解图节点、工具加载节点或图计划。执行侧传入有限工具调用接口，内核继续按现有 callable 机制使用能力。

### 4.3 实际工具总量

最终工具集合按真实合并结果计算：包提供的静态工具、已准备业务工具，以及合并后唯一的 `final_answer`，总量不得超过 120。保留名称冲突检查；不能通过静默去重、截断或把绑定上限写死为 118 处理不同静态注入数量。

以现有 `_agent_tools` 的真实合并位置为最终校验点，快照和 callable 继续消费同一结果。超量必须在首次模型请求之前明确失败，模拟 transport 调用为 0。

准备阶段能够取得本次可信静态声明时可复用同一规则提前拒绝；不要为提前计数构造 Agent 执行器、初始化模型或运行节点业务。若要求覆盖全部自定义静态工具形态的 `start` 前拒绝，但现有注册尚不传递该信息，先报告局部契约缺口；不得悄悄增加全局工具注册机制。来源、ACL、目标实现缺失仍保持原有启动前拒绝要求，不因此后移。

### 4.4 来源必须真实可核对

对加载声明及每个真实目标，都从同次 `RunBasis.definitions` 取得非空来源，并与本次冻结的包身份、版本及加载依据核对；节点引用仍使用准确 `component_id + component_version`。发现缺来源或依据不一致时拒绝准备，不回退当前 registry、不按名称或 latest 猜测包，也不人工填充来源字段。

范围限定在本轮需要包来源的工具准备路径。现有自定义 registry 的普通查询可能允许 `source=[]`，不能为修复工具准入而把全项目无来源查询一并删除。

自定义 registry 场景下，没有同次包来源依据就拒绝这项工具绑定；默认包加载继续提供真实来源。若需要为自定义入口增加正式来源传递参数或公开加载契约，先按 B0 说明影响，不能直接接受调用方随意提供的包名作为可信证据。

### 4.5 缺准备与正常空集合

核对 `_bound_tool_specs` 时区分“本次准备帧存在但该 Agent 没有业务绑定”与“整份准备帧丢失”。前者仍允许原有无业务工具的 Agent，后者按既有缺准备显式报错原则处理，不临时重建或悄悄变成静态工具模式。

此项是原契约保护，不据受控删除帧的注入测试宣称正常用户会丢帧。若修改触及直接内核测试或非图调用上下文，先区分真正不使用这套桥的入口，不借本项强制所有 Agent 依赖图执行。

### 4.6 次要实现与明确不扩展

配置层保存绑定及两部分 presentation，保存后独立读取，再用于真实准备和运行。先使用现有配置文档入口，不为本轮新建复杂前端表单；节点目录和端口必须与实际注册一致。

104 号的旧双节点样本和静态 `prompts.tool@2` 不自动转换成新权威。如何保留旧版本、选择新版本，以及是否需要用户修改旧图，应在局部契约说明；未获准的旧文档迁移、包选择重写和节点删除不实施。

| 诊断 | 复用适用错误；区分不支持目标、缺来源、缺准备、配对错误和工具超量，不强行统一错误码 |

一个可见节点、一个成对输出、上下文前中后、Agent 自身 ACL 和逐次接纳均已定，不重复请用户选择。具体命名和小型私有函数由施工方依现有模式处理；新公共契约、旧图使用方式变化及未确认的跨 Agent 共享等问题，须报告具体理由、范围和建议，由用户决定。
