## 1. 已确认范围与对 81 号的订正

首批目标：配置应用统一受理配置修改、核验编辑依据、处理原请求及结果、仲裁当前配置；Store 保存已接纳状态的投影，不再自行决定正式文档能否覆盖。

本批沿用以下取舍，不在实施时重复扩展：

- 维持立即提交、提交期间拒绝再次编辑；不引入自动排队、持久本地草稿、延迟保存或乐观显示。
- 保留 Store 的 `document/saved_document/saved_revision`，暂不改成每次读取都 clone 的 computed，不追求物理上只剩一份正文。
- 提交正文与版本必须来自同一次编辑基线；不自动换依据、合并、rebase、重试或重放未知请求。
- 统一的是当前前端应用内的配置受理和更新职责；跨浏览器及独立节点页继续由后端共享业务、事务和 CAS 协调，不增加全局调度服务。
- 配置提交与现有归档/删除相互排斥，并保护删除、应用重装后的迟到响应；归档/删除业务仍归现有管理模块。
- 固定修订查看、历史回执核实、当前配置读取分别表达；后端 operation、摘要、回执、表结构、存储版本及运行准备语义不变。

## 3. 模块职责与调用关系

```text
普通编辑 / 节点表单 / 明确的撤销重做
    -> 配置应用：编辑基线核验、提交互斥、原请求与结果处理
    -> 既有通信适配
    -> 既有后端配置功能接口 -> 配置业务 -> 配置数据接口 -> 数据管理

当前配置读取 / 保存返回 / 已核实的历史回执候选
    -> 配置应用：按来源及版本统一仲裁
    -> 已接纳状态
    -> Store 单一投影写入
    -> 编辑器、节点字段、正式操作消费者

固定修订读取 -> 固定内容查看，不写当前配置
现有管理模块 -> 归档/删除；与配置提交协调门禁及响应失效
```

| 模块 | 本批负责 | 需要撤出的职责 |
| --- | --- | --- |
| `application/workflowConfiguration.ts` | 每工作流的 accepted、统一接纳、编辑依据、提交/核实/确认现有流程和锁状态 | 不承接归档 SQL、运行调度或完整项目管理业务 |
| `stores/workflowGraph.ts` | 组合实际入口、维护 UI/会话/历史投影、应用安装关系；用一个函数写正式配置投影 | 目录自行比较版本、盲信 `lastResult`、核实返回即覆盖、等待后重新拼依据 |
| `application/workflowEditing.ts` | 产生明确编辑操作，同时交付产生结果时的基线；保持现有会话稳定性检查 | 不独立决定正式配置版本，不替请求换依据 |
| `plugins/workflowFrontendSdk2.ts` | 扩展身份和允许字段校验，向配置应用提交原请求 | 不重复接纳结果，不维护另一套正式版本规则 |
| `workflowManagement.ts` / `workflowManagementRequests.ts` | 保留现有管理业务、原请求证据和回执；在真实入口协调门禁 | 不替配置应用写正式正文，不因接口统一接管配置业务 |

## 4. 当前配置接纳规则

### 4.1 来源先于版本判断

当前目录/当前单项读取、经过原请求校验的保存响应、原回执候选可以送交同一配置仲裁。固定修订读取不能因带有较大的 `revision` 或偶然存在 `edit_sequence` 而成为 current。

请求是否成功、原请求是否可以结案、正文是否可以成为当前投影，分别记录。只读 current 访问器提供应用已经接纳的状态，不把 `lastResult` 暴露成正式依据。

### 4.2 沿用现有后端版本含义

依据 [配置保存业务:346](../../backend/src/phase1_agent/workflow_configuration.py#L346)：

| 操作 | 工作流身份 | 固定 `revision` | 当前 `edit_sequence` |
| --- | --- | --- | --- |
| 首次保存 | 新身份 | 1 | 1；请求依据为 0 |
| 展示或可调配置修改 | 原身份 | 保持 | 加 1 |
| 无需派生的固定修改 | 原身份 | 加 1 | 加 1 |
| 内容未变化 | 原身份 | 保持 | 保持 |
| 需要用户确认、尚未同意 | 原身份 | 不写 | 不写；提案不成为 current |
| 明确确认后的派生 | 新身份 | 新身份从 1 开始 | 新身份从 1 开始；原身份不变 |

会话修订及归档状态另有含义，不参与这组正文排序。

对同一身份、同一生命周期的当前观察，实施参考如下；返回类型和函数名称可沿用本地风格，但含义不可散落到 Store：

| 候选与 accepted 的关系 | 处理要求 |
| --- | --- |
| 尚无 accepted，来源有效且格式合法 | 接纳候选；不能用此分支接纳固定读取、未知来源或已删除对象的旧响应 |
| 编辑序号更小，固定修订不更大 | 陈旧，保留 accepted，不发正式投影变化通知 |
| 两个版本都相同且正文一致 | 重复，不更换正文引用、不重复推进历史或选择 |
| 编辑序号更大，且 `0 <= revision 增量 <= edit_sequence 增量` | 接纳较新观察；允许跨过未观察到的中间版本，不要求只加 1；每次固定修订推进都消耗一次编辑序号 |
| 同编辑序号但修订或正文不同，两个版本出现相反方向，或较新观察的修订增量超过编辑序号增量 | 明确报告冲突，保留 accepted；不按“revision 优先”强行选择 |
| 来源、格式或身份不合法 | 明确拒绝，不写正式投影 |

候选冲突不自动成为新的持久锁或自动修复流程。若同版不同正文确实来自现有组合规则，保留原证据并停住该分支，查明来源；不能把静默覆盖或忽略当作正常兼容。

### 4.3 目录批次与管理元数据

目录接纳逐行产生结果：接纳、重复、陈旧、冲突或无效。行处理失败不得先污染本行投影，也不应阻断其他有效行；调用方必须保留错误明细，不能把部分失败包装成全部成功。

`latest_published_revision` 对同一身份使用不倒退的观察规则；旧正文行不能顺带回退名称、节点数等配置投影。`archived` 不由配置序号表达，继续由管理结果及有时效保护的目录管理观察维护。

管理请求的现有 `mutationGeneration` 等保护须核对操作开始前、操作进行中发出的目录请求，以及操作完成后返回的情形；不能仅在管理开始时更新一次代次便宣称删除不会被旧目录恢复。本批复用并补齐现有响应失效保护，不引入新的持久目录或全局队列。

## 5. 编辑基线与提交正文

### 5.1 普通编辑

1. 在产生 next 的同一次编辑操作中捕获基线正文、身份、固定修订和编辑序号，确认来源为已接纳配置且 Store 投影与其一致。
2. 修改发生在该基线的副本上；基线和 proposed 一同交给配置应用。不得仅传 proposed，随后从别处补取当前版本。
3. 初始化或其他必要等待结束后，再核对基线仍等于 accepted，同时重新核对管理/配置门禁。
4. 依据变化则明确拒绝本次编辑，提示重新读取；不重打序号、不自动重跑编辑函数、不发送业务请求。
5. 依据仍有效才捕获不可变原请求，按既有规则留证、提交和处理结果。后端仍做最终 CAS。

比较正文可沿用现有规范签名，不增加自定义哈希协议。基线在前端有效不保证另一客户端未修改，后端 CAS 拒绝仍须原样处理。

### 5.2 专用节点表单、创建、复制与撤销

| 来源 | 必须保留的区别 |
| --- | --- |
| 节点表单 / SDK | `expectedConfig` 与序号来自同一已接纳正文；必要等待后重验；保留扩展身份、字段权限和节点类型检查 |
| 新建 | 明确新身份、依据 0、固定修订 1；创建暂态不能被当成已保存配置 |
| 无会话复制 | 目标是新身份；源是捕获的已接纳内容，源序号不能沿用成目标 CAS 依据；保留当前会话复制拒绝边界 |
| 撤销/重做 | 历史快照是修改目标，不是提交基线。单独捕获当前 accepted 和对应历史栈顶目标；等待后核验两者，作为一次明确的历史恢复操作提交 |
| 取消现有派生询问 | 不写配置，不把提案投影成 current；明确确认仍用既有新请求身份，基线已变则拒绝 |

撤销允许以当前基线提交历史内容，必须限于经过历史目标核验的操作，不能因此给普通编辑开放“任意旧正文配当前版本”的通道。提交未被接纳时，不提前消费撤销栈或改写正式投影；重复接纳也不能重复推进历史。

## 6. Store 投影、回执与初始化

### 6.1 正式字段单写

Store 保留正式投影字段，只有一个函数负责写入 accepted 正文、保存基线、修订及其名称/节点数投影。该函数消费应用明确接纳的状态，不重新实现版本排序。

接纳通知或显式接纳结果可以采用现有 Vue/应用组合方式；必须保证同一次接纳只有一个投影出口。应用可在边界 clone 保护内部状态，但不能每次 getter 都生成新对象供组件比较。Store 在一次真实接纳时取得稳定对象，同版重复读取不替换引用。

创建/复制尚未保存的暂态、未安装配置应用的旧测试面、取消暂态显示，不能被伪装成 accepted。对生产装配已经安装应用的正式路径，禁止通过这些分支绕开配置提交。暂态恢复为正式内容时也从 accepted 投影恢复，不能由任意 Store 值反向声明正式依据。

先保留 [正式消费者](../../frontend/src/application/workflowManagement.ts#L61)、[节点页准入](../../frontend/src/application/frontendNodeEntry.ts#L45)、[变量注册](../../frontend/src/domain/workflowVariableRegistration.ts#L70) 的接口。验证它们继续读取一致的已保存投影；确需读取应用 accepted 时逐个迁移，不先删除字段或改成只读 computed。

### 6.2 成功事实、接纳和证据结案

| 情况 | 本批要求 |
| --- | --- |
| 结果与原请求不匹配 | 保留 pending，不能视为保存成功，也不能覆盖 current |
| 保存返回有效并被接纳 | 更新投影一次，再按既有条件处理证据结案；Store 不再另行 accept |
| 已接纳，但证据结案失败 | 投影仍表示已保存事实；保留原请求和锁，通过现有核实入口处理，不谎报业务回滚 |
| 原回执有效但落后于 accepted | 核实原请求，保留较新 current；不得由 Store 用历史结果回写 |
| 有效成功事实与同版冲突观察相遇 | 保留成功事实、冲突错误和待核实原请求；沿用现有不自动结案的保护，不通过 catch 回填正文 |
| 业务响应丢失或证据写入不确定 | 维持现有 unknown 门禁，只核对原证据/原回执；不得自动发送新请求 |

现有 [应用测试:247](../../frontend/src/application/workflowConfiguration.test.ts#L247)、[275](../../frontend/src/application/workflowConfiguration.test.ts#L275)、[287](../../frontend/src/application/workflowConfiguration.test.ts#L287) 分别记录结案失败、旧回执和接纳冲突的保护。迁移时保留这些验证意图；`lastResult` 可以记录诊断事实，但不再作为正式投影后门。

### 6.3 安装与重新装配

生产由 [useWorkbenchFrontendHost](../../frontend/src/composables/useWorkbenchFrontendHost.ts#L13) 安装应用。去除把任意 Store 正文反向 `observe` 成正式依据的默认路径；生产启动通过真实当前读取建立 accepted，测试通过明确的读取替身建立基线。

若有必须保留的重装场景，核对其真实调用后，以受信的已接纳状态交接或明确当前读取完成初始化；不从未保存 Store 值推导 accepted，不静默丢掉 pending。具体实现复用安装令牌及清理回调，旧应用的订阅、提交完成和 finally 不得更新新应用投影或清除新锁。

## 7. 生命周期协调与兼容边界

### 7.1 双向互斥

门禁必须落在实际方法调用上，不只落在按钮：

- 配置保存、节点表单、确认和历史恢复，在留证/发送前检查同一工作流的管理 busy/pending/unknown，以及归档或删除状态。
- 归档/删除在实际管理入口检查配置初始化、提交、pending/unknown；同时保护现有可直接调用的管理命令路径。
- 跨 `await` 后重验，避免最初检查通过后另一类操作占用；不为此新增排队或在两个入口分别实现不同锁规则。
- 非当前工作流的必要证据初始化在操作入口显式完成，再判断两类门禁；初始化失败保持现有错误和锁，不能把尚未初始化的所有目标永久禁用，也不能跳过读取直接放行。
- 已知提交完成但结案失败仍受原请求门禁保护，不能当作普通空闲对象删除。
- 管理请求变为 unknown 时不能由配置请求绕开；配置 unknown 也不能通过归档/删除清空证据。

协调采用现有应用组合层的有限状态查询/门禁，配置与管理保留各自原请求 owner 和业务。若必须改变跨客户端锁、后端管理 CAS 或原请求 owner，停止并报告，不借前端互斥扩大到服务端协议重做。

### 7.2 删除与迟到响应

最终本地删除清理安排在正式删除回执已核实、管理原请求结案成功之后。当前 `ports.accept` 先清条目、outbox 随后结案的顺序，会使结案失败的 owner 从基于 Store 条目的待核实列表中消失；本批须订正这项时序，不能把删除成功视为证据已经结案。

回执已确认但结案失败时，保留原管理 owner、成功事实、锁及现有核实入口，不允许运行或配置写入，也不把后端删除事实改记为失败回滚。正常返回和 `reconcile` 结案成功后复用同一路最终清理，再移除目标配置缓存/投影及既有会话历史投影。只调整现有管理完成和清理次序，不新建证据中心或删除恢复交互；`forget` 不得删除待核实证据。

施工落点须同时撤出 `acceptManagementReceipt` 的接纳即删除和 `manageWorkflow` 的直接最终清理，统一接到 send/reconcile 证据结案后的完成处。可复用 outbox 结案成功后的 `refresh()` 回调；不能使用 `setCompletionHandler` 代替，因为它发生在 `writePending(null)` 之前。现有已删除提示与管理核实横幅可继续使用。若结案后本地清理异常，须报告投影清理错误，不能把已完成的证据重新称为 pending 或重发删除。

此项保证当前应用装配内仍可定位待结案 owner；不承诺刷新后自动重新发现已经从后端目录消失的定义。[现有证据查询](../../frontend/src/adapters/requestEvidenceApi.ts#L52) 要求准确 owner，尚无此装配发现路径。本批不新增 owner 枚举或恢复交互；若后续验收要求跨刷新发现，须先报告最小查询与装配影响，另行决定，不能称本批已完成完整恢复。

核对目录、配置返回、核实返回、订阅和重新安装各类迟到结果：旧生命周期不能重建已删除 entry、重新选中已删除对象、污染派生目标，或释放新生命周期的锁。使用现有对象身份、请求代次和安装令牌完成局部失效保护；不新增持久墓碑或恢复服务。

派生沿用现有选择保护：源工作流不被改写；只有提交时对应视图仍有效才跟随目标，后台结果不抢用户的新选择。

## 10. 冲突处理与汇报停止线

| 发现情况 | 处理 |
| --- | --- |
| 接纳规则需要静默覆盖同版不同正文、重置序号或重打旧请求 | 保留 accepted 与原请求；报告来源、版本、正文差异及受影响分支，不自行决定恢复规则 |

| 同版差异来自注册表、默认值或 current/fixed 组合 | 先定位实际差异；不凭假设批准“同版覆盖”，必要时单列契约决定 |
| 删除清理会移除未知原请求或未结案事实 | 不清证据、不放行删除；区分缓存清理和请求生命周期 |
| Legacy 样本需要补 current、迁移业务数据或恢复已退役 API | 不作为夹具修复；报告真实生产依赖、数据路径和替代范围后等待决定 |
