## 5. 正式职责与通信主干

以下是当前已验主干的职责说明；不是每行新增一个服务，也不是用一个管理器统管所有领域。

| 职责 | 实际承载与调用关系 | 维护边界 |
| --- | --- | --- |
| 功能管理与业务模块 | 变量、上下文、聊天、检查点等保有具体算法和业务；普通节点/工具调用真实实现 | 不自行激活、不决定下游图顺序，不要求节点内部每一步登记业务结果 |
| 配置管理 | `configuration_service.py` 受理，`WorkflowConfiguration` 维护规则，配置修改经所属数据端口保存 | 三来源适配保留；保存不执行节点，不热改当前运行 |
| 定义与注册 | 来源维护声明和真实实现，`WorkflowDefinitionCatalog` 提供首批只读查询，`RunBasis` 绑定同次运行来源 | 不建第二份可编辑定义权威；缺依据不回退服务当前表执行业务 |
| 项目包支持 | 复用既有包 loader、启用版本和选择机制，准备时取得所需准确来源 | 当前有基础，不等于发现/安装/热更新/发布平台全部完成 |
| 执行 | `GraphWorkflowService` 协调整次调用，编译/图执行计算参与和推进，宿主承载具体执行器，Agent 内核在 Runtime 内活动 | Agent 在执行层内不表示要与图执行模块耦合；前端连接不等于节点常驻执行 |
| 数据管理 | `WorkflowDataManagement` 分发，配置/定义/执行及信息/事实等所属数据模块承接，保持领域和原事务 | 正常执行 RunData 与无依据管理性 RunBoundary 分开；有限端口不向上暴露通用连接/任意 SQL |

工作流是整体资产与运行承载；工作流图只是其中的节点及关系；图执行计划是派生结果；流执行协调准备、图调用及结束。会话是数据隔离和归属，不设包揽业务的会话层。一个图成功返回不等于最终结算和通知都成功。

新增功能应沿已明确的配置、定义、执行、数据接口接入；确需新业务边界时另行论证。保留的管理/历史只读适配不是另一个正常执行业务入口，不以全仓 `repo` 零命中作为本次达标条件。

## 6. 图内主要操作顺序与结果边界

| 操作族 | 当前主要顺序与完成含义 |
| --- | --- |
| O1 配置 | 回执匹配/精确回放 → 共用规则与定义级运行锁 → 配置及原回执事务 → 独立读与前端接纳；锁期拒绝新提交，含无变化和确认派生 |
| O2 定义/能力 | 已启用准确包来源 → 注册声明/真实实现 → 只读目录 → 本次 RunBasis；不隐式取 latest，不凭提示正文取得执行权 |
| O3 受理/准备 | 现行聊天 `patch_input → start` → 捕获依据 → 准备期编译/类型/实现/权限核验与工具资源帧 → prepared 与 chain_start 原事务 → 提交后调度；准备不执行业务或模型 |
| O4 图推进 | 本次依据 → 执行期编译或复用保留结果 → 输入求值 → 原生/宿主调用 → 结果接纳后推进；两次编译职责不同 |
| O5 Agent 工具 | 同次帧精确目标 → Agent 自身 ACL/参数/归属 → 真实 executor → 每次写入独立事务 → 独立重读 → 返回；后续失败保留已接纳结果 |
| O6 领域接纳 | 节点输出/约定写集/进度在原节点事务接纳；工具写、事实、信息绑定按各自既有窄事务；不合成整图大事务 |
| O7 控制 | 活动链/回执条件 → 原事务内归属、状态、CAS → 有依据 RunData 或无依据 RunBoundary → 保留/释放；无依据 pause/close 不是续跑许可 |
| O8 结束 | 当前路径适用的终态、commit、成功检查点、聊天绑定、manifest 原共同结算 → 提交后通知 → 独立窄诊断 → 保留或释放；round 与 event 按各自语义，不强制一律生成同样记录 |
| O9 消费 | wait 反映最新一次执行调用；查询/回执/快照消费正式事实；业务已提交但通知失败显式分别表达，不撤销业务、不盲目重跑 |
| O10 图外交接 | 生命周期只将配置所属删除片交给配置域；资源走 application 正式入口；自有节点页取项目资产；其他项目业务和酒馆资产按原归属保留 |

Q10 无依据异常收尾及 Q11 无依据 close 的相关结束 manifest 统一使用同链 `chain_start`；缺失、身份/结构不符或坏 JSON 显式失败并回滚，不从当前 fixed document/registry 补造。Q11 对外为 `storage_contract_violation`/500；Q10 收尾失败回滚后，wait 仍保留原 `run_basis_unavailable`。

通知不是共同业务事务的一部分。整轮业务已提交但通知失败通过 `round_committed_notification_failed` 及持久窄诊断表达；逐项结果不保存异常 message。新执行调用替换旧 wait 异常，close 不冒充新调用清除它；超时不推断业务失败。异步 HTTP 202 已返回后，不能因后续通知失败事后替换该响应；等待与查询诊断的结果不等于改写原受理响应。
