## 2. 局部契约

### 2.1 本次绑定值

新增 [run_basis.py](../../backend/src/phase1_agent/run_basis.py) 的小型瞬态值 `RunBasis`：

- 只含本次冻结 registry 和同一 registry、同次 manifest 构造的 `WorkflowDefinitionCatalog`；
- 构造时校验 registry 已冻结、定义查询确实使用同一个 registry；
- 不持久化、不建表、不形成第二份可编辑定义，也不替代管理查询。

取得点：

- `GraphWorkflowService._start_run` 在进入准备事务前取得一次 `RunBasis`，并把它传给 `_prepare_run`；普通启动、event、chat submit/reroll 都走这一入口。
- 直接调用 `_prepare_run` 的兼容路径可以在入口处自行取得；生产运行入口不再在配置合成之后重新取服务表。
- `_execution_registries` 沿用原 chain 映射，值由裸 registry 改为完整 `RunBasis`。
- `_require_run_basis(chain_id)` 是执行用途的统一严格读取；缺失时返回 `run_basis_unavailable`，不重取、不换来源、不重建。

### 2.3 明确保留的边界

- **类型证据写入关口**：准备中的 `TypeContractStore.check_registry` 仍调用原存储、原事务，可能登记缺失证据；没有把它塞进只读定义口，也没有改成只读或提前写入。数据适配留到 3.2-A。
- **bundle 历史校验**：`GraphRecordStore(definition_registry=self.registry)` 未改为本次 registry；`_validate_changes` 仍可能沿会话历史读取其他修订并完成原 bundle 校验。没有为避开历史定义而取消或缩小校验。
- **历史与公开读取**：`definition_query`、`definition_references`、`_document_available`、`GraphPublic` 输出/历史观察仍使用当前来源；`graph_information.read_information` 的 live 读取使用本次绑定，history 在绑定已释放时继续走既有精确注册校验和历史 reader；`_read_runtime_fact_page` 是注册的历史 reader，绑定存在时用本次 registry，释放后用当前精确注册。
- **关闭**：执行成功后不保留绑定；失败链若已释放绑定，之后的管理关闭仍可为结束 manifest 使用当前来源。该路径不再继续执行、不重放业务，也不据此取得执行许可。暂停链的 archive/delete 关闭在绑定仍存在时使用绑定；控制关闭同样优先使用绑定。
- **前端快照通知**：`_accept_frontend_node_output` 和 `_read_frontend_snapshot` 仍使用当前来源。它是提交后的通知消费者，不回写节点结果，也不作为节点接纳依据；相关接线留到 3.3/3.2。
- **提供方资源**：内容资源的运行内读取使用本次 `data_types`；提供方资源继续走其专用服务，未在本步改写供应商资源管理。
- **继续限制**：`resume`、`retry_archive`、`retry_acceptance`、`retry_failed_node` 仍要求同进程 `_futures` 和原结果；没有新增跨进程恢复、自动重建或未知效果重放。
- **管理写路径**：`_write_configuration`、`_patch_node_configuration`、`_save_configuration_update` 等管理编辑仍使用当前来源；没有借 3.1 改写编辑器或全部定义消费者。

### 2.4 P2 补漏：执行异常收尾不再回退当前定义

独立复审在 3.1 收口前发现一项 P2：`_execute` 的异常收尾把 `registry=None` 传给结束 manifest，[graph_platform.py](../../backend/src/phase1_agent/graph_platform.py) 随即按 `self.registry` 重算资源依赖。该调用发生在缺绑定的失败路径，不属于已允许保留的“释放后管理关闭”。

本步修正：

- `_save_manifest` 新增显式 `fallback_manifest` 参数；只有该参数存在且 `registry is None` 时，才读取**同一条链**已经持久化的 `chain_start` manifest，复用其 `package_lock` 和 `global_resources`。
- 该分支不再取得当前定义、不调用 `_resource_identities`，也不把当前类型目录用于 manifest；缺少已准备边界时按 `storage_contract_violation` 失败，不伪造证据。
- `_execute` 异常收尾显式传 `fallback_manifest=("chain_start", chain_id)`；`chain_start` 由同一 `_prepare_run` 事务写入，属于本次运行依据。
- 控制关闭、失败链释放后的管理关闭仍按第 2.3 节保留原当前来源路径；本修正只改执行异常收尾，不扩大管理关闭迁移。

方向性测试见 [test_run_basis.py](../../backend/tests/test_run_basis.py) 的 `test_execute_without_captured_basis_fails_closed_with_explicit_diagnostic`：丢失绑定后执行，断言 `_resource_identities` 一次也未调用，结束 manifest 的 `package_lock`/`global_resources` 与准备边界一致，状态和诊断仍为 `recovery_unavailable`/`run_basis_unavailable`。修复前该调用会命中当前 registry，测试会失败。
