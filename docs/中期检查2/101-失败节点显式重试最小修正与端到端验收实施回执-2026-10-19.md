## 2. 实际产品改动

### 2.1 原调用配置作为策略依据

[graph_failed_retry.py](../../backend/src/phase1_agent/graph_failed_retry.py) 的 `_capture_failed_retry` 原先把固定文档中的 `declaration["config"]` 传给 `failed_retry_validator`，而 `_prepare_failed_retry` 创建新调用时复制的是持久 `node_run.config`。固定文档不一定等于该次实际消费的配置（可调覆盖场景），会导致策略判断与实际重试配置不同源。

修正为：

```python
policy = entry.failed_retry_validator(deepcopy(run["config"]), deepcopy(evidence))
```

`run` 是该失败 `node_run` 的持久记录；策略、候选依据和新调用现在使用同一份实际调用配置。配置分类、固定修订和“本次配置固定”的语义没有改变。

定向证据见第 4.4 节：修正前该测试收到固定声明 `{}`，修正后收到持久调用配置 `{"label": "persisted"}`。

### 2.2 控制预检使用本次运行依据

[graph_service.py](../../backend/src/phase1_agent/graph_service.py) 的 `control` 在 `retry_failed_node` 预检中原本固定用 `self.registry` 打开读取会话。现在在保留依据时使用 `basis.registry`，仅在依据缺失时退回当前来源以便拒绝：

```python
registry = basis.registry if basis is not None else self.registry
with self._data_management.read_execution(registry=registry) as probe:
```

实际重试仍在控制事务内用 `_require_run_basis` 重新取得依据，缺依据时拒绝。没有构造“当前表与本次表不同”的活包故障，因为现有包选择门禁阻止活跃执行期间换包；本条为来源一致性修正，不是已复现的产品故障。

### 2.3 无依据分支清理

`_control_change_current` 的 `retry_failed_node` 分支在依据缺失时，第二道 `require` 已经以 `failed_retry_unavailable` 拒绝，其后的 `execution_transaction(...)` 和 `_prepare_failed_retry` 不可能到达。本项删除该不可达准备，保留同一错误码和拒绝顺序：

```python
require(False, "failed_retry_unavailable",
        "The failed invocation has no retained run basis", 409)
```

无依据 pause/close、其他控制动作的兼容分支均未改动。

## 3. 测试包与真实宿主

新增 [test_failed_node_retry_integration.py](../../backend/tests/test_failed_node_retry_integration.py)：

- 通过 `CapabilityPackage` / `PackageManifest`（schema 2）和现有加载器注册，包 id 为 `sample.failed-retry`，只加入测试服务的 `enabled_packages`；
- 真实 `ExecutorDefinition` / `ExecutorReference`（`sample.failed-retry-executor@1.0.0`，`same_process`）和真实 `RuntimeHost`；
- 第一次 `advance` 在发布一条 `attempt` 事实后抛错，`dispose` 真实执行并计数；第二次新句柄返回确定结果；
- 节点 `failed_retry_validator` 只认可 `graph_node_failed` 这一准确失败边界，不使用“任何异常都允许”的宽泛许可；
- A、C 为可计数的原生节点，B 为受控宿主节点；计数器只用于观察，不构成产品重试策略。

没有替换 `_capture_failed_retry`、`_prepare_failed_retry`、许可判断、数据端口或宿主快照来让正向测试通过；配置来源测试的包装只用于隔离“固定声明”和“持久调用配置”两个来源。

## 4. 验收证据

### 4.1 真实正向路径

`test_public_retry_after_hosted_failure_completes_and_preserves_prefix`（第 124 行）：

1. 经公开 `service.start` 启动 A → B → C；
2. B 首次失败：A 调用 1 次并已接纳，B 调用 1 次且 `failed`，C 仍为 `prepared` 未执行；
3. 失败会话 `available_actions == ["retry_failed_node", "close"]`；
4. 经公开 `service.control(action="retry_failed_node")` 重试，返回 `prepared`，等待后会话 `succeeded`；
5. A 调用 1 次、B 调用 2 次、C 调用 1 次；
6. B 两次 `node_run_id` 不同，旧记录仍为 `failed`，新记录为 `succeeded`；
7. `chain.node_run_ids[next_node_index]` 指向新调用，`node_run_attempts` 保留旧、新两个身份；
8. 原上游 `output_id` 和 payload 不变，新 B 的 `input_refs` 精确指向该上游输出；
9. 旧 `attempt` 事实仍属于旧 B 调用，重试后没有改写、没有新增事实；
10. 成功 B 的输出进入 C，最终公开输出为 `retry: prefix`；
11. 旧宿主句柄释放一次，成功后新句柄释放一次，`_runtime_hosts` 无残留。

### 4.2 回执重放

同一正向测试用相同 key 和相同 `expected_revision` 重复控制，返回原回执；A/B/C 计数、调用身份和事实均不再增加。未用新的 `expected_revision` 冒充同一请求。

### 4.3 拒绝边界

1. `test_retry_without_registered_policy_is_not_offered_or_dispatched`（第 230 行）：
   - 未注册 validator 的节点失败后 `available_actions == ["close"]`；
   - 直接请求报 `failed_retry_unsupported`；
   - B 调用次数仍为 1，node_run 集合不变，宿主无残留。
2. `test_retry_without_retained_run_basis_is_rejected_without_a_new_handle`（第 260 行）：
   - 受控移除 `_execution_registries` 中的本次依据后，动作仍显示可用，但请求报 `failed_retry_unavailable`；
   - 没有新 B 句柄、没有新 node_run、没有下游调用。
3. `test_retry_rejects_changed_state_basis_without_a_new_handle`（第 288 行）：
   - 通过测试注入写入一项变量状态，改变候选依据；
   - 请求报 `failed_retry_basis_changed`，B 调用次数和 node_run 集合不变。

### 4.4 配置来源

`test_capture_uses_persisted_invocation_config_for_the_policy`（第 360 行）：

- 用包装把“固定文档声明配置”和“持久 node_run 配置”显式分开；
- 修正前 validator 收到固定声明 `{}`，测试失败；
- 修正后 validator 收到持久调用配置 `{"label": "persisted"}`，测试通过。

该测试只证明配置来源，不宣称产品已存在可调配置与 validator 同时注册的节点；当前产品没有这种组合。

### 4.5 控制预检依据

`test_retry_precheck_reads_with_the_retained_run_basis`（第 328 行）包装 `WorkflowDataManagement.read_execution` 记录注册表来源：

- 控制开始时读取 active chain 的探测仍使用服务当前 registry（只读定位，不授权执行）；
- `retry_failed_node` 预检的读取使用本次保留 `RunBasis.registry`；
- 重试成功后独立读取最终状态。

该测试证明第 2.2 节的预检来源修正，未构造活跃换包；现有包选择门禁仍阻止正常入口在活跃执行期间换包。

### 4.6 端口、事务与独立重读

正向测试在重试控制前安装 `ExecutionRecords.put_node_run/put_chain/put_session` 计数，重试后均命中；业务层没有通用 `GraphRecordStore` 直写。事务后经 `WorkflowDataManagement.read_execution` 独立读取：

- session 的 `active_chain_run_id` 为 `None`；
- chain 为 `succeeded`，attempts 保留两次 B；
- 旧 B 为 `failed`，新 B 为 `succeeded`，新 B 配置等于旧 B 配置；
- 上游 output 仍在；
- head commit 的 source 为 `completed_execution`；
- 成功检查点存在，结束 manifest 为 `succeeded`。

节点接纳、最终结算和事实仍是各自的原有事务；控制事务仍共同保存新 node_run、chain 调用索引与 prepared 状态、session 修订。

### 5.1 首次失败与修正记录

- 测试初建时出现 `factory` 本地变量顺序错误和 `NodeDefinition(executor_ref=...)` 参数错误，属于测试夹具构造错误，修正后重跑；

- 修正后正向路径在**未改产品代码**的情况下通过，说明既有机制在固定配置样本上成立；
- 配置来源测试在修正前失败（validator 收到 `{}` 而非持久配置），按第 2.1 节修正后通过；这是本项发现的唯一产品语义缺陷；
- 无依据清理前后拒绝行为一致，由第 4.3 节回归覆盖。
