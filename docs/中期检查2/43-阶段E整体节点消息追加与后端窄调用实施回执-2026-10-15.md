## 2. 真实写入证明与事务

旧显式读取/追加节点的`FRONTEND_VIEW@1`要求真实`view`输入边。整体节点在内部读取自己的项，没有该图输入；本批没有伪造内部节点、边、调用身份，也没有删除旧producer验证。

[frontend_node_contracts.py](../../backend/src/phase1_agent/frontend_node_contracts.py)新增独立`FRONTEND_NODE_APPEND@1`证明，包含准确owner、读取CAS依据、完整保留前缀、真实content输入绑定、角色及本次`node_run_id`。消息仍以不可变产物引用保存，不在会话状态中另存正文副本。

[frontend_contracts.py](../../backend/src/phase1_agent/frontend_contracts.py)只为准确`frontend.node@1`增加新证明分支，核验：

- 实际producer、writer及自有项registrar是同一个节点实例，且会话和项完全一致。
- 本次持久化`node_run.config`中的`object_key/role`、真实输入绑定和授权读取记录与证明一致。
- 来源是已接纳的`TEXT@2`产物；旧对象修订与保留前缀正确，稳定entry ID可从真实来源和本次调用重建。
- 期望值完全等于被证明的追加结果，不准覆盖旧记录或伪造来源。

[session_objects.py](../../backend/src/phase1_agent/session_objects.py)的内部产物解析补充`consumed_config`和`reads`，保留旧`config`来源不变；写校验上下文补充真实`writer_node_id`。[host_sdk.py](../../backend/src/phase1_agent/host_sdk.py)仍接纳旧上下文，新增writer必须为准确UUID或初始化时的空值。

证明、CAS更新、对象回执及commit产物在现有结算事务内保存，发生异常全部回滚。原operation key的同请求重放直接返回原对象回执，不增加revision；换key重复提交同一已保存的新节点证明会因陈旧依据或归属被拒绝。旧producer分支保留原校验和原同值处理。

## 3. 提交后读取与展示缓存

普通执行器的`context.object_read`读取本次调用的冻结副本。结算finalize仍在事务内，不能把该副本或计算后的追加结果称为实际写后读取。

[graph_service.py](../../backend/src/phase1_agent/graph_service.py)在`_change`成功返回、设置`settlement_committed=True`之后，调用[frontend_node_snapshots.py](../../backend/src/phase1_agent/frontend_node_snapshots.py)：

1. 核对真正成功的node_run、chain、准确节点声明及输出回执。
2. 以自己的真实节点ID调用`SessionObjectStore.read`，再次核对项类型、registrar及reader ACL。
3. 固定此次对象值与`revision_id`，沿该值的授权产物闭包解析正文，生成展示快照。
4. 按工作流、节点实例和会话缓存深拷贝，附真实对象revision和来源调用身份。

`read_frontend_node_snapshot(W,R,N,S)`显式读数据并刷新缓存；`get_cached_frontend_node_snapshot(W,R,N,S)`只观察上一次快照，不重新读取当前值。另一个合规节点更新数据层后，原缓存不会自行变化；再次后端读取后才变化。返回副本被修改不影响缓存或数据层。

提交后读取失败沿现有`result_committed_notification_failed`如实报告，已经成功保存的消息和回执不回滚，不自动重新执行追加。显式重新读取及重复完成通知只更新快照，不追加第二份消息。事务未提交的失败不会创建缓存。

本批只安装后端缓存，没有浏览器连接、推送总线或网络路由。“前端打开时发送快照”的传输接线仍属于E3/E4，不能把缓存写好等同于已经推送到页面。

## 4. 准确节点的同进程窄调用

[frontend_node_operations.py](../../backend/src/phase1_agent/frontend_node_operations.py)提供后端门面：

```python
node = FrontendNodeOperations(service).bind(
    workflow_definition_id=W, definition_revision=R,
    node_binding_id=N, session_id=S,  # S可空；bind不建会话。
)
node.patch_input(text, expected_edit_sequence=E, idempotency_key=K)
node.read_snapshot()
node.start(expected_session_revision=revision_or_none, idempotency_key=K)
node.pause(expected_session_revision=revision, idempotency_key=K)
node.read_receipt("start", {"expected_session_revision": None, "idempotency_key": K})
```

门面只接纳已绑定实例的允许操作，调用者不能选择另一输入目标、对象键、任意operation或完整上下文正文：

- **输入修改：** 从保存配置取得准确`input_node_id`，在同一事务内核对绑定、目标和编辑序号，调用E1共用repo保存内核。`graph.frontend-node.patch-input`按原窄请求保存独立回执，保留`unchanged/saved/confirmation_required/derived`；重放先取原回执，不读最新图重建正文。
- **读取：** 仅读自身登记项，返回上述显式重读快照，无会话时不能读取会话数据。
- **启动：** 已有会话按准确预期revision启动；无会话第一次运行先create，再从create原回执取得sid/revision启动。创建和启动保留两个实际结果，不冒充一个原子事务，不使用返回中的假revision或重新读取后的revision。
- **暂停：** 直接复用正式`control(action="pause")`，运行期间无需等图调度到节点；接纳请求不等于已经到达暂停安全点。

start/pause使用现有事务回执保存原请求及冻结派发依据，再在事务外调用正式能力，稳定子key区分各阶段。正式调用前不持服务锁，避免与host锁的反向依赖。已有原请求重放只核实原生回执，不重新派发；缺失原生回执返回明确`unknown`和失败阶段，不自动重试或重基。

create已成功、start被拒绝时，首次返回真实新sid及start诊断，不删除会话或创建另一份。后续若没有已接纳的start回执，只报告尚未核实，不把临时诊断当持久化业务成功。

新门面仅同进程开放，未加入`GraphApplication.COMMANDS`或现有generic HTTP入口，未扩建request-evidence目录或新pending表。浏览器的原请求通信及对应窄操作证据适配仍需在E3接续，不能将本门面直接作为任意命令代理。
