## 2. 首批真实路径与范围

### 2.1 必须完整接通的主链

```text
现有工作流运行入口
→ 确定准确会话与工作流修订
→ 取得本次注册结果及同源定义查询
→ 经配置数据端口读取、按配置规则合成本次配置
→ 编译参与图，检查并准备必要资源和宿主
→ 保存 prepared 依据并提交既有后台执行
→ 图执行调用原生节点或已注册宿主执行器
→ 节点结果、约定写入与图进度共同接纳
→ 必要共同结算、状态及资源释放
→ 既有消费者独立读取结果
```

先以普通调用贯通，再覆盖共享执行链的 event 分支、暂停继续及故障边界。原生节点和受控宿主执行器都应有代表证据，不以纯 `execute_graph` 内存计算替代服务实际接线。

必要会话创建、种子状态和已有图外命令沿用原业务。独立成立的会话创建不并入新造的整次运行事务；只有真实运行路径所需的最小适配进入本批，不迁移项目创建、归档、删除等管理业务。

## 4. 运行依据与调用的核心实现思路

### 4.1 先分清注册结果的作用范围

| 用途 | 采用的依据 |
| --- | --- |
| 管理目录、配置编辑、新运行的来源 | 服务当前注册结果及其对应来源信息 |
| 本次准备、图执行、节点接纳、运行内数据校验、必要结算 | 本次绑定的冻结 registry 和同源定义查询 |
| 存活调用的 live 信息消费 | 本次绑定及原 owner / generation，不因缺失而转 history |
| 已结束或重启后的 history 查询 | 按既有 owner / generation、持久 information binding 和历史 reader 契约读取；缺少所需来源时报告不可用，不要求保留已释放的运行副本 |

不得全局替换 `self.registry`。例如 [历史事实读取](../../backend/src/phase1_agent/graph_information.py#L88)与 [live/history 分流](../../backend/src/phase1_agent/graph_information.py#L228)必须按用途处理；管理历史查询不是运行副本缺失时的执行降级通道。

当前事实历史 reader 仍会通过准确节点注册解析执行器引用，不能描述为已持久保存完整 run registry 或原执行器实现证据。本批不在此新增历史来源证明机制；若该规则需要改变，另行报告具体影响。

### 4.2 本次绑定的最小实现

1. 继续复用 `self.registry.detached(frozen=True)`，不在每次运行重新加载包。
2. 在配置合成之前取得本次注册结果，同时捕获对应包来源信息，构造同源 `WorkflowDefinitionCatalog`。来源信息与 registry 必须来自同次已发布加载结果，不能执行到一半再取服务的新 manifests。
3. 复用现有 chain 映射提供集中、严格的本次绑定读取；可以用小型私有绑定值组织 registry 与 query，不新建持久调用实体或第二份可编辑定义。
4. 运行调用明确接收绑定。共用辅助可以保留管理用途，但运行调用不得用缺省参数偷偷取当前表；不临时替换 `self.registry` 再恢复。
5. 取得运行依据失败时，在计算、宿主调用及结果接纳前阻断；保留真实诊断和必要清理，不用当前实现重新解释本次业务。
6. 在所有继续、重接纳和收尾路径正确保留、使用及释放绑定。历史回执重读不重建绑定，不重复准备宿主，不重新执行业务。

校验复用已有规则：准确工作流包需求满足现有可用包锁的子集条件；参与闭包的节点、端口、定义及执行器引用一致。宿主额外包合法，休眠未知节点不因此被强制执行或全部校验，不增加全 registry 哈希或任意可信内存篡改防护。

[输入声明](../../backend/src/phase1_agent/graph_input_declarations.py#L80)是编辑器和消费者查询，不直接改成 run-only API。本批真实运行准备若消费声明，则使用同一绑定；其余双输入收窄只在有实际依赖时局部处理，不能借此重写全部编辑器。

### 4.3 配置求值与节点调用不变的部分

本次采用的配置继续保存到 `node_run.config`，执行及继续从该依据取用，不重新合入 current。节点内部何时计算具体值仍由节点决定，启动准备不提前执行节点业务。

当前内容资源和模型请求有各自读取时点；统一注册依据不改变这些时点。当前工作流的可调配置在后来被合法保存为 B，不代表在途调用应由 A 热更新为 B；下一次调用采用新值与本次保持固定分别验证。不借此新增或扩大配置修改锁的政策。

继续沿用原生 callable 与宿主执行器两条实现适配，二者均受本次依据、调用和接纳边界约束。宿主不接管节点内部业务，节点不负责启动自己或推进下游。

## 5. 执行数据接口与模块拆解

### 5.1 依赖方向与领域分离

```text
流执行 / 图执行桥接 / 具体功能
→ 所属功能的有限数据接口
→ WorkflowDataManagement
→ 对应领域的数据模块
→ 现有仓储、SQLite 及事务适配
```

以下是端口意图和候选布局，不冻结新类名或要求一行一文件。优先复用现有数据模块；确有独立职责再拆小模块。

| 数据职责 | 有限操作的意图 | 内部复用与边界 |
| --- | --- | --- |
| 配置依据 | 读准确固定修订、匹配修订的当前覆盖 | 复用配置数据端口；合成和分类规则仍在配置业务 |
| 运行记录与输出 | 读准确会话/chain/node 调用关系，保存既有状态、配置、进度、输出及关联 | 内部复用 `GraphRecordStore`；不向执行业务开放任意 record kind 或 `get/put/rows` |
| 变量运行状态 | 读当前状态，按原 CAS、key 和事务保存，维护原快照绑定 | 复用 `ProgramVariableStore`；不在本批重定变量定义载体或初始化语义 |
| 节点私有态 | 读指定会话节点状态，按原类型和版本规则保存 | 与变量当前值、会话对象分开；不向节点公开仓储 |
| 会话对象 | 准确对象读取、授权修订读取及写意图应用 | 复用 `SessionObjectStore`；本次运行使用绑定类型规则，保留 CAS、权限和引用校验 |
| 运行事实 | 明确 owner、stream、sequence 的读取及接纳 | 复用 `RuntimeFactStore`；不混入可变对象仓储，不新建通用命令回执副本 |
| 资源、输入和产物读取 | 准确资源身份、已接纳输入及授权产物读取 | 按各自领域分发，保留原读取时点、来源闭包和访问边界；不接管项目资源 CRUD |
| 共同结算的持久适配 | 原有 commit、manifest、聊天调用依据、候选绑定及检查点所需的有限存取 | 上层协调原业务，各所属适配绑定同一事务；不把这些业务改写进万能执行仓储 |
| 类型合同核验 | 承接原准备中 `check_registry` 的准确核验意图 | 这是可能写入的既有操作，不塞进只读 `DefinitionDataSession`，不自动改变证据维护权和时点 |

数据管理入口可以将同一原事务绑定为多个有限端口，供上层组合使用；端口组合只汇集访问能力，不在数据仓储之间建立业务调用。`configuration_data.py` 中的管理入口可以继续分发独立领域模块，不要求先重组整个数据平台。

### 5.2 装配边界与通信撤出

候选实现可参照现有 `_configuration_change`：在装配边界增加执行命令适配，将原 `GraphRecordStore.atomic` 绑定成有限数据会话，再交给业务回调。执行读取也由数据入口装配相应只读端口。

必须区别：

- 装配/事务适配可以接触原 store 和 records，用于绑定现有事务；这不等于执行业务可继续任意通信。
- `_prepare_run`、节点接纳、运行推进、控制及本批宿主桥接的内部业务逐步改用有限端口，撤出选定路径中的 SQL、仓储构造和直接 repo 读写。
- 可以先用端口转发原实现，再整理内部代码；只有实际链路经过端口，才能记录“骨架接通”。
- 仓储之间不互调。跨领域规则在上层协调，数据模块只承接其领域数据。
- 原 `_change` 仍服务其他管理业务；本批不以搬走这个共用函数为由整体拆解 `GraphWorkflowService`。

这里的“逐步”表达本批内部施工顺序，不表示本批结束可以把选中链的旧直连继续留到以后；收口时按第 9.2 节逐项核对。

本批运行用途的必迁调用清单包括：`_prepare_run` 的依据读取与 prepared 写入，`_execute` 的状态装配和终态写入，`_save_effects/_settle_node_result/_node_event`，共同结算调用的 `_commit/_append_success_checkpoint/_save_manifest`，控制回调，以及宿主的输入、产物、owner 和事实桥接。共用方法可保留管理用途；其本次运行分支及实际调用到的功能辅助必须经过所属有限端口。

例如，将 `collect_checkpoint_state(repo, ...)` 原样藏进一个执行仓储，不等于功能和存取已经分开。本批共同结算所需的检查点收集继续在功能层保留准入、投影及差异规则，其配置和对象读取改经所属端口，最后由检查点数据适配持久化；未涉及的装载、查询和分叉路径单列保留，不扩成整个检查点工程。

有限接口名称、参数、返回内容和候选 `execution_data.py` 等文件，在施工局部契约中记录。不得以接口为名返回通用 repo、数据库连接、任意 SQL 或任意持久回调，随后宣称通信已收口。

### 5.3 特殊路径的保留与处理

[准备中的类型合同检查](../../backend/src/phase1_agent/graph_service.py#L647)可能登记缺失证据。应由数据内部明确的核验适配绑定原事务承接，不将只读定义证据端口变为隐式写入口。若准备改成纯读取、提前写入或改变首次登记语义，先报告并由用户决定。

同一关口也涉及 [会话对象类型核验](../../backend/src/phase1_agent/session_objects.py#L52)：现有对象仓储会调用类型合同存储。施工局部契约须明确它如何复用核验适配并保留原证据写入语义，不能一边声明领域分离，一边隐瞒本批对象路径仍直接跨领域调用仓储；也不能顺带重写所有范围外对象和全局资源路径。

[模型授权桥](../../backend/src/phase1_agent/graph_runtime_host.py#L119)中有使用调用方提供的只读连接的适配；专用 [模型资源读取](../../backend/src/phase1_agent/model_request_resources.py#L47)已有 `mode=ro/query_only` 边界。触及实际已用路径时只迁移对应存储桥，不改成普通存储、不另开写连接；未安装服务不为完成测试而启用。

信息绑定、历史目录、项目资源 CRUD 和其余能力旁路应在回执中登记准确留存点。本批若必须触及其运行内桥接，就纳入准确端口与验证；不能将一整份共用文件笼统标为已迁移或全部范围外。

`get_run`、检查点列表及读取、独立会话查询、公开历史观察等现有只读消费者可以保持原存取实现，本批验证其消费正确，不以“消费者验证”名义扩大为全部查询迁移。相反，节点正在执行时依赖的输入、产物或 owner 读取，即便没有写入，也属于本批选中的运行内通信。

## 6. 必须保留的事务、错误与锁边界

| 边界 | 必须保留 |
| --- | --- |
| 准备事务 | prepared 记录、节点调用配置和会话活动指向按原命令事务成立；准备失败不发布半套可执行环境 |
| 节点接纳事务 | 该节点约定写入、输出、node/chain 进度和相应会话修订共同接纳；接纳前缀不是整图事务 |
| 事实接纳事务 | owner、generation 或 stream 校验及 immutable fact 原独立接纳；不能拖到节点结束后才保存原本应在外部调用前成立的事实 |
| 普通成功结算 | 运行终态、存在聊天调用时的候选绑定、会话 commit、成功检查点及结束 manifest 保持原共同事务 |
| event 和失败分支 | 不强行增加普通轮候选、commit 或成功检查点；按原分支保存终态和结束依据 |
| 通知 | 持久接纳后通知失败不抹除事实、不授权业务重放；失败显式报告，不默认继续 |
| 继续与重接纳 | 保留同进程、准确结果及依据的现有限制，不合并 `resume`、`retry_acceptance`、`retry_archive`、`retry_failed_node` |

活跃写事务中使用同一有限数据会话，不另开普通 `SqliteStore`。独立重读在原事务结束后进行；普通关闭重开不等于严格只读回执路径。

事实写不能直接套 `_change/GraphRecordStore.atomic`，否则会额外产生管理幂等回执。数据层以窄事务适配在原同一事实事务中协调 owner 检查和 `RuntimeFactStore.accept`，宿主只取得有限操作，不取得 store 或 connection。

事务适配仍须执行原 bundle 校验、operation/key、请求摘要、回执身份和故障注入点，不生成第二份回执。`GraphRecordStore._validate_changes` 可能沿会话历史读取其他修订，不能把整个校验集合误当作本次参与节点，也不能为避免错误绕开校验。

开始、控制及结算的既有幂等回执判断须保持先后关系：命中原回执不重新准备环境；关闭后重读原控制回执，也不能因为运行绑定已释放就错误地要求重新取得活跃执行依据。历史观察与回执查询不会产生新的执行许可。

不要给数据管理统一加服务锁。宿主、信息绑定及控制回调现有锁策略各有约束；不得在持服务锁时等待宿主锁或 provider 调用，造成原本已避免的锁反转。

抛错后中止当前业务调用链并显式报错，之前已接纳结果保留。必要诊断和资源释放不视为继续下游业务；错误记录本身失败时不能改取当前实现或重放业务掩盖异常。

## 7. 四步执行工作单

### 9.2 阶段收口要求

必须分别有证据证明：绑定消费统一、数据骨架真实接通、本批内部直连撤出、图/控制消费者取用正确、跨层和错误边界通过。回执列出未迁路径及原因，不能把整份文件或全部执行层宣称为已清理。

| 逐项验收范围 | 收口要求或允许留存的原因 |
| --- | --- |
| `_prepare_run`、`_execute` | 主链的 session、固定/当前配置、prepared 记录、执行状态装配及终态读写经过有限端口 |
| `_save_effects/_settle_node_result/_node_event` | 节点写集、输出、接纳进度及关联校验不在业务中直接持有仓储、通用 repo 或连接 |
