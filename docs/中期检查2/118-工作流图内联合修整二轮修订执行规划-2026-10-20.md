## 1. 目标、依据与基线

本轮修订目标：

1. 把 1.0-4.0 首批成果接成职责一致的真实主链，配置、定义与数据组件在选定范围内成为正式边界，而非保留可绕行的正常双路径。

“转正”按真实调用、维护权和允许的通信能力验收；不是要求改名、搬文件、每个领域新建服务，或让所有 HTTP/页面经过同一个万能入口。工作流整体、节点图、流执行、图执行、节点实现与宿主继续按 [92 号](92-工作流业务对象与操作职责表及3.0边界整理-2026-10-19.md)区分。

### 2.1 补证事实及对旧材料的限定

- **Q8**：请求证据与业务在同一 SQLite 文件，但证据写入、业务提交、证据结案各自独立事务；未知只核实不重派。owner 最多一条 pending，单条请求有容量限制；没有总量/TTL 清理。`read_evidence` 经普通 `SqliteStore` 初始化，不能作为严格只读核查工具；见 [request_evidence.py:135](../../backend/src/phase1_agent/request_evidence.py#L135)、[storage.py:44](../../backend/src/phase1_agent/storage.py#L44)。结案后同键 write 返回原 pending 快照属待验证组合，不能自动改写原回执语义。
- **Q17**：三个操作是只读管理查询；management 是服务选择与应用作用域，不是新增的调用方鉴权。当前源码无 UI 消费者；旧展示消费者已退役，本地过期 `dist` 不能算当前源码消费证据。查询不写业务结果也不自动证明底层连接严格只读。
- **Q21**：配置整份保存与节点页补丁均未读取运行态；固定修订与 `node_run.config` 快照只能证明当前链隔离，不是写入禁令。已有暂停时修改可调配置的测试意图，后续须按 G21 定案调整，不能以旧测试反推产品规则。
- **Q14**：117 已订正 116 的“唯一现行客户端”为“保留旧调用代码”：旧页面关闭、业务脚本按不可执行内容托管，consumer 作用域不再放行对应输出操作。不能写成有现行可用 UI，更不能为此恢复页面或放开权限。
- **Q3**：117 的“先停服”或必须先给定默认库路径的旧前置不照搬。用户最新要求是确认实际 develop 路径、只读核查、不自动停服；有历史行不等于有未结依赖，native/origin 能配对也不等于已核实原请求。

Q8/Q17/Q21 的原补证报告在忽略目录 `backend/.local/q8-q17-q21-2026-10-20/`；本文保留接手所需结论，不要求复制或入库本地报告。代码未显式配置 journal mode，不能推断真实库“无 WAL”；SQLite `timeout` 也不等于没有锁等待。实际库模式及现场状态留 G3 核查。

| 职责 | 正式调用边界 / 本批落点 | 不取得的权力 |

| 执行协调 | `graph_service` 负责何时准备、图推进、接纳、控制及结束；`graph_execution` 调节点实现 | 不把能力内部子步骤注册为调度表，不让 Agent 内核直接耦合图执行器 |

| 通知与投影 | 消费已提交状态，表达自身发送或刷新结果 | 不把通知成功当作持久业务成立的条件，不反写已成功业务为未提交 |
| 能力与 Agent 工具 | 按同次准备帧、真实 Agent ACL、共同 executor 调用，工具逐次接纳 | 不临时发现/加载，不借普通节点实例权限，不扩大到任意节点工具化 |

选定业务内部撤出直接通信后，不保留旧正常路径作备用回退。底层原事务/回执适配、批准的历史只读以及显式无依据管理边界分别登记，不以全仓 `repo` 命中数作为“转正”指标。

### 3.1 图内操作主干

```text
配置来源 → 配置功能接口 → 共用规则 → 数据管理/配置域 → 正式配置与独立读取
能力来源 → 原真实 loader → 内部定义查询 → 同次 RunBasis
运行受理 → 原准备事务：
  配置与会话门禁 → 参与计划编译 → 类型/实现核验
  → 工具/资源/服务准备帧 → prepared 记录与 chain_start
准备提交后 → 后台执行 → begin 转 running → 装配已保存配置/结果
  → 执行期编译或精确保留结果复用 → 原生/宿主调用
  → 节点接纳事务 → 下游推进
  Agent 内工具写：独立逐次接纳与独立重读
结束 → round 成功共同结算 / event、失败、暂停、关闭各自分支
  → 提交后通知 → 按状态释放或保留 → 独立查询与消费者
```

准备帧成立不等于业务执行；返回结果不等于正式接纳；图完成不等于结算成功。正常 round 的终态、commit、成功检查点、聊天成功绑定与结束 manifest 保持原共同结算关系；event 不强套 round 成功行为。节点、工具、事实/信息绑定和最终结算的不同事务不合成一个大事务。详细条件仍以 116 的 O1-O10 和实际代码为核对依据，本批交付其修订后的正式操作表，不安装外层 `0-9000` 注册机制。

### 4.8 接纳分类隔离验证：Q16，本批只验证

静态缺口是用 `reason_code` 有无代理“是否可再次接纳”：见 [RuntimeHost.drive](../../backend/src/phase1_agent/runtime_hosting.py#L298)、[retry_acceptance](../../backend/src/phase1_agent/runtime_hosting.py#L357)及执行异常收尾。精确幂等只保护特定事实/回执，不证明所有无码异常可安全重试。

生产宿主 [graph_runtime_host.py:295](../../backend/src/phase1_agent/graph_runtime_host.py#L295)未装 `result_sink`。因此必须走真实包 Agent 终端 fact 接纳，不能用合成 result_sink 替代该证据；节点结算在 host 成功后发生，单独记录。静态核对已确认，当前失败后的精确接纳恢复由显式 `retry_acceptance` 控制经过状态、同进程候选与依据校验后重新提交执行；见 [graph_service.py:1326](../../backend/src/phase1_agent/graph_service.py#L1326)及 [重新调度](../../backend/src/phase1_agent/graph_service.py#L1518)。`graph_execution` 的 pending 分支只是重入后选择接纳适配，不是自动调度；补充材料中的“同进程自动重试”不作为当前事实沿用。

| 隔离场景 | 必须观察，不预改政策 |
| --- | --- |
| 带码但已有确定结果、接纳可恢复 | Agent 完成结果、终端 fact、host 状态/释放、图诊断、是否还有精确接纳入口 |
| 带码的确定性拒绝 | 分清结果/身份违约与当前 owner/状态不允许；是否终止及是否误保留 |
| 无码且提交状态未知 | 注入写前、提交边界及确定性程序错误，不能只用 OSError 推断未写入 |
| 已提交但确认丢失 | 故障落在实际 COMMIT 成功之后、确认交回之前；比较持久行、原 receipt、业务与 transport 次数，观察允许的精确再次接纳是否重复 |

测试侧注入，不加生产开关、自动恢复、重跑 Agent 或对 unknown 盲重放；已有 before-commit 注入不能冒充 after-commit。提交成功后确认丢失可在测试侧包装真实接纳回调，待原提交成功返回后再抛注入错误，不吞掉原失败或伪造提交。只有在隔离场景已知真实提交事实且现行准入允许时，才显式触发原精确结果再次接纳来观测幂等，记录触发次数与原因。

交付每场景的输入身份、失败阶段、host/candidate/graph 状态、处置、retry 可用性、独立读取及 executor/kernel/transport/持久写次数。探针结果记“观察现状”，不能把启发式误分类固化为目标行为回归以获得绿色。

**G16**：Lead 审核实际证据后交用户决定下一批契约。“已接纳 / 明确未接纳 / 状态未知”与“同一确定结果能否再次接纳”必须分开讨论，不从错误码直接推导。本篇不授权实现新分类或改变重试政策；补证完成也不等于分类问题已修复。
