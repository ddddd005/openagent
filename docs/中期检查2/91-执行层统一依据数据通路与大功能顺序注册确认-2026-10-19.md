## 2. 当前问题与已确认：统一本次运行的注册依据

### 2.1 两种 registry 的关系

当前是同一种 [NodeRegistry](../../backend/src/phase1_agent/graph_contracts.py#L456)在两个作用范围内使用：

| 对象 | 当前作用 |
| --- | --- |
| `self.registry` | 服务当前持有的注册结果，包含节点定义与实现绑定、执行器、数据类型、宿主服务、信息来源和包版本等 |
| `run_registry` | 启动时由服务注册表复制并冻结，绑定本次运行 |

构造方式是 `self.registry.detached(frozen=True)`，见 [冻结复制](../../backend/src/phase1_agent/graph_contracts.py#L628)和 [运行准备](../../backend/src/phase1_agent/graph_service.py#L642)。它不是两个独立能力来源，也不是重复加载出来的两个权威。注册表不承载画布实例的全部配置、运行数据或输出。

副本创建时，两者的注册内容一致。当前 [包变更入口](../../backend/src/phase1_agent/graph_platform.py#L69)还禁止在活跃运行及保留执行环境期间替换包，正常流程通常能够保持一致。因此，本次确认的是结构风险，未复现新的运行依据混用故障。

### 2.2 当前缺口

1. 编译使用本次冻结表，但 [服务定义查询](../../backend/src/phase1_agent/graph_service.py#L229)以及部分实现检查、资源预检和 [宿主准备](../../backend/src/phase1_agent/graph_runtime_host.py#L186)仍使用服务当前表，同源关系靠调用点保持。
2. [节点结果接纳](../../backend/src/phase1_agent/graph_service.py#L738)和 [执行取用](../../backend/src/phase1_agent/graph_service.py#L1010)存在“本次注册表缺失时回退服务当前表”的分支。
3. [输入声明接口](../../backend/src/phase1_agent/graph_input_declarations.py#L80)同时接受 `registry` 和可选 `definitions`：编译使用前者，声明查询使用后者，接口本身没有绑定二者同源。现有调用可以正确传入，本轮未复现错配。
4. [定义引用查询](../../backend/src/phase1_agent/workflow_definitions.py#L266)提供当前准确注册状态和工作流的包锁信息，但没有将两者的来源符合性连成完整运行依据。编译器已有 [准确包版本检查](../../backend/src/phase1_agent/graph_contracts.py#L762)，不能说成没有包检查，也不能把宿主额外安装其他包当作冲突。

`availability = registered` 只表示相应准确注册存在，不自动承诺工作流可以执行或其包来源已经冻结。

### 2.3 用户确认的修正方向

- 完善加载、注册、本次运行绑定和取用之间的衔接，修复实际缺口；不另造一份可独立编辑的能力权威。
- 本次运行涉及的定义查询、准备、编译、调用和结果接纳，统一采用其绑定的注册结果。
- 本次副本缺失或与本次运行要求不符时明确报错，不回退服务当前注册表遮掩异常。
- 服务当前注册表继续服务于管理查询和后续新运行，不要求所有管理查询转为依赖某次运行的副本。
- 冻结注册依据不等于启动时算出全部动态值，也不等于冻结全部项目资源或外部模型请求；继续遵循 90 号求值语义。

副本与本次运行的具体校验方式、错误码和接口签名仍需局部施工规划确认，本文不预建通用版本证据或快照平台。

## 3. 当前问题与已确认：执行数据通路

### 3.1 两个明确缺口

| 缺口 | 当前事实 | 已确认的处理方向 |
| --- | --- | --- |
| 数据通路尚未接合 | 运行准备直接读取配置仓储，执行侧直接使用变量、会话对象、输出和运行事实存储 | 接入数据管理入口和对应领域模块，打通真实读取、写入及结果返回 |
| 执行与存储职责混在一起 | 执行协调和宿主模块仍构造仓储、访问记录或 SQL，并操作事务 | 划清执行功能，接入已有实现，逐步将跨结构调用收口到已规划接口 |

代表位置是 [运行准备](../../backend/src/phase1_agent/graph_service.py#L624)、[节点写入接纳](../../backend/src/phase1_agent/graph_service.py#L714)、[执行数据装配](../../backend/src/phase1_agent/graph_service.py#L973)和 [宿主运行事实接纳](../../backend/src/phase1_agent/graph_runtime_host.py#L86)。现有 [数据管理入口](../../backend/src/phase1_agent/configuration_data.py#L152)已经承接配置和定义证据领域，不能据此宣称执行领域也已迁完。

目标通信方向：

```text
工作流执行或具体功能模块
→ 所属功能的数据接口
→ 数据管理入口
→ 对应领域的数据模块
→ 仓储与数据库适配
```

接口须参与实际通路。初期可以转发现有实现，随后将本批跨层通信收拢到接口；不能只增加未被真实消费者使用的空壳。

### 3.2 拆分约束

1. 数据管理内部的配置、定义、变量、会话对象和运行记录等职责分别承接，不相互调用其他领域仓储。跨领域业务由上层明确协调。
2. 调整代码归属时保留既有事务边界，所需领域操作可绑定同一已有事务；不在自己的写事务中另开普通存储连接形成嵌套写入。
3. 保留节点写入意图、执行侧共同接纳等已有配合方式，不改成所有节点自行提交数据库，也不由 Runtime 重新裁决所有节点内部业务。
4. 后续失败保留此前已接纳结果；运行终态、聊天候选绑定、会话提交记录、成功检查点和结束记录的共同结算不拆散。
5. 整理项目维护的调用路径，不给用户扩展代码增加强制隔离平台、逐步回执、全节点结果登记或内部步骤表。

本轮没有按上述方向迁移产品代码，也没有确定全部新文件或数据端口的方法签名。

## 4. 当前机制：外层运行与图内执行分别存在

当前能力包主要在 [服务初始化](../../backend/src/phase1_agent/graph_service.py#L88)时加载；每次工作流启动再准备本次所需依据和环境，不应理解为每次启动都重新导入所有包。

普通启动的代表链路为：

```text
前端请求启动，必要时先保存可调输入
→ 校验目标，必要时创建会话
→ 读取本次配置，复制并冻结注册表
→ 编译节点图，确定参与范围和节点顺序
→ 检查资源依赖，准备宿主服务及聊天调用环境
→ 保存节点配置、运行身份和 prepared 记录
→ 提交后台执行，启动请求返回
→ 后台读取执行数据，调用图执行模块
→ 图内按序调用节点实现，逐个接纳结果
→ 完成共同结算
→ 更新视图和通知，释放运行资源
```

这只是当前代表路径的概括，不冻结以后每个功能的准确数字位置，也不表示所有触发都必须经过同一个前端输入节点。

外层顺序目前主要由 [工作流操作](../../backend/src/phase1_agent/workflow_operations.py#L160)、[运行准备与启动](../../backend/src/phase1_agent/graph_service.py#L624)、[执行与最终结算](../../backend/src/phase1_agent/graph_service.py#L973)中的调用代码组织。启动请求返回不等于后台工作流已执行完成。

图内顺序由 [GraphCompiler](../../backend/src/phase1_agent/graph_contracts.py#L759)根据真实数据边和控制边计算，再由 [图执行模块](../../backend/src/phase1_agent/graph_execution.py#L248)推进。具体业务由节点包的实现或已注册执行器完成。当前尚没有本文确认的统一“大功能顺序注册表”。

## 5. 已确认：工作流层级的大功能顺序注册

### 5.1 注册粒度与数字区间

用户提出 `0–9000` 的大顺序空间，每 `1000` 分一个顺序区间；区间内允许按具体数字注册，内置功能可按 `0、100、200……` 等位置留出扩展间隔。第一版先采用三类，其余位置预留：

| 首版区间 | 大类 | 代表内容 |
| --- | --- | --- |
| `0000–0999` | 构建与准备 | 确定运行依据、构建环境、编译节点图、准备必要能力和数据 |
| `1000–1999` | 工作流执行 | 调用图执行模块，由其按图内顺序执行节点并接纳结果 |
| `2000–2999` | 执行结束处理 | 业务结算、检查点、通知、资源释放等 |

“执行结束处理”表示图执行之后的工作，不表示已经正式宣告整轮业务成功。必要结算仍属于成功条件，不能因进入该区间就提前报告成功。

用户最新明确：顺序注册只针对工作流层级的大功能，不要求每个功能下的子模块注册到表中。联系紧密的多个内部动作可以集中为一个注册单元，由该模块自行组织。

位置示意：

```text
0100  内置大功能甲
0150  插件大功能
0200  内置大功能乙
...
1100  执行整个节点图
```

上述具体位置仅为示例，不是已冻结的内置序号清单。

### 5.2 不混用的三个范围

- 工作流大功能顺序：由本机制组织准备、图执行及结束处理等外层调用。
- 图内节点顺序：继续由编译器根据数据边和控制边计算，不要求画布节点另占一个大功能序号。
- 功能内部实现：由所属模块自行组织，不强制登记子函数、内部算法或 Agent 每一步思考和工具选择。

数字表达先后，不自动表达适用条件、事务归属或能力权限。不能将各注册项理解为无条件从小到大全部运行，也不能用提前注册绕过必要准备或拆开共同结算。具体失败阻断范围不在本文讨论。

### 5.3 谁声明、谁执行

| 位置 | 本轮确定的职责方向 |
| --- | --- |
| 定义与注册 | 承载大功能调用声明及其顺序位置，供可信内置代码、包或插件提供 |
| 执行层的整体运行模块 | 取得本次注册结果，组织大功能的执行顺序并调用 |
| 图编译与图执行模块 | 在“执行节点图”这个大功能内部，计算节点顺序、传递输入并推进调用 |
| 对应功能和节点模块 | 实现各自业务，返回输出或错误，不拥有外层后续功能的控制权 |
| 工作流基础支持 | 受理启动和控制请求，确定运行目标及会话指向，传递状态和错误 |
| 配置与数据管理 | 分别维护允许修改的配置，以及所属领域的持久数据和事务 |

这是职责划分，不要求一个职责必对应一个新文件，也不要求立即把现有集中服务整体重写。

用户插件可以声明扩展位置，不自动等于普通工作流用户可以从页面任意修改内置顺序。哪些基础位置固定、哪些区间对哪类扩展开放，以及用户是否可以改序，尚未形成具体权限契约。本文不默认开放。

同序号冲突、准确公共注册格式、功能引用方式及实际内置序号清单仍需后续局部规划确认，不在本文补建复杂依赖调度器。

## 6. 已澄清：前端节点不是常驻执行主体

### 6.1 用户实际关注点

用户担忧候选、重roll和分叉功能会使前端节点脱离工作流管理，或使工作流执行内功能与运行外操作混在一起。用户没有要求前端节点持续存在或保持激活执行。

需要区分：

| 路径 | 职责边界 |
| --- | --- |
| 图内节点执行 | 接受工作流调度，获取输入、完成功能、输出或抛错，调用结束后不自行继续工作 |
| 运行外操作入口 | 接收读取、候选选择、重roll、分叉等请求，交给工作流对应功能模块校验和执行 |
| 页面连接与通知 | 展示状态、读取结果、接收通知，不等于节点业务正在持续执行 |

图未运行时可以有受管理的操作请求；这不代表节点在运行外常驻激发。节点不能以页面存在、数据已持久化或通知连接仍在为由自行计算、写入或触发后续功能。

“是否需要常驻前端节点”不再作为用户待决需求；后续应检查的是节点有没有越过受调度调用及工作流功能入口的执行路径。

### 6.2 当前源码已经存在的分离

| 操作 | 当前路径及事实 |
| --- | --- |
| 输入修改 | [前端节点操作](../../backend/src/phase1_agent/frontend_node_operations.py#L142)委托配置功能接口，不靠图内节点持续运行来保存 |
| 启动与控制 | 同一适配模块委托 `WorkflowOperations`，由工作流服务执行启动或控制 |
| 重roll | [聊天操作适配](../../backend/src/phase1_agent/workflow_chat_operations.py#L97)委托 [工作流聊天服务](../../backend/src/phase1_agent/workflow_chat_service.py#L232)，最终进入 `_start_run`，重新走准备和执行 |
| 候选选择 | [工作流聊天服务](../../backend/src/phase1_agent/workflow_chat_service.py#L259)选择候选并恢复相应计算基线，通过已有事务提交 |
| 分叉 | [工作流聊天服务](../../backend/src/phase1_agent/workflow_chat_service.py#L333)按检查点和候选依据创建目标会话，不由图内前端节点常驻完成 |
| 图内前端节点 | [节点实现](../../backend/src/phase1_agent/frontend_node_v2.py#L16)处理图输入并生成聊天写入依据；对应接纳在明确结算边界完成 |
| 通知连接 | [连接模块](../../backend/src/phase1_agent/frontend_node_connections.py#L60)维护展示连接和通知，不负责派发或重放业务 |

聊天操作当前还通过 [操作基线检查](../../backend/src/phase1_agent/workflow_chat_service.py#L61)调用既有会话与版本门禁。本次没有复现前端节点脱离工作流自行运行的故障，也没有据此宣称所有路径已经审核或收口。

现有 `execution_class = working/non_working` 是整个节点参与普通图执行的分类；不是节点内部“页面交互、准备、图执行”等职责的拆分机制，不能用一个字段代替上述边界。

后续真实接线应核对入口、门禁、图内调用和资源释放是否各有归属，不为了前端页面增加常驻节点执行器。

## 7. 状态归属与本轮排除的事项

本轮已经解释但未另行入文档的区分是：节点计算完成、结果持久接纳、工作流共同结算，以及完成通知不是同一个事实；后发生的错误不能覆盖此前真实成立的结果。

节点或能力负责自己的业务结果和错误；执行侧维护调用位置、接纳及运行推进；数据管理承接持久化和事务结果；基础支持和前端传递、读取及展示诊断。沿用 90 号已有职责，不新增逐步骤状态机。

当前 [提交后通知处理](../../backend/src/phase1_agent/graph_service.py#L875)已经区分“结果已提交”和“通知失败”。本轮只保留该事实及边界，没有规定所有能力失败都只影响通知，也没有改变已有错误中止和继续条件。

新接入或规则尚不明确的能力失败，会阻断哪个功能、后续调用、整次运行或其他业务范围，用户明确留待下一轮讨论。本文不制定能力失败分类表、统一阻断政策、自动重试、回退、补偿或新的恢复机制。

## 8. 后续接手与交付边界

接手时先读 90、91 号确认方向，再沿第 4 节真实链路整理大功能及其所属模块。后续局部执行规划需要确定本批接口、注册单元、真实数据范围、准确依赖与验证方式，不将本文的示例序号直接安装为最终协议。

已确认方向与待决事项分开处理：

- 已确认：运行依据统一，副本异常明确报错；执行数据入口真实接通；跨结构调用逐步收口；前端节点受工作流管理；只登记工作流层级大功能；首版采用三类顺序区间。
