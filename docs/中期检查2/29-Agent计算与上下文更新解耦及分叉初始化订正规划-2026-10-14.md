## 3. 项定位与正常数据流

| 信息 | 谁处理 | 含义 |
| --- | --- | --- |
| 精确类型名与 schema version | 定义/类型登记、获取/更新节点及数据层 | 描述值结构和可用交互契约，不能代替项身份 |
| `object_key` | 配置、获取/更新节点及数据层 | 在工作流登记中选择一份独立项；不与 Agent 节点 ID 混用 |
| `workflow_session_id` | runtime、节点交互宿主及数据层 | 当前值仍按 `(session_id, object_key)` 定位和隔离 |
| `registrar_node_id` 候选字段 | 宿主登记及配置 | 说明哪个实例提供该项，不授予读写权，也不限定实际执行者 |
| 实际 producer、输入 refs 和 facts | 执行证据与更新核实 | 证明谁使用什么输入产生此次计算，不表示数据属于该 Agent |

同一类型的项 A/B、同一工作流的会话 S/T 都可区分；类型、项和会话错配必须拒绝，不静默选择另一项。

```text
类型声明 + 独立项登记
        |
获取节点选择具体项 -> 加载时的值 -> 装配后的计算内容 -> Agent
        |                                            |
        |                                  计算结果 + 真实执行证据
        |                                            |
        +-> 更新节点核对原加载、具体项和执行事实 -> 候选投影
                                                     |
                                       显式提交到数据层
                                                     |
                                       后续再次加载读取新值
```

Agent 可以维护本次计算中的消息、工具状态、精简结果和正常暂停现场。这些不是持久数据项；精简的持久覆盖仍由显式更新节点完成。runtime 不代读写，也不补上下文固定先序。

Agent 计算侧不读取 `object_key`、registrar、持久 owner、head revision 或 revision ID 来决定行为。宿主可以保留完整输入 artifact、原请求和运行身份用于准确核实；持有只读证据不等于让 Agent 业务解释持久数据归属。

## 4. Agent与更新节点接续

1. 保留 `PROMPT@6` 外层字段及版本，保留整份输入 artifact 的精确接纳和装配校验，不改成“只验 messages 大概相同”。Agent 计算输入取已核实的消息及算法所需属性，持久项元数据由宿主/上下文侧处理。
2. Agent 输出计算结果和真实执行证据，首选核对能否直接复用现有 `AGENT_RECEIPTS@1`。操作序列、final、snapshot 和精简事实已有已接纳 facts 可供更新侧核实；不为保留旧包装而继续让 Agent 输出持久 `next_view` 或 CAS basis。
3. 更新节点接收准确加载 view 和准确执行证据，从原 prompt artifact 核实本次计算实际使用的加载值、模型、策略与执行事实，再重建持久候选；目标必须等于该原加载项，不能把基于 A 的结果写到 B。
4. 实际执行 Agent 可以不同于项的登记者。允许合法选择另一实例登记的数据，不放宽真实 producer、会话、精确输入、facts 顺序、完整工具结算或 final 证明。
5. 正式写入仍走普通节点授权、类型校验、当前 CAS 和同节点输出/对象写入/真实回执原子接纳。更新节点未调用、失败或未接纳，不产生持久更新。

这要求更新活动端口和精确组件契约，不能继续按28号“`AGENT_CONTEXT_UPDATE@1` 外层完全不动，只适配嵌入 view”的清单施工。新执行证据端口名、可复用类型的准确限制及必要精确版本由最小消费者清单审阅确定；本页不安装新通用证据协议、自动换版或旧格式业务兼容。

`context_update_v2` 等历史/未接入执行证明只核对实际活跃消费者，不因这次订正顺带安装另一套 executor 或请求机制。已退役 `context.adopt` 继续不可执行业务；旧原请求只读解释及准确旧回执验证保持隔离。

## 5. 保存状态与新会话初始化

**成功点收集：** runtime 判定整回合成功后，检查点从固定登记、明确类型准入及源会话已接纳当前值收集。收集不依赖是否存在获取节点、merge 节点或 Agent 已输出的候选，不读取未写回的流内值。通过数据层的可信内部职责限定源读范围，不冒充 `readers[0]`，也不向普通节点开放全量读取能力。

**分叉初始化：** 保留既有前缀复制及完整事务，由所选成功点的物化状态初始化唯一新目标。白名单项定位按准确登记和 object key，不寻找 Agent owner 或目标 writer。

必要校验仍包括：

- 源检查点、完整父级/full-diff、工作流及固定 revision 均准确；只装载本批白名单的合规逻辑值。
- 目标是本次准确创建的新会话，尚无运行、commit/ref、节点产物或正常写入历史；不覆盖源或任何已使用的会话。
- 固定绑定、登记、精确类型和全部目标项吻合；目标 CAS 使用实际初始化状态，并保持事务内准确核对。
- 数据层初始化写入维护类型校验、引用合规、目标自己的值/版本及会话范围。保存的是内联逻辑状态，不伪造源 revision、节点 invocation 或 Agent 更新证据。
- 新会话、检查点前缀、白名单装载和目标自己的单次 commit/snapshot/ref 同事务；任何项或最后提交失败都完整回滚，源不变。

普通 `SessionObjectStore.read/apply` 的节点 ACL、CAS 和类型写入规则不放宽；新增/调整的内部保存状态初始化职责不能成为任意已有会话的写入口，不添加 `skip_authorization` 之类公开开关，也不复用旧 `restore_logical` 历史证明路线。

初始化不执行获取/更新节点，不创建其 node_run 或伪装正常节点写回回执。分叉自身的真实请求身份与原子操作回执仍保留。目标之后的实际运行仍只按用户编排显式加载/更新。

无 writer、多个合法 writer、没有官方 merge 组件都不应仅因此阻断白名单项的成功点收集和新目标初始化。后续普通节点写入是否获权仍按其 ACL 判断，这与检查点限定内部职责分开。

逻辑状态最小候选仍为 `agent_contexts[object_key] = {"value": ...}`，不再携带 `agent_node_id`。28号提出的 checkpoint record 新版本及 SQLite `CHECK(schema_version=1)` 影响仍须在最小接口清单核对；不增加检查点 Head、数据历史平台或第二套会话存储，不自动处理既有库。
