# 工作流配置层与配置存储详细勘察执行规划

日期：2026-10-18，Asia/Shanghai。

性质：为决定第一步局部施工方向准备的详细勘察任务书。本文基于一次简要文档与源码核对，规定后续应查什么、按什么顺序查、如何分工和回执；不是详细勘察已完成的报告，不批准产品代码修改、接口安装、数据库操作或 Git 提交。

## 1. 定位与边界

本篇接续[70 号执行顺序](70-工作流配置起步与逐层接入执行顺序-2026-10-17.md)第 1 步“配置数据盘点”，为第 2–3 步“配置与数据薄口、配置存储”准备决策材料。[72 号](72-工作流六层代码勘察参考-2026-10-17.md)继续作为源码地图，不改写为对象级调查结论。

详细勘察要回答：

1. 配置管理实际维护哪些对象、内容、定义和引用，各自如何表示？
2. 谁产生、校验、修改和消费它们，正式入口与旁路分别在哪里？
3. 配置操作经过哪些模块，实际保存了什么，如何按准确身份重读？
4. 配置存储如何保留固定修订、当前配置、事务、回执及错误？
5. 对照已确认职责，第一步可以整理哪条局部通路，还有哪些决定必须先问用户？

这里的“配置层派生的数据存储”指配置业务所需的存储职责及其现有实现，位置在数据管理内部；不表示配置业务模块可以直接操作表，也不表示需要新建物理数据库。“派生内容”另指绑定、映射、展示等生成结果，两者分别调查。

沿用已确认边界，不重新论证：

- 当前只针对工作流底层运行及其必要接口。工作流基础支持仅负责启动、恢复、抛错、当前状态和会话指向。
- 项目创建、删除、归档、复制和项目启用包管理属于项目能力层，不进入本轮建设；节点实例增删、选区复制和既有配置确认派生规则不能因此漏查。
- 不建立功能性会话层；保留工作流定义域与会话域的逻辑归属，可共用 SQLite。
- 配置管理维护配置规则，通过数据管理保存；运行侧请求静态配置修改时回到配置管理。
- 变量定义及默认值与会话当前值分开，定义不要求先有会话；具体载体和初始化仍待确认。
- 定义来源保留维护权，定义目录提供只读消费视图；项目资源不因引用而转移所有权。

依据：[66 号数据契约](66-工作流数据管理与定义域会话域契约-2026-10-17.md)、[67 号配置交互契约](67-工作流基础支持与配置管理交互契约-2026-10-17.md)及其 2026-10-18 订正、[69 号局部骨架规划](69-工作流架构局部骨架与分批执行规划-2026-10-17.md)、[71 号名词口径](71-工作流架构与会话数据名词口径-2026-10-17.md)。

## 4. 整体重点

1. **对象归属先于存储位置。** 分开记录业务维护方、逻辑数据域、实际仓储和物理存储；不能从“同表”“同一服务”“当前选中会话”反推所有权。
2. **写入与重读成对。** 从前端操作追到底层保存，再从正式读取追回视图；同名读取可能取当前合成值、固定修订或原请求冻结结果。
3. **修订与当前值分别说明。** `edit_sequence`、固定定义 `revision`、会话/对象修订、节点/包版本、schema 和存储版本不是同一个版本轴。
4. **配置合法与可执行分别说明。** 查清存储结构校验、配置业务校验、精确定义查询、图编译的调用时点；合法但不完整的配置可保存这一现状不能被“统一校验”悄悄取消。
5. **派生不等于无权威。** 对象键、权限、绑定和事件有业务含义；展示标签、端口视图、快照和冻结证据也不能一概按缓存处理。
6. **固定清单具体分析。** 哪些是来源枚举，哪些是受信任权限，哪些是真正缺少登记、查询或管理能力，应分别举证；不预定把所有白名单改成开放注册。
7. **事实、目标、差异与决定分栏。** 源码是实现证据，已确认文档是目标依据；目标尚未实现、当前实现尚未核实、语义尚未决定是三种不同状态。

## 7. 必查链路与问题

### 7.1 入口与修改路径

| 路径 | 必须说明的事实 |
| --- | --- |
| 工作台配置编辑 | 表单/画布操作 → store/application/SDK 的实际接线 → HTTP/应用命令 → 配置方法 → 数据保存 → 回执/新视图 |
| 独立节点页输入修改 | 专用通道 → 精确前端节点绑定 → 输入目标校验 → `_patch_node_configuration` → 原生事务及返回；与工作台路径的共用和差异 |
| 窄配置补丁 | `patch_node_configuration` 的实际调用者、许可及可达状态；不能仅因存在方法就声称已有公开 HTTP 入口 |
| 固定/可调/展示修改 | 各自保存内容、序号变化、无变化结果；有有效会话时固定修改的确认与派生，以及源工作流/会话是否改变 |
| 节点增删、替换、选区复制 | 绑定、权限、对象键、边、节点引用、事件和包锁如何联动；哪些由前端生成，后端如何校验 |
| 变量配置与当前值 | 保存配置、会话空壳、运行登记/初值和当前值分别是什么；对“无会话可定义”的目标差异举证，不决定新载体 |

至少贯通工作台和独立节点页两类入口。撤销/重做、扩展配置提交等若汇入同一路径，可共用后端证据，但必须记录实际汇合点、安装状态和前端结果接纳差别。

每条链写清原始请求形状、命令/operation、幂等键和目标身份，以及返回的 outcome、变更类别、目标身份/修订与诊断。工作台原请求 evidence、服务事务回执、前端视图接纳是不同环节；独立节点页还须记录专用 owner/evidence/native receipt，不将两套回执身份合并。

### 7.2 配置存储与重读

先查 `workflow_current_configuration`，再查 `records` 中的 `workflow_definition_revision`、`node_binding`，最后追查 `idempotency` 及应用命令身份是否参与该操作、如何关联，以及与业务写入的事务关系：

- 当前配置各列/JSON 成员与固定文档如何对应，哪些字段进入哪份表示？
- `node_binding.config`、修订文档中的节点配置与当前配置的重叠各有什么用途，谁是何种读取下的依据？不预先判为无用副本或第二权威。
- `_save_definition`、`_write_configuration`、`put_current_configuration` 与 `atomic` 分别负责什么，事务由谁开启，哪些校验在事务内外？
- 事务读集合包括哪些当前配置、修订、有效会话条件和精确定义；经应用命令上下文保存的身份记录是否也在同一 `idempotency` 表，不能凭概念名另画一张不存在的表。
- 固定修订、展示/可调修改、确认询问、确认派生和无变化结果，分别写哪些业务记录与回执？
- 确认询问不写配置或新工作流，不代表不保存命令回执；应区分业务变更和证据落库。
- `get_definition(id)`、`get_definition(id, revision)`、列表、节点快照和原请求回执分别读取哪份依据？保存回执不等于独立重读证据。
- 表初始化、版本检测和兼容读取有哪些副作用？仅记录源码，不为调查实例化普通 `SqliteStore`。

会话状态和归档标记若参与可编辑性或派生判断，查明调用及条件即可；不借机调查项目归档、删除等完整业务。

### 7.3 定义、Runtime 与能力消费

从具体配置字段出发，追到消费者需要的最小边界：

- 配置管理如何查询准确 `NodeDefinition`、schema、端口、对象访问和可调规则；当前查询、目录投影及运行编译分别是什么。
- 固定清单在哪里产生、如何查询、由谁维护；允许扩展和受信任许可是否是不同机制。
- `_prepare_run` 何时读取固定文档或合成当前配置，运行如何记录实际消费值；保存成功与运行采用分别报告。
- 检查点配置投影如何取得固定修订及允许字段；只报告现有准入与读取，不扩大为全量快照。
- 若发现执行侧发起配置修改，追回配置保存；若未发现，记录检索范围与目标尚未落实，不创造一条已接通链。

相邻入口参考：`graph_service.py::_prepare_run`、`graph_records.py::_validate_consumed_configuration`、`checkpoint_collection.py::collect_checkpoint_configuration`。不需要通读全部 Agent 内核、模型服务或重roll/分叉实现。

### 7.4 错误与验证证据

按已查链路选分支，不建立所有对象乘所有错误的全量矩阵。至少说明：

- 编辑依据过期、请求目标/精确类型不匹配、定义缺失或字段无修改许可，在哪里拒绝，有无业务写入。
- 保存中断时配置、固定修订、绑定与回执是否同事务回滚；源码依据和测试断言分别记录。
- 同 key 同请求、同 key 异请求、结果未知后的核实如何保持原身份，不自动重发、不以今日当前值代替旧回执。
- 错误如何从仓储/配置到应用和前端，是否存在静默替代、丢失分类或只显示成功的路径。

测试候选先阅读 `test_workflow_configuration.py`、`test_configuration_mutations.py`、`test_configuration_application.py`、`test_configuration_evidence.py`，以及前端 `workflowConfiguration.test.ts`、`workflowConfigurationStore.test.ts`、`workflowEditableInput.test.ts`。按具体测试函数和实际入口映射，不将整文件视为本轮范围；合成注册不证明当前内置包已安装同一行为。

本轮只登记验证意图、现有断言及缺口，默认不运行测试。需要新的离线探针时先说明不能仅靠阅读回答的问题、隔离路径与副作用，取得相应范围后再执行；历史测试结果不转记为新验证。

## 8. 三路分工与协调

在 S1 初始清单和 S2 基准链统一后，详细勘察可按下表三路只读并发：

| 路线 | 主任务 | 交付 | 不自行决定 |
| --- | --- | --- | --- |
| A：配置与操作 | 前端两类入口、应用路由、配置规则、增删替换/复制、正式结果接纳 | 操作/可达性表、当前调用链、前端派生规则位置 | 新配置 API、将全部前端规则迁入后端 |
| B：数据与存储 | 记录格式、配置表、仓储、初始化、修订、事务、回执和重读 | 存储映射、写集合/事务表、读视图差异、持久化错误链 | 迁表拆库、统一事务或新增第二份权威 |
| C：来源与消费 | 精确定义、固定清单/注册、派生视图、Runtime 采用、变量/检查点配置边界 | 来源/登记/查询表、消费者依赖表、语义未决项 | 注册平台、变量载体/初始化、可调生效或检查点扩张 |

整合负责人维护对象编号、目标依据、差异与待决表，并复核跨路事实。模块内工作是查清已定职责内部规则；跨层联查是核对同一对象通过不同职责时的身份、形状、修订、事务和结果，二者不得互相替代。

必须统一协调：

- 两种前端入口是否指向相同配置业务，具体请求与回执身份是否不同。
- 业务维护权、定义来源、逻辑域和实际存储不能各路各定一套。
- 固定修改的确认派生与项目一般创建/复制的范围区别。
- 配置保存原子性；节点接纳和最终成功结算是不同边界。配置勘察只记录依赖，不把成功结算改为提交后能力写入。
- 专用只读回执使用 `mode=ro`/`query_only` 并在普通服务构造前分流；不能因统一数据口建议而要求其初始化 Runtime 或普通存储。
- `graph_service.py`、`workflow_configuration.py`、`graph_contracts.py`、`graph_store.py`、应用入口和 `stores/workflowGraph.ts` 等共享集中点，按方法联合审阅；后续代码接线另指定单一负责人。

跨层调用、共用 SQLite 或 import 本身不是违规证据。报告应区分正常消费、绕过目标入口、职责共置和真正语义冲突。

## 9. 第一批方向如何形成

详细勘察结束后，仅推荐一个优先候选和必要的备选，不直接铺开全部配置层：

1. 候选已有真实入口、实际存储和独立重读路径，能够保留现有规则与错误。
2. 能具体画出“当前路径”和“拟经过配置薄口、数据薄口的局部路径”，复用现有模块，不要求先拆完集中服务。
3. 能说清哪些是模块内部整理，哪些是配置/数据/定义/前端之间的接线，以及共同身份、版本和事务条件。
4. 不依赖尚未决定的变量结构、可调范围或生命周期语义；确实依赖时明确列为前置，不用临时默认绕开。
5. 有小型隔离验证意图，能证明保存、独立重读、冲突和真实错误，而不是仅验证新增转发函数。

简单输入配置可作为调查样本，但本篇不预定它就是首批施工对象。最终建议要比较实际覆盖、改动范围、未决依赖和验证成本。

提交用户的最小方向建议应包含：对象/操作范围、现有可复用部分、建议涉及方法/文件、两个薄口各转发什么领域意图、原事务如何保留、验证意图、延期内容与所需决定。这里只写候选职责和调用意图，不定新类名、完整 API、表结构或扩展机制。

## 11. 待决处理与完成判据

延续 69 号未决清单，尤其是：

- 可调值的作用范围、影响哪些会话、生效时点及重roll基线。
- 变量定义载体、现有登记节点定位、当前值初始化及既有数据处理。
- 当前局部所需注册对象、精确身份、维护/查询契约。
- 派生内容新增持久化、失效机制、版本/事务调整等超出既有行为的决定。

报告应给出事实、原因、受影响路径和可选择的方向，再交用户决定。生命周期、能力失败与插件扩展若只影响后续阶段，保留关联，不将其全部解决作为配置勘察的前置。

详细勘察完成，是指对象和代表操作可追踪，保存与重读的依据可解释，已确认目标与实际差异可核查，未决及未查范围不被掩盖，并足以让用户决定第一步范围。它不等于配置层改造完成，也不要求所有未决已经解决。

若首批候选仍依赖用户决定，应明确提出问题；若对象或主链仍未追通，应如实标为部分完成。用户确认方向及代码范围后，才按“局部论证 → 极简骨架 → 内部填充 → 跨层验证”进入施工。
