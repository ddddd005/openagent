## 6. 核心契约与实现思路

### 6.1 T2：声明必须参与取得

工作流声明最少含能力身份、接入声明/契约版本、来源引用、按角色取得入口引用、必要环境、生命周期、公开业务契约引用、前端接入引用及跨域依赖。接入版本不冒充产品发布版本，也不等于工作流内部 package_lock；名称可由工程在本模块内固定，含义不能混用。

声明及显式可信 callable binding 由来源共同提供；项目只校验和索引。Host 首次取得某角色时从定义管理查到该绑定，核对声明、环境和角色，再沿工作流原构造路径创建并缓存。不得保留一条绕过声明的正常硬编码取得路径，使声明仅能 describe；也不得把定义管理变成任意模块导入器。

依赖条目对应“调用方、提供方/契约引用、用途、条件、实际调用位置”。跨域清单至少覆盖存储环境、资源/全局内容、供应商/模型请求、凭据、请求证据及必要前端关系。供应商/内容尚未项目化时，明确引用现有 operation、ServiceDefinition 或可信提供接口，并标注现阶段承载，不伪造它们已注册成项目子能力。

静态检查只核对声明、契约和可信绑定；不能为检查依赖调用 `host.provider_configuration/content_configuration/request_evidence` 等懒属性而提前建库或取得资源。具体引用记录、凭据、ACL 和执行包可用性仍在原业务准备/调用阶段检查。诊断说明依赖、条件、结果与安全 reason code，不包含凭据或业务正文，不新增自动回退。

当前定义管理仍以可信本地查询为正式消费者，不因新增声明自动开放 HTTP 或完整前端目录；已有前端扩展绑定/签名核对继续使用，工作流整体声明只引用必要关系。

### 6.2 T3：摘要与正文分离

拟采用以下最小查询，复用 `POST /api/graph/queries`、management scope；命名如需调整须前后端与文档一起更新，不改变语义。

| 查询 | 参数 | 每行字段 |
| --- | --- | --- |
| `definition.summaries` | 可选 `include_archived: bool`，默认 false | `workflow_definition_id, display_name, fixed_definition_revision, edit_sequence, archived, node_count, session_count, has_current_configuration` |
| `session.summaries` | `workflow_definition_id`；可选 `include_archived: bool`，默认 false | `workflow_session_id, workflow_definition_id, definition_revision, revision, name, metadata_sequence, archived, active_chain_run_id, status` |

对已有正式固定记录但无 current 的项，保留目录可见性：`has_current_configuration=false`、`edit_sequence=null`，名称/修订来自真实固定记录；不伪造可编辑或可复制能力。没有正式记录的本地草稿不进入后端摘要。工作流数量是明确过滤范围内正式目录行数；`session_count` 统计该工作流全部正式会话（含归档），从原会话记录即时聚合，不计草稿或待核实行、不另存 COUNT 权威。若界面显示过滤后的会话行数，应与这一总数明确区分。

目录仓储直接投影 current 标量、固定记录必要 JSON 路径/绑定数、会话头/名称/归档及必要 chain/head 信息；不先读取全部历史 document，不组合每张图，不读节点输出/变量/对象/私有态来拼摘要。不为方便复用 `list_definitions()` 或逐项 `_view()` 后丢字段。

每次摘要响应在工作流域独立读事务内形成一致视图，复用同库环境；不承诺两次 HTTP 响应同一快照。保留当前可解释的行顺序和过滤范围，必要排序在领域内确定并记录，不引入新的用户排序功能。

会话 `status` 复用工作流实际选择规则：本会话 active 优先，否则 head 所选 chain，再否则 idle。event 跳过、继承来源和 rebind 版本差异等由原历史规则解释；允许读必要 head/commit/history_refs，不承诺完全不读历史或 O(1)，但不得改成“最新本会话 chain 的状态”。不在摘要提供依赖内存候选的执行动作权限。

前端按下列顺序接线：

1. 摘要刷新只更新目录投影，不把摘要伪造成 `GraphDocument`/`GraphSession`，不以缺详情删除本地草稿或 pending。
2. 打开工作流先 `ensureDefinitionEntry` 经已有 `definition.read` 取正式 current，交现有配置接纳/版本仲裁，再构造/更新 entry；之后才 refresh、激活与轮询。须修复当前 `activate` 无 entry 即返回的依赖。无 current 的正式旧项读取到 fixed 时，只能沿现有固定只读表达，不能冒充 current 接纳、补造 edit_sequence 或自动迁移；若前端缺少可保持的只读展示，先报告局部缺口。
3. 会话列表使用摘要，选择会话后仍经 `session.read` 取完整视图；运行控件、历史、名称写入门禁及命令前版本检查继续使用详情。已有“显示归档”开关须保持有效：消费者请求含归档全集后本地筛选，或随开关重查，不能默认排除后仅本地切换。
4. 保留 mutationGeneration、view token、session selection token、同序号正文冲突、pending/草稿保护；摘要不能绕过单一配置接纳入口覆盖详情。
5. 侧栏可保留明确标识的草稿/待核实行，正式数量仅统计正式摘要项。目录消失、删除后的核实投影与已确认删除清理分开，不用刷新强行抹掉原请求。

新增 query 除 `QUERIES` 外，还要补 `validate_parameters` 对新名称的身份/过滤严格校验；不能只有注册项而放过 bool、UUID 或额外字段。

### 6.3 T4：归拢界面、状态与调用

| 内容 | 处理 |
| --- | --- |
| 名称/改名、视图页签、复制、放弃修改、运行控件挂载及 disabled 占位 | 迁到工作流区域，随迁状态、回调、样式，不重写控件内部业务 |
| graph 原请求、configuration 原请求、management 原请求三类横幅 | 归工作流，保留原核实与迟到响应保护；T5 复制 pending 由本域通道展示 |
| legacy 原请求/无法解析旧记录横幅、全局 ErrorToast、项目导航/容器 | 留项目，旧记录不混成新工作流 unknown |
| 配置 application / SDK / 工作流激活与目录启动 | 代码归工作流装配入口；项目调用该入口，不能把业务协调散留 App |
| 扩展 host/挂载环境、原已归域组件 | 保留现有职责，不重建通用插件平台、不重复搬写 |

`WorkbenchSidebar` 与工作流主区是共同祖先下的不同子树。工作流可提供 setup composable，由 App 的共同祖先 setup 薄调用；扩展 host 与工作流 application/SDK 的创建和 provide 要按依赖有序完成，确保两棵子树取到同一实例。不得只在 main 内 provide 导致侧栏不可用，也不得每个区域创建一套提交/核实状态机。

装配先于目录读取、首次 `activate` 及配置提交；`persistence.initialize` 的旧记录读取仍留项目。导航保护可抽取共享的本域辅助，但不改变切换、确认、放弃修改和用户结果流程。项目保留布局和装配调用不算职责失败；验收重点是业务规则、状态、watch 与 handler 是否归本域。

T4 不新增创建专用 command，创建仍复用 `definition.update` 新身份分支。回执内正式 document 接纳与创建后独立读取是两种证据；已有 `definition.read` 足够后续独立读取，不新开读取接口，不强制每次业务提交额外 GET。

### 6.4 T5：拟采用的复制公开契约

本批新增独立 `definition.copy`，authority 显式归 management，复用通用 commands；原生 operation 拟为 `graph.definition.copy`。以下是后续按本文实施的合同草案，不是已安装协议：

| 项目 | 字段与约束 |
| --- | --- |
| 原请求 | `source_workflow_definition_id, expected_source_definition_revision, expected_source_edit_sequence, target_workflow_definition_id, target_name, idempotency_key` |
| 身份/版本 | 源/目标为不同合法 UUID；两来源版本为正整数；目标名复用现有非空、最长 128 的规则；幂等键复用现规范 |
| 正式结果 | `schema_version=1, kind=workflow.configuration-copy-result, outcome=copied`；原来源 id/两个版本；目标 `workflow_definition_id, definition_revision=1, edit_sequence=1, session_id=null`；正式 `document` 与恒等 `node_id_map` |
| application receipt | accepted 明确投影复制结果的来源、版本、目标、初始计数和空会话事实，request_sha256 仍绑定完整原请求 |
| 失败/未知 | 原有明确拒绝与 unresolved 表达；不在成功 kind 内伪造 saved/unknown，不把无回执当成未提交证明 |

前端目标身份及名称在提交前固定；名称默认可沿用现有“副本”文案，但超长时在显示/捕获请求前作确定性处理，不改变已写证据的原请求。只发送来源与版本，不发送整个待复制 document，也不从选中旧会话的固定修订替代 current。发生来源冲突先刷新并由用户重新发起，不自动改版本重试。

目标必须没有任何正式定义/current 或冲突管理记录；若身份已存在，明确冲突，不能走更新分支覆盖。内部 node/edge/object/event/control 引用保留且自洽，外部资源/包保持引用。复制不新增资源存在性/安装检查，也不绕过原正式配置组合/结构校验。

**事务顺序固定：**

```text
校验请求形状与固定身份
→ 复用原配置命令事务：BEGIN IMMEDIATE
→ 先查同 operation/key 回执并比对原请求摘要
  → 命中：返回原结果，不再读取源/目标，不重建已删除目标
  → 未命中：事务内读源 current + 确切 fixed
      → 核对来源版本、正式来源、归档分支已获决定
      → 核对目标不存在
      → 深拷贝配置，改目标身份/名称，revision=1，目标 edit_sequence=1
      → 原配置校验/固定修订及 current 写入/事务内回读
      → 写复制原生回执与 application identity
→ 同事务提交；异常原样回滚业务及回执
```

来源读与目标写共用配置领域端口、同一连接/事务。不可在该事务内调用另开 store 的独立读入口，否则可能阻塞，也不能变成读后再写的竞态。只对新目标写配置，不借 `_save_configuration_update(source)` 修改或锁住源；必要时复用其纯校验/写入辅助，不通过修改源语义强行复用。

独立回执读取使用原请求加持久原结果校验，不能要求当前 source/target 仍存在、版本未变或当前 registry 仍加载原节点。源推进/删除、目标后来删除，不得破坏已提交结果核实；核实不复建任何数据。本批首次组合仍用现有工作流 registry 语义，不静默替换缺失节点/包。

**必须成套接线：**

| 层 | 需要落实 |
| --- | --- |
| 应用命令 | `COMMANDS`、参数校验、`MANAGEMENT_COMMANDS` 显式身份、服务方法与分派 |
| 原生身份 | `native_command_request` 对应原生 operation、精确原请求规范化；digest 与实际事务完全一致 |
| accepted | `application_accepted_result` 的新 kind 投影，不依赖默认字段遗漏来源 |
| 回执读取 | `graph_receipts._validate_result` 新结果分支，核对请求、正式 document、身份/版本/初始状态；复用只读原生/origin 读取 |
| 前端传输/结果 | 专用 copy adapter/domain 校验命令与独立回执、accepted 与 result 一致，不塞到只接受完整 session 的旧结果分支 |
| 证据与接纳 | 原请求先持久，随后发一次命令；结果接纳/结案分责；unknown 保留并只读核实，目录和编辑 entry 经既有版本仲裁接纳 |

### 6.5 复制请求、结果与重开

建议新复制通道使用 `owner_kind=workflow-configuration-copy`、`owner_id=源工作流 id`，复用既有证据字段和“一 owner 一 pending”索引，不改证据表/核心契约。已知正式来源可在重开时按 owner 恢复捕获的原请求；不能只把未知目标的本地 draft 当唯一核实入口。

同一来源的该复制通道提交中/待核实时不再发送新复制，结案后允许再次生成不同副本，不限制副本数量。它不套进全局编辑/运行锁，不因复制 pending 停掉源工作流，也不自动新增后端删除禁令。来源修改不改变已捕获原请求；已提交结果依原回执核实。

成功后接纳正式目标配置、登记正式目录，`session_id=null`，会话摘要为空；不会自动创建会话。发起时捕获视图令牌，仅当前视图仍对应原操作时打开目标；迟到结果只更新正确目标的正式投影，不夺取后来选择的视图。拒绝不得增加正式计数；unknown 只能显示待核实，不能宣称副本完成。先接纳正式业务结果、再证据结案；结案失败保留待核实和可重核状态，不能抹去已确认业务事实。

前述目录接纳针对首次即时结果；重开/迟后核实得到的是原创建事实，不能据此宣称目标现在仍存在。原回执 matched 后，目标当前可用性以独立摘要/`definition.read` 接续确认；已经删除、已有更新或当前不可用时，分别保留当前权威投影或显示“原复制已确认，目标现不可用”，不把历史 document 重新登记为正式现存项，不打开已删除目标。该读取在回执核实之外，不成为历史回执有效的前提；目标当前不可用不把已确认原结果改回 unknown。

已知 owner 的持久恢复与“失去目录入口的请求发现”分开：新建从未正式入目录、来源删除或其他未提供发现入口的情况继续登记范围；本批不新开全局 evidence list。新通道不能破坏既有配置/管理恢复，也不得声称所有重开场景都已覆盖。若验收要求进一步保证这些场景可在 UI 发现，按 §10 报告新流程需求。

