### 3.3 R3：G16 错误环节、传播与处理

提交事实至少分三层：执行器/服务终端 fact、节点结果结算、成功轮 checkpoint/commit；另有已提交后的通知结果。不能压成一个“成功/失败”或根据有无 `reason_code` 判断是否可再接纳。

| 当前场景 | 源码/历史观察 | 目标讨论需保持什么 |
| --- | --- | --- |
| 有确定结果，fact 尚未提交 | 原 Q16 有码与无码异常导致不同候选保留；当前 [runtime_hosting.py:298](../../backend/src/phase1_agent/runtime_hosting.py#L298) 等仍依错误码决定 | 确定结果是否保留、身份是否有效与错误码分开 |
| fact 已提交，返回确认丢失 | Host 在成功确认前保留 envelope；[runtime_fact_store.py:38](../../backend/src/phase1_agent/runtime_fact_store.py#L38) 对准确身份和完整相同内容幂等，不同内容拒绝 | 同一事实不得重复插入；不能据此允许任意业务重放 |
| 终端 fact 已提交，节点/轮结算未完成 | [graph_execution.py:520](../../backend/src/phase1_agent/graph_execution.py#L520) 保存可用的原结果恢复依据；[graph_service.py:1312](../../backend/src/phase1_agent/graph_service.py#L1312) 仍按 reason_code 参与分类 | 原结果、原 basis、原 owner/fence 与结算层次分别记录 |
| 节点结果已提交，通知失败 | 现有 result_committed_notification_failed 分支 | 业务事实保持；不能再执行业务来补通知 |
| 无确定结果或依据缺失 | 现行拒绝盲目再接纳，继续调用要求同进程准确候选和状态 fence | 不自动重跑 Agent/模型/工具，不凭错误类型发明结果 |

用户订正：**先明确错误产生的环节和责任，再按错误类型处理；不是 Agent 的问题，就不重走 Agent。** 再次接纳只是分类后的一个分支，不作为 G16 的全部目标。发生位置与已产生的业务效果分别表达，不能只把异常换一套名称。

| 错误环节 | 责任与接收方 | 处理边界 |
| --- | --- | --- |
| Agent 生成的工具参数违反契约 | 调用内容问题，返回当前 Agent 明确的参数错误 | 不重启整段 Agent；不把工具/环境错误伪装为参数错误 |
| 参数正确而工具/依赖执行失败 | 工具或依赖错误，按工具调用通路返回 | 不归责 Agent；是否允许再调用另由工具契约决定 |
| 工具可能产生效果，但返回结果无法确认 | 向 Agent 返回准确的“结果未知”错误，保留核实依据 | 返回错误不附带自动重试许可；未知副作用不能重复执行 |
| Agent 输出内容本身违反输出契约 | 输出内容问题 | 与合法结果的落盘/传递失败区分，具体输出处理沿该契约 |
| Agent 已完成且输出合法，保存/接纳或后续节点失败 | 由实际失败环节向调用方/用户表达 | 保留原结果，只处理相应环节，不重走 Agent/模型/工具 |
| 已提交业务后的通知失败 | 通知错误 | 保持业务已提交事实，不转成业务重放 |

有限再次接纳沿已讨论方向：人工显式动作，同进程、准确 owner/原 basis fence、完整原结果、接纳端可识别精确重复；明确身份/权限/内容违约仍拒绝。先限现有真实 retained 路径，不承诺所有包/服务都具备恢复能力。先形成“环节/责任/确定结果/提交层次/返回对象/允许动作”矩阵，再确定内部表示与必要契约接线；不预先新增公共成功枚举或通用错误平台。

步骤：按上述六类追踪错误产生和传播 → 复核当前九场景及提交层次 → 固定目标差异矩阵与接纳端可信证据 → 最小内部分类和错误返回接线 → 验证各环节单独处理及已完成部分不重跑。候选 `runtime_hosting.py`、`graph_execution.py`、`graph_service.py` 及必要工具/Agent/服务适配；先列实际消费者再定直接影响面，具体扩围先报告。保留独立 fact 事务 [configuration_data.py:314](../../backend/src/phase1_agent/configuration_data.py#L314)。

验收不只看 code：先验参数错误正确返回 Agent、工具错误不错误归责、结果未知不导致自动重发、合法 Agent 结果后的故障不重走 Agent；再独立重读临时库，核对 fact/节点/轮记录、候选、envelope/hash、模型与工具调用计数。覆盖提交前回滚、提交后确认丢失、节点投影失败、最终 checkpoint 失败、通知失败；再次接纳不重驱动内核、不改变原结果、不同内容冲突、fence 改变拒绝、重开无 continuation 拒绝、多恢复来源冲突保持。

### 3.5 R5：Q8 请求证据

Lead 与 B 路复核的三事务：证据 write 的证据行、证据操作回执与 origin 同事务；业务由原领域事务提交业务事实/业务回执；resolve 独立更新证据状态并写结案回执。不能把统一入口解释为跨三次调用的原子提交。

| 事实 | 影响与本批处理 |
| --- | --- |
| [request_evidence.py:154](../../backend/src/phase1_agent/request_evidence.py#L154) 优先回放原 write 回执 | resolve 后重放仍可返回旧 pending 快照，是冻结回执现行契约；当前状态应重读，不能直接改回执为当前值 |
| [resolve_evidence](../../backend/src/phase1_agent/request_evidence.py#L211) 不核查成功业务回执 | verified 表示确定结论，包含明确拒绝；不是业务成功，不能偷偷收紧为“必须业务成功” |
| 证据确认失败时前端不派发业务；业务确认而结案失败继续锁定 | 分开“留证未知”和“业务未知”；只读核实不重发 |
| PK 与 pending 部分唯一索引，加 BEGIN IMMEDIATE | 同库基本竞争约束已存在；实例 RLock 不是跨进程业务协调，完整组合仍未验 |
| 单请求 canonical bytes 上限 3,900,000；无总量/TTL/自动清理 | 规模边界而非已复现容量事故；本批先用合成数据测有界读取，不删除历史证据 |
| owner 读取解码该 owner 全部历史 | R4 摘要与旧 owner 详情分开；坏历史记录策略不能靠静默跳过处理 |

推荐 R5a 先补有限组合，不改以上已定契约：留证插入后回滚；留证提交后丢确认且业务零发送；业务提交丢确认后 receipt matched；明确拒绝可结案；resolve 提交前回滚/提交后丢确认；**resolve A → 新 pending B → 回放旧 A write → 当前读取仍为 B**，不重发 A、不解锁 B；同 owner 不同 key 竞争及异摘要冲突；单请求限制边界与有界历史读取。

同库双连接和隔离双进程测试只操作全新临时库，不启停既有服务。不得把其通过扩大为跨进程运行恢复。容量检查先记录合成条数、字节和读取范围，不自定业务配额或性能承诺。新建/孤立 owner 的发现由 R4 完成，R5 不再建另一目录。

若组合揭示实际消费者把冻结回执当当前状态，提出局部“重读当前证据并核对准确身份”修正；不得为通过测试改回执历史、合并事务或自动归档。TTL、配额、删除、resolve 强关联业务成功、跨进程 continuation 均属于新增规则，触发 G-EVIDENCE 停报。保持现有规则无需重新询问用户。
