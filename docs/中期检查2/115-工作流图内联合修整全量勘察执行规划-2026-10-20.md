### 3.2 主链顺序的初步地图

下图针对已阅读的普通启动与成功路径，表达后续调查起点，不代替各分支的完整时序表：

```text
运行入口 / WorkflowOperations（需要时先创建会话）
→ start / event 入口
→ 捕获本次 RunBasis
→ 原准备事务：
    会话与配置依据 → 编译参与计划 → 类型和实现核验
    → 工具帧、资源预检与服务帧准备 → prepared 记录与 chain_start
→ 准备事务提交后安排后台执行
→ chain 在 begin 事务中转为 running → 装配已保存配置、状态和输出
→ 执行期编译 / 符合条件时复用保留结果
→ 需执行图时取得执行器宿主
→ 按真实边推进节点：
    输入装配 → 原生或宿主调用 → 结果核验 → 节点接纳
    Agent 内部允许多次调用已准备变量工具，每次写回独立接纳
→ 按结果分支完成结束处理
→ 普通 round 成功时完成适用的共同结算
→ 状态通知与运行条件对应的资源释放 / 暂停保留
→ 独立查询和消费者读取
```

准备就绪不等于业务已经执行，节点返回不等于已持久接纳，图完成不等于最终结算成功。event 不无条件执行普通 round 的聊天绑定和成功检查点；图外聊天命令也不等于常驻激活图节点。准确条件和提交先后必须在全量回执逐项注明。

## 4. 全量勘察范围与闭合方式

### 4.1 “全量”的含义

本次是约定图内范围的全量静态勘察，不是全项目重构、全业务算法审查或全量动态验收。与 113 号代表验收相比，本次必须先列全入口、组件调用、现有节点调用类别、持久写入和结果消费点，再逐项给出去向，不能只复查 1.0-4.0 的已通过样本。

调查清单由以下四个来源交叉建立：

1. **入口清单**：`GraphApplication` 的现行 commands/queries、图 HTTP、前端节点 HTTP/channel、运行薄口、前端 TS 与当前自有静态客户端实际调用。退役回执契约不当作现行可执行命令。
2. **能力清单**：从 [builtin_packages.py](../../backend/src/phase1_agent/builtin_packages.py)、包 manifest、注册回调和可信扩展接入契约静态追踪节点、类型、执行器、服务、信息源及前端扩展。区分可提供、默认选择、项目已保存选择和本次参与，不推断实际用户项目已启用什么。
3. **通信与写入清单**：从正式组件消费者正向追踪，再从仓储/连接、registry 查询、状态更新、写意图接纳和通知回调反向追踪，确认每个相关生产调用点所属操作。
4. **消费与证据清单**：运行返回、公开输出、对象/变量、事实、信息、manifest、检查点和前端投影各自的实际读取方；现有测试只用于索引覆盖意图及副作用。

清单至少标明“本次图内主干、必要交接、允许保留、图外范围、退役/仅测试、待确认”。按路径去重，不以每个内部函数或每个组合建立矩阵。同类节点可按共同调用方式归组，但组内现有导出须有身份及差异去向；新增发现的自有调用点必须回填清单。

动态生成或外部插件内容无法仅凭静态代码还原时，记录可信接入口、可见声明、限制及未知范围；不得装载用户插件、构造服务或执行注册回调来补齐。影响核心结论的未知保留为受限结论或待补调查，不写成全量已证明。

## 8. 证据要求与勘察完成标准

本轮及后续静态勘察均不默认执行 pytest、前端测试、类型检查、构建、服务、浏览器、HTTP listener 或模型请求。测试索引可从 [113 号第 8 节](113-工作流1.0至4.0阶段中期验收执行规划-2026-10-20.md#8-定向验证与证据要求)、[114 号](114-工作流1.0至4.0阶段中期验收与整体收口回执-2026-10-20.md)及 [测试说明](../TESTING.md)接续，再按新增调查的操作补当前有效测试意图。没有覆盖时登记缺证，不新建测试或恢复旧矩阵。

回执按四种证据分别陈述：本次静态调用事实、与当前源码身份对应的历史实际结果、仅阅读得到的测试意图、尚未确认的行为。历史通过数不转记本轮，不把“全量勘察”写成“全量测试已通过”。

全量勘察完成应满足：

1. 四类来源清单有明确调查边界，每个相关现行入口、节点导出类别、生产写入/状态点和消费者都有归属或明确待确认；没有未说明地漏掉另一客户端或特殊入口。
2. O1-O10 实际存在的操作已给出调用链及主要分支，公共步骤与特有条件能区分；不存在的行为不补造。
3. 正式组件的实际调用权、依据和数据/状态权威清楚，普通绕行、内部适配、只读及图外交接分别有依据。
4. 两项已批准移交准确记录，新发现问题、未验意图、保留项和扩大范围的建议不混成一个“全部待修”清单。
5. 完整链条与证据表能说明 1.0-4.0 如何接上、哪些是静态接线、哪些曾被运行验证、哪些仍缺证；核心未知未核清时限制相关结论。
6. 已提供用户可以逐项决定的修订候选及依赖，没有在回执中默认选择新机制或宣称产品转正完成。

勘察完成不要求问题已经修好，也不以“没有 High 级问题”替代清单闭合。需要补动态证据、改变行为或进入图外业务内部时，先报告目的、范围和影响，获准后另行安排。
