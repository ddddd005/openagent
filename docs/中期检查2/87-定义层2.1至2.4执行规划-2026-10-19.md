## 4. 目标交互与模块拆解

以下位置表示职责，可以由函数或小模块实现，不要求一行一类，不建立全项目万能入口。

| 位置 | 负责 | 保持分开的内容 |
| --- | --- | --- |
| 工作流侧加载接口 | 受理准确包需求，接收加载结果及诊断 | 不承担项目安装、下载、启用配置和版本选择业务 |
| 临时本地来源适配 | 提供明确的可信包集合，调用现有加载器 | 不扫描任意目录，不在来源缺失时改用默认全集 |
| 定义注册接口及注册模块 | 公共形状、来源、类别分发、依赖和既有冲突规则的协调 | 不把定义视图注册成第二份执行实现 |
| 类别适配 | 复用该类定义校验、准确引用、只读解析及必要规则调用 | 不把所有对象压成一个没有分类约束的字典 |
| 定义查询接口及解析模块 | 准确查询，解析来源和工作流引用，返回只读消费视图 | 不在读取时临时装载包、补造持久证据或修改配置 |
| 定义层数据接口 | 提出有限的定义证据及来源依据需求 | 不取得表名、SQL、连接或任意事务回调 |
| 数据管理入口 | 将领域请求分发到相应独立数据模块，协调已定事务 | 不承揽定义合法性、配置策略或运行准备规则 |
| 定义数据模块与仓储 | 保存、核验及读取本批确认的定义持久记录 | 不直接调用配置仓储或会话仓储 |
| 配置数据模块与仓储 | 读取准确工作流修订及其引用依据 | 不维护类型定义目录，不在读取时重新推导配置业务 |
| 消费者的本层模块 | 使用定义完成配置、展示或执行准备 | 不绕接口自行维护另一份定义权威 |

```text
工作流准确包需求
→ 工作流侧加载接口
→ 临时本地来源适配（未来替换为项目级来源）
→ 现有加载器及类别注册适配
→ 本批定义注册与查询边界
    ├─ 已注册包定义 → 只读消费视图
    └─ 定义层数据接口 → 数据管理入口
                          ├─ 定义数据模块 → 定义证据仓储
                          └─ 配置数据模块 → 准确固定修订及引用依据
→ 配置、编辑器等消费者
```

数据管理入口分别分发两类读取。定义业务在上层组织所需关系，数据仓储之间不串接调用；共享 SQLite 和既有事务基础不因此要求物理拆库。

## 5. 前置一：统一格式、注册规则与存取边界

### 5.1 最小局部契约

先形成一份包含下列信息的契约草案。这里明确要回答的问题，不冻结 JSON 键名、方法签名或新表。

| 信息 | 需要确定的含义 |
| --- | --- |
| 类别 | 首批节点、数据类型及类别扩展的识别方式；未知类别明确报错 |
| 准确引用 | 保留现有 component、type、scope 等引用，不将全部对象强改为同一种版本号 |
| 来源 | 包身份和版本、宿主来源或工作流准确修订；区分维护方与共同提供者 |
| 记录格式版本 | 表示封套和正文如何解析，分别于包版本、类型 schema 版本、工作流修订和编辑序号 |
| 分类正文 | 哪些属于来源定义，哪些是按实例配置计算的结果，哪些是展示或可用性信息 |
| 依赖 | 明确的定义引用及其解析方式；不默认递归加载缺失来源 |
| 持久化 | 哪些记录已有、哪些确需新增、保存的权威性质、读取与登记的事务要求 |
| 结果与错误 | 接纳、查询和冲突的可诊断结果；沿用现有错误，不静默覆盖或自动换版本 |

统一公共流程和分类扩展约定，优先用既有定义对象和校验器作适配。新增同类定义复用该类别；新增类别补充必要 schema、校验和解析适配，不要求修改每个消费者，也不能承诺任何新语义都无需代码。

### 5.2 必须保留或先确认的现有例外

- `register_shared_data_type` 允许多个包提供字节一致的准确数据类型；“来源”不能简单等同于只有一个包的所有权。
- `NodeRegistry.update_declarations` 允许同一准确节点版本在受信任作用域内只更新 `checkpoint_save`、`execution_class`。不能用“所有同版本全文必须不变”的新规则默默取消它；本批适配先保留，若持久化要求改变该语义则提交用户决定。
- `NodeDefinition.to_dict()` 含派生配置策略，目录还含 `executable`、`availability` 等可用性信息。内容摘要、展示正文及运行可用性须分别界定，不能直接给整条目录行取摘要后当作永久定义身份。
- 定义描述和实际实现绑定分别传递。函数、factory、validator 等不进入可序列化正文，也不能由 JSON 反向恢复实现。
- 变量定义的载体和初始化仍未定；本批不以对象绑定或变量注册节点替代这一决定。

前置完成标准：共同字段的含义、首批类别及适配方式、版本与冲突语义、来源维护权和持久范围已形成可施工的局部契约；影响这些事项的待决项先解决。普通命名、私有函数拆分和文件布局可由落实方在已定契约内选择并记录，不要求逐项重新授权。

## 6. 前置二：极简真实包加载适配

### 6.1 样本与真实逻辑

建议参考 [test_capability_packages.py](../../backend/tests/test_capability_packages.py#L23) 中的受控包模式：一个简单自定义节点、一项数据类型、明确的包版本及必要依赖，实际经过 `CapabilityPackageLoader` 和 `HostRegistration`。新样本须显式声明 `manifest.exports` 中的数据类型和节点导出，验证实际登记与声明一致。需要动态输入声明时另选已有内置代表，不把所有特性塞进一个合成包。

测试必须实际经历：

1. 给定明确包集合和准确需求，进行依赖解析。
2. 执行包注册回调，核对实际注册与 manifest 导出一致。
3. 经本批定义接口查询注册结果，并核对来源和准确引用。
4. 由既有执行路径调用一个无模型、无外部副作用的实现，产生可断言结果。
5. 注入缺依赖或注册失败，验证诊断及原有结果不受半批注册污染。

仅将 registry 直接注入测试、mock 一个加载结果或返回静态目录，不能证明这个适配已接通。

### 6.2 占位的边界和未来替换

本地来源适配用于本轮架构测试，不向生产默认包集合加入测试包，不新增公开安装入口、插件路径扫描、下载、热更新或项目包管理 UI。不因接入极简适配而迁移现有项目启用包配置。

工作流侧保持“准确需求 → 加载结果与诊断”的职责边界。项目级来源接入后，替换本地来源和装配依赖，继续向同一注册、定义及实现消费边界提供内容。包接入宿主的装载注册，与本次工作流实例和 Agent 工具的运行准备分别记录；前置样本不证明 75 号同等加载已全部实现。

现有 `GraphWorkflowService` 初始化同时组合来源、读取选包、加载和核验类型证据。首批优先通过明确装配参数接入测试适配；若必须改造生产初始化或管理选包事务才能接通，先报告必要性及影响，不能以抽出通用加载器为由重构全部宿主。

## 7. 首批对象、存取及依赖方向

| 对象 | 首批建议 | 维护与存取边界 |
| --- | --- | --- |
| 节点类型定义 | 一项真实包节点，以及配置消费需要的已有内置节点 | 来源维护；经类别适配注册、查询；实现绑定仍取自可信注册 |
| 数据类型定义 | 一项受控数据类型，复用已有证据记录 | 现有注册和版本语义保留；证据经独立定义数据模块存取 |
| 工作流内关系 | schema 3 固定修订中的实例身份、准确类型引用和 package lock | 经配置数据读端口提取；是实例使用关系，不冒充新的节点类型 |
| 实例配置与当前覆盖 | 仅在配置消费者确需时读取 | 仍由配置管理维护；不复制到定义证据仓储 |
| 其他注册类别 | 保留既有接口，列出后续适配清单 | 首批未迁移不能宣称全部定义统一完成 |
| 包来源持久记录 | 先提交必要性、归属与格式 | 现有类型证据不含完整包来源；不自动新增通用表或改旧证据摘要 |

读取工作流来源时，优先使用 `fixed_document(workflow_id, revision)` 的准确持久依据。不要让定义解析回调当前配置合成：`_compose_configuration` 本身需要查询节点定义，这样会形成“配置合成 → 定义查询 → 当前配置合成”的循环。

持久化落实要求：

- 既有类型证据的 declaration 和 digest 不重写、不补来源后重新计算，不以新封套改写历史证据。
- `TypeContractStore.get` 与可能写入的 `check/register/check_registry` 分成读取和登记核验意图；普通定义查询不因此建立缺失证据。
- 首次证据写入沿用已有所属保存事务；不在其外先提交证据，也不在同一命令内另开存储导致自锁。
- 复用加载器暂存和旧冻结结果的隔离。持久证据失败时不把本批新目录宣告为可用，不自动重新登记或覆盖冲突记录。
- 临时本地装载失败、持久提交失败及注册结果发布失败分别记录。若现有事务和装配不足以保持本批结果一致，先提交局部时序方案，不引入后台补偿、自动重试或双写。

有一处需要落实方重点核对的现有时序：[CapabilityPackageLoader.load](../../backend/src/phase1_agent/capability_packages.py#L465) 在返回前更新加载器内部的历史契约字典；[configure_capability_packages](../../backend/src/phase1_agent/graph_platform.py#L85) 随后才进入数据库事务并持久提交，成功后替换服务的 registry。按静态代码，持久提交失败时服务仍保留旧 registry，但加载器的历史契约字典已经改变。本轮未复现该失败，不能将它描述为已验证缺陷，也不能宣称整个加载器状态随数据库回滚。新路径须在持久成功后才发布消费者可见结果；如需改变 loader 的准备/提交契约或既有项目管理行为，先报告必要性、范围及方案，由用户决定。

“独立重读”与“严格只读连接”分别解释。普通 [SqliteStore](../../backend/src/phase1_agent/storage.py#L49) 打开时仍执行初始化事务和 DDL；本批在临时库关闭重开读取，不等于 `mode=ro` 或 `query_only`，不得替代专用只读回执路径。活跃写命令中读取依据应绑定原有有限数据会话，不能另开普通存储，被自身的 `BEGIN IMMEDIATE` 阻塞。

已知范围外调用还包括 [session_objects.py](../../backend/src/phase1_agent/session_objects.py#L52) 和 [global_resources.py](../../backend/src/phase1_agent/global_resources.py#L122) 直接使用类型证据仓储。本批记录这些残余路径，不连带迁移会话或全局资源业务，也不据首批接线声称所有证据调用已统一。
