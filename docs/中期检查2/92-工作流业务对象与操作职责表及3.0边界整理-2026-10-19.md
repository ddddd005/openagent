## 1. 最新决定与阅读口径

本篇对下列事项接续或订正早先讨论；未涉及的来源维护权、数据归属、事务和安全规则继续保留。

| 事项 | 当前已确认的口径 |
| --- | --- |
| 3.0 内部范围 | 运行依据消费、图与调用整理、执行数据通路、运行控制、配置求值及节点自由度 |
| 单独立项范围 | 外层大功能顺序注册、外层调用粒度，以及明确纳入专项的大交叉重构；不以“跨层”二字将 3.0 必要工作全部排除 |
| 必要接线与迁移 | 完成 3.0 目标所需的真实接线和局部职责迁移仍在 3.0 内，不能只建空接口，把实际消费全部推迟 |
| 失败政策 | 抛错即中止当前业务调用链并显式报错，不默认继续后续业务；首版不引入可忽略失败分类 |
| 内置顺序保护 | 未来顺序注册首版允许插件在开放位置注册，不允许覆盖或修改内置位置 |
| 业务整理先行 | 区分静态对象、一次执行过程、执行记录和完成事实，避免因沿用同一个词而扩大职责 |

因此，[68 号第 7 节](68-工作流运行与能力调用契约-2026-10-17.md#7-能力失败和运行失败)原先列举的多类失败策略，不作为当前首版必须建设的分类机制；90、91 号中仍标为待讨论的失败阻断问题，按本篇最新决定解释。91 号的数字顺序方向保留，但其机制建设已从 3.0 移到单独项目。

“3.0”指 [70 号](70-工作流配置起步与逐层接入执行顺序-2026-10-17.md)中定义消费之后的执行接入施工批次，不是 65 号原总体规划中的第三个里程碑。本篇不据此冻结 3.1–3.4 的步骤编号、文件拆分或新方法签名。

## 2. 业务对象表

以下是业务含义和责任口径，不是新实体清单。一个现有结构可以承载多个概念，同一概念也可以由多个现有模块协作完成；不要求一行对应一个类、表、服务或独立状态机。

### 2.1 静态资产、定义与配置

| 对象 | 表达什么 | 身份、来源与维护方 | 不应混同 |
| --- | --- | --- | --- |
| 工作流（作为资产） | 整体承载对象，包括工作流图、实例配置、定义与资源引用，以及适用的运行规则 | 现有身份为 `workflow_definition_id`；其自有配置由配置管理维护，包能力和项目资源仍由原来源维护 | 不是单独一张节点图，也不包含所有会话的当前值、运行结果或所引用能力的私有代码副本 |
| 工作流文档 | 当前代码中保存、传输工作流配置及依据的具体文档 | 含 `revision`、节点、边、配置、绑定和包锁等；适用时另有 `edit_sequence`，沿用既有接纳规则 | 不是纯拓扑；文件名或函数名带 `graph`，不表示正文只有图关系 |
| 工作流图 | 工作流内部节点实例及数据、控制关系构成的结构 | 当前由文档中的节点和边等表达；节点引用其类型和实例配置 | 不承揽工作流启动、最终结算、全部图外命令；本篇不要求从现有文档物理拆出一份纯图对象 |
| 节点类型定义 | 一类节点的配置结构、端口、约束及必要调用要求 | 准确身份为 `component_id + component_version`；来源模块或包维护，定义目录提供只读视图 | 不是某个画布实例，不是实现函数本身，也不是一次节点调用 |
| 节点实例 | 工作流中对某种节点类型的具体使用及配置 | 现有身份为 `node_binding_id`，绑定准确类型版本；由配置管理维护 | 不是共享能力实现，也不是运行期间自行常驻的主体 |
| 能力来源与能力实现 | 可供多个工作流及允许的入口复用的真实功能 | 由对应模块、节点包或能力插件包提供；使用者引用，不复制维护权 | 不等同于菜单分类、画布实例或代码字段 `NodeDefinition.capabilities`；不预定一能力一包或一能力一工具 |
| 注册结果与定义视图 | 已有定义及可信实现的登记结果，以及供消费者取用的只读解析结果 | 现有 `NodeRegistry` 承载注册关系，`WorkflowDefinitionCatalog` 提供首批查询；来源继续维护定义 | 查询视图不是第二份可独立编辑的定义权威；“已注册”也不等于某个工作流已经准备完成 |
| Agent 工具入口 | 向 Agent 暴露已绑定真实能力的调用入口 | 绑定、共同调用及同等加载原则按 [75 号](75-工作流能力资产与节点工具统一调用接续规划-2026-10-18.md)；具体接口尚待该路径规划 | 不继承其他节点实例的配置、引用或身份，不因有工具描述就具有真实执行能力 |

工作流自有内容的维护与引用来源的维护分别描述。例如，工作流可以保存一个节点实例及其包版本引用，但不因此取得修改包定义的权利。

代码中的 `NodeDefinition.capabilities` 用于相应能力要求与授权检查；本篇所说“节点承载可复用能力”是业务含义，不能把两者直接合成同一种注册对象或沿用同一字段安装新协议。

### 2.2 会话、执行依据与调用记录

| 对象或过程 | 表达什么 | 当前身份或实现对应 | 数据及完成边界 |
| --- | --- | --- | --- |
| 会话 | 数据的归属与隔离边界，绑定工作流和固定定义修订 | `workflow_session_id`，记录活动 `chain_run` 等引用 | 可包含多次调用及不同种类的数据；不建立包揽所有会话业务的功能性会话层 |
| 本次运行依据 | 本次确定的工作流修订、采用的配置、输入、绑定注册结果及必要引用 | 当前分布于准备文档、冻结 `run_registry`、节点运行配置及相关准备记录 | 这是需要统一消费的依据集合，不是本篇新建的统一快照表；也不表示冻结全部项目资源和后续模型请求 |
| 图执行计划 | 根据本次图和定义编译得到的参与范围、顺序、输入关系及必要定义 | 现有 `GraphPlan`，当前没有独立持久身份 | 是派生计划，不是静态图、全部外层调用顺序或运行结果；不据此新建耐久计划实体 |
| 一次工作流调用 | 对一个工作流发起执行后，由准备、图执行及必要结束处理组成的整体过程 | 当前由多个函数和记录配合；不新增 `flow_run_id` | 用于解释流执行范围，不承诺当前已有一个覆盖该概念的独立记录 |
| 图执行 | 按图执行计划推进参与节点，处理节点输入、输出、接纳及中断位置 | `execute_graph`；现有 `chain_run` 保存目标、顺序、进度及相关状态 | 图完成不自动等于共同结算成功；`chain_run` 还承载部分外层收尾状态，不把它硬解释成纯图或纯流实体 |
| 节点调用 | 某节点实例在本次执行中的一次实际调用 | 普通图路径以会话、`chain_run_id`、`node_binding_id` 和节点 `run_id` 关联，接口常称 `node_run_id` | 实例可被多次调用；一次调用的成功返回与持久接纳分别表达，不强制记录其每个内部步骤 |
| 节点结果与运行数据 | 已有明确边界的输出、读写依据、事实、错误和进度 | 现有 `node_run`、`workflow_output`、运行事实及所属领域记录 | 归会话关联的运行数据；节点、执行与具体功能各自维护业务，数据管理完成相应存取 |
| 更大的一轮业务调用 | 业务上从请求到结束的范围，可能包含数据操作、一次工作流调用及其他功能 | 目前按具体业务表达，不预设统一身份或固定层级 | 不必等于一个 `chain_run`，也不要求新建 run / 轮次 / 批次三层结构；准确外层粒度由单独项目处理 |

“运行图”若仅指编译所得结构，后续优先写“图执行计划”；若包含运行位置和已接纳结果，应把这些运行状态另外说清，不用一个词同时替代计划、进度和记录。

## 3. 执行与业务职责表

执行层是职责范围，内部包含流执行和图执行；不要求因此建立两套 Runtime。节点具体业务仍由功能或节点实现负责，宿主负责其执行承载。

| 责任位置 | 负责什么 | 不负责什么 | 当前实现参照 |
| --- | --- | --- | --- |
| 工作流基础支持 | 受理运行相关启动、控制、状态与错误查询，明确工作流目标和会话指向 | 不组织上下文内容，不承担项目创建、归档、删除等管理业务 | `WorkflowOperations` 等运行入口 |
| 流执行 | 协调一次工作流调用的准备、图调用、必要结算、控制和结束；使用既定外层调用关系 | 不计算图内业务拓扑，不实现所有节点业务；当前不安装外层顺序注册机制 | `GraphWorkflowService` 的准备、启动、后台执行和控制等现有配合 |
| 图编译与图执行 | 从图和本次依据计算参与范围与顺序；装配输入、调用节点、衔接结果接纳并推进或中断 | 不决定项目级业务顺序，不允许节点自行指定后续消费者 | `GraphCompiler`、`execute_graph` 及接纳回调 |
| 节点或具体能力实现 | 接受调用、获取输入、实现自己的功能、形成输出或回报、失败抛错；持久数据明确存储、引用和写回 | 不在未激活时自启动，不控制后续消费者，不强制暴露内部每一步 | 原生 callable、注册执行器和各功能模块 |
| 执行器宿主 | 承载具体执行器，关联调用身份、控制请求、事实及必要资源生命周期 | 不等于整个执行层，不取得全部工作流业务所有权 | `RuntimeHost`、`GraphRuntimeHost` 的相应配合 |
| 配置管理与定义目录 | 前者维护正式配置及修改规则，后者提供来源明确的定义消费结果 | 不把运行当前值当成配置；定义查询不接管包实现的维护 | 已有配置功能接口、定义查询接口 |
| 数据管理 | 分领域承接数据读取、写入、归属和版本条件、事务及存储适配 | 不重新裁决全部节点业务；内部领域模块不相互调用其他领域仓储 | 已有配置、定义通路；执行领域仍需接线 |
| 前端节点操作入口与页面连接 | 入口转交相应工作流命令；连接展示数据并传递状态变化 | 页面存在、连接存在不等于节点激活，不构成常驻业务执行器 | `BoundFrontendNodeOperations`、`FrontendNodeConnections` |

“流执行”指一次工作流调用的整体执行协调，不是模型 token 的流式输出，也不包揽任意更大业务。`Runtime` 在旧文档中是较宽的执行统称，当前源码中的 `runtime.py`、`RuntimeHost` 及 `GraphWorkflowService` 又各有具体含义。后续描述任务时优先写清“流执行协调、图执行、执行器宿主或 Agent 内核”，不只凭文件名判断层级，也不把 Agent 内核改归通用执行层。

## 4. 操作职责表

本节只列已经有意义的框架动作和业务动作，不要求节点作者按此穷举内部步骤。表中目标职责不表示现有路径均已完成迁移；列入候选、重roll、分叉等操作是为了辨明责任，不自动将这些能力的全部内部迁移纳入首批 3.0。

### 4.1 从入口到图执行

| 操作 | 谁发起、谁协调 | 消费依据与数据方向 | 完成含义和边界 |
| --- | --- | --- | --- |
| 保存可调输入或修改配置 | 工作台、前端节点页等入口发起，配置功能接口协调 | 定义校验及配置业务 → 配置数据接口 → 数据管理 → 配置仓储 | 正式配置保存和接纳成立；不是已经调用节点或启动工作流 |
| 受理启动与确定目标 | 运行入口受理，流执行协调；必要的会话创建沿用既有实现 | 准确工作流、会话、修订、输入及既有门禁 | 请求受理或返回 `prepared` 不表示后台运行完成 |
| 取得并绑定运行依据 | 流执行的准备职责协调 | 经所属数据接口读取配置；使用本次绑定注册结果取得定义与实现关系 | 本次依据明确，缺失或不符报错；不回退服务当前 registry |
| 编译图执行计划 | 流执行调用图编译模块 | 本次图、采用配置、输入及同源定义 → 图执行计划 | 确定参与范围和节点顺序；不取代外层大功能调用顺序 |
| 准备必要服务及执行环境 | 流执行协调，宿主及具体功能按要求准备 | 消费本次绑定注册结果、计划及必要资源引用 | 所需调用条件就绪，不提前执行业务；不要求每次启动重新导入全部包 |
| 推进图执行 | 流执行调用图执行模块，后者推进图内调用 | 计划、已接纳前缀、输入输出及控制信号 | 返回图执行结果或暂停、错误；尚须处理当前调用适用的结算 |
| 调用节点与求值 | 图执行或约定能力调用渠道发起，节点实现自身功能 | 本次固定配置、上游输入、明确的数据引用；按功能实际使用时求值 | 完成该次调用的输出或抛错；不将输出解释为持续变化的活跃值 |
| 读取或提出更新领域数据 | 节点或功能发起，执行侧承接约定访问与接纳 | 所属功能的数据接口 → 数据管理 → 对应领域模块和仓储 | 返回真实读取或写入结果；写入意图本身不等于已提交 |

Agent 工具同等加载及共同调用继续按 75 号约束。该路径尚未确定的绑定格式、具体准备步骤和连续写入可见性，不由上述表格补定，也不把完整工具迁移自动纳入首批 3.0。

### 4.2 接纳、控制与图外命令

| 操作 | 谁协调、谁维护业务 | 消费依据与数据方向 | 完成含义和边界 |
| --- | --- | --- | --- |
| 接纳节点结果 | 执行侧衔接节点结果与数据管理，各领域保留业务规则 | 按既有节点接纳边界保存输出、约定写入和运行进度 | 接纳成功后才能把相应结果作为已完成前缀供下游消费；不要求所有节点自行提交 SQL |
| 暂停、继续及关闭 | 运行入口受理，流执行协调图执行与宿主 | 准确执行身份、状态及既有控制条件 | 请求暂停与已经到达暂停点分开；继续、结果重接纳及已有受限重做不混同，不扩大可重放范围 |
| 共同结算 | 流执行协调，聊天、检查点等功能执行各自规则，数据管理保持共同事务 | 保存本次适用的运行终态及结束依据；普通业务轮成功路径还共同处理会话提交、成功检查点，并在存在相应聊天调用时绑定候选 | 必要结算成功后才能报告该范围成功；不是每个普通调用都有聊天候选，也不是事件调用无条件生成候选或检查点 |
| 抛错中止 | 当前功能报告错误，执行协调者停止当前业务调用链，入口对外传递 | 保存可确认的事实和诊断，保留此前已接纳结果 | 不继续后续业务，不因旧结果已提交而伪称全部成功；必要错误记录和资源清理不是继续业务 |
| 重roll | 页面或业务命令经工作流聊天操作入口发起，重roll业务负责基线和候选规则 | 读取同轮规定基线及输入，重新进入运行准备和图执行 | 是受管理的新一次计算，不是前端节点常驻调用，也不是任意失败自动重放 |
| 选择候选 | 工作流聊天功能校验并执行 | 候选、对应检查点及会话版本依据 → 恢复选中计算状态并保存选择 | 选择结果按已有事务成立，不自动等于启动新图执行 |
| 分叉 | 工作流对应能力校验并执行 | 准确检查点或候选依据 → 建立目标会话及相应数据、引用 | 源会话不因分叉被改写；建立分支与执行目标工作流分开 |
| 状态读取与通知 | 基础支持、查询入口及前端连接读取或传递 | 消费已有状态、结果和诊断 | 通知不是持久化的替代物；通知失败不抹除已经提交的事实，也不授权重新执行业务 |

图外命令可以在图未执行时通过合法入口被调用，但仍服从各自会话、状态和版本门禁。“图未运行”不等于所有操作均可执行，也不等于存在一个脱离管理而激活的节点。

## 5. 完成、状态与失败不能混用

| 事实 | 能说明什么 | 不能据此说明什么 |
| --- | --- | --- |
| 配置保存完成 | 正式配置变更已按规则成立 | 当前已有运行已热更新，或某个节点已执行 |
| 启动请求返回 | 启动请求已得到对应受理结果 | 图或整次工作流调用已成功结束 |
| 节点实现成功返回 | 本次具体计算或功能按其契约返回 | 所有输出和写入已由执行侧持久接纳 |
| 节点结果接纳完成 | 相应输出及约定写入已经成立，执行位置可按接纳结果推进 | 后续节点、最终结算或更大业务链一定成功 |
| 图执行成功返回 | 本次图内参与节点已走到相应完成边界 | 所有必要外层结算已经成功 |
| 共同结算完成 | 该路径要求共同成立的终态、数据和记录已经提交 | 后续展示通知必然成功，或当前之外的其他业务全部结束 |

失败规则补充：

1. 未成功运行的节点或功能向调用方抛错；执行层中止当前业务调用链，显式报告失败，不默认跳过或继续。
2. 先前已接纳内容保留。更晚失败既不自动回滚全部前缀，也不能覆盖已经提交的真实结果。
3. 错误诊断、必要资源释放及既有待确认处理不视为继续下游业务；不据此新增补偿、自动重试或回退机制。
4. 任意自定义代码抛错，不证明其没有产生外部效果。继续沿用已有准确结果和控制条件，不承诺通用回滚或自动重放。现有 `retry_acceptance`、`retry_archive`、`retry_failed_node` 等有条件的显式操作不因本篇自动取消，也不扩张为通用失败重试。
5. 首版不建设可忽略错误、可选失败能力或全节点内部结果登记。既有专用诊断保留，但不能成为新注册功能默认吞错的依据。

节点接纳后的能力输出通知、前端快照接纳，与纯展示连接的 `state_changed` 不是同一个动作。当前前一类处理失败可报告 `result_committed_notification_failed`，使运行进入不能重放的错误状态，但已接纳节点结果仍保留；不能把它笼统解释成“界面未刷新，业务可默认继续”。此处区分既有事实，不新增可忽略失败分类。

这些是确认的目标语义，不是本轮对所有现有异常路径完成了验收。

## 6. 代表链路与现有模块

### 6.1 业务关系示意

```text
运行入口
→ 流执行：确定目标与本次依据
→ 图编译：形成图执行计划
→ 流执行与宿主：准备本次计划所需环境
→ 图执行：按计划调用节点、衔接接纳并维护进度
    → 节点或执行器：实现具体业务，返回输出或错误
    → 数据管理：分领域完成约定存取与事务
→ 流执行：按当前既定调用关系完成必要结算与结束
→ 状态查询或通知展示
```

这是职责示意，不是冻结准备函数的准确调用顺序；当前仍沿用现有外层函数配合，图编译与环境准备的具体依赖须在真实路径规划中核对。更大的业务可以在一次工作流调用前后另有功能操作，不把这幅图扩成包办所有项目业务的执行系统。

```text
节点页候选 / 重roll / 分叉请求
→ 对应工作流操作入口及门禁
→ 所属能力模块
→ 必要时进入流执行，或仅完成本次能力操作
```

节点图执行、页面命令和通知连接是不同路径；不把页面中的每个按钮实现成激活一个图节点。
