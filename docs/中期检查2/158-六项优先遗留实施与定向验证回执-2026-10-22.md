## 3. G16 环节、责任与工具参数决定

用户在实施期间明确同意：**普通工具参数 schema 任一非法，整批零执行，错误反馈给当前 Agent，由它重新生成调用。** 已记入 [157 第 12 节](157-六项优先遗留勘察与分批执行规划-2026-10-22.md#12-实施授权与工具参数批次决定)，不把它解释为工具自动重试授权。

| 环节 | 接收方 / 本次行为 | 不得混淆 |
| --- | --- | --- |
| 普通工具 schema 参数错误 | 原批次所有工具零执行；同一 Agent 收到既有 `user/protocol_feedback`，按原预算生成新批次 | 原始 `model_result` 保留；无效 assistant 调用不进入已接纳历史，不伪造 tool result/dispatch |
| 身份、严格 JSON、未知工具、final 排他性错误 | 先完成整批协议门禁，仍走原 `protocol_error` | 参数反馈不能绕过这些门禁；不把错误批次伪装为 unknown |
| 工具明确错误 / 结果未知 | 沿原工具结果和未知 observation 返回当前 Agent，未知批次不自动重放 | 返回错误不等于授予新副作用权限；不承诺后续模型自行调用的跨批去重 |
| 合法 Agent 结果后 fact 保存失败 | 保留准确结果及原 envelope；人工显式再次接纳原 fact | fact 回滚与 COMMIT 后确认丢失独立查库；不再驱动 Agent/模型/工具 |
| 终端 fact 后投影失败 | `result_projection` / `projection`，保留准确候选；再次失败仍归同一环节 | 不是 Agent 输出内容错误；不能降成笼统接纳或持久化错误 |
| 节点 / 轮结算失败 | `node_acceptance` / `round_acceptance`，复用原候选、原依据和 fence | fact、节点、轮三层提交分别核对；缺依据/身份/权限/内容冲突仍拒绝 |
| 已提交后通知失败 | 保持原已提交事实及独立通知诊断 | 不重跑已成功业务来补通知 |

私有 `result_acceptance.py` 只在**真实 SQL 写/提交边界且前置身份、schema、fence 已过**时给持久化错误标记；不是按 `reason_code` 或错误码白名单授予再次接纳。已知接纳环节的无码程序错误可保留准确结果，但责任仍区分 projection、acceptance 与有标记的 persistence。

新 `tool_batch_validation.py` 与 schema-2 独立事实证明共同消费冻结工具定义。验证覆盖混合合法/非法批次零工具执行、同一调用后续合法批次、暂停/继续、真实离线 Agent 图、伪造反馈和将合法批次替换为反馈被拒绝。完整矩阵见本地 `backend/E3-MATRIX.md`。

交叉审阅发现并修复一项本批 P2：初版只在首次 `advance` 标记投影，显式 `retry_acceptance` 再次投影失败会误报 `result_acceptance/acceptance`。现在在 `recover_acceptance` 的实际投影/验证边界标记，不包含 terminal fact 发布；仓库回归分别覆盖消息投影、回执验证连续失败两次后成功，事实 ID、终端 fact 行数和执行计数不变。独立首轮红件保留，不改写为夹具问题。

## 5. R4 / R5 通信与证据交互

新增 management-only query `request-evidence.pending`，沿原 `/api/graph/queries` 分派。只允许 `workflow-configuration`、`workflow-configuration-copy`、`workflow-management`；不开放 provider/content/private-node 发现。

返回 `schema_version=1`、`kind=workflow.request-evidence-page`，每项只有 owner_kind/owner_id/operation/idempotency_key/request_digest/resolution=pending。limit 默认 50、范围 1–100；cursor 为精确四坐标，确定性字典序 keyset，读取 `limit+1`。不按不存在的创建时间排序。

独立 SQLite `mode=ro + query_only + BEGIN`，不构造 `RequestEvidenceService`、不迁移、不选 `request_json`；不存在库/表为空页且不创建文件，元数据损坏固定安全 500，存储不可读 503。摘要不验证正文完整性，也不据此授予业务派发权限。未知 operation 可见但不提供本入口的核实动作。

前端按摘要精确读取原证据并比对完整坐标和 digest，再装载原通道并复核实际读到的证据，然后只读 receipt 核实。发现恢复时不将历史 document/session 投影为当前状态、不复活已删 owner。复制回执也不代替目标当前读取。

R5 窄修覆盖配置、配置复制、管理三通道：

1. evidence.write 的冻结回执不再当作“当前仍是 A pending”的证据；派发前独立读取，必须准确匹配当前 pending。
2. 结案前单独核对：允许准确 A 仍 pending，或 A 已 verified 且无其他 pending，以处理 resolve 已提交但确认丢失。
3. A verified、B pending 时不清 B、不解锁、不修改原文、key、digest；陈旧 A 的业务/结案回执不能覆盖 B。
4. write、领域业务、resolve 仍是三个独立事务；发送前重读不构成读与业务派发的跨请求原子保证。

实际组合包括两真实子进程争用本批临时库同 owner（仅一个 pending）、3,900,000 字节 canonical 原请求边界及超一字节拒绝、1000 verified + 120 pending 的合成历史分页。它们证明该合成规模与返回边界，不是性能、容量配额或无限历史承诺；原按 owner 的详情读取仍读该 owner 完整历史。

真实孤立链用合成库完成保存/复制/删除及响应丢失，关闭重开后无工作流目录行仍能发现三条原证据，通过准确原回执核实结案，不复活已删工作流。前端则是受控 transport 的分段证据，不将其数量冒称浏览器端到端。

一项非阻断交互限制：从旧发现摘要核实后若 resolve 提交丢确认，第二次点击该旧摘要可能因 A 已 verified 而拒绝；刷新原请求列表后，可沿已装载通道只读核实完成本地清锁。没有自动重发业务。
