# 配置单一受理与 Store 投影影响评估

日期：2026-10-19，Asia/Shanghai。

性质：按用户“查看这样订正 Store 后会出现什么问题”的指示，对“削减 Store 正式配置权限、由配置应用统一受理、增加每工作流队列”的方案做只读影响评估。**本文没有修改产品代码或测试，没有提交、启动服务、调用模型或运行全量测试。** 三路并发调查分别覆盖 Store 生产消费者、配置应用/协议、测试与生命周期；配置协议一路的结论以本批最终报告为准。

2026-10-19 接续：用户认可先处理架构、保持现有提交互斥，后续两路 Sol 勘察及首批施工安排见 [82 号执行规划](82-配置单一受理与Store投影首批执行规划-2026-10-19.md)。首批仅统一受理、正式投影、编辑基线和生命周期协调，不引入本文路径 A 中夹带的队列接口、持久草稿或新解锁交互；版本关系、历史回执处理和部分调查表述按 82 号第 1、4 节订正。本文保留为原影响调查，不单独作为完整施工范围。首批实际施工与验证结果见 [83 号实施回执](83-配置单一受理与Store投影首批实施回执-2026-10-19.md)，其中 1.4-B 原竞态已修正，但本文提到的队列、持久草稿、跨刷新发现和多客户端仍不在首批。

## 1. 结论

方向可行，但“削权”实际上包含三件不同的事，不能当成一次局部改写：

1. **单一受理权**：目录读取、保存结果、固定读取都不能绕过配置应用的版本判断。这是修复 80 号迟到目录竞态的必要部分。
2. **Store 投影化**：Store 不再自己判断正式文档能否覆盖。可以保留 `entries.document` 作为投影字段，由唯一写入函数更新；不必立刻改成 computed，也不必删除 `saved_document`。
3. **草稿与队列**：持久草稿、每工作流串行队列、提交后等待再更新，是更大的行为变更。当前普通编辑是“立即提交、提交中禁止再编辑”，并没有持久草稿；引入草稿/队列会改变既有交互和测试契约。

补充事实：配置应用已经有“每工作流一个 accepted 文档 + 原请求证据 + 确认/派生 + busy/pending”的雏形，并不是从零开始。真正缺的是把 Store 的三条写路径（目录、`lastResult`、历史回执）收口到它、提供逐行目录结果和接纳通知，以及补齐确认/unknown 的持久出口。后端 `definition.update` 的 CAS/回执、`definition.read/list`、`request-evidence` 足以支撑；**不需要改后端**，前提是队列只对队头持久化证据、legacy schema 1/2 只读。

最重要的结论：

- 只做“单一受理 + Store 单写投影”，问题可控，主要工作是迁移 `saved_document` 消费者、目录行处理和生命周期清理。
- 如果同时做“删除 Store 正式副本 + `document = draft ?? accepted` 的 computed + 持久草稿 + 队列”，会遇到多个 P0 级问题，尤其是表单校验、引用身份、撤销/重做、归档/删除竞态和约 27 个测试文件的硬结构依赖。
- 队列不是修复该竞态的必要条件。迟到的读取需要**版本仲裁**；队列只解决顺序，不能替代版本比较。

## 2. 当前事实：Store 并不是“草稿 + 已保存”

普通编辑的现状（[workflowEditing.ts:20-32](../../frontend/src/application/workflowEditing.ts#L20-L32)、[workflowGraph.ts:520-532](../../frontend/src/stores/workflowGraph.ts#L520-L532)）：

```text
editable() -> editing.edit() 从 entry.document 克隆 next
           -> acceptDraft()
           -> submitConfigurationDocument() 立即提交
           -> 接纳后才写回 entry.document
```

也就是说：

- 安装配置应用时，Store 在提交期间仍显示旧的已接纳文档；提交成功后由 `acceptConfigurationResult` 写回。
- Store 没有“用户改完先放本地、稍后保存”的持久草稿；`saved_document` 与 `document` 通常相等，差异主要出现在创建/复制/撤销等暂态。
- `canEdit` 已包含 `configurationSubmitting` 和配置应用 `locked`（[workflowGraph.ts:512-517](../../frontend/src/stores/workflowGraph.ts#L512-L517)），提交中再次编辑会被拒绝，测试也明确断言这一点（[workflowConfigurationStore.test.ts:193-200](../../frontend/src/stores/workflowConfigurationStore.test.ts#L193-L200)）。

因此，“Store 保留草稿、提交排队、成功后统一更新”不是把现有逻辑搬个位置，而是**改变自动保存语义**。必须先决定是否要这个产品行为。

## 4. 关键问题详解

### 4.1 `saved_document/saved_revision` 是“干净基线”，不是冗余字段

大量正式操作要求“当前文档就是正式保存的那一份”：

- 创建会话、启动、提交事件、归档/删除：`saved_document` 与 `document` 的签名必须相等（[workflowManagement.ts:61-72](../../frontend/src/application/workflowManagement.ts#L61-L72)、[:125-128](../../frontend/src/application/workflowManagement.ts#L125-L128)）。
- 节点页入口：`saved_document` 必须存在、修订匹配、节点配置一致（[frontendNodeEntry.ts:45-60](../../frontend/src/application/frontendNodeEntry.ts#L45-L60)）。
- 变量注册：`saved` 判定依赖 `saved_document` 签名与 `saved_revision`（[workflowVariableRegistration.ts:70-78](../../frontend/src/domain/workflowVariableRegistration.ts#L70-L78)）。
- UI：会话修订、未保存提示、复制/删除按钮（[GraphSessions.vue:55-73](../../frontend/src/components/GraphSessions.vue#L55-L73)、[WorkflowSidebar.vue:74-79](../../frontend/src/components/WorkflowSidebar.vue#L74-L79)、[App.vue:55](../../frontend/src/App.vue#L55)）。

如果直接删除这两个字段，会出现两个方向的错误：

- 已经正式保存的工作流被当成“没有 accepted”，会话/运行/事件/节点页被永久拒绝；
- 或者用 draft 误当 accepted，未保存修改也能启动。

**可行做法**：保留字段作为只读投影，由配置应用的 accepted 结果更新；或者提供 `accepted(workflowId)` 访问器并逐个迁移，暂时保留兼容 getter。不要先把字段删掉再迁移消费者。

### 4.2 表单/节点编辑的基准冲突

节点字段编辑器传入的 `expectedConfig` 来自当前 UI 文档；`patchNodeConfiguration` 和 SDK2 却用配置应用里的 accepted 文档做比较（[workflowGraph.ts:355-366](../../frontend/src/stores/workflowGraph.ts#L355-L366)、[workflowFrontendSdk2.ts:48-64](../../frontend/src/plugins/workflowFrontendSdk2.ts#L48-L64)）。

当前没有持久草稿，所以两者通常相同。一旦引入 `draft ?? accepted`，用户改了普通字段但尚未保存时，节点表单会携带 draft 的节点配置去和 accepted 比较，结果是：

- 静默返回 `null`，用户看到“保存没反应”；
- 或者 SDK2 抛 `stale_edit_sequence` / `graph_configuration_access_denied`。

这不是字段迁移能解决的，必须决定：节点表单是否只允许在 clean 状态编辑，还是改为按 draft 基准提交并在接纳时合并。

### 4.3 引用身份与响应式

[FrontendNodeFields.vue:14](../../frontend/src/components/FrontendNodeFields.vue#L14) 使用：

```text
sdk.document.value === props.document && entry.document === props.document
```

`application.document(id)` 目前返回 `graphClone`（[workflowConfiguration.ts:253-255](../../frontend/src/application/workflowConfiguration.ts#L253-L255)），每次访问都是新对象。若 Store 的 `document` 改为从应用读取的 computed/clone，这个身份判断恒为 false，前端节点字段会永久禁用。

同时，[GraphRunControls.vue:25](../../frontend/src/components/GraphRunControls.vue#L25) 等 watcher 直接观察 `graph.document` 对象身份；每次 clone 会触发无意义重跑，甚至造成输入声明反复请求。

**可行做法**：Store 继续保存一个稳定的 `document` 对象，由单一写入函数替换；投影不要每次 clone，也不要让 `application.document()` 的 clone 直接成为 Store 的 `document`。

### 4.4 目录读取的四个缺口

1. **版本**：只比较 `revision >= saved_revision`；配置保存不推进 `mutationGeneration`，迟到的同修订 A 会覆盖 B（80 号已复现）。
2. **批量原子性**：Store 先写 `entry.document`，再调用 `observe`；`observe` 对同 `edit_sequence` 不同正文抛错，`loadDefinitions` 外层 catch 直接返回 false，前面已处理的 entry 保留，后面的行不再处理。`observe` 只比较 `edit_sequence`，不比较 `revision`；同序号不同正文也可能来自 `_compose_configuration`/注册表默认值变化，不一定是损坏，不能一律当整批失败。
3. **元数据**：`latest_published_revision` 在 [workflowGraph.ts:232](../../frontend/src/stores/workflowGraph.ts#L232) 无条件赋值，旧行可把它回退；`archived` 也在同一循环无条件写。
4. **legacy**：`loadDefinitions` 为所有 `GraphDocument` 建 entry（[workflowGraph.ts:219-225](../../frontend/src/stores/workflowGraph.ts#L219-L225)），但配置应用只接受 schema 3 + `edit_sequence`（[workflowConfiguration.ts:51-59](../../frontend/src/application/workflowConfiguration.ts#L51-L59)）。schema 1/2 行没有 accepted 来源，若 Store 不再保存目录行，`document` 会为 null，`activeManagement`、`refresh`、`selectSession` 等直接解引用会崩。后端对“有历史修订但没有 current 行”的定义也拒绝 update（[configuration_service.py:364-366](../../backend/src/phase1_agent/configuration_service.py#L364-L366)），所以 legacy 工作流实际是只读的，但 UI 仍可能允许编辑再报错。

目录加载必须拆成两件事：

- **管理投影**：注册工作流、archived、latest_published_revision、选择；
- **配置接纳**：只有通过统一 `accept` 的 schema 3 文档才更新正式文档。

两者不能由同一句 `entry.document = doc` 完成。

### 4.5 生命周期竞态

`manageWorkflow`（[workflowGraph.ts:571-581](../../frontend/src/stores/workflowGraph.ts#L571-L581)）只检查 `busy`、`applicationBusy`、`entry.pending`，**没有检查 `configurationSubmitting` 和配置应用 `locked`**。因此：

- 配置提交进行中，用户可以归档/删除；
- 删除后 `finishManagedDeletion` 只清 Store 的 entries/history/sessions（[workflowGraph.ts:546-570](../../frontend/src/stores/workflowGraph.ts#L546-L570)），配置应用的 accepted 文档、每工作流队列、pending 证据都没有清理；
- 随后到达的配置接纳结果找不到 source entry，`acceptConfigurationResult` 抛“原工作流已不存在”，但应用可能已经接纳。

如果队列只排配置提交，不排 archive/delete，这个竞态仍然存在。要彻底解决，**每工作流队列至少应覆盖定义级操作：保存、归档、删除**；读取可以不入队，但必须按版本丢弃。

### 4.6 协议与队列的具体缺口

配置应用已经是“每工作流一个 `documents` 副本 + 原请求证据 + 确认/派生 + busy/pending”的雏形，但还不是唯一受理者：

- `accept` 没有返回值，`observe` 公开且被 Store 直接调用；没有“逐行目录结果”“接纳通知”“移除工作流”的 API。
- Store 仍在目录加载、`lastResult`、历史回执三条路径上直接写正式文档。
- SDK2 的窄补丁先由 `ports.submit` 接纳一次（[workflowConfiguration.ts:138](../../frontend/src/application/workflowConfiguration.ts#L138)），随后又调用 `ports.accept`（[workflowFrontendSdk2.ts:91](../../frontend/src/plugins/workflowFrontendSdk2.ts#L91)），是双重受理。
- `lastResult` 在 `accept` 之前就写入（[workflowConfiguration.ts:137](../../frontend/src/application/workflowConfiguration.ts#L137)），Store 又在失败时用它回写（[workflowGraph.ts:336-339](../../frontend/src/stores/workflowGraph.ts#L336-L339)）；它表示“最近收到的响应”，不是“最近被接纳的当前”。

当前是“提交中锁住编辑”，不是“排队”：

- `configurationSubmitting` 阻止同一工作流的全量提交（[workflowGraph.ts:312-313](../../frontend/src/stores/workflowGraph.ts#L312-L313)）；
- SDK2 的 `pending` Set 阻止同一工作流的窄补丁并发（[workflowFrontendSdk2.ts:42](../../frontend/src/plugins/workflowFrontendSdk2.ts#L42)、[:51](../../frontend/src/plugins/workflowFrontendSdk2.ts#L51)）；
- 配置应用 `submit` 在 `locked` 时抛 `graph_configuration_pending`（[workflowConfiguration.ts:161-162](../../frontend/src/application/workflowConfiguration.ts#L161-L162)）；
- 测试明确断言“提交中第二次编辑返回 null/被拒绝”（[workflowConfigurationStore.test.ts:193-200](../../frontend/src/stores/workflowConfigurationStore.test.ts#L193-L200)、[workflowFrontendSdk2.test.ts:101-102](../../frontend/src/plugins/workflowFrontendSdk2.test.ts#L101-L102)）。

改成队列会改变这些契约，并且必须处理一个状态机，而不是只加一个数组：

```text
idle -> queued -> sending -> accepted
                        ├-> rejected (end, refresh current)
                        ├-> unknown (stop queue, reconcile/abandon)
                        └-> confirmation_required -> await-answer -> queued/derived/cancelled
```

- 入队项是**精确原请求**还是出队时重建？重建会改变证据与 CAS 依据。
- 出队时必须重新校验 `expected_edit_sequence`/`revision`，不能把旧请求直接发。
- `unknown` 必须停住整个工作流队列，先核实回执；不能自动重试，也不能跳下一条。
- `confirmation_required` 必须暂停队列；等待确认期间不能占着 `configurationSubmitting`，否则 UI 按钮会被 `activeConfigurationLocked` 禁用，形成死锁。
- 派生会换目标工作流，source/target 队列必须隔离；后台派生不应抢当前选择。
- 归档/删除入队时，`expected_revision` 也要在出队时重算；无 accepted 的草稿不能归档/删除。
- 后端每 owner 只允许一个 pending 证据（[request_evidence.py:32-35](../../backend/src/phase1_agent/request_evidence.py#L32-L35)、[:191-195](../../backend/src/phase1_agent/request_evidence.py#L191-L195)），所以队列若想把每个排队项都持久化，必须改后端；推荐只对队头写证据。
- `unknown` 之后目前没有“归档原请求并解锁”的出口；后端已支持 `resolution:"archived"`，前端类型/流程没有接（[request_evidence.py:206-223](../../backend/src/phase1_agent/request_evidence.py#L206-L223)）。
- 确认询问目前只在内存里，刷新即丢；若改成每工作流横幅，需要决定是否跨刷新保留、等待期间能否继续编辑。
- 观测性不足：`configurationPendingRequests` 只看 pending（[workflowGraph.ts:408-414](../../frontend/src/stores/workflowGraph.ts#L408-L414)），初始化失败、queued、冲突都不会显示；`error` 是单字符串，无法表达多项。

### 4.7 不能进入当前接纳的读取

以下读取必须与“当前正式配置”分开，不能调用统一的 `accept` 去更新 accepted：

- 固定修订读取：`GraphHistory.vue:51`、`workflowCommands.ts:67`、`workflowGraph.refreshPublishedRevision`（[workflowGraph.ts:604-613](../../frontend/src/stores/workflowGraph.ts#L604-L613)）；后者只更新 `latest_published_revision`。
- 历史回执：`reconcile` 用 `readReceipt` 得到的是原请求的历史结果，可能已经落后于当前 accepted（[workflowGraph.ts:422-425](../../frontend/src/stores/workflowGraph.ts#L422-L425)）。
- `lastResult`：只用于错误提示/兼容，不是 accepted。
- 目录行：必须经过逐行接纳，不能先写 Store 再 observe。
- install 的反向 seed（[workflowGraph.ts:163](../../frontend/src/stores/workflowGraph.ts#L163)）：把 Store 文档塞回应用，没有后端版本校验；重挂载时应重读目录或显式注入 accepted，不能把 seed 当权威。

类型上也应把“当前配置文档”和“固定修订文档”分开；现在 `GraphDocument.edit_sequence?` 允许固定修订文档混入 `GraphConfigurationDocument`，编译期无法阻止误受理。

### 4.8 测试与初始化

- 约 27 个测试文件直接构造整条 saved entry 或给 `entry.document/saved_document/saved_revision` 赋值；若字段删除或只读，build 会失败，Vitest 下会 TypeError/静默失效。
- [workflowApplication.test.ts:262](../../frontend/src/stores/workflowApplication.test.ts#L262) 明确断言“document 已本地编辑、saved_document 仍是旧正式版”，这是两份副本的核心契约；目标下必须改写为 accepted 投影断言。
- [workflowLifecycle.test.ts:55-59](../../frontend/src/stores/workflowLifecycle.test.ts#L55-L59) 的目录行是 schema 2，依赖 `loadDefinitions` 直接把它写成 saved；schema 3 化后这条契约需要明确保留还是退役。
- `installWorkflowConfigurationApplication` 的 observe 循环（[workflowGraph.ts:158-165](../../frontend/src/stores/workflowGraph.ts#L158-L165)）是测试和重挂载的唯一 bootstrap；生产是 install-before-load，所以通常空跑，但测试大量依赖它。移除后必须提供“重读目录”或“注入 accepted”的明确入口。
- `configurationApplicationVersion` 只用于安装失效（[workflowGraph.ts:104](../../frontend/src/stores/workflowGraph.ts#L104)、[:117](../../frontend/src/stores/workflowGraph.ts#L117)、[:160](../../frontend/src/stores/workflowGraph.ts#L160)），不是读版本；如果投影读应用，必须让投影依赖它或改用 `shallowRef` 应用句柄，否则重装后不重算。
- `workbenchPersistence` 只抽取旧 pending 证据（[workbenchPersistence.ts:37-66](../../frontend/src/stores/workbenchPersistence.ts#L37-L66)），不恢复编辑文档；`readLegacyWorkbenchEvidence` 需要 `document/saved_revision/session_id/pending`，**不要求** `saved_document`。但不能再从 `storeSnapshot` 生成旧记录，否则会把 draft/投影误记成正式 basis。

## 5. 两条落地路径

### 路径 A（推荐）：单一受理 + Store 单写投影

- 配置应用保留每工作流的 accepted 文档、原请求证据、版本比较；新增：
  - `accept(observation) -> {status: accepted|discarded|conflict|invalid, revision, editSequence, document?}`；
  - `acceptDirectory(rows)` 逐行返回，坏行不中断整批；
  - `accepted(workflowId)`/`acceptedRevision`/`acceptedEditSequence` 只读访问器；
  - `enqueue(request, context)`、`answerConfirmation`、`abandon/archive`、`forget(workflowId)`；
  - `onAccepted(change)` 或等价的“已接纳版本”通知，供 Store 投影。
- Store 保留 `entries.document`、`saved_document`、`saved_revision` 作为投影字段，但**只有一个写入函数**（如 `applyAccepted`）能改它们；`loadDefinitions` 不再直接写，也不直接调用公开的 `observe`。
- `document` 仍是稳定对象，不改成每次 clone 的 computed；避免引用身份和 watcher 问题。
- 目录读取：逐行交给应用 `acceptDirectory`；accepted 才更新投影；`latest_published_revision` 用 `max`，stale 行不写；archived 单独更新；schema 1/2 只读兜底。
- 暂不引入持久草稿；保持“立即提交、提交中禁止编辑”。这样 `saved_document/saved_revision` 消费者和大部分测试可保留。
- 队列只用于定义级写操作（保存/归档/删除），每工作流一条；读取用版本丢弃，不排队。若暂不做队列，至少把 archive/delete 纳入 `configurationSubmitting` 的锁，并清理应用状态。
- 队列采用 `idle -> queued -> sending -> accepted/rejected/unknown/await-confirmation` 状态机；只对队头写证据（后端每 owner 单 pending 的约束）；`unknown` 停队列并允许显式归档；确认等待不占提交锁；出队重算 revision。
- 后端不需要改；固定修订读取、历史回执、`lastResult` 不得进入当前 accept；类型上区分 current 与 fixed 文档。

### 路径 B（更大）：单一副本 + 草稿 + 队列

- 应用持有唯一 accepted；Store 只保留 `draft`、撤销栈、UI 状态；`document = draft ?? accepted`。
- 需要同时解决：草稿基准（base revision/edit_sequence）、节点表单按 draft 提交、copy/undo/derived 语义、schema 1/2 legacy 槽、引用身份、约 27 个测试文件。
- 还要解决：确认等待与锁、unknown/abandon、队列项证据时机、同序号组合差异、固定读取隔离、多标签页单写者假设。
- 收益是彻底消灭双副本；代价是产品行为（是否本地草稿、提交中能否继续编辑）和迁移面都显著扩大。建议作为后续架构阶段，单独规划。

## 6. 迁移顺序（若走路径 A）

1. **先加特征测试**：投影一致性、迟到目录旧行、latest 不倒退、draft（若引入）保留、删除/归档与提交并发、schema 2 目录行、unknown/确认不自动恢复。
2. **应用侧先提供**：`accept`（带状态与版本）、`acceptDirectory`（逐行结果）、`accepted` 访问器、`enqueue/answerConfirmation/abandon/forget`、统一比较（revision → edit_sequence）；先不接队列，只把这些接口做成 Store 的唯一入口。
3. **Store 加单写 seam**：`applyAccepted(workflowId, document, source)`；`loadDefinitions` 只处理管理元数据并调用应用；投影字段由 seam 更新。
4. **迁移正式消费者**：`workflowManagement` 的干净判断、`frontendNodeEntry`、`workflowVariableRegistration`、`workflowCommands` basis、`inspect`、`refresh`/`selectSession` 的稳定 ID；固定读取与历史回执不进入 accept。
5. **处理生命周期**：delete/archive 纳入同一 per-workflow 锁或队列，delete 清理应用 accepted/队列；derived target 建投影并清 source/target 规则；`forget` 清理缓存。
6. **最后**再考虑删除 `saved_document/saved_revision` 或改成只读 getter；冻结 legacy fixture，停止用 `storeSnapshot` 生成旧记录；补确认/unknown 的 UI 出口。

## 7. 必须先决定的问题

1. `acceptedDocument` 是**每工作流一份**，还是全局只保留当前选中一份？现状是每工作流一份；后者会改变多工作流目录和 UI。
2. 是否引入持久本地草稿？若不引入，路径 A 可以保留现有自动保存语义；若引入，节点表单、撤销、copy、提交失败/unknown 的草稿去留都要定。
3. 队列项是**精确原请求**（CAS 失败即拒绝）还是出队时重建（会改变原请求/证据）？排队是否算已提交、能否取消？
4. 证据在**入队时写**还是**队头写**？入队写需要改后端“每 owner 单 pending”的约束；队头写可以不改后端。
5. 正式配置已更新时，下一次编辑是拒绝并要求刷新（推荐，防覆盖）、自动 rebase，还是保持 last-writer-wins？
6. `unknown` 时队列停止还是全部失败？是否允许用户显式“归档原请求并解锁”（后端已支持 archived）？
7. 确认询问是否跨刷新持久？等待确认期间是否允许改草稿？确认 UI 是每工作流横幅还是全局模态？
8. 同 `revision` + `edit_sequence` 但正文不同：按同版丢弃，还是 integrity 错误锁定该工作流（不得中断整批）？
9. schema 1/2 目录行保留只读 legacy 槽，还是明确退役/迁移？（影响 `workflowLifecycle:55-59`、`workflowGraph:109-120`）
10. derived 目标是否自动打开？后台派生是否只通知、不抢选择？
11. `latest_published_revision`/“正式配置已更新”是硬门禁（必须刷新才能继续编辑）还是仅提示？
12. 多标签页是否假设单写者？另一标签的 pending 冲突如何提示？
13. install 在 load 之后（测试/重挂载）：重读目录，还是要求调用方注入 accepted？
14. `revision` 更高但 `edit_sequence` 更低、或同 `edit_sequence` 不同 `revision` 的精确处置；这会影响统一 `accept` 和现有 `workflowConfiguration.test` 的冲突用例。
