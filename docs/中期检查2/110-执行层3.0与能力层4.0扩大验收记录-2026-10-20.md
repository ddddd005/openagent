新增 [test_tool_binding_control_acceptance.py](../../backend/tests/test_tool_binding_control_acceptance.py)，复用既有隔离变量图、真实能力实现及受控模型，不新增产品机制。

### 3.1 首笔写入后暂停，再继续

1. 图中无普通变量读写实例；注册后的变量为 0 / revision 2。
2. Agent 工具 `set(10)` 完成真实接纳与独立重读后，测试 wrapper 暂缓把结果返回 Agent；这不是在数据库写事务内暂停。
3. 经公开 `control(pause)` 请求，释放 gate 并等待本链确实进入 `paused`。此前 set 的成功事实已成立，只有一次写入、一次模型请求。
4. 暂停状态下模拟迟到调用，用新的调用身份直接进入同一工具宿主，被 `tool_invocation_scope_invalid` 拒绝，executor 和写回执不增加。
5. 经公开 `resume` 继续 add/read/final；最终值 12 / revision 4，写入恰为 set、add 两次，首笔工具执行身份只结算一次。
6. 相同控制请求重放返回原回执；完成后工具帧、RunBasis、RuntimeHost 释放；重开库仍保留准确状态、值、修订和回执。

### 3.2 首笔写入后暂停，再关闭

采用同一安全边界，确认暂停后执行公开 `control(close)`：

- 保留 set 的 10 / revision 3 和唯一写回执，不执行 add，不继续请求模型。
- 会话为 `closed`，工具帧、RunBasis、RuntimeHost 释放。
- 相同关闭请求不重复执行；重开库状态、变量和回执一致。

两项只证明已接纳写入后的安全边界，不等于写事务中暂停/关闭竞争、关闭任意在途工具、服务 shutdown 或完整控制矩阵。

### 3.3 工具调用前丢失 RunBasis

首次工具 `invoke` 前受控移除本链运行依据，保留准备帧和服务当前 registry：

- 工具桥明确抛 `run_basis_unavailable`，真实变量 executor 调用为 0。
- 模型已产生本次工具请求，所以 transport 为 1；不能表述为“启动前零模型”。
- `wait()` 显式抛同一诊断，持久链为 `recovery_unavailable`，只允许 `close`；不是普通业务节点失败的 `failed`。
- 对象与注册后状态完全一致，没有工具幂等行或对象写回执；工具帧释放，无默认来源回退执行。

该状态沿用既有 `test_run_basis` 和异常收尾规则，本轮未改变错误分类或恢复策略。
