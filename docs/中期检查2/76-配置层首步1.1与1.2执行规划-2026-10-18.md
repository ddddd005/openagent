## 3. 目标链与职责

### 3.1 配置修改主链

```text
工作台修改 / 前端节点发起修改
-> 各自的通信与来源适配
-> 配置层功能接口
-> 配置层对应业务模块
-> 配置层数据接口
-> 数据层管理接口
-> 对应数据模块 / 配置仓储 / 数据库适配
-> 现有共享 SQLite
```

这是职责和调用关系，不代表每个位置必须新建一个类、进程或服务。接口可以是同进程调用；不为形成层次而引入网络通信。

### 3.2 各位置承担什么

| 位置 | 承担 | 不承担 |
| --- | --- | --- |
| 来源适配 | 保留工作台整文档提交、节点页窄补丁、精确 owner 和原请求证据；转换为配置意图 | 不自行实施配置分类、派生或直接持久化 |
| 配置层功能接口 | 受理、检查操作形状、分发、协调本层依赖并返回结果或错误 | 不成为全项目入口，不集中全部配置业务规则 |
| 配置业务模块 | 节点合同及策略校验、目标核对、分类、确认派生、投影和结果语义 | 不构造存储、不执行 SQL、不取得通用 repo 或任意表访问能力 |
| 配置层数据接口 | 承接本层配置数据需求，负责与数据层交互和必要参数适配 | 不另存完整配置、不重复业务判定、不自建回执或事务体系 |
| 数据层管理接口 | 按领域意图分发，协调原有存取条件、事务和记录校验 | 不替配置业务决定可调/固定、确认或派生 |
| 配置仓储与数据库适配 | 映射现有固定修订、节点投影和当前覆盖，完成记录读写与数据库适配 | 不生成另一套业务权威，不承担前端交互或执行调度 |

必要的节点定义继续来自现有准确注册来源。配置业务消费明确的只读声明，不在模块内部自行加载包或建立定义权威；本两步不建设完整定义目录。

### 3.3 接口如何管理

按配置、数据、运行等职责各自维护公开操作和依赖。一个接口可以有多个领域操作，不一操作一入口；也不机械要求一层只能有一个方法。新增入口须说明服务对象、调用方、目标和与已有入口的区别。

配置层数据接口是本层对外数据通信口，数据层管理接口是数据管理的受理口；两者不是两个配置存储权威，也不能互相回调形成配置与数据的循环依赖。

### 6.3 保留原子事务，撤出通用仓储能力

现有 `GraphRecordStore.atomic` 顺序是：开启事务、核对原命令回执、执行回调、校验变更、写原生回执和必要应用身份、提交；异常回滚。当前业务回调直接收到通用 repo，这是本次需要整理的关键边界。

实施方向参考：保留原事务持有者，让配置层数据接口的有限操作使用同一命令事务；数据管理内部可以继续使用原 repo，但不把 repo、连接或任意数据库回调交给配置业务。这个方向不等于新建通用事务平台。

施工前必须明确“有限领域存取如何绑定原事务、来源核对在哪里执行、谁负责最终提交”的局部方案。未明确时只能继续不依赖它的规划，不能先把业务读写搬到事务外，也不能以新接口名包装后继续透传 raw repo。

事务保护次序应保持：

1. 固定原始请求及其身份；原生重放核对先于重新读取今天的配置。
2. 原命令事务内完成必要来源核对、配置依据读取、编辑序号和固定修订检查。
3. 配置业务判断修改类别、确认或派生，并通过本层数据接口提出存取。
4. 数据管理在同一事务内完成记录写入和原有变更校验。
5. 写原生回执及适用的应用身份，统一提交；任何异常仍统一回滚。

工作台保留 `graph.definition.update`，节点页保留 `graph.frontend-node.patch-input`。节点页外层已开启事务，不能在内部直接调用自带 `_change` 的公开 `patch_node_configuration`，造成再次开事务和第二份回执。

前置请求证据仍是原来的独立事务，不被合并到配置保存事务。确认询问和 unchanged 是有业务回执的正常结果；陈旧修改等异常不能被改写成正常保存结果。

### 6.4 保留数据权威与读取语义

| 载体 | 本批保留的性质 |
| --- | --- |
| `workflow_definition_revision.document` | 固定修订完整原文；目前仍含当时可调/显示值，不在本批剥离 |
| `node_binding` | 同一固定修订的逐节点投影；原 bundle 一致性校验保留 |
| `workflow_current_configuration` | 当前显示、可调覆盖和编辑序号，不是第二份完整定义 |
| `idempotency` | 原命令的历史接受事实，不能覆盖或以今日配置重建 |
| `pending_commands` | 原始请求证据，不是配置业务权威 |

`revision` 与 `edit_sequence` 分别传递；不能因新增接口把它们合并。current UPSERT 自身不是完整 CAS，现有事务内版本检查不能在拆解时丢失。

独立重读必须在保存事务完成后通过新一次读取取得持久依据，不只返回保存阶段已经合成的对象。隔离验证可控制无其他写入时断言一致；实际并发下，当前读取可能已更新，不能要求它永远等于某次旧回执。

常规存储打开仍会初始化表并盖存储版本，因此“重读”不等于“物理只读”。本批建议不扩建新的只读配置适配；是否消除常规读取副作用仍属 74 号 Q12。专用回执读取继续保留 `mode=ro`、`query_only`，不得改为构造普通存储、初始化 Runtime 或重新发命令。

1.1 完成标准：

### 11.1 判断原则

采用最新明确用户决定和对应授权范围；历史方案、源码现状及已有测试不能反向批准新行为。本文对角色和阶段的明确接续优先于 74 号较早的问题表，但不消除未解决的产品语义。

### 11.2 具体冲突的处理

| 发现情况 | 取舍与汇报要求 |
| --- | --- |
| 原业务必须拿通用 repo 才能在同一事务内工作 | 报告有限领域操作和原事务适配的缺口；不得透传 repo，也不得把依据读取移出事务 |
| 节点页绑定校验与配置业务共享事务，接新接口会嵌套事务 | 保留原核对顺序及外层回执，报告适配方案；不直接改调自带事务的公开方法 |
| 新接口要求改 operation、摘要、应用身份或证据结案语义 | 停止此改动，说明历史证据与重放影响；不随统一业务合并回执 |
| 为了读取需要补造 current 行、填默认值或重建历史记录 | 属于迁移/历史数据决定，不能自动修复或静默回退 |
| 整理必须改表、新增持久事实、提高存储版本或访问业务库 | 提交必要性、影响对象和准确范围，等待独立决定 |
| 所需查询跨入项目管理、变量、检查点或运行生命周期 | 明确依赖和最小必要范围，不因共用服务文件顺带施工 |
| 测试要求恢复退役入口或旧架构 | 不为测试恢复产品 API；按当前验证意图重新审阅，不能冒称测试退役即行为修复 |
| 同时发现外部修改或更晚文档决定 | 保留修改并核对；若影响本批边界，停止受影响部分询问用户 |

汇报应包含：具体事实与证据、冲突的已定要求或缺失前置、受影响文件和数据、可选方向及代价、建议方向、当前尚可继续的独立工作，以及需要用户作出的决定。未经决定不扩大施工。
