## 2. A1 统一配置接纳与版本仲裁

[配置应用](../../frontend/src/application/workflowConfiguration.ts) 新增：

- `acceptDocument(document, source)`：唯一接纳决定，返回 `accepted / duplicate / stale / conflict / fixed / invalid` 及对应文档。
- `observe` 成为严格包装：格式无效、同版不同正文或版本关系冲突仍抛出既有错误码；陈旧、重复和固定来源不写 current。
- `acceptDirectory`：逐行返回结果，单行无效或冲突不抛断整批。
- `accepted(workflowId)`：供 Store 投影读取的稳定对象；重复接纳不替换引用。
- `forget(workflowId)`：仅在管理业务与证据结案后清理 accepted 缓存和空闲请求通道。

版本规则集中为：同一身份下编辑序号更小为陈旧；同序号要求修订和正文一致，否则冲突；序号更大时要求 `0 <= 修订增量 <= 编辑序号增量`，否则冲突。固定修订来源始终不成为 current。`lastResult` 保留为诊断事实，不再作为 Store 正式投影依据。

行为证据见 [配置应用测试](../../frontend/src/application/workflowConfiguration.test.ts)：固定读取隔离、陈旧/同版异文冲突、可调与固定推进、修订跳变拒绝、重复引用稳定、目录部分失败不中断。该文件最终 **23 passed**。

## 3. A2 Store 正式投影单写

[Store](../../frontend/src/stores/workflowGraph.ts)：

- 目录读取按行调用 `acceptDocument`，只从 `accepted` 投影正文、保存基线和修订；陈旧行不再覆盖较新正文，冲突行报告错误但继续处理其他行，`latest_published_revision` 改为不倒退。
- 保存/核实/节点表单结果统一经 `projectConfigurationResult` 读取 accepted；新增 `projectChangedAcceptance` 只在应用已经接纳时更新投影。删除 `entry.lastResult` 回填旁路；证据结案失败时仍投影已写入正文并保留锁，核实后再清锁，回归见 `workflowConfigurationStore.test.ts`（**10 passed**）。
- `projectAcceptedState` 成为正式投影写入点；目录接纳和结果接纳共用它。同版重复不替换引用、不重复推进历史；只有接纳正文与本次请求正文一致时才记录这次编辑的历史，外部较新观察不冒充本地编辑。
- 安装函数默认不再把 Store 正文反向 `observe` 成正式依据；测试使用显式 `{ seed: true }`。
- `discardDraft` 从 accepted 恢复；没有 accepted 时不把任意 `saved_document` 声明为正式依据。
- [SDK2](../../frontend/src/plugins/workflowFrontendSdk2.ts) 删除重复 `ports.accept`，SDK 只提交原请求并返回结果。

迟到目录行现由应用判定为陈旧，Store 保持已接纳的 B；[1.4-B 验收测试](../../frontend/src/stores/workflowGraphConfigurationBasis.test.ts) 已由“记录分歧”改为“应用和 Store 一致”，最终 **3 passed**。

## 5. A4 生命周期协调与删除时序

- 配置提交和节点表单在真实入口检查管理 pending/busy、归档/删除状态；管理入口在归档/删除前初始化配置证据并检查配置锁和提交中的请求，不只依赖按钮禁用。
- [资源 outbox](../../frontend/src/application/resourceOutbox.ts) 的完成回调改为携带已完成原请求，并且只在 `writePending(null)` 成功后调用；[管理请求](../../frontend/src/application/workflowManagementRequests.ts) 只在 `definition.delete` / `session.delete` 回执已确认且证据结案后通知完成。
- 定义删除回执到达时只标记 `deleted` 并保留条目和待核实 owner；结案成功后才执行最终本地清理并 `forget` 配置缓存。删除成功但证据结案失败时，条目、锁和现有核实入口仍在，回归见 [生命周期测试](../../frontend/src/stores/workflowLifecycle.test.ts)（**9 passed**）。
- 目录/结果/核实/重装等迟到响应继续由对象身份、请求代次、安装关系和 accepted 判定局部失效；不新增墓碑、全局队列或恢复服务。

跨刷新恢复边界：本轮只保证当前应用装配内仍能定位待结案 owner 并核实；若刷新后后端目录已无该定义，现有证据查询要求准确 owner，尚无枚举发现路径，因此不承诺刷新后自动重新发现。需要跨刷新发现时必须先报告最小查询与装配影响，另行决定。
