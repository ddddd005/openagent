## 2. 六层口径与判定方法

六层按本轮给定顺序排列。该顺序表示阅读顺序，不表示依赖顺序或施工先后；施工顺序仍按 70 号。

| 层级 | 已确认的目标职责 | 当前主要代码形态 |
| --- | --- | --- |
| 基础支持层 | 只负责工作流运行相关的启动、恢复、抛错、当前状态及会话指向 | HTTP 与应用命令中的运行入口、宿主运行组合、运行页面公共承载；同入口中的项目管理操作另列 |
| 配置层 | 静态工作流及其修订、节点实例与类型版本、端口/边/分组、节点配置和静态内容、绑定、包锁、配置修改规则 | 配置服务、配置策略、窄修改许可、编辑器输入声明 |
| 数据层 | 统一数据存取、归属与版本、事务与 CAS、记录/仓储、数据库适配、只读展示与回执读取 | store、record 校验、领域仓储、会话对象仓储 |
| 定义层 | 读取并解析来源模块的定义，提供统一的只读定义视图；定义维护权归来源 | NodeRegistry、TypeRegistry、已有注册汇总；包加载和各类 contract 模块作为来源及注册相关代码参考 |
| 执行层 | 工作流运行图、编译与执行顺序、节点调用、运行推进、事实与错误、完成判断、生命周期通知 | 编译器、`execute_graph`、RuntimeHost、运行编排 |
| 功能层 | 具体业务节点与可区分能力（检查点、重roll、分叉等） | 节点包、Agent/模型/上下文/聊天/Lorebook、能力模块 |

判定时使用以下约定：

1. **按主职责归类。** 一个文件同时承担两层职责时，正文给主归属，并在“跨层职责与依赖”一节单独说明；不把文件物理移动当作职责已经分开。
2. **定义、配置与具体数据按用途区分。** 定义描述规则，配置是具体实例的设置，具体数据表示符合相应定义的对象或内容。持久定义和配置也是数据管理的存取对象；数据管理覆盖工作流定义域和会话域，不能把“数据”限定为会话内容。
3. **“执行层”只指工作流 Runtime。** Agent 内核与执行器属于节点内部实现，归功能层；`runtime.py` 不是工作流 Runtime 的同义词。
4. **“功能层”包含能力模块。** 按 71 号口径，检查点、重roll、分叉等是功能层中的可区分能力，不另立第七层。
5. **前端不单列第七层。** 工作流运行的公共承载与通信按基础支持相关代码阅读，配置表单按配置职责阅读，节点页面与业务交互按功能职责阅读；项目目录和管理界面另列。数据投影与页面交互分别标注，未定细节不据组件名称直接定责。
6. **不为尚未安装或已退役的路径补分类。** 旧草稿、旧请求证据、未安装原型和测试工具按实际调用状态单列，不强行塞进六层。
7. **跨层依赖与跨层职责分开。** 读取其他层的数据或定义、调用其接口是依赖；实现其业务规则或承担修改权才涉及职责混置。访问路径是否绕过目标接口另作判断，不以 import 或共用数据库直接断言越层。

快速阅读路径：先看第 3 节总览；查具体文件看第 4–9 节；查跨层集中点看第 10 节；查项目级/历史/工具代码看第 11 节；查与 70 号步骤的对应看第 12 节。

## 3. 总览

| 层级 | 主要后端文件规模 | 当前主要入口 | 现状特点 |
| --- | --- | --- | --- |
| 基础支持层 | 运行入口与公共承载相关文件，含跨层文件 | `server.py`、`graph_application.py`、`workflow_host.py` | 现有入口同时路由运行和项目管理；只将运行薄口列为本阶段职责 |

| 执行层 | 约 8 个运行文件 | `graph_execution.py`、`runtime_hosting.py`、`graph_service.py` 的 `_execute` | 串行执行；真正编排仍在 `GraphWorkflowService` |
| 功能层 | 约 50 个节点/能力文件 | `builtin_packages.py` 组合的节点包、检查点/聊天能力 | 体量最大；节点业务与能力模块直接触达数据与配置 |

当前代码的实际调用骨架如下。它描述现状，不是目标调用链；目标方向见 69 号第 4 节。

```text
server.py / graph_http.py
→ graph_application.GraphApplication
→ GraphWorkflowService（13 个 mixin 的集中类）
   ├─ 配置：WorkflowConfiguration → GraphRecordStore / graph_contracts
   ├─ 运行：start / _prepare_run → GraphCompiler → execute_graph
   │        → RuntimeHost / GraphRuntimeHost → 节点包 host_call
   ├─ 能力：checkpoint / chat / frontend node operations
   └─ 读取：GraphPublic / GraphInformation
→ SqliteStore / GraphRecordStore / SessionObjectStore / ...

只读回执：server.py 提前分流 → graph_receipts.py → 只读 SQLite
```

集中类 `GraphWorkflowService` 定义在 [graph_service.py](../../backend/src/phase1_agent/graph_service.py#L73)，同时继承 `WorkflowChatService`、`WorkflowConfiguration`、`WorkflowLifecycle`、`GraphEditingHost`、`GraphFailedRetry`、`GraphEvents`、`GraphInformation`、`GraphRuntimeHost`、`GraphFrontendNodes`、`GraphResourceHost`、`GraphPlatform`、`GraphPublic`、`GraphHistory`。这是当前最需要单独阅读的跨层结构。

### 4.2 现状观察

- `GraphApplication` 当前分发配置、注册、信息、回执及管理请求是共享路由事实，不决定这些业务的目标归属。工作流基础支持仍只负责运行相关的启动、恢复、抛错、当前状态和会话指向。
- `workflow_host.py` 是懒加载组合根；`workflow_lifecycle.py` 中的归档、删除及项目管理元数据按项目能力层相关代码单列，不因挂在同一宿主或集中服务就并入工作流运行基础。
- 只将前端壳和工作台中的运行公共承载按基础支持阅读；目录、管理、配置、运行和结果交互按实际用途分别记录。`GraphWorkbench.vue` 和 `stores/workflowGraph.ts` 是需要按方法核对的集中点。
- `graph_receipts.py` 的“不初始化 Runtime、不写业务数据、不重发未知请求”是当前专用只读保证，阅读基础支持入口时必须保留这一区分。

### 5.2 现状观察

- 模块层面，`workflow_configuration.py` 只依赖 `configuration_mutations`、`graph_contracts` 和契约工具，没有直接导入 `storage`/`graph_store`；实际事务由调用方 `GraphWorkflowService` 的 `_change`/`GraphRecordStore` 提供。这是当前配置层相对清楚的一面。
- 配置方法并不全在配置模块：`_save_definition`、`_document`、`_change` 在 `graph_service.py`，`update_definition`、`patch_node_configuration`、`_save_configuration_update` 在 `workflow_configuration.py`。阅读配置保存链需要同时看两处。
- `graph_contracts.py` 与 `workflow_configuration` 之间有配置策略校验、默认策略及图校验的相互依赖。这是模块级契约与配置规则的共置现状，后续按具体操作整理；不能仅凭文件归类把它等同于只读定义目录反向维护配置。
- 前端有两种修改入口：工作台配置链和独立前端节点 `patch_input` 链。后者由 `frontend_node_operations.py` 调用集中服务的 `_patch_node_configuration`，窄修改许可规则仍在 `workflow_configuration.py`/`configuration_mutations.py`；联调时必须同时覆盖两种入口。
- 项目启用包选择由 [`graph_package_selection.py`](../../backend/src/phase1_agent/graph_package_selection.py) 保存，`GraphPlatform.configure_capability_packages` 明确是项目管理操作；包加载器负责依赖解析。工作流自身的 `package_lock` 是配置管理维护的修订依据，经数据管理保存；[`graph_contracts.py`](../../backend/src/phase1_agent/graph_contracts.py#L240) 的校验函数所在位置不改变该归属。
- 正式配置提交不要求图可执行；固定修改在有效会话下要求确认派生，可调修改原地保存。该规则在 `workflow_configuration.py` 与前端 `workflowConfiguration.ts` 中都有对应表达，阅读时不要只看其中一侧。

### 8.2 现状观察

- 当前工作流执行是串行的：`execute_graph` 按 `GraphPlan` 的顺序推进，等待全部纳入计划的节点完成；输出节点不直接宣告回合成功，完成判断仍在运行编排层。

### 9.2 现状观察

- 功能层是当前体量最大的层。节点通过 `CapabilityPackage`/`HostRegistration` 注册，公共宿主服务通过 `HostServiceRegistry` 提供；[`builtin_packages.py`](../../backend/src/phase1_agent/builtin_packages.py) 是当前内置包组合根。
- 检查点、聊天/重roll/分叉是功能层中的能力模块，不在执行层。当前 `checkpoint_collection.py`、`checkpoint_loading.py` 直接导入 `session_objects`、`workflow_configuration`、`graph_records` 等；`workflow_chat_service.py` 直接导入检查点、配置修改许可、`graph_store`。能力模块当前通过领域仓储直接取数，而不是统一经数据入口。
- `workflow_chat_service.py` 353 行、`workflow_chat_operations.py` 195 行、`workflow_chat_runtime.py` 184 行，聊天能力合计约 732 行；阅读重roll/候选/分叉时应按“操作规则 → 检查点/数据 → 前端节点消费者”三部分一起看。
- `runtime.py`（`SnapshotKernel`）1,181 行，是 Agent 节点内部实现；`agent_executor.py` 是包内执行器适配。二者可以调用模型和工具，但不是工作流调度器。
- 模型族中多个文件 docstring 写 “Uninstalled M1/M3” 或 “未安装”。当前 `model_package.py`、`model_host_service.py`、`graph_runtime_host.py` 已引用 `ModelRequestService`、`ModelRequestResourceReader`、`ModelRequestFactReader`；`runtime.py`、`agent_executor.py` 引用 `model_execution_contracts.py`/`model_execution_requests.py`。这里存在“文档措辞落后于调用事实”的情况，分类按实际调用点，不按旧 docstring 判定安装状态。
- `workflow_operations.py` 通过 `self._service._lock`、`self._service._store()` 和私有方法读回执，说明独立操作功能仍与集中服务耦合；它不是纯契约模块。
- 上下文功能族同时包含节点注册、持久算法、更新证明、精简和契约校验；`context_contract.py` 归定义层，其余按功能层阅读。不要因为文件名都带 `context_` 就认为它们同层同责。

## 13. 勘察结论

1. **工作流六层都有相应代码，但不是六个包或六个类。** 基础支持只管运行薄口，配置维护工作流配置，数据管理两域存取，定义目录只读消费来源，执行是工作流 Runtime，功能是具体节点与能力。项目管理能力不并入工作流基础。
2. **`GraphWorkflowService` 是最主要的职责集中点。** 1,309 行、44 个方法、13 个 mixin，导入 32 个内部模块（含懒加载）。每批先梳理所涉及方法、共享依赖和事务，并指定接线负责人；不以整体拆完服务为配置起步的前置。
3. **配置层模块相对独立，但入口分散。** 配置修改仍需统一入口与数据通路；工作流 package lock 继续由配置管理维护，项目启用包选择另列。配置策略与图契约的代码依赖按本批路径核对。
4. **数据层没有单一门面。** 仓储按领域拆开，`storage.py` 跨领域初始化，`session_objects.py` 知道检查点/聊天语义，`graph_receipts.py` 是专用只读适配。按 66 号建立统一数据交互口，需要先决定这些边界的归属，而不是再建一个万能 `DataLayer`。
5. **定义相关代码与编译共置，目录基础并非空白。** 已有精确定义查询和只读注册汇总；来源维护、目录消费与运行图编译分别描述，编译结果不作为通用定义目录。
6. **执行层是工作流 Runtime，不是 Agent 内核。** `graph_execution.py`/`runtime_hosting.py`/`graph_runtime_host.py` 是执行层；`runtime.py` 的 `SnapshotKernel` 是 Agent 节点内部实现，归功能层。命名相近，阅读时必须区分。
7. **功能层体量最大，能力模块与数据/配置耦合最深。** 检查点、聊天/重roll/分叉直接调用仓储和配置；`frontend_node_operations.py` 把配置、执行、聊天和快照放在同一操作面。
8. **项目级资源、旧证据和测试工具不在六层内。** 全局提示词/Lorebook、供应商/凭据、旧草稿、离线契约校验和测试工具应保持独立归属；不应为了层数整齐而把它们并入工作流定义域或数据层。
9. **前端不是第七层。** 运行公共承载、配置编辑、具体业务交互、数据展示和范围外项目管理分别阅读；`stores/workflowGraph.ts` 与 `GraphWorkbench.vue` 不能整体归入某一层。
