## 2. 建设主线与已确认方法

| 主线 | 目标与涉及范围 | 展开深度 |
| --- | --- | --- |
| 一、工作流的内容与能力承载基础 | 从工作流范围的配置、数据管理、定义及注册管理取用关系入手，向功能层、执行层等消费者提供可用接口 | 当前优先展开 |
| 二、节点与插件的合规扩展 | 梳理功能和节点的包加载、自定义节点接入与调用，涉及项目基础、项目数据管理、工作流节点加载、统一连线和节点框架映射 | 第一主线建立必要接口后分批论证；不预设完整插件平台方案 |
| 三、其余项目建设 | 项目能力层的创建、删除、归档、复制等管理能力及其他项目架构 | 当前只记录归属，按后续需求展开，不混入工作流底层运行施工 |

当前“写死”的问题，主要指模块能够处理哪些对象、提供哪些作用，仍依赖预设清单和固定逻辑。这是速搭阶段的取舍，不能笼统归因为耦合，也不能把现有注册表和包加载基础说成完全不存在。

已确认采用以下施工方式：

1. 从当前步骤涉及的局部结构开始，写清对象、职责、调用和数据归属。
2. 先论证逻辑与必要边界；中等复杂度的新职责、接口契约和产品行为交由用户决定。
3. 边界清楚后，可以增加极简中间接口，内部暂时转发现有实现，接通选定的真实路径。
4. 再逐步填充模块内部，将业务规则和存储适配整理到相应位置，并联调相邻模块。
5. 随施工扩大已明确的结构；不提前填满全部架构，不用额外回退、重试或第二套权威掩盖问题。

## 3. 职责结构与数据归属

### 3.1 职责结构

| 职责 | 业务内容 | 数据交互与边界 |
| --- | --- | --- |
| 基础支持 | 仅负责工作流运行相关的启动、恢复、抛错、工作流当前状态、会话指向等薄口职责 | 使用明确的工作流身份和会话指向接入相应操作；不承担项目创建、删除、归档等管理业务，不组织、装配或更新上下文内容 |
| 配置管理 | 节点实例、类型版本绑定、连线、配置、声明、派生内容和变更规则 | 读取准确声明，将配置修改经数据管理保存；明确修改目标和作用范围 |
| 功能与节点 | 完成具体内容处理和业务操作，包括上下文读取、装配、更新等 | 节点借执行 / Runtime 层访问相应数据；自身业务规则不因数据存入会话域而转交“会话层” |
| 执行 / Runtime | 运行图、执行顺序、节点与功能调用、运行推进、事实与错误、完成判断和生命周期通知 | 通过数据管理读取运行依据、承接节点数据访问并保存执行结果；需要修改配置时请求配置管理 |
| 声明来源、注册管理与定义目录 | 来源维护声明及其注册；目录提供统一的只读解析和消费视图 | 分清声明产生、维护、注册和取用；具体管理接口与存储形式在局部施工中确认，不新增一套声明权威 |
| 数据管理 | 统一承接数据存取、归属校验、版本及事务、存储和数据库适配 | 各功能保有业务维护职责；数据库读写不因此分散回各功能模块 |
| 检查点、重roll、分叉等能力 | 按各自规则消费数据并产生相应记录或引用 | 检查点也是会话域数据的消费者；能力业务与 Runtime 通用推进职责分开 |

“每个职责模块有自己的数据存储和消费”表示其业务数据有明确归属和维护方，具体存取仍由统一数据管理承接。数据管理是架构统称，可以由多个领域接口和适配模块组成，不要求万能 `DataLayer` 类。

基础支持维护的当前工作流状态和会话指向，与 Runtime 内部的运行推进分别描述；接线时核对状态来源和更新路径，避免形成相互覆盖的两套状态。这里的“恢复”沿用现有能力边界，不扩张为进程重启后自动重建活动执行。

### 3.2 数据归属

| 数据 | 逻辑归属 | 维护或消费方式 |
| --- | --- | --- |
| 静态工作流、节点实例、准确类型版本、连线、节点配置、绑定、package lock、画布编辑结果 | 工作流定义数据 | 配置管理维护，其他功能按需读取 |
| 变量声明、类型、默认值、作用范围与允许操作 | 工作流定义数据或相应声明来源 | 声明可在没有会话时建立；不与当前值合成一个只能运行后创建的对象 |
| 会话身份、固定定义修订、状态和数据绑定 | 会话数据 | 保存归属与引用；运行准备、运行推进及能力操作使用必要数据接口，项目管理操作归项目能力层 |
| 变量当前值、上下文、逻辑聊天、候选 | 会话数据 | 按具体会话隔离，由相应节点和功能维护；上下文不是基础支持的功能 |
| 节点运行、链运行、事实、输出、错误和完成信息 | 会话关联的运行数据 | 执行 / Runtime 维护，进一步区分具体运行和节点运行 |
| 检查点记录、候选及分叉引用 | 会话关联数据 | 相应能力维护；检查点内容只收明确准入的数据及允许的配置投影 |
| 项目提示词、Lorebook、供应商、模型配置 | 项目级资源 | 工作流保存引用或必要依据，引用不转移所有权 |

归属由数据项用途和声明确定，操作再提供准确目标，数据管理校验绑定、版本和写入条件。例如，同为“变量”操作，修改声明与默认值、更新会话 A 的当前值是两种不同操作。不能仅凭调用者所在层级、变量名称或界面“当前会话”猜测写入位置。

继续使用共享 SQLite；逻辑归属和接口区分不等于物理拆库，也不直接要求表迁移、复制数据或拆事务。

## 4. 用代表调用链核对局部结构

以下表达职责顺序，不预定类名、HTTP 路由、消息总线或完整 API 形状。

```text
配置编辑：
前端操作 → 应用入口 → 配置管理
                      ├─ 读取定义目录中的准确声明
                      └─ 数据管理校验和保存 → 返回新视图或错误

工作流启动 / 恢复：
基础支持薄口（工作流状态、会话指向、启动 / 恢复目标）
→ 执行 / Runtime 入口 → 读取明确运行依据并推进 → 返回状态或抛出错误

上下文读写：
节点 → 执行 / Runtime 层 → 数据管理 → 指定会话的上下文数据
写入按节点接纳与事务边界保存，向节点或调用方返回真实结果

执行侧请求配置修改：
节点按钮触发功能执行 → 执行侧发起修改意图
→ 配置管理校验目标和规则 → 数据管理保存 → 返回结果

能力数据消费：
检查点能力 → 经数据管理读取准入数据及必要配置读取视图
→ 保存检查点；重roll、分叉分别消费规定基线和引用
```

上下文读写由节点的具体逻辑发起；Runtime 承接访问与执行接纳，数据管理完成存取及校验。这条链不经过一个负责上下文内容的基础支持模块。

执行侧调用配置管理的职责方向已明确，但不代表所有前端编辑都要先运行节点，也不代表配置保存后当前运行立即热更新。现有可调配置的作用范围、生效时点和重roll基线仍须专门确认。

## 6. 局部施工与分批顺序

### 6.1 每批共同步骤

每批先明确：处理对象及来源、管理方、消费者、数据归属、调用方向、身份与修订条件、事务及错误结果。涉及检查点时另写准入关系。

1. **局部结构论证**：对照当前路径和目标路径，确认该批职责及必要契约，登记未决项。
2. **极简骨架接通**：用表达领域意图的小接口转发现有实现，切入选定真实路径；不暴露任意表操作或数据库连接给上层。
3. **模块内部填充**：整理声明、校验、数据组织和存储适配，保持已定外部语义。
4. **跨层联调与记录**：验证准确目标、保存与重读、冲突和错误，再扩大到下一条路径。

转发实现可以长期保持简单。完成状态分别记录为“局部结构已确认、骨架已接通、内部职责已整理、跨层验证已通过”，不以新增文件或接口数量作为完成依据。

### 6.2 建议实施批次

以下为执行建议，具体接口、文件拆分和待决行为仍按当批论证确认。

| 批次 | 施工内容与结果 | 前置与联调关口 | 对应 65 号阶段 |
| --- | --- | --- | --- |
| A：对象与路径清单 | 先列工作流定义、配置、变量声明 / 当前值、上下文、运行记录的来源、维护方、消费者和现有读写入口；画第 4 节的局部链 | 只明确当前路径需要的职责；待决项进入第 8 节 | 一 |
| B：最小数据与定义消费骨架 | 建议先选已有静态配置读写和已有会话数据读写，接入统一数据管理；并整理准确声明的最小只读查询口 | 确认接口意图、归属、版本及事务；保留现有存储适配，不顺带迁移数据 | 二，提前准备三、四的必要接口 |
| C：配置与基础支持接线 | 配置保存、节点绑定和派生内容接数据管理；覆盖工作台及独立节点页；基础支持薄口接启动、恢复、状态、会话指向和错误 | 可调配置与相关行为先决；节点派生身份、权限和原请求回执须联调 | 三 |
| D：声明与会话数据落实 | 让变量声明不依赖会话；核对会话值初始化、节点上下文及变量读写、运行数据保存 | 先确认变量声明载体和初始化规则；与配置、执行、检查点数据形状对齐 | 二的语义落实，与三、四接续 |
| E：目录扩展与 Runtime 整理 | 从既有运行图整理准确声明消费、功能调用、状态推进和事实保存；逐步覆盖功能与能力声明 | 定义数据、会话数据接口可用；生命周期作用范围和完成语义需确认 | 四 |
| F：能力接入 | 先接检查点保存 / 装载与结算，再分别接重roll和分叉；生命周期按注册声明调用相应能力 | 检查点准入、失败影响和原子结算论证通过；不把所有操作改成运行结束后动作 | 五 |
| G：阶段收口 | 对照职责、真实路径和代表性离线证据审阅，登记未完成能力与新问题 | 每批已有局部证据；不为全量终版扩范围 | 六 |

准确声明的最小只读查询口是配置和执行的共同依赖，建议提前准备；完整目录扩展仍在 E 批。B–D 可按已确认路径交叠推进，不必等待全部仓储整理完成，也不能越过所依赖的语义决定。

第二建设主线在上述必要接口可用后，再选一个代表性自定义节点 / 功能包接入流程进行论证，检验注册、加载、连线、映射与调用。它可以提前暴露接口问题，但不在第一主线中预建完整 SDK、插件市场或新的加载平台。项目级支撑建设到什么范围，在该主线展开时再确认。

## 7. 内部工作、联调与三路协作

### 7.1 工作分类

| 工作 | 模块内可独立完成的内容 | 必须联调的内容 |
| --- | --- | --- |
| 数据管理 | 已定接口内的数据校验、仓储适配与查询实现 | 配置保存、运行写入、会话绑定、跨记录事务与回执 |
| 定义与注册 | 已定声明的准确身份校验、注册管理及只读投影实现 | 来源注册、配置和执行消费者对同一声明的取用 |
| 配置管理 | 配置分类、合法性和派生规则 | 两条前端入口、节点身份与绑定生成、定义保存、会话覆盖及新视图 |
| 基础支持 | 薄入口、当前状态和会话指向的接线、错误向外传递 | 启动 / 恢复目标、执行返回状态、异步操作归属 |
| 执行 / Runtime | 运行图和调用规范内部整理 | 节点数据访问、事实接纳、配置变更请求、状态及生命周期 |
| 能力 | 检查点准入投影、候选规则、分叉身份映射等内部实现 | 轮前准备、数据装载、成功结算、失败状态和显式能力命令 |

“模块内部”以外部契约已经明确为前提。跨模块业务行为不能仅通过移动文件或增加转发宣布完成。

### 7.2 三路协作建议

| 满足的条件 | 路线一 | 路线二 | 路线三 |
| --- | --- | --- | --- |
| 局部盘点开始 | 数据归属、仓储与事务路径 | 配置、前端及基础支持入口 | 定义取用、Runtime 及能力依赖 |
| B 批接口明确 | 数据管理适配 | 准确声明的最小只读视图 | 配置规则或运行图内部准备 |
| 基础数据通路可用 | 变量声明及会话数据路径 | 配置与两条前端入口 | 基础支持薄口及 Runtime 数据接线 |
| E–F 批契约明确 | 运行推进与事实适配 | 能力注册和检查点接入 | 候选、重roll与分叉规则准备 |
| 检查点联调通过 | 重roll接入 | 分叉接入 | 跨层验证与边界审阅 |

三路并发指开发任务协作，不引入运行时并行调度。一个人也可以按同样依赖顺序推进。

统一协调以下事项：

- 共同身份、作用范围、修订 / CAS、命令和回执，以及模块间错误表达。
- 声明与数据的维护权、可调配置的生效规则、生命周期事件和能力失败影响。
- 跨模块事务和状态转换；特别是成功结算不能由不同路线各自改变。
- 共享文件的最终接线。`graph_service.py`、`workflow_configuration.py`、`graph_contracts.py`、`capability_packages.py`、应用命令 / HTTP 入口及前端 `stores/workflowGraph.ts` 按批指定一个接线负责人，避免并发改写同一职责。

前端当前生成的对象键、权限、绑定和变量登记事件含有真实语义；职责迁移要保存或明确替代这些规则，不能当作重复展示逻辑直接删除。

## 8. 尚待确认的实施决定

| 事项 | 已确定的边界 | 仍需确认的具体内容与影响 |
