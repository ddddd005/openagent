# 工作流架构阶段总规划

日期：2026-10-17，Asia/Shanghai。

性质：本阶段指导规划。本文用于统一实施方向、发现问题和调整架构，不是终版架构落成声明，也不替代三份职责契约。

2026-10-18 边界订正：当前建设对象仅为工作流底层运行。工作流基础支持只负责运行相关的启动、恢复、抛错、当前状态和会话指向；创建、删除、归档、复制等项目管理能力归项目能力层，本阶段不建设该层。下文第 2.2、3、4 节涉及基础支持的较宽原始表述保留为规划来源，不再作为当前施工或完成要求；以[69 号职责订正](69-工作流架构局部骨架与分批执行规划-2026-10-17.md#1-阅读关系与本轮订正)和[70 号执行顺序](70-工作流配置起步与逐层接入执行顺序-2026-10-17.md)接续。

## 1. 本阶段定位

当前项目已经具备工作流、节点、数据类型、会话、运行时、检查点和能力包等雏形，但职责仍分散在工作流服务、多个 mixin、仓储、前端 store 和能力包之间。本阶段的目标不是一次完成一个绝对细致、完全可用的终版架构，而是把现有雏形整理为可继续演进的标准化框架。

本阶段施工应持续完成以下循环：

1. 根据职责契约整理现有代码。
2. 发现现有边界、存储和调用路径中的问题。
3. 修正实际问题并保留诊断证据。
4. 根据发现的问题优化契约和后续规划。

因此，阶段结束时允许仍有未落成的高级能力，但不能继续存在没有归属、没有交互接口或绕过数据管理的关键路径。

## 2. 总体架构理解

### 2.1 层级和模块不是同一维度

“层级”表示某类职责应该由什么边界承担；“模块”表示代码、服务或适配器的组织方式。一个模块可以跨越多个层级，但必须在接口和文档中明确它在每个层级承担的职责。

“工作流数据层”在本阶段是一个架构统称，包含数据定义、数据读写、变更、展示、存储和数据库适配等模块，不要求存在一个名为 `DataLayer` 的万能类。

### 2.2 工作流范围内的主要职责

```text
工作流基础支持
├─ 工作流工作台和前端承载
├─ 工作流初始化
├─ 工作流创建、删除、归档、复制
├─ 会话创建、关闭、恢复和管理
└─ 错误表达与基础运行地基

配置管理
├─ 静态工作流维护
├─ 节点加载、构建、绑定和维护
├─ 节点图、节点配置和节点组
├─ 节点派生内容
└─ 前端修改指令的统一入口

功能执行 / Runtime
├─ 工作流运行图
├─ 执行顺序规范化
├─ 功能调用规范化
├─ 运行状态和运行错误
└─ 运行生命周期通知

能力模块
├─ 检查点
├─ 重roll
├─ 分叉
└─ 后续可插入的工作流扩展能力

定义 / 注册 / 声明目录
├─ 统一查看定义和声明
├─ 向配置、Runtime、能力模块提供消费接口
└─ 不持有、收集、创建或直接修改定义

工作流数据管理
├─ 工作流定义域
├─ 工作流会话域
├─ 数据类型和数据规则
├─ 读写、修改、更新和版本
└─ 数据库及存储适配
```

### 2.3 母层的阶段范围

项目级数据域本阶段只保留框架位置、接口方向和未来接入点，不先建设完整项目级数据平台。工作流是本阶段的主要施工范围，项目级内容、供应商和插件管理保持现有能力并为后续接入预留边界。

本阶段默认采用逻辑分域和现有共享 SQLite 的方式，不以物理拆库作为完成条件。数据库表、仓储和事务可以继续共享基础设施，但工作流定义域和工作流会话域必须有不同的归属、接口和写入路径。

## 3. 分阶段推进顺序

### 阶段一：边界盘点和契约落地

- 确认定义域、会话域和项目级引用的清单。
- 盘点现有直接存储、绕过服务和重复注册路径。
- 建立三份职责契约。
- 对未决语义保留问题清单，不用临时实现掩盖。

### 阶段二：工作流数据管理整理

- 建立统一的数据管理交互入口。
- 将定义、数据、存储和数据库适配分开。
- 将工作流定义域和会话域的仓储边界固定下来。
- 修正变量声明与变量值的归属。
- 明确提示词、节点内容、节点配置和运行产物的归属。

### 阶段三：基础支持和配置交互整理

- 将工作流台、工作流生命周期和会话管理归入基础支持职责。
- 建立配置管理的统一调用接口。
- 将前端节点可调输入修改改为经过配置管理，再由配置管理调用数据管理。
- 整理节点加载、绑定、节点维护、派生内容和前端映射。

### 阶段四：定义目录和 Runtime 整理

- 扩展只读定义目录，覆盖数据类型、节点配置、功能模块和能力声明。
- 建立工作流运行图。
- 将执行顺序和功能调用规范化。
- 把运行错误、运行事实和批次完成状态纳入会话域。

### 阶段五：能力模块接入

- 将检查点、重roll、分叉拆成独立能力模块。
- 明确三者不同的调用时机和数据依赖。
- 由 Runtime 发出生命周期通知，按注册能力执行后续操作。
- 论证检查点的准入名单、数据层交互和配置快照读取边界。

### 阶段六：阶段收口和下一阶段规划

- 对照本规划和三份契约进行代码审阅。
- 保存代表性流程的离线验证证据。
- 记录仍未完成的高级能力和新的架构问题。
- 不为了达到“全量终版”而扩大本阶段范围。

## 4. 阶段结束标志

阶段结束时，应同时满足以下条件：

1. 数据管理已经有明确的统一交互模块，并能区分工作流定义域、工作流会话域及其数据库归属。
2. 维护代码中的数据读写原则上通过数据管理接口完成，不能把绕过数据管理作为正常开发路径。此项是开发维护指标，不把它伪装成对未来所有用户或开发者的绝对技术限制。
3. 工作流定义和会话数据有明确边界，变量声明不再要求先绑定会话才能创建；变量当前值仍按会话隔离。
4. 提示词、节点内容、节点配置、前端布局、运行结果和检查点数据各自有明确归属。
5. 配置管理有稳定的交互接口，前端节点输入修改经过配置管理，再由配置管理调用数据管理。
6. Runtime 已有工作流运行图，并负责执行顺序、功能调用、运行错误和批次结束通知。
7. 检查点、重roll、分叉已作为可区分的能力模块规划和接线，Runtime 不再直接硬编码全部后续功能。
8. 定义目录能够统一提供数据类型、节点配置、功能模块和能力声明的消费视图。
9. 基础支持职责覆盖工作流工作台、工作流生命周期、会话管理和前端对应承载。
10. 所有仍未解决的边界问题都有记录，未用临时绕过方式制造“已完成”假象。

这些标志表示雏形架构已转为可演进的标准化框架，不表示所有功能已经达到终版产品质量。
