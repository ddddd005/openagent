## 4. C1：控制分支删繁

当前只有公开 `control` 调用 `_control_change_current`。`control` 持服务锁读取活动链并选择保留的 basis：有 basis 走 `_control_change_data`，没有 basis 才进入 `_control_change_current`，事务内还复核活动链未变。

无依据分支的 resume/retry_archive/retry_acceptance 先检查状态和 `_futures`，再要求链存在于 `_execution_registries`；后一道检查在该入口条件下必然拒绝。因此其后的 pending/candidate 校验、状态依据比较及写 `prepared` 不可由正常入口到达，不是实际运行回退。

实施仅删除该拒绝后的成功尾段，保留：

- owner、action、会话及定义有效性、修订、包诊断、活动链、状态和同进程条件的现有检查顺序。
- `recovery_unavailable` 及现有消息、状态码；`retry_failed_node` 的 `failed_retry_unavailable` 分支保持不变。
- 幂等回执优先重放，不因原运行依据已释放而拒绝原控制回执。
- 有依据的 `_control_change_data` 正常继续、结果重接纳及归档重试逻辑。
- 无依据 pause/close 的持久状态更新、原共同事务和资源释放行为。

施工前重新验证唯一调用点及锁约束。若现场新增可达调用，先报告，不按旧行号直接删除。无需为清理死代码加入新拒绝策略、测试专用生产开关或兼容回退。

## 5. D1：信息绑定有限迁移

### 5.1 核心接线

保持宿主 sink 的参数和调用时机，建议接线为：

```text
图调用普通节点 / RuntimeHost 创建或恢复宿主调用
→ RuntimeHost 绑定信息路由
→ GraphInformation._accept_information_bindings(owner, generation, definitions)
→ WorkflowDataManagement 的信息绑定有限接纳入口
→ 信息绑定领域存储适配
→ 既有 workflow_information_bindings 表
```

建议有限入口名为 `accept_information_bindings(owner, generation, definitions)`，沿用原回调无业务返回值语义。空 definitions 保持不打开存储、不产生绑定。不得以接受任意 callback、repo、SQL 或连接的万能入口代替领域操作。

将现有仓储代码归入独立信息绑定数据模块，不维护两套 SQL 或双写副本。`GraphInformation` 写入回调只委托数据入口，不再持有写事务。宿主仍经同一 callback 调用，不另造加载、通知或异步补写链。

### 5.2 必须保持的事务与身份

| 边界 | 本批要求 |
| --- | --- |
| 存储 | 沿用原 store factory、表名、字段、主键及初始化语义；不新增表定义或存储版本，不迁移历史行 |
| 事务 | 新 store，原 `BEGIN IMMEDIATE`，一批 definitions 共同提交或回滚，最后关闭 store |
| 事务独立性 | 不加入准备、节点接纳、运行事实或最终结算事务；不改成服务命令 `_change`，不新增管理回执 |
| 唯一键 | 保持 `node_run_id + source_id + exact_version + generation` |
| 校验 | 原 owner 格式、正整数 generation、source reference 和 canonical JSON 比较不变 |
| 幂等与冲突 | 相同键、owner 和声明重复接纳不增行；同键重定义仍报 `information_binding_conflict` |
| 错误 | 原异常向调用方传播；不静默继续、不补偿重放、不把失败包装为成功 |

当前 `InformationBindingStore` 构造时在显式写事务前初始化已有表。搬移时保留该时点，不能顺带改变全局存储启动顺序。批量回滚测试先初始化隔离表，再比较业务行，避免把首次建表误当绑定写集的一部分。

`accept_fact` 可作为数据入口管理独立事务的现有写法参考，不能直接复用其运行中 owner 检查、返回回执或故障语义。信息绑定发生的时点和运行事实不同，本批不新增“必须处于 running”等业务准入。

### 5.3 锁与历史边界

- 持久化 sink 不新增服务锁；`RuntimeHost` 调用 sink 时不持宿主锁，不能因迁移改变锁顺序。
- provider 读取仍在服务锁外执行；数据库等待不通过持服务锁等待宿主或 provider 解决。
- 写入失败后，原 router 绑定释放和宿主失败处置仍生效；不留下可正常读取的伪成功 live 绑定。
- live 仍要求原本次运行依据；依据释放后不回退当前 registry 执行或读取 live。
- history 仍按准确 owner/generation/declaration 和原授权读取，不要求历史保留已释放 RunBasis，不回退最新运行。
- `get/list` 等原独立历史查询不在本批迁移；若仓储类移动，只调整必要导入，不把历史读接到可写执行端口。

允许保留薄写入 callback 和历史读取，但回执须明确哪项已迁移；不能宣称 `GraphInformation` 全文件已撤出仓储。
