# 测试规模核查：当前测试是不是太大了

2026-11-04 · 只读静态核查（未运行任何测试、未改文件、未启停服务、未写数据库）
工作树：`develop`，HEAD `8bd2717`。数字来源：文件/AST 静态统计 + 仓库内既有测试执行回执（历史实测）。标注「推断」者为估算。

---

## 0. 结论

**是偏大，但"大"的性质不是注水。** 分四点说：

1. **比例正常**：测试 94.8k 行 vs 源码 59.2k 行（后端 1.64:1、前端 1.47:1、合计 1.60:1），平均 32 行/后端用例、21 行/前端用例。契约型后端 1–2:1 属常见区间（经验判断，非本项目证据）。
2. **没有注水信号**：名称级逐字重复仅 1 组/2 个函数；无空断言用例约 1.1%；`skip`/`xfail` 标记为 0；近零旧版本号引用（`agents.execute@4/@5/@8/@9`、`context.*@2~@4` 出现 0 次）。上一轮旧债清理是有效的。
3. **但绝对量和成本偏高**：后端约 **4.5k 用例 / 264 文件 / 74.8k 行**，前端约 **1.5k 用例 / 128 文件 / 20k 行**；后端全量实测 **20.5 分钟**（4,569 用例，2026-10-22 回执），项目政策已默认"只按改动范围跑、不跑全量"（`docs/TESTING.md:3`）——**全量已经超出日常执行预算，这就是"太大"的实际含义**。
4. **真正的问题在结构，不在用例数量**：无 `conftest.py`、约 390 条跨测试文件 import、`test_graph_service.py`（278 行/1 个用例）被 **117 个文件**当作夹具 import、25 份重复的 `service` fixture、53 个 ≤2 用例的碎片文件；前端 42% 的测试行压在同一个 store 的跨层复测上、21% 的行在重复验证后端已测的契约。另有仓库级赘物：未跟踪的 `backend/build/lib` 副本 **29,272 行**、根 `.local` **8.16 GB / 约 10 万文件**。

**可精简空间（推断）**：测试行约 **-11%~-17%（10k~16.5k 行）**，磁盘另可清 **29k 行构建副本 + 8 GB 临时数据**；核心现行行为（44.1%）与边界/故障注入（47.5%）**不建议砍**。

## 2. 规模是怎么来的：不是失控膨胀

- 2026-10-17 清理收口：后端 4,053 passed、前端 112 文件/1,456 passed。
- 现在：后端约 4.5k、前端约 1.5k（10-21 实测 1,509）。**两周增长约 +11%（后端）与 +3%（前端）**，与源码增长同步：同期后端 Python 源码 1.97 MB → 2.41 MB（**+22.3%**），测试 2.96 MB → 3.63 MB（**+22.6%**）——比例稳定在 ~1.5，没有"测试越写越多、代码越写越少"的失衡。

## 3. 后端：规模、构成与结构问题

### 3.1 构成

| 分档（互斥启发式） | 用例 | 占比 | 说明 |

### 3.2 集中度：平坦，不是少数巨文件

Top10 文件只占测试行 **10.1%**、Top20 占 **18.1%**；中位 **7 用例/文件**。规模是"很多小文件"而非"几个巨无霸"，这既说明没有单点维护灾难，也意味着**任何跨模块改动都要碰很多文件**。

### 3.3 结构问题（"大"的主要来源）

| 问题 | 证据 | 影响 |
|---|---|---|
| **没有 conftest** | 全仓 0 个 `conftest.py`；`backend/pyproject.toml` 只有 `testpaths=["tests"]` | 共享只能靠测试模块互相 import |

## 4. 前端：规模不大，但跨层重复明显

- 规模：128 文件 / 20,005 行 / 945 声明（运行约 1,500；10-21 实测 1,509 passed）；无全局 `vitest.config`/setup，无快照；`testUtils` 12 文件 476 行。
- 目录倍数（测试/源码）：**stores 2.44×、adapters 2.34×、application 1.75×**、components 1.01×、domain 0.72×、plugins 0.99×。
- 冗余形态（不是字面重复——136 个 `describe` 全唯一、跨文件 it 标题重复仅 1 组）：
  1. **单一 store 跨层复测**：50 个测试文件（39%）直接 import `workflowGraph`/workspace store，308 用例、8,415 行（**42% 行**）；stores 目录已有 26 文件，application/components 再各测一遍同类行为。
  2. **重复验证后端契约**：25 个文件 / 218 用例 / 4,243 行（**21% 行**）测的是文档结构、配置分类、`node_id_map`、`changed_categories`、回执等后端已覆盖的契约。

  4. **退役旧行为**：7 文件 / 34 用例 / 904 行（4.5%），不是主因。
- 断言强度：≤2 个 expect 的占 22.6%，严格"仅存在/被调用"2.0%——**主要不是浅测，而是 setup 重**（如 `workflowConfigurationStore` 707 行/9 例 = 79 行/例）。

## 6. 四维判断

| 维度 | 判断 | 依据 |
|---|---|---|
| 比例 | **正常** | 1.60:1；32 行/后端用例；与源码同步增长 |
| 绝对量 | **偏大** | 约 6k 用例 / 95k 测试行；后端全量 20.5 分钟 |
| 构成 | **基本健康、局部冗余** | 逐字重复 <0.2%、空测 1.1%、skip 0；但历史/架构 8.4%（宽 16%）、结构重复明显、前端跨层重复 42%+21% |
| 成本 | **偏高** | 全量不再是日常闸门；跨文件依赖约 390 条；29k 行副本 + 8 GB 临时数据 |

**结论**：**"太大"成立，但不是"注水式的大"，而是"覆盖广度 + 结构耦合 + 仓库赘物"三层叠加。** 优化应以**结构收敛与清理**为主，而不是砍用例数量——因为断言语义密度是健康的。
